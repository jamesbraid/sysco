# L2 board contract: the core, the memory map and the devices the shipped firmware expects

What the L2 controller board must look like for the shipped L2 image to run: which CPU core, which addresses answer, in what width, and which peripherals the boot code, the kernel and the daemons touch. Everything is read from the L2 image of IRIX 6.5.30 (`/usr/cpu/firmware/sysco/l2.bin`, firmware 1.44.0, 2,924,652 bytes, sha256 `6bcfda07a24cb4d56850922dab17a98223abcd14221d307e3a8c3778434e8761`) and its inflated kernel. Container layout and the cramfs are in [l2/image-layout.md](../../software/firmware/l2/image-layout.md); the user-space device nodes are in [l2/devices.tsv](../../software/firmware/l2/devices.tsv) and [l2/daemon.md](../../software/firmware/l2/daemon.md). Nothing here was measured on a board.

## How to read this note

- **Addresses.** "Flash address" is the CPU address the image is linked at. The file header says the load address is `0xfe000000` (bytes 0x08 to 0x0b of `l2.bin`), and the first code byte of the flash sits at file offset 0x2c, so **file offset = flash address - 0xfe000000 + 0x2c** (established: the reset code at flash `0xfe000100` is the first non-zero run after the zero-filled vector area, at file offset 0x12c). "Kernel address" is the kernel's virtual address; the kernel is a flat binary linked at `0xc0000000`, so kernel address = `0xc0000000` + offset into the inflated kernel (gzip stream at file offset 0x4a218, 1,430,148 bytes inflated). "Wrapper address" is a RAM address inside the decompressor stage (below).
- **Disassembly** is PowerPC big-endian by capstone 5.0.7 over the carved bytes. Register-field names for the on-chip peripherals come from the public Linux `8xx_immap.h` header (structure member names and order; checked in the Linux tree) and the public MPC860 family manual; a name taken only from there is a hint, and is marked.
- **Grades** are those of [../AGENTS.md](../../AGENTS.md): *established* (the routine or table was read and the claim follows), *inferred* (reasoned from partial evidence, reasoning stated), *unknown* (no shipped image or public source settles it). Each unknown ends with the software test that would settle it.
- Raw values are given as the code writes them. Where a bit-field decode would need a manual page that was not opened, the decode is not attempted.

## 1. Image stages

`l2.bin` holds two copies of a small ROM stage, a gzip kernel and a cramfs (established; sizes and offsets in [l2/image-layout.md](../../software/firmware/l2/image-layout.md)). Reading the code shows how they chain:

| Stage | Flash address | File offset | Role | Grade |
|---|---|---|---|---|
| Stage A, vectors and early init | `0xfe000100` (reset), vector stubs at 0x100 steps from `0xfe000100` to `0xfe001f00` | 0x12c to 0x209c | reset entry, exception stubs, the first hardware setup (section 3) | established |
| Stage A, console loader | `0xfe004550` to `0xfe005db3` (copied to RAM `0x00e00000`, entry `0x00e009ac`) | 0x457c to 0x5ddc | prints status on the serial console, validates the second stage, hands over | established |
| Stage B, vectors and early init | `0xfe040100` and following | 0x4012c onward | a second copy of the same reset code; the first 0x1f94 bytes of flash `0xfe040000` are copied to RAM address 0 by stage A and executed from `0xfe040100` | established |
| Stage B, decompressor ("wrapper") | `0xfe04453c` to `0xfe04a1ec` (copied to RAM `0x00700000`, entered by an absolute branch) | 0x44568 to 0x4a218 | PCI and USB bring-up, MAC address fetch, gunzip of the kernel, jump to the kernel | established |
| gzip kernel | `0xfe04a1ec` | 0x4a218 | inflated to RAM address 0 | established |
| cramfs root | file offset 0xd521d | 0xd521d | mounted as the RAM disk root | established (layout), see image-layout |

Evidence: stage A copy loop and `ba 0x00e009ac` at flash `0xfe001fbc` to `0xfe002018`; the validate-then-copy-then-call routine at `0xfe004f98` to `0xfe004fe0`; stage B copy to `0x700000` and `ba 0x700000` at flash `0xfe0044cc` to `0xfe04453c`-relative end of the routine (file offsets 0x444a0 to 0x44568).

### The image-header record

The 32-byte record at flash `0xfe2ca00c` (file offset 0x2ca038, after the build stamp `20060717113711` and version `1.44.0`; see image-layout) has this shape. Established by summing it: eight big-endian words `0x00030020`, `0xfe040000`, `0x0028a02c`, `0x0028a02c`, `0xfe2c9ff4`, `0xfe2ca004`, `0xfe2ca030`, `0x0721df60` add to zero modulo 2^32.

- Word 0: record type 3 in the high half, length `0x20` bytes in the low half. The validator at flash `0xfe004ff4` sums words from the start of the record for type 3 (and from the second word for types up to 2) and calls the image corrupt (`INVALID IMAGE HEADER CHECKSUM`) unless the sum is zero. Established (the code at `0xfe005010` to `0xfe005060`).
- Word 1 is the base of the second stage, `0xfe040000`. Words 2 and 3 are `0x0028a02c` (2,662,444), which equals the second-stage base plus this value, `0xfe2ca02c`, the end of the cramfs. Words 4 to 6 point at the build stamp, the version string and the following table. Meaning of word 7 is not read (it is the balancing word of the sum). Words 2 and 3: inferred (arithmetic only).
- The loader reaches the record through a pointer stored in the first word of flash `0xfe040000`, which holds `0xfe2ca00c`. Both the pointer and the record address must lie in `0xfe000000` to `0xfe3fffff` and be word aligned, or the loader prints `INVALID IMAGE HEADER POINTER` / `ADDRESS` and stops (established, `0xfe0050a8` to `0xfe00519c`).
- On any failure the loader prints a block starting `BOOT FAILED !!!!` that tells the operator to run a recovery sequence from the host over the console serial line, then halts. It does not retry. Established from the strings at flash `0xfe0059a4` onward and the branch structure; what the recovery sequence sends is not in the image (the host tool named in the text is not among the files held; see unknown U7).

## 2. The CPU core

- **A PowerPC MPC8xx-family microcontroller with the PowerQUICC communications processor, big-endian.** Established by: the reset code writes the internal-memory-map register, SPR `0x27e` (IMMR), with `0xfa200000` at flash `0xfe000110` (file offset 0x13c); it programs the memory controller, the time base registers at IMMR+0x200 and the clock/reset registers at IMMR+0x280; and the kernel has the MPC8xx watchdog (`wdt_mpc8xx_init`), the communications-processor I2C driver (`cpm_iic_*`), the 8xx serial driver (`init_8xx_ports() for SGI L2`) and a fast-Ethernet driver with PHY probe (`fec`). The FEC exists only on the "T" variants of the MPC860 family, so the part is an MPC860T or a close relative (inferred from the driver being present and used; the part marking is not in any image). The note [README](../../README.md) calls it an MPC860; the exact variant and speed grade stay inferred.
- **Machine setup in the reset code.** MSR is written `0x00001002` (ME and RI set, everything else clear, so translation is off and the CPU is in supervisor mode; established, `mtmsr` at flash `0xfe000104`). The caches are disabled, unlocked and invalidated by writes of `0x04000000`, `0x0a000000` and `0x0c000000` to SPRs `0x230` and `0x238` (instruction- and data-cache control; the command values and register names are hints from the Linux 8xx startup code; the sequence is established as bytes). Two debug-control SPRs (`0x9e` set to 7, `0x95` cleared) are written; their names were not checked (unknown, harmless to the contract).
- **Clock.** Both console stages carry a small board-information block that says the bus clock is **50 MHz**: stage A stores `0x32` (50) at words 2 and 3 of its block (flash `0xfe0051f0` to `0xfe005238`), and the wrapper stores `0x02faf080` (50,000,000) at the same words (wrapper `0x704bc8` to `0x704bf0`). The same blocks hold the RAM size `0x01000000` (16 MiB) at word 1 and the console baud `0x9600` (38,400 in decimal; `0x9600` is the hexadecimal spelling of 38,400) at word 6. Established as stores. The two stored clock values are not equal in unit and that matters: the console baud-rate divisor is computed as ((word 2 >> 4) / word 6) << 1, with the enable bit `0x10000` or-ed in (stage A at flash `0xfe005558` to `0xfe005574`; the wrapper repeats it at `0x704408` to `0x70441c`). Stage A's word 2 is `0x32`, so its quotient is 3 / 38,400 = 0 and it loads BRGC1 with `0x10000`; the wrapper's word 2 is 50,000,000, so its quotient is 81 and it loads `0x100a2` (established, arithmetic on the stored values; the field layout of the register is the public `CPM_BRG_*` set in Linux `cpm1.h`, lines 172 to 179, divisor mask `0x1ffe`). The wrapper's value is the one that gives roughly 38,400 baud from 50 MHz; stage A's does not, so what rate the stage A banner actually runs at is not derivable from the code (U9b). The time-base busy-wait (flash `0xfe004500`; wrapper `0x700108`) converts milliseconds to ticks as (ms x 1000 + 59) / 60, which treats one tick as 60 microseconds; how that relates to the oscillator, SCCR and PLPRCR is not worked out, so the real length of the 500 ms delays is **unknown** (U2).
- **Wrapper-to-kernel register contract.** The kernel entry (kernel address `0xc0000000`) copies r3 to r7 into r31 to r27 and later uses them as the board-information pointer, initrd start and end, and command-line start and end, the usual 32-bit PowerPC embedded convention (inferred: the first five instructions are `mr r31,r3` through `mr r27,r7`; the meaning of each is the public Linux 2.4 convention, not read from a kernel routine). It then clears r24, invalidates the TLB, and builds the MMU mappings for the first 8 MiB of kernel space and for the IMMR window before turning translation on (established as instruction sequence at kernel addresses `0xc0000018` to `0xc00000d0`; the page sizes and attribute values written to SPRs `0x310` to `0x31e` were not decoded; U6).

## 3. Reset and early hardware setup

Read from flash `0xfe000100` (file 0x12c) and the setup routine at flash `0xfe0042f0` (file 0x431c); stage B repeats the same code at `0xfe040100`. All established as register writes; names of the on-chip registers are hints from `8xx_immap.h` unless noted.

1. **IMMR = `0xfa200000`.** All on-chip registers below are IMMR plus an offset.
2. **IMMR+0x000 (SIU module configuration) = `0x707a0900`.** Field decode not attempted (U3).
3. **IMMR+0x280 (SCCR) = `0x62000000`; IMMR+0x284 (PLPRCR) = `0x00005040`.** Decode not attempted; the multiplication factor field, taken at face value, is zero, so the PLL decode needs the manual (U2).
4. **Time base and RTC keys.** Key value `0x55ccaa33` is written to IMMR+0x300 and IMMR+0x320 after clearing them (the unlock pattern for the protected registers); IMMR+0x200 (time-base status/control) gets `0x00c3`; a halfword `3` goes to IMMR+0x320.
5. **Memory controller.** `MPTPR` (IMMR+0x17a) = `0x0200`; `MAMR` (IMMR+0x170) = `0x18804000`. A 64-word UPM-A program is then loaded: for each word index 0 to 63 the word at flash `0xfe0041f0` + 4 x index (file offset 0x421c onward) is stored to `MDR` (IMMR+0x17c) and then the index is stored to `MCR` (IMMR+0x168) (opcode 0, which is "write to array" in the public map; hint). After the load, `MCR` is written `0x8000202d`, then `0x80002030` eight times, `MAR` (IMMR+0x164) is written `0x88`, and `MCR` is written `0x80002013` (flash `0xfe0042f0` to `0xfe0043a0`; established as the stores). In the public map the top bit selects "run pattern", bit `0x2000` selects bank 1 and the low six bits are the start address in the array, so the shape is: one run at array address `0x2d`, eight runs at `0x30`, a mode value `0x88` on the address bus, one run at `0x13`. That is the shape of an SDRAM power-up (precharge, eight refreshes, mode-register set); inferred from shape, see U1. The words are listed in section 6.
6. **Chip selects.** `BR0` (IMMR+0x100) = `0xfe000001`; `OR0` (IMMR+0x104) = `0xff800940`. Banks 1 to 7 are loaded by a seven-iteration copy from the table at flash `0xfe0043b4` (file 0x43e0): see section 5.
7. The routine at flash `0xfe00441c` copies the vector area (flash `0xfe000100` for 0x1e94 bytes) to RAM address `0x100` and checks nothing (an XOR is computed and discarded; established). Exceptions after this point therefore run from RAM-resident copies of the same stubs, which save the register file and call a common handler at flash `0xfe004050` with r20 = `0x1002` (the handler body at file 0x407c to 0x4218 is a standard register save and restore; the reporting path is not read; U8).
8. A byte-wide device at `0xfa100000` is then driven (flash `0xfe00448c` to `0xfe0044fc`, section 7 device D). SYPCR (IMMR+0x004) is written `0xffffff80` once in stage A, at flash `0xfe004f78` to `0xfe004f84`, but that code is the **failure path**: it is the branch target of the not-equal test after the header validator returns non-zero (`cmpwi r3,0` / `bne` at `0xfe004f3c` and `0xfe004f40`), it is also where control lands if the second stage ever returns, and it is followed directly by the `BOOT FAILED !!!!` text call. On a successful boot the loader copies the second stage and calls it without writing SYPCR (established, `0xfe004f44` to `0xfe004f74`). No store to IMMR+0x004 appears in the reset code, the rest of stage A, or the wrapper outside the failure-path store above (a scan of the reset code, stage A and the wrapper for immediate-offset stores with displacement 4 through any non-stack register; indexed stores were not checked). **The service register at IMMR+0x00e is different: the wrapper does write it.** Re-read in 1.44.0 (`l2.bin`, sha256 `6bcfda07a24cb4d56850922dab17a98223abcd14221d307e3a8c3778434e8761`): from flash `0xfe044bbc` the wrapper loads the high half of the register base, stores the halfword `0x556c` at displacement 0xe, then the halfword `0xaa39` at the same displacement; the same pair is stored again at flash `0xfe044e08` to `0xfe044e14`, and the key `0x556c` is loaded a third time at flash `0xfe044e24`. This agrees with [l2-kernel-interface.md](../../software/firmware/l2/kernel-interface.md) section 8, and the earlier scan here missed these stores (established as stores; that they service a running watchdog is inferred). The failure-path store of `0xffffff80` is a word store at displacement 4 (re-read at flash `0xfe004f78` to `0xfe004f84`, established). So on a normal boot the watchdog is in whatever state the chip resets to; that reset state is **unknown** here (U22). The kernel's watchdog init (kernel `0xc0137520` to `0xc0137634`) shows what it does with each state: if the command-line disable flag is set it writes `0xffffff80` itself; otherwise it tests bit `0x4` of SYPCR and, when clear, prints "SWT not enabled by firmware" and gives up; when set it or-s in `0xffff0003` and starts servicing the register at +0x0e with the two key halfwords `0x556c` and `0xaa39` (established, instruction sequence; bit `0x4` is SWE by the position convention of the public `sc_sypcr` member, hint).
9. Stack: stage A uses RAM `0x003f0000` in the first stub (`lis r1,0x3f` at flash `0xfe0041dc`) and `0x00e077c0` once running from RAM (`0x00e018cc + 0x6000 - 0x100`, rounded down to 16; flash `0xfe00202c` to `0xfe002040`). The wrapper's stack top is `0x0070ce80` by the same arithmetic from `0x00706e8c` (wrapper `0x700064` to `0x700078`). Established.

The Linux 2.4 daemon libraries reach the flash through `/dev/mem` at `0xfe000000` (daemon.md) and the NVRAM and partition database sit in its top 128 KiB (`0xfe3f0000` NVRAM, per daemon.md), which agrees with this map.

`OR` values decode, for the base-address mask, as the address bits the bank ignores. Reading them: OR0 `0xff800940` gives an 8 MiB block, OR1 `0xff000400` 16 MiB, OR2 and OR4 `0xfffe....` 128 KiB, OR6 `0xffff....` 64 KiB, OR7 `0xff800930` 8 MiB. These are established as numbers, with a mask bit of 1 meaning the address bit is compared (so OR0 `0xff80....` covers 8 MiB; the same convention is why OR5 is not a contiguous window, see the PCI row above). OR5's low bits `0x8` are the bit the public header names `OR_SETA` (`8xx_immap.h` line 143, external transfer acknowledge; the effect is from the chip manual, which is not held, hint only): the PCI bank therefore probably takes its cycle termination from outside the processor. The other low-half timing and wait-state fields (`0x940`, `0x400`, `0x938`, `0x930`, `0x108`) were not decoded and are part of U1. BR3 and OR3 are zero in the table: bank 3 is unused.

## 6. The UPM-A program

## 7. Devices

For each device: what the firmware does to it, what it expects back, and the grade. Device letters are used in the map above.

### A. Serial console and the operator ports (on-chip CPM serial controllers)

- **The boot-time console is SCC2 in polled mode, one byte per buffer descriptor.** Established from stage A: the entry `0xfe004efc` calls the board-information setup at `0xfe0051f0`, which stores the clock, RAM size and baud words and calls the serial initialiser at `0xfe00539c`; that routine programs SCC2 and ends by storing `0x100` into a RAM variable (RAM `0xe01860`, stage A data) that the transmit routine (`0xfe0055a8`), the receive routine (`0xfe005614`) and the ready test (`0xfe005678`) read as a port selector. The wrapper repeats the same initialiser (wrapper `0x704244` to about `0x704434`). Details, as register addresses (IMMR plus offset; names from the public CPM map in Linux `cpm1.h` and `8xx_immap.h`, a hint):
  - The communications-processor register base held in stage A data (flash `0xfe005dac`, value `0xfa2009c0`) is IMMR+0x9c0. SCC2's mode register low half is at IMMR+`0xa20` (base + 0x60); it is written `0x00028004` and then or-ed with `0x30` to enable receive and transmit (`0xfe00552c` to `0xfe005584`). The UART data-sync register (IMMR+0xa2e) is `0x7e7e`, the protocol-specific mode register (IMMR+0xa28) is `0x3000`, the event register (IMMR+0xa30) is cleared by writing all ones and the mask register is zero.
  - SCC2 parameter RAM is at IMMR+`0x3d00` (the public map puts SCC2 at offset 0x100 from the 0x3c00 page, `PROFF_SCC2`, `cpm1.h` line 62): receive base halfword `0x800` at +0, transmit base `0x808` at +2, `RFCR`/`TFCR` = `0x10`, `MRBLR` = 1. The descriptors are in dual-port RAM at IMMR+`0x2800` (receive) and `0x2808` (transmit); each holds its buffer address in its second word, and the buffers are placed at the top of the RAM size held in the information block, minus 0x20, rounded down to 16 bytes (the transmit buffer four bytes above). The channel is initialised by writing `0x41` to the command register at IMMR+0x9c0 and polling until it clears (`CPM_CR_CH_SCC2` is `0x0004`, `cpm1.h` line 37, shifted into the channel field; hint). The clock-routing register at IMMR+0xaec is written zero, which the public map reads as baud-rate generator 1 for both directions of every channel (`SICR_RCLK_SCC2_BRG2` is the non-default `0x800`, `cpm1.h` line 185; hint). Baud-rate generator 1 is IMMR+`0x9f0`; the divisor it gets is in section 2, clock paragraph.
  - The selector encodes the page: for a non-zero selector the routines read the parameter RAM at IMMR+`0x3c00` plus the selector, so `0x100` selects SCC2; selector zero selects the page at IMMR+`0x3e80`. The selector starts at zero (stage A data is cleared from `0xe01860`) and is set to `0x100` at the end of the initialiser, before the first byte is printed (established). A byte is sent by waiting for the descriptor's ready bit (`0x8000`) to clear, storing the byte at the buffer address held in the descriptor, setting length 1 and setting ready; a byte is received by the mirror sequence.
  - **A second, SMC1 initialiser exists but is not on the boot path.** The routine at flash `0xfe00525c` follows the board-information setup and programs SMC1 (parameter RAM at IMMR+`0x3e80`, mode halfword at IMMR+`0xa82` cleared, then `0x4820`, then or-ed with 3; baud-rate generator 1 loaded the same way; the same descriptor slots `0x2800` and `0x2808`). No instruction in stage A calls it and no word anywhere in `l2.bin` holds its address; grade: not on the boot path is **established** for the calls read, "unreferenced" is **inferred** (an indirect call through a computed address was not ruled out). The wrapper has the SCC2 initialiser only.
  - Pin hand-over writes common to both stages (stage A flash `0xfe0051a0` to `0xfe0051ec`): port B registers at `0xab8` (`0x3030`), `0xabc` (`0x30`), `0xac2` (`0x30`), `0xac4` (`0x3000`), and port A/C registers at `0x950` to `0x966`. Which package pins carry SCC2's transmit and receive lines is unknown (U9). The console speed the wrapper programs is 38,400 baud (the stored `0x9600`; stage A is U9b).
- **Kernel serial.** The kernel announces `init_8xx_ports() for SGI L2` and registers four ports (`ttyS%02d at 0x%04x` is printed per port; established as the strings and the registration loop at kernel address `0xc013bad8` to `0xc013bf2c`, which runs for line numbers 0 to 3). The static port table is at kernel address `0xc012c70c`, four entries of `0xcc` bytes. In entry n the word at +0x08 is `n x 0x100`, the word at +0x0c is `0x1e`, `0x1d`, `0x1c`, `0x1b` for n = 0 to 3, and the word at +0x14 is `0x10000 + n` (established as table bytes). In the public CPM map the vector numbers `0x1e` down to `0x1b` are SCC1 to SCC4 and the parameter-RAM pages are `0x100` apart, so **`ttyS0` to `ttyS3` are the four on-chip SCCs, in order** (inferred from the public numbering; the driver code that consumes the fields was not followed past the registration loop). This agrees with the shipped nodes: `/dev/ttyS0` (4,64) modem, `/dev/ttyS1` (4,65) console, `/dev/ttyS3` (4,67) a 9600 8N1 link read by the display program (devices.tsv).
- Port pin-control writes at kernel address `0xc013ba30` to `0xc013bad4` set port A (IMMR+0x950 to +0x954 = `0`, `0xff`, `0`) and port C (+0x960 to +0x966), and read-modify-write four registers at offsets `0xf8`, `0xfc`, `0x102` and `0x104` of the communications-processor base (IMMR+0x9c0, so IMMR+0xa78 to +0xac4 in the public map: the baud-rate generator and port B area), then write `0x1b120900` to offset `0x12c` of that base. Established as writes; the fields are not decoded (U9).

### B. I2C bus and the vital-product-data EEPROM

- **The wrapper reads 256 bytes from an I2C device at 8-bit address `0xa4` (7-bit `0x52`), offset 0, through the on-chip I2C controller.** Call at wrapper address `0x705114` to `0x70512c` with arguments `0xa4`, buffer `0x706d8c`, offset 0, length `0x100`; success is a return equal to 0x100. On failure it prints the reason, `RETRYING.....`, and loops; a persistent failure prints that the L2 may need a power cycle. The transfer routine (`0x704714`) uses the I2C block of the CPM at IMMR+0x860 (mode `1`, event register cleared with `0xff` at +0x870, command `0x81` at +0x86c, in the public map) and buffer descriptors in dual-port RAM (IMMR+0x2000 plus the base halfwords held in the I2C parameter RAM at IMMR+0x3c80). The first byte of the transmit buffer is the device address with bit 0 cleared and the second is the offset. Established.
- **Record format.** The 256-byte block holds a chain of records starting at byte 10: one tag byte, one length byte, the data; a tag byte `0xff` ends the chain (wrapper `0x705130` to `0x705190`). The caller asks for **tag 8** (call at `0x704c24`) and prints six bytes as the Ethernet address (it prints `Ethernet address from Motorola VPD EEPROM is` and checks it read at least six); on failure, `ERROR! Could not get Ethernet Address`. Established. What the first ten bytes hold, and whether other tags are read by the kernel or daemons, is U12.
- The vendor-product name "Motorola VPD" in the message is a vendor string only; the EEPROM part number is not in any image (U12).

### C. PCI bridge and the USB host controllers

- **The PCI bridge is reached at `0xfa210000` and its configuration access pair is at offsets `0x500` (address) and `0x504` (data).** The wrapper's accessors read and write those two registers with `eieio` ordering (wrapper `0x704d90` to `0x705034`): byte, halfword and word reads and writes at `0x504` plus the byte lane, after `0x500` is loaded with (bus<<16 | device<<8 | register & 0xfc) and bit 0 for a configuration cycle on bus other than 0 (established). The kernel strings `QSpan interrupt status`, `PCI error, cmd: ... be: ... addr: ... data:` and `QBus error, tc: ...` and the public Linux 2.4 `qspan_pci.c` driver (a hint, not read in this note) say the bridge is a Tundra QSpan-family part. **Part identity: inferred** from the kernel strings; the bridge's own ID is not read by the firmware (U13).
- **Bridge programming by the wrapper** (`0x704ce0` to `0x704d8c`), raw values at the offsets from `0xfa210000`: `+0x004 = 0xf9000147`, `+0x00c = 0`, `+0x010 = 0x01000000`, `+0x030 = 0`, `+0x03c = 0x100`, `+0x100 = 0x88800080`, `+0x104 = 0x80000000`, `+0x110 = 0`, `+0x114 = 0`, `+0x13c = 0`, `+0x140 = 0x81000000`, `+0x400 = 0x00780008`, `+0x404 = 0`, `+0x408 = 0`, `+0x600 = 0xeff0000f`, `+0x604 = 0`, `+0x608 = 0`, `+0x800 = 0x000c1013`, `+0xf00 = 0x01000000`, `+0xf04 = 0x800000d1`, `+0xf10 = 0`, `+0xf14 = 0xc00000d1`, `+0xf80 = 0x81000000`. Established as writes. Register names and field meanings need the bridge's manual (not held), so the decode is **unknown** (U13). Test: U13 in section 9. Take the public manual of the candidate bridge family and, for each of the 23 offsets above, check that the offset is a register of that part and that the written value leaves its reserved bits clear. One offset that is not a register, or one value with a reserved bit set, rejects the identity; a full match gives the names and fields. If no such manual is obtainable, the decode stays unknown.
- **Device discovery.** The wrapper reads the vendor/device dword of PCI device numbers 4 and 5 on bus 0 (function 0; the routine multiplies the device number by 8) and accepts **vendor `0x11c1`, device `0x5801` or `0x5802`** (compares `0x580111c1` and `0x580211c1`); anything else prints `Bad PCI_VENDOR_ID for slot`. It then writes the first base register (offset `0x10`), reads it back and compares, and writes the interrupt-line register (offset `0x3c`). Device 4 gets base `0xc0000000` and interrupt line 8; device 5 gets base `0xc0001000` and interrupt line `0xa` (wrapper `0x704c9c` to `0x704cbc`, routine `0x704940`). Established. Vendor `0x11c1` is the public PCI vendor ID of the Lucent/Agere family (hint from the public PCI ID list; not opened here). The kernel then runs the generic OHCI driver (`usb-ohci.c`, `USB OHCI at membase`), so the devices are OHCI USB host controllers; what interrupt inputs of the processor those line values `8` and `0xa` correspond to is not worked out (U21). Class code is not checked by the wrapper; a conforming OHCI register file must answer at the two windows (established requirement from the OHCI driver being used).
- **What speaks on those ports** is the L1 controllers' USB device side, driven by the kernel's `sgil1` driver (daemon.md). The match rules are U14.

### D. The byte-wide peripheral at `0xfa100000`

- Window: BR4 `0xfa100401`, OR4 `0xfffe0930` (8-bit, 128 KiB).
- Drive sequence in the early setup (flash `0xfe00448c` to `0xfe0044fc`; the wrapper writes `0x18` to offset 3 at `0x704ba8` to `0x704bb8`): write byte `0x00` to offset 0, wait 500 ms by the time-base routine, write `0x80` to offset 0, write `0x18` to offset 3, write `0x0e` then `0x0f` to offset 1, wait 500 ms, write `0x0e` to offset 1. Established as the byte sequence. **What the device is: unknown** (U4). The sequence resembles neither a 16550 divisor-latch sequence nor anything in a public driver I could name, so no part is claimed. The kernel maps this window but the code read never touches it. The earlier search looked for the 32-bit literal only and missed that the kernel builds the address with a `lis` of `0xfa10`: at kernel `0xc0132a28` it is the second of six calls to an ioremap-shaped routine (`0xc000ba60`, which page-aligns the range and applies a default attribute word of 2; the name is inferred from that shape), each with a base in r3 and a size in r4: IMMR `0xfa200000` size `0x10000`; `0xfa100000` size `0x1000`; `0xfa210000` size `0x10000`; `0x10000000` size `0x20000`; `0xfe000000` size `0x400000`; and `0xfa210000` size `0x10000` again (established, `0xc0132a18` to `0xc0132a5c`). That is the only `lis` of `0xfa10` or `0xfa11` in the inflated kernel (scanned over every aligned word), so after the mapping the kernel can reach the device only through the pointer the mapping returns, which was not followed (U4). Test: U4 in section 9; its first step, the consumers of the pointer the mapping call returns at kernel `0xc0132a2c`, is a bounded read of the instructions after that call in the kernel's init routine, and the byte values `0x80`, `0x18`, `0x0e` and `0x0f` are compared with datasheets of byte-wide line drivers only after that read shows what the kernel does with the pointer. ### E. LCD controller and display

- Window `0x10000000` to `0x1001ffff`, 16-bit port. **The kernel names the controller as an Epson SED1375/SED1374** (`lcd137x: Epson SED%s LCD controller detected` with the two string choices `1375` and `1374`, `SGI L2 (SED137x LCD controller) frame buffer device`, device `sgil2fb`). Established as strings and the init routine at kernel address `0xc013ab10` to `0xc013ad6c`.
- **Frame buffer and registers.** The frame buffer base is `0x10000000` (stored at kernel address `0xc013ab2c`); the register block is at **`0x1001ffe0`** (base + 0x20000 - 0x20; routine at `0xc013ab94` to `0xc013aca4`). The routine writes bytes at register offsets 1 to 0x1c of that block and then fills the visible area. Offset values: `[1]` and `[2]` built from panel descriptor flag bytes (shifted and OR-ed), `[3] = 3`, `[4] = width/8 - 1` (width from the descriptor, a halfword), `[5]/[6]` = height-1 low/high bytes, `[0x12]/[0x13]` repeat height-1, `[8]`, `[0xa]` from descriptor bytes, `[0x19] = 0x1e`, the rest zero. Established as stores. The register names (the public SED1375 datasheet is the hint) were not matched; U16. The routine also writes a zero byte to `0x1000ffe0`, the same offset in the lower half of the window; purpose unknown (U16).
- **Panel table.** Two panels, selected by an option string compared with `color` or `mono` (described below): `Hantronix HDM3224C (320x240, 8-bit passive color)` and `Hantronix HDM3224 (320x240, 4-bit Greyscale)`. The two descriptors are at kernel address `0xc012bcf8` (mono) and `0xc012bd14` (colour), `0x1c` bytes each (established, read as bytes). Layout read from the entries and the init routine: word 0 points at the selector string (`mono` or `color`), word 1 at the description string (`Hantronix HDM3224` / `Hantronix HDM3224C` and their long texts above), halfwords at +8 and +0xa are width `0x140` (320) and height `0xf0` (240), repeated at +0xc and +0xe; the byte at +0x10 is the base-2 logarithm of the bits per pixel (2 for mono, so 4 bits per pixel; 3 for colour, so 8 bits per pixel), established because the init routine computes the row stride in bytes as (width << that byte) / 8 (`0xc013ab34` to `0xc013ab54`); bytes +0x11 to +0x15 are packed into controller register 1, and bytes +0x16 to +0x19 together with the logarithm byte shifted left by 6 into register 2 (so that byte lands in the top two bits of register 2, which is consistent with a bits-per-pixel select; the register layout is from the public SED1375 datasheet, hint, not opened), and bytes +0x1a and +0x1b go to registers 8 and 0xa (`0xc013abb8` to `0xc013ac98`); the meaning of those fields is U16. The offset range `0x103d00` to `0x103f30` of the inflated kernel, cited in the first version of this note, is an unrelated table of `mac` interface names and pointers. The descriptor in use is held in a kernel variable at `0xc012f5f0`, which starts out pointing at the mono entry. It is replaced by the colour entry only when the framebuffer driver's option handler (`0xc013aecc`; registered with the driver name `sgil2fb` in a table at `0xc0159a08`) is given a comma-separated option equal to `color`, or by the mono entry for `mono` (established, `0xc013af08` to `0xc013af58`). By the public Linux 2.4 framebuffer convention that handler is fed from a `video=sgil2fb:...` command-line option (inferred; the generic option parser was not read). The wrapper's command-line fragments hold no such option (section 7G), so unless the operator overrides the command line the panel is **mono** (inferred; see U17 and U20).
- **Initial image.** After the register writes the routine fills the frame buffer from a 38,400-byte source table at kernel `0xc01226f8`, reading it from the last row to the first. Each source byte becomes `0xf0` if its high nibble is non-zero (else 0) or-ed with `0x0f` if its low nibble is non-zero (else 0), so both nibbles are thresholded, not just the low one (established, `0xc013ad08` to `0xc013ad3c`). The outer loop advances a byte index by the row stride and stops once it exceeds `0x95ff` (`0xc013ad50` to `0xc013ad58`). For the mono panel the stride is 160 bytes, so it fills all 240 rows: 38,400 bytes. For the colour panel the stride is 320 bytes (8 bits per pixel), so the same bound fills only 120 of the 240 rows (established, arithmetic on the stride from the descriptor byte). The earlier note's "320 x 240 / 2, 4 bits per pixel" held for the mono panel only.
- User space: `l2gui` opens `/dev/fb0` (devices.tsv) and the touch input is on `/dev/ttyS3` (U18).

## 8. Boot flow in one place

1. Reset at flash `0xfe000100`: caches off and invalidated, IMMR = `0xfa200000`, SIU/clock/time-base setup, memory-controller banks and the UPM-A DRAM program, vectors to RAM, the byte-wide device sequence (section 3). Then the stage-A console loader is copied to RAM `0xe00000` and entered.
2. Stage A prints `Validating L2 Controller Flash image....` on SCC2, validates the image-header record (section 1), then copies the first 0x1f94 bytes of flash `0xfe040000` to RAM 0 and calls `0xfe040100` (stage B reset code, which repeats step 1, then copies the wrapper to RAM `0x700000` and jumps).
3. Wrapper (RAM `0x700000`): initialises the serial console, resets and programs the PCI bridge, probes PCI devices 4 and 5, assigns their windows and interrupt lines, reads the EEPROM and prints the MAC address, builds the command line, inflates the kernel to RAM address 0, flushes the instruction cache and branches to address 0 (wrapper `0x7000f8` to `0x700100`; it prints `Uncompressing Linux...` and then `Now booting the kernel`).
4. Kernel at `0xc0000000` virtual (physical 0): maps itself, mounts the cramfs RAM-disk root, starts `init` (see rootfs.md).

Evidence for 2 and 3 is the routines and strings cited above; the exact order of PCI bring-up against EEPROM read in the wrapper is established from the call order at `0x704c20` to `0x704cbc` (bridge init at `0x704c98`, EEPROM at `0x704c24`, device setup at `0x704ca8`/`0x704cb8`).

## 10. What the board must provide, summarised

For the shipped 1.44.0 firmware to run to the point where the daemon starts and talks to an L1 over USB, the board needs (grades as above): an 8xx-class big-endian PowerPC with its register space at `0xfa200000`; 4 MiB or more of flash at `0xfe000000` holding `l2.bin`; 16 MiB of DRAM at address 0; an SCC2 console UART (polled, parameter RAM at IMMR+0x3d00, 38,400 baud as the wrapper programs it); an I2C EEPROM at address `0xa4` answering a 256-byte read with a tag-8 record; a PCI bridge at `0xfa210000` with two OHCI-compatible USB host controllers (vendor `0x11c1`, device `0x5801` or `0x5802`) at PCI device numbers 4 and 5; and a fast Ethernet MAC with a PHY. An LCD controller at `0x10000000` is needed for the display (kernel), and the byte-wide device at `0xfa100000` for the early write sequence (ROM stages; the kernel also maps its first 4 KiB;  the device's reply, if any, is never read in the code followed, established by absence of a load from that window in the routines read).

## 11. Review (2026-11-10)

An independent reader checked version 1.44.0 of this note (committed as `7922ca5`) against `l2.bin` and the inflated kernel and reported six errors. Each was re-checked here by disassembling the same bytes (capstone 5.0.7, PowerPC big-endian; the image hash is the one in the opening paragraph and the gzip stream ends at file offset 872,477). What changed:

| Finding | Outcome | Where it landed |
|---|---|---|
| The boot console is SCC2, not SMC1 | **Upheld.** The initialiser the loader calls programs SCC2 (parameter RAM at IMMR+0x3d00) and sets the port selector to `0x100`; the SMC1 routine has no caller.
