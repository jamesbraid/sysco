# L1 to Bedrock hand-offs: the ordered events the firmware drives

This note lists, in the order the firmware performs them, everything the Origin 300 and C-brick L1 does that the compute node's Bedrock chip (or the node's processors) can observe: the reset sequences with their delays, the soft-reset and NMI bits, the front-panel triggers, and the power-state notice sent to the peer L1. It reuses [power-reset-cbrick.md](../../software/firmware/l1/power-reset-cbrick.md), [power-reset-ibrick-rbrick.md](../../software/firmware/l1/power-reset-ibrick-rbrick.md), [ip45-io-expanders.md](../../software/firmware/l1/ip45-io-expanders.md) and [board-boot-contract.md](../../software/firmware/l1/board-boot-contract.md) and does not repeat their tables. It corrects and extends them where a re-read found more (section 9 lists the changes).

Grades follow [../AGENTS.md](../../AGENTS.md): **E** established (routine read in full), **I** inferred, **U** unknown. Each unknown names the software test that would settle it (section 8).

## 0. Inputs and conventions

- Image: IRIX 6.5.30 `l1.bin`, L1 1.44.0, sha256 `c355c542554a41b23b69dca4c201c566e8352e8f9fb870d2365c74cdd8ab0c0f`. **Package 0** (`Base 1MB image`, body sha256 `3c8a7aa93eb38502289cf0c2921ea91e6800228005bd8abd67425ce615f7b364`) is the C-brick reference (board source literal `IP35.c`, brick type `C`). **Package 1** (`Fuel/PE/O300 1MB image`, body sha256 `9db44f3bb06ec90475035781766e1ca7e924f15a0ed215cf855c1f491275fdd1`, board literal `IP45.c`, brick type `4`) is the Origin 300. Addresses are first-bank (`0xffe00000` base). Container offset = `0x68` + (address - `0xffe00000`) for package 0, and `0xefdd0 + 0x2c` + (address - `0xffe00000`) for package 1. The package 1 listing is committed ([l1/disasm/mcf5206e-1.44.0-fuel-pe-o300/l1.lst](../../software/firmware/l1/disasm/mcf5206e-1.44.0-fuel-pe-o300/l1.lst)); the package 0 listing is regenerated with a 68040-mode decoder (capstone) and is not committed.
- **Tick.** Every delay below is a count of firmware ticks passed to the delay routine (`0xffe40e54` in both packages), which puts the calling task to sleep for that many kernel clock units. The kernel clock counter advances by one in the timer-1 interrupt routine (`0xffe4032e`, vector 29 at `0xffe10ff4`) and is cleared at start-up (`0xffe43c38`). The routine addresses are the same in both packages; the data address is not: `0x30003b20` in package 0 (`addq.l` at `0xffe40330`, `clr.l` at `0xffe43c38`) and `0x30003c10` in package 1 (same two addresses). E. The delay argument is read in that unit: I (the sleep-queue arming routine `0xffe40090` was not read). The wall-clock length of a tick is a function of the unmeasured processor clock: [board-boot-contract.md](../../software/firmware/l1/board-boot-contract.md) infers 48 MHz and a 100 Hz tick from the timer-1 reference `0x752f` with prescale 16. So 1 tick = 10 ms is **I**, conditional on the clock (unknown, section 8).
- **Expander writes.** "Set(idx, m)" and "clear(idx, m)" are the masked expander writes of [ip45-io-expanders.md](../../software/firmware/l1/ip45-io-expanders.md): the routine replaces the masked bits of the expander's shadow byte and sends the whole shadow byte to the expander's wire address once, even when the byte does not change. In package 0 the set routine is `0xffe65ef8`, the clear routine `0xffe65f1c`, the general one `0xffe65e84(idx, mask, value)`; in package 1 they are `0xffe65bb0` (set), `0xffe65bd4` (clear) and `0xffe65b3c` (general). E.
- **Reason codes** passed to the wrappers (name routine `0xffe4eca0` in package 1, `0xffe4f050` in package 0). The firmware's own names, read from the switch at `0xffe4f050` and the strings at `0xffe4f420` onward: 1 `COMMAND`, 2 `PANEL`, 3 `OS`, 4 `ENVIRONMENTAL`, 5 `DON'T CARE`, any other value `unknown`. Call sites seen use 1 (console commands), 2 (front-panel buttons), 3 (the general request `0x2001`, from an L2 or host) and 5 (`power up` and `power down`); no call site passes 4 in either package, so what would raise it is U (section 8). The call-site descriptions in this note ("front panel", "request from an L2 or host") are descriptions of the callers, not firmware names. The log line `reset (%s)`, `NMI (%s)` and the like is written for every reason except 5 (reset and soft reset) and always for NMI. E.

## 1. The lines, and what each one is called

Both boards describe the Bedrock-facing controls as two byte-wide expanders on the board's two-wire bus, segment 3, at wire addresses `0x42` and `0x44`, with the same applied start-up values on both boards. E (descriptor tables: package 0 `0xffe455dc`, entries 6 and 7; package 1 `0xffe45c90`, entries 2 and 3).

| Expander | Wire address | Name, C-brick | Name, Origin 300 | Applied at start | Input mask | Grade |
|---|---|---|---|---|---|---|
| index 6 (C), 2 (O300) | `0x42` | `BEDROCK CNTL 1` | `ASIC CTRL 1` | `0x72` | none (C), `0x20` (O300) | established |
| index 7 (C), 3 (O300) | `0x44` | `BEDROCK CNTL 2` | `ASIC CTRL 2` | `0x8a` | none (C), `0x02` (O300) | established |

The Origin 300 start value is the same `0x72` and `0x8a` as the C-brick's; only the input mask differs. `0x20` and `0x02` are input-bit masks, not start values: the firmware ORs the mask into the byte it writes, and both masks are already set in the applied bytes (`0x72` has bit `0x20`, `0x8a` has bit `0x02`). Both packages' tables were re-read for this note (package 0 at `0xffe455dc`, package 1 from the descriptor array the board-boot notes cite).

The bit uses are identical in both images' hooks, so the two boards drive one control block (inferred: the labels differ, the addresses, applied bytes, bit masks and order of use agree; no image says the O300 `ASIC` is a Bedrock). The manual calls the NMI line "the NMI signal in I/O expander B_0100001x" (SGI Origin 300 Server Owner's Guide 007-4498-002, printed page 194, `nmi`): `0100001x` is wire address `0x42`, which agrees with the NMI bit sitting in this expander (established for the address match in the image; the manual is the source of the signal's name).

| Bit | Mask | Function | Grade |
|---|---|---|---|
| `CNTL 1` bit 7 | `0x80` | soft-reset line. Idle 0, pulsed 1 by `softreset` | E for the writes, I for "pulsed high means asserted" (only that it is set then cleared) |
| `CNTL 1` bit 6 | `0x40` | NMI line. Idle 1, driven 0 then 1 by `nmi` | E for the writes, I for polarity (low is the pulse) |
| `CNTL 1` bit 0, bit 1; `CNTL 2` bit 0 | `0x01`, `0x02`; `0x01` | the reset group: cleared by every hold, set by every release in a fixed order (section 4) | established |
| `CNTL 2` bits 3 to 7 | `0xf8` | strap or configuration bits written once per release | E for writes, U for meaning |

Which Bedrock input each bit reaches, and which Bedrock state survives each line, is not in any image: U (section 8). The only independent statement is the manual's one for `reset` ("sets various control and status signals back to their default values and reboots the operating system", printed page 201) and `nmi` (printed page 194), and the IP35 PROM's own strings, which show the software split: the PROM has a separate Hub-register NMI and soft-reset path (`PI_NMI_A`, `Sending soft reset to all CPUs on NASID`, `Soft reset received`; `ip35prom.img` in the 6.5.30 firmware set, sha256 prefix `d74b4b7e`, string offsets `0x7a910` (`Sending soft reset to all CPUs`), `0x8a875` (`Soft reset received`) and `0x730f8` (`PROM NMI HANDLER`)). Public Linux IP27 code does the same through hub registers (`arch/mips/sgi-ip27/ip27-nmi.c`, `SEND_NMI` writes `PI_NMI_A` plus the slice offset; `ip27-reset.c` writes `NI_PORT_RESET`). Both are **hints for the Origin 2000 Hub, not for Bedrock**, and say nothing about what the L1 expander bits reach.

## 2. Wrappers around every hook (the part earlier notes left open)

Each hook is called through a wrapper that logs, then does bookkeeping, then calls the board hook from the descriptor (`0x30001e30` in package 0, `0x30001f20` in package 1; hook offsets `+0x98` hold, `+0x9c` release, `+0xa0` "second reset?", `+0xa4` soft reset, `+0xa8` NMI). E for every call below; effects marked I where the callee was not read through.

**Hold wrapper** (package 0 `0xffe4f29c`, package 1 `0xffe4eeec`), no delay of its own, in order:
1. `0xffe36a04`: for ports 2 to 9, call `0xffe54a84(port, 0)`, then `0xffe3681c(0)`. These are the node-link and console UART service calls of [quad-uart-and-serial-links.md](../../software/firmware/l1/quad-uart-and-serial-links.md); not read (unknown for the bytes they put on a link, if any).
2. `0xffe5039c(0xff, 4)` (package 1 `0xffe4ffec`): for every entry of the port table at `0x30000134` (24-byte records) in state 2 or higher and with the right mode bits, call the port-down routine `0xffe50288`. Its log text is `port_down(%s) %s (%s)` with the action `clr LPOK` when the record's flag `0x10` is clear and `force link` otherwise (strings at `0xffe51234` to `0xffe5125e`). The port-down routine drives a port-status expander bit (`0xffe50084`: clear when record flag bit 0 is set, set otherwise, expander index in record byte 2, mask in byte 3) and a hook from the descriptor (`+0xc4`). So **before any hold, the L1 drops its local-port-OK signal on every NUMAlink or XIO-facing port** (the manual's `port` command names the status bits: remote power OK bit 0, local power OK bit 1, link LED bit 2, software LED bit 3, printed page 199). E for the call, text and structure; I that "clr LPOK" is the action taken in the all-ports case; U for the per-board port records (which expander bits).
3. `0xffe4c818` (package 0): clears the word `0x3000010c`, which is the low-power monitoring count of step 7 of the release wrapper (`0x300000fc` + `0x10`) cleared without the log line. Package 1 calls `0xffe4c468` instead (`0xffe4c474`, the address an earlier version of this note gave, is that routine's `rts`): it clears `0x30000138`, the package 1 monitoring count (`0x30000128` + `0x10`, see release step 7). E.
4. Hook `+0x98`. A nonzero hook result is returned unless step 2's code is already nonzero.

**Hold wrapper for the `reset hold` command and for power-down and power-up** (`0xffe4f2f0` in package 0, `0xffe4ef40` in package 1) additionally runs `0xffe7219c` (package 1 `0xffe7204c`) first, after logging `reset hold (%s)` for reasons other than 5: if the word at `0x30000044` is nonzero it writes six values to the parallel-port data register (MBAR + `0x1c9`, `PPDAT`): `PPDAT |= 0x08`, then `|= 0x18` accumulated, then `0x38`, `0x28`, `0x38`, `0x30`. E for the sequence. The routine also prints the debug text `sn1sc_reset_sic()` (`0xffe73808`) when the debug word `0x30000040` is nonzero. E.

**The pulse runs.** The word at `0x30000044` is set to 1 by the scan-interface initialiser `0xffe71ee0` (package 1 `0xffe71d90`), called once from start-up at `0xffe105ba` (same address in both packages). The store is `move.l d0,$4(a5)` at `0xffe71faa` (package 1 `0xffe71e5a`) with `a5` = `0x30000040` and `d0` = 1, so it is not an absolute-address store, which is why an earlier search for the address missed it. Before it the initialiser clears bits 5:4 of the word at MBAR + `0xca` (`PAR`), writes `PPDAT` `0x31` and `PPDDR` (MBAR + `0x1c5`) `0xfe`, then writes `PPDAT` `0x38`, `0x28`, `0x38`, `0x30` (the last four values of the pulse; `0xffe71f6c` to `0xffe71f86`). A second call logs `JTAG already initalized` (`0xffe73648`, module literal `sn1sc.c`). After start-up the word is 1, so the `-2300` early exit of the scan routine (below) is not taken. E. The pin roles of `PPDAT` bits (bit 0 TDO, 3 PSI, 4 TRST, 5 TMS, 6 TCK, 7 TDI) come from the firmware's own `TAP values: trst= psi= tck= tms= tdi= tdo=` print routine (`0xffe723a4`, format at `0xffe7381c`; argument order read from the pushes), see [l1/mcf5206e-peripherals.md](../../software/firmware/l1/mcf5206e-peripherals.md): E for the print's bit order, I that the labels name what the board wires to those pins (unknown for the board nets, section 8). So the sequence ORs PSI and then TRST into the value it reads (after the initialiser's `0x31`, TRST and TMS are already high), writes `0x38`, drops TRST (`0x28`), raises it again (`0x38`) and ends with PSI low (`0x30`); TCK (bit 6) is never set by the pulse routine. The debug name `sn1sc_reset_sic()` makes it the "reset SIC" pulse (name from the string only, I).

**Release wrapper** (package 0 `0xffe4f144`, package 1 `0xffe4ed94`):
1. Log `reset release (%s)` unless reason 5.
2. If MBAR + `0x41` bit 7 (`SYPCR` software-watchdog enable, armed with `0xfe` by `0xffe562d4` at start-up, [l1/board-boot-contract.md](../../software/firmware/l1/board-boot-contract.md)) is set, call the reset-brick routine `0xffe72214` (package 1 `0xffe720c4`) with the brick type character and a pointer for the error; if it reports failure return the error without touching the hook. Its debug text is `sn1sc_reset_brick(btype=%u)` (`0xffe737ea`). It is not a bare check: it pulses and scans on every release while the watchdog is armed, which is the normal case. In order: (a) error `-2300` and return failure if the word `0x30000044` is zero (not the case after start-up); (b) the six-value pulse above (`0xffe7219c`, call at `0xffe72256`); (c) if the descriptor word `+0xc0` (`0x30001e30 + 0xc0` in package 0, `0x30001f20 + 0xc0` in package 1) is nonzero, call that hook with arguments (`0xff`, 1, a context pointer) and return success when it returns zero (below); (d) otherwise dispatch on the brick type through the byte-offset table at `0xffe722a8` (package 1 `0xffe72158`), indexed by type minus `0x25`: types `%`, `A`, `C`, `G`, `I`, `N`, `P`, `R`, `X`, `Y` run one 0x18-bit scan (`0xffe74474` in package 0) with a type-specific pair of small constants (`C`: 0 and 7), and `-2301` is returned if the scan fails; every other type, including `4`, skips the scan; (e) the pulse again, then return success. So type `C` in package 0 gets pulse, scan, pulse on every release, and type `4` in package 0 would get pulse, pulse. **Package 1** sets the `+0xc0` hook in its descriptor initialiser (`0xffe45c7a` to `0xffe45c80`, hook `0xffe45af0`); package 0 does not. The package 1 hook does ten 0x18-bit scans (`0xffe74324`): one, eight identical ones in a loop, and a last one equal to the first, each failing with `-2303`, then runs the pulse once more because its second argument is 1. So an Origin 300 release is pulse, ten scans, pulse, and brick type `4` never reaches the table. E for all of it as read; I for what a scan shifts (argument meanings were not decoded) and U for the TAP data (section 8). The firmware therefore performs these pin writes and scans on every release; the early exit is the only way to skip them, and it needs `SYPCR` bit 7 clear.
3. **10 ticks.** E (`moveq #$a` at `0xffe4f1a8`).
4. For brick types `C 3 5 4 A 6 9 7 8 0 Q @ O B F H L` (compare chain `0xffe4f1b4` to `0xffe4f224`): `0xffe34510`, then `0xffe3517c` (clears the registered event subchannel word, see the next point). E. Other types skip both.
5. `0xffe36a04` (the port-service call above), then `0xffe52a30(0xff, 0)` (package 1 `0xffe52680`): for each of the first N ports (N = word at descriptor `+0x74`), `0xffe54a84(10 + i, 0)`. U for effect.
6. Hook `+0x9c`.
7. `0xffe4c828` (package 1 `0xffe4c478`): clears the power block's "just powered" word and, if the low-power monitoring count is nonzero, logs an internal error and turns that monitoring off. The two data addresses differ: package 0 base `0x300000fc` ("just powered" `0x30000114` = base + `0x18`, count `0x3000010c` = base + `0x10`); package 1 base `0x30000128` ("just powered" `0x30000140`, count `0x30000138`). E. Then `0xffe50b74(0xff, 5)` (package 1 `0xffe507c4`): for every port in state 2 or higher whose flags allow, call `0xffe500fc` and `0xffe509a4`. These are the counterpart of step 2 of the hold wrapper and raise the ports again; the text is not read, so "restores local-port-OK" is I. E for the call structure.

**Soft-reset wrapper** (package 0 `0xffe4f0ec`, package 1 `0xffe4ed3c`): log `soft reset (%s)` unless reason 5, then hook `+0xa4`. Nothing else. E.
**NMI wrapper** (package 0 `0xffe4f0a4`, package 1 `0xffe4ecf4`): log `NMI (%s)`, then hook `+0xa8`. No port or UART call. E.

## 3. C-brick (package 0) hooks, with byte-level effect

Start state (established for the applied bytes, U for whether this application runs on an L1-only restart, see [ip45-io-expanders.md](../../software/firmware/l1/ip45-io-expanders.md)): `CNTL 1` = `0x72`, `CNTL 2` = `0x8a`.

**Hold hook `0xffe44bd4`:** (1) a mismatch between the two processor-module type bytes (`0x30000090`, `0x30000091`) and persistent settings `0x56` and `0x57` (a type of `0x0f` is skipped; read through `0xffe59fbc`) logs a notice and re-runs the default voltage margins (`0xffe4e40c`); when that returns zero the hook stores the two type bytes back into settings `0x56` and `0x57` (`0xffe59184`, `0xffe44c80` to `0xffe44ca4`), otherwise it logs an error and stores nothing; (2) the board flag byte at `0x30000098` (set once by `IP35_Init`, `0xffe44ae0`, which logs "called twice" on a repeat) must be nonzero, else the hook returns `-900` before touching any line; (3) clear `CNTL 1` `0x80`, `CNTL 1` `0x02`, `CNTL 2` `0x01`, `CNTL 1` `0x01`, in that order, no delay; (4) per processor module (type byte, expander 13 and module 1, then expander 15 and module 2), `0xffe44b48`: type `0x0f` does nothing; types 1, 3, 4, 5, 6, 7 and 10 run the margin routine `0xffe4e4f8` and wait **10 ticks**, then every type except `0x0f` sets bits `0xc0` of the module's `VCC OK` expander (jump table at `0xffe44b66`, read from the bytes: offsets 72 for 0, 2, 8, 9, 11 to 14, 36 for 1, 3 to 7, 10, 32 for 15). E.
Resulting expander bytes from the start state: `CNTL 1` `0x72`, `0x70`; `CNTL 2` `0x8a`; `CNTL 1` `0x70`. The set of processor-module types {1, 3, 4, 5, 6, 7, 10} is the set that also gets the extra reset in section 5 and the reset-time margin step: the log text "reset again MIPS" ties it to the MIPS module types (inferred for the name, E for the set).

**Release hook `0xffe44dfc`**, in order (established; strap rules as in [power-reset-cbrick.md](../../software/firmware/l1/power-reset-cbrick.md) section 6):
1. `CNTL 2` mask `0xf8` := `D`, where `D` = `0x08`, plus `0x80` when the strap-7 rule holds, plus `0x20` when persistent setting `0x28` is nonzero, plus `0x10` when setting `0x29` is nonzero. Bit 6 is written 0. Result: `0x02 | D` (bits 0 to 2 of `0x8a`'s `0x02` survive).
2. **10 ticks**; clear `CNTL 2` `0x08`.
3. **10 ticks**; set `CNTL 1` `0x01`.
4. **10 ticks**; per module (expander 13 / module 1, then 15 / module 2) `0xffe44d54`: type `0x0f` nothing; otherwise clear `0xc0` of its `VCC OK` expander, **3 ticks**, and for types {1, 3, 4, 5, 6, 7, 10} run `0xffe4e450` (restore the margin; also drops the low-power-monitoring count) and **10 ticks** (jump table at `0xffe44db8`, bytes 54 and 22).
5. Set `CNTL 2` `0x01`, then set `CNTL 1` `0x02`, no delay.
From a hold state of (`CNTL 1`, `CNTL 2`) = (`0x70`, `0x8a`) and `D` = `0x08`: `CNTL 2` `0x0a`, `0x02`; `CNTL 1` `0x71`; `CNTL 2` `0x03`; `CNTL 1` `0x73`. The earlier note listed the module step before the set of `CNTL 1` bit 0; the order above is the code's (`0xffe44ed4` set, `0xffe44ef0` wait, then `0xffe44efc` module step).

**Soft-reset hook `0xffe445e8`:** flag-byte guard (`-900`); set `CNTL 1` `0x80`; **10 ticks**; clear `CNTL 1` `0x80`. Bytes from `0x73`: `0xf3`, then `0x73`. E.
**NMI hook `0xffe4463c`:** guard; clear `CNTL 1` `0x40`; set `CNTL 1` `0x40`, two consecutive writes with no delay. Bytes from `0x73`: `0x33`, then `0x73`. The pulse width is therefore the gap between two two-wire transactions: U in time (section 8). The hook ignores its argument, so the "node" and "slice" the `nmi` command takes do not select a line (established: the hook reads no stack argument); the command only records a target mask in `0x30000124` (node) and `0x30000128` (processor), `0xff` meaning all (`0xffe4efd4`, E), which the command later prints as `NMI %d.%d %d%c`. Which processors the node's firmware sees as interrupted is therefore decided downstream of the L1 (inferred).

## 4. Origin 300 (package 1) hooks

Descriptor initialiser `0xffe45bac` stores hold `0xffe453e4`, release `0xffe4552c`, second-reset test `0xffe45060`, soft reset `0xffe45084`, NMI `0xffe450e0`. Three hooks test the board byte `0x3000009c` (set by `IP45_Init`, `0xffe44ff4`, called with the constant `0x0a` at `0xffe45ab2`) against `0xff` and return `-2500` (`0xfffff63c`) if it is `0xff`: hold (`0xffe453e4`, compare at `0xffe453f2`), soft reset (`0xffe45084`) and NMI (`0xffe450e0`). Release (`0xffe4552c`) has no such test: it loads the byte directly as the expander index (`movea.l #$3000009c` at `0xffe455b2`), and the second-reset test (`0xffe45060`) reads the other byte `0x3000009d` with no guard. Before `IP45_Init` has run, a release would therefore index expander `0xff` (the init always runs at registration, so this is not reachable in normal start-up: I). So that byte is the expander index 10, `XBRIDGE CONTROL` (established for the constant, I for its use as a bus-select-style guard; the board note of [ip45-io-expanders.md](../../software/firmware/l1/ip45-io-expanders.md) already tabulates index 10). The expander is named index `X` below.

**Hold `0xffe453e4`:** write `X` mask `0x0b` := 0 (selecting segment 5 of the bus switch first, which is a side effect of the write); clear `ASIC CTRL 1` `0x80`; clear `ASIC CTRL 1` `0x02`; clear `ASIC CTRL 2` `0x01`; clear `ASIC CTRL 1` `0x01`; `0xffe45348(4, 8)`: if expander 4 (`POWER CONTROL`) is present: for processor-module PSC codes 1 to 4 run `0xffe4e148(8, 14)` and **10 ticks**; then set expander 4 `0x10` and then `0x20`. No other delays. E. Order of the four `ASIC` clears equals the C-brick order (`CNTL 1` `0x80`, `0x02`, `CNTL 2` `0x01`, `CNTL 1` `0x01`).
**Release `0xffe4552c`:** (a) if `0xffe4c2fc()` is nonzero (a predicate over the supply records, not read in full: U for its meaning) the strap-7 and `X` bit-2 rule is evaluated: `d7` := `0x80` and `d6` := 0 when the global word `0x3000015c` is set and setting `0x2a` is nonzero, or when it is clear and module record 1 is valid with its `+0x30` word nonzero; else (valid record with a zero word) `d7` := 0 and `d6` := 4, and with no valid record both settings `0x2a` and `0x2b` are first cleared and `d7` := 0, `d6` := 4; then **10 ticks**, `X` mask `0x0b` := `0x0a`, **10 ticks**, `X` mask `0x0b` := `0x0b`. (b) `d7 |= 0x08`, `|= 0x20` when setting `0x28`, `|= 0x10` when setting `0x29`. (c) `ASIC CTRL 2` mask `0xf8` := `d7`; `X` mask `0x24` := `d6`; **10 ticks**; clear `ASIC CTRL 2` `0x08`; **10 ticks**; `0xffe45488(4, 8)` (clear expander 4 `0x10`, then `0x20`, **3 ticks**; for PSC codes 1 to 4 run `0xffe4e0a0(8)` and **10 ticks**); set `ASIC CTRL 1` `0x01`; **10 ticks**; set `ASIC CTRL 2` `0x01`; set `ASIC CTRL 1` `0x02`. E for the order, delays and masks.
**Soft reset `0xffe45084`:** set `ASIC CTRL 1` `0x80`; **10 ticks**; clear. E. **NMI `0xffe450e0`:** clear `ASIC CTRL 1` `0x40`; set `0x40`; no delay. E.
**Second-reset test `0xffe45060`:** returns 1 when the PSC code byte `0x3000009d` is 2, 3 or 4, else 0. E. Section 5 shows when it matters.

## 5. The `reset` command and the double reset during power-up

Reset wrapper (package 0 `0xffe4f324`, package 1 `0xffe4ef74`), argument = reason, in order (established):
1. Log `reset (%s)` unless reason 5.
2. `n := 2` if `0xffe4c7e4` (package 1 `0xffe4c434`) returns nonzero, else 1. That routine returns the `+0xa0` hook's result only when the "just powered" word `0x30000114` is nonzero; otherwise 0. The hook returns 1 on the C-brick when either processor-module type byte is in {1, 3, 4, 5, 6, 7, 10} (`0xffe4458c`, table bytes at `0xffe445b4`), and on the Origin 300 when the PSC code is 2, 3 or 4.
3. For iteration i = 0 to n-1: for i = 1 only, log `reset again MIPS` and wait **400 ticks** (`0x190`, `0xffe4f37c`); then the hold wrapper (section 2, without the parallel-port pulse); **10 ticks**; the release wrapper. An error from either wrapper is returned at once.

The "just powered" word is set to 1 by the power-up routine after its supply walk (package 0 `0xffe4d0e8`, package 1 `0xffe4cd38`; data addresses as in step 7 of the release wrapper) and cleared by step 7 of the release wrapper (`0xffe4c828`, package 1 `0xffe4c478`). In package 1 the word is `0x30000140` and the reset wrapper's helper `0xffe4c434` reads it; in package 0 it is `0x30000114` (helper `0xffe4c7e4`). So the second reset happens **only inside `power up`** (the call `reset(5)` at package 0 `0xffe4d15e`, package 1 `0xffe4cdae`), and only for those module types. Two other call sites pass reason 5 and are separate (section 6); the word is already 0 by then, so they do one pass. A `reset` typed afterwards, a front-panel reset and a request-driven reset (reason 3) see the word at 0 and do one pass. E for the code; I for "this is a MIPS-module retry" (name from the log line only). The existing note described `reset` as a single hold, 10 ticks, release; that holds for every case except `power up`.

Cost of one pass, C-brick, in ticks: hold = 10 per present module with type in the set; wrapper gap = 10; release wrapper = 10 + hook; release hook = 30 + 13 per present set-type module + 3 per present other-type module. Two in-set modules: 20 + 10 + 10 + 30 + 26 = 96 ticks, 0.96 s at the inferred 100 Hz. In `power up` the second pass follows 400 ticks after the first release returns (4 s at 100 Hz), so the node sees two full hold and release cycles about 4 s apart. The count leaves out the reset-brick pulses and scans of the release wrapper (section 2), whose time is U. E for the arithmetic, I for seconds.

The plain `power up` path waits **50 ticks** (`moveq #$32` at `0xffe4d14e`, delay call at `0xffe4d152`) before this `reset(5)` for the brick types listed in [power-reset-cbrick.md](../../software/firmware/l1/power-reset-cbrick.md) section 2, item 6, and calls it at once for the others (established). The `reset hold` command (`0xffe198f4`) calls `0xffe4f2f0(1)` (hold only, with the parallel-port pulse). The `reset` command is refused with "ERROR: power appears off." unless the supply-state routine reports all on (established, [power-reset-cbrick.md](../../software/firmware/l1/power-reset-cbrick.md)).

## 9. What this note changes in earlier notes

- `reset` is hold, 10 ticks, release **once**, except inside `power up`, where it runs twice with 400 ticks between for the processor-module types in section 5 (earlier note: always once).
- The hold and release wrappers also quiesce and restore every L1 port (the `port_down` family, text `clr LPOK`/`force link`), which the earlier note listed as three unfollowed calls.
- The C-brick release order is: strap, 10, clear bit 3, 10, set `CNTL 1` bit 0, 10, module step, set `CNTL 2` bit 0, set `CNTL 1` bit 1 (earlier note placed the module step before the set of `CNTL 1` bit 0).
- Origin 300 hook bodies are tabulated in section 4; `ASIC CTRL 1` and `2` carry the same bit uses as `BEDROCK CNTL 1` and `2`.
- `DISPLAY CONTROL` input bit 1 is the NMI button and bit 2 the reset button.
- The tick is established as one timer-1 interrupt; its length stays inferred.
- The parallel-port pulse and the reset-brick scan routine run: the gating word `0x30000044` is set at start-up. The release wrapper pulses and scans on every release while the watchdog is armed (section 2); earlier text called both unreachable or unknown.
- Reason codes have the firmware's names (`COMMAND`, `PANEL`, `OS`, `ENVIRONMENTAL`, `DON'T CARE`); the tick counter, the "just powered" word and the monitoring count are package-specific addresses; the Origin 300 release hook has no board-byte guard; the power-up routine has a second `reset(5)` site for three brick types.

### 11.2 `softreset <n>` and `nmi <n>` (established)

- **Type C (package 0).** The hooks `0xffe445e8` and `0xffe4463c` never read their argument (section 3). `softreset 1` resets exactly what `softreset` resets: both nodes, by the one shared `CNTL 1` bit 7 pulse. Same for `nmi`. E.
- **Type 6 (package 2).** The descriptor hooks are `0xffe50b68` (soft reset) and `0xffe50b88` (NMI); each calls the node iterator `0xffe5e0d4(node, routine)` with the per-node routine `0xffe63750` or `0xffe637d8`. ### 11.3 `reset <n>` on type 6 (established for the calls, I for the effect)

The record at `0xffe18680` routes to `0xffe167a0`, which rejects an index above 4 ("invalid node index") and otherwise calls `0xffe63dec(n)`, the same per-node routine the brick-wide hold hook runs for every enabled node (hook `+0x98` is `0xffe50ad0`, iterating with `0xffe5e0d4`). ### 11.4 `cpu d` and `node d` (established for the guards, stores and hooks)

Both refuse when the supply-state routine (package 0 `0xffe4c6ac`, package 2 `0xffe6cb10`) is nonzero, that is when any supply is on, with the "power must be down" text. Both then call a board hook, and only when the hook succeeds, persist the result.

- **`cpu d [<node>x]` (package 0).** `0xffe528c8(idx)` for one CPU, or all four for `disable all`. The L1 stops or starts monitoring the node's parts; it does not drive an expander line to the node in these two hooks. E for the structure and that no expander write is on this path; I that the flags are monitoring-enable flags (flag-table roles from the neighbouring error text only).
- At power-up (the diagnostic routine at `0xffe5e368` onward) a nonzero setting `0x70` logs a "Node Disabled" line and sets the flag bytes at `0x30000609`, `+0`, `+1` and `+3` (established for the store; the flags' consumers were not followed, U). Every hold, release, soft reset and NMI call routed through the iterator then skips the disabled node: **a disabled type 6 node is neither held nor released by any brick-wide `reset` or `power up`**, so its reset group keeps whatever state it had when disabled (established for the skip; I for the state, since power was down at that time).

### 11.5 What the PROM and Bedrock can see

- The C-brick `cpu d` line is the only per-part signal: a bit of the `PIMMn POWER` expander (established for address and bit). Where it lands in the node is not in any image (unknown); the L1 labels it only through the expander name. A PROM or kernel reading CPU presence from Bedrock would see an absent or silent processor, not a message (inferred).
- `softreset <n>` on type C is indistinguishable from `softreset`; on type 6 only the chosen node's soft-reset line moves. `nmi` likewise.
- The strings `FLED_DISABLED` ("CPU is disabled by env variable") and `FLED_KILLED` ("CPU disabled by another") in the package 2 LED-code name table (`0xffe40254`, `0xffe40164`) are PROM-side LED codes the L1 only prints. They show that the PROM has its own disable path (an environment variable) that is separate from the L1 settings above (established for the strings and table; I for their origin).
- Nothing in these paths changes the power-state word, the peer notice, or the supply sequencing: power remains brick-wide (established).
