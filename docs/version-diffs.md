# Version diffs

What changed between the four firmware sets, for the Origin 300 L1 package and the L2 image. The sets and their files are in [firmware-versions.md](firmware-versions.md).

| Set | L1 (package 1, Fuel/PE) | L2 |
|---|---|---|
| IRIX 6.5.22 overlays | 1.24.8 | 1.24.1 |
| patch SG0005762 | 1.32.15 | 1.32.4 |
| IRIX 6.5.30 overlays | 1.44.0 | 1.44.0 |
| patch SG0007149 | 1.48.1 | 1.48.0 |

The L1 package is labelled `Fuel/PE 1MB image` in 1.24.8 and 1.32.15 and `Fuel/PE/O300 1MB image` in 1.44.0 and 1.48.1. That it is the Origin 300 package in the two earlier sets is inferred from the same package slot and the same load and reset values.

The tables are generated by `tools/re-run python3 scripts/version_diff.py`:

- [version-diffs/l1-routines.tsv](version-diffs/l1-routines.tsv): one row per added, removed or changed routine, with addresses, lengths, similarity and the first differing instruction.
- [version-diffs/l1-request-codes.tsv](version-diffs/l1-request-codes.tsv): each general request code in each set, with its handler address and whether the handler body matches 1.44.0.
- [version-diffs/l2-bytes.tsv](version-diffs/l2-bytes.tsv): the L2 kernel and cramfs measurements.

Grades: **established** means read in the image; **inferred** means reasoned from partial reads or from a pairing rule; **unknown** means not settled by any image read so far.

## Method

Routines. Entries are `link.w a6` prologues, absolute `jsr` and `bsr` targets, and the vector-table handlers. A routine runs from its entry to the next entry. Its text is decoded with capstone in 68040 mode, and every in-image address (`0xffe0xxxx`) is replaced by `ADDR`.

- Same bytes: the raw routine matches.
- Same code, moved: the masked text matches.
- Changed, RAM address only: the masked text matches once RAM operands (`0x30xxxxxx`) are masked too.
- Changed: anything else.

Pairing across a set boundary aligns the routine fingerprints in address order. Unmatched runs are paired by instruction-multiset similarity, at 0.5 or more. What is left over is added or removed. The pairing is inferred. Each changed row carries its similarity.

Limits. A routine reached only by a computed jump has no entry, so it is folded into its predecessor. One 63.7 KB stretch in 1.24.8 has no entry inside it (see below). Each body holds the program twice, 0x70000 bytes apart, and the counts include both copies.

Request codes. The general request dispatch is a compare chain followed by word-offset jump tables. The chain is run concretely for every code from 0x0000 to 0x7fff. The entry point differs by set (the code is loaded from d2, a4 or d5). No code stopped at an instruction the interpreter does not model. The 39 general-request rows of the curated 1.44.0 table ([l1/request-codes.tsv](l1/request-codes.tsv)) all agree with the run.

## L1 routines

| Step | Same bytes | Same code, moved | Changed, RAM only | Changed | Removed | Added |
|---|---:|---:|---:|---:|---:|---:|
| 1.24.8 to 1.32.15 | 923 | 368 | 490 | 901 | 2,126 | 2,318 |
| 1.32.15 to 1.44.0 | 1,891 | 746 | 1,050 | 446 | 867 | 917 |
| 1.44.0 to 1.48.1 | 5,042 | 0 | 0 | 8 | 0 | 0 |

Each set has 4,808 (1.24.8), 5,000 (1.32.15) and 5,050 (1.44.0 and 1.48.1) routines, both copies included. The vector table, the first 0x400 bytes, is identical in all four sets (established).

Bytes in removed and added routines: 418,492 removed and 422,780 added from 1.24.8 to 1.32.15 (inferred, from the pairing). From 1.32.15 to 1.44.0, 150,648 removed and 152,300 added. The changed routines have a median similarity of 0.765 in the first step and 0.871 in the second.

**1.44.0 to 1.48.1.** The two bodies differ at 42 byte positions (established, from a byte comparison of the whole body). The version and build positions are ASCII text, so they are data (established from the bytes). The decoder also reads them as instructions, which is why the routine rows show text changes at those spots. All 42 positions fall in the version strings, the build stamp and the bank record described below, so no executable byte changed (established, each position read in context).

- Version string `1.44.0` becomes `1.48.1`: two bytes near `0x10aab` and two near `0x13ef3`, with mirrors 0x70000 higher.
- Build stamp `20060717182038` becomes `20070122113420`: 11 bytes in the window `0x7a44f` to `0x7a460`, with the mirror at `0xea44f`.
- Six bytes at `0x7fd39` to `0x7fd3f` (and `0xefd39` to `0xefd3f`) differ: the low three bytes of word 7 and of word 8 of the 48-byte bank record at `0xffe7fd1c` ([l1/personalities.md](l1/personalities.md#the-bank-record)). Word 8 is the additive sum of the bank before the record, and the sum recomputed over the 1.48.1 bank equals the stored `0xa82b0f11` (1.44.0: `0xa83e0909`), so it moved because the strings moved (established). Word 7 moved with it so the twelve record words still add to zero (established: both sums are zero); word 7 is the balancing word and no code is known to read it. The pointers beside them (`0xffe7a44c` and `0xffe7a45b`) are record words 4 and 5, which point at the build stamp and version string and did not change.

The eight changed routines are the ones that contain these bytes: `0xffe10570` and `0xffe80570` (version string), `0xffe13eea` and `0xffe83eea` (second version string), `0xffe7a344` and `0xffeea344` (build stamp and version string), and `0xffe7f9a0` and `0xffeef9a0` (the six-byte table).

**1.44.0 to 1.48.x in the other ColdFire packages (established, from a byte comparison of each pair of bodies).** Packages 0, 2 and 3 have the same length in both sets, and the packages differ in the same classes as package 1 and in nothing else:

| Package | Differing byte positions | Classes |
|---|---:|---|
| 0 `Base 1MB` | 44 | two version strings, the build stamp and a second version string beside it, record words 7 and 8, each twice (the bank repeats) |
| 1 `Fuel/PE/O300 1MB` | 42 | as above, with one version string and one build stamp |
| 2 `MIPS 2MB` | 68 | two version strings, build stamp and version string, record words 7 and 8, one word in the table that follows the record, two words in the tail of that table, each twice |
| 3 `Legacy 2MB` | 62 | the same classes as package 2 (this package reports 1.48.0 in its own strings and 1.48.1 in its stamp area) |

The table after the record in the 2 MB packages is a list of 32-bit entries headed by three words (1, a byte length, one more word). Its entries carry a tag in the top byte and a bank offset in the low 24 bits; the two tag-3 entries name the bank offsets of record words 7 and 8 (`0x9a2a8` and `0x9a2ac` in package 2), and the one differing header word and the two values after the tag-3 entries are the other changed words. The table's role is inferred only, from one message in the 6.5.30 `flashsc`, which refuses an L1 flash binary that has no "relocation tables" (the string sits beside the check for both A and B images); its words were not decoded. Package 5 (`2MB image`) is not the same length in the two sets (1,778,732 and 1,768,320 bytes, last addresses `0xfffb242b` and `0xfffafb7f`), so it is a rebuilt body and was not compared byte by byte.

Because the bodies of packages 0 to 3 differ only in strings, the record and its table, everything read in 1.44.0 about their code (the request dispatchers, the I/O register accesses, the protocols) holds for 1.48.x unchanged. For the Origin 300 package that includes the register and protocol rows of [l1/io-registers.tsv](l1/io-registers.tsv) and [l1/protocols.tsv](l1/protocols.tsv): a register scan of the 1.48.1 package would repeat the 1.44.0 result.

**1.32.15 to 1.44.0 (inferred).** Most code is reused and most RAM operands moved. 1,891 routines match exactly and 746 match once addresses are masked. One example of a changed routine: the 1.32.15 routine at `0xffe296f4` (232 bytes, paired with 1.44.0 at `0xffe2972c`, similarity 0.977) first differs at `moveq #$e, d1` against `moveq #$12, d1`. The rest of the pair is not read here. Routines that differ only in RAM operands are counted separately, for example the 1.32.15 routine at `0xffe41bd4`, whose first difference is a `pea` of `0x30003e24` in place of `0x30003e44`.

**1.24.8 to 1.32.15 (inferred).** Only 923 routines match exactly. The 1.32.15 image is a substantial rearrangement of the 1.24.8 image by this measure. The 63.7 KB row at `0xffe00b28` is one routine only because no entry lies inside it. Its first 16 bytes are a small routine (a link, a branch to subroutine at `0xffe00994`, an unlink and a return), and its only link instruction is at that start. The rest is fill: 0xff bytes make up 98.7% of the row, and one run of 61 KB starts at `0xffe01008` (established for 1.24.8). The same length, first bytes and fill fraction hold in all four sets (established). The row is not split. Its role is unread; it is probably unused image space (inferred from the fill).

## L1 request codes

The general dispatch accepts these codes in each set (established, from the chain run).

| Set | Codes accepted |
|---|---|
| 1.24.8 | 0x0001 to 0x0010; 0x1001 to 0x100b; 0x2001 to 0x2008; 0x3001; 0x4000 |
| 1.32.15 | 0x0001 to 0x0011; 0x1001 to 0x100c; 0x2001 to 0x2008; 0x4000 |
| 1.44.0 | 0x0001 to 0x0011; 0x1001 to 0x100c; 0x2001 to 0x2008; 0x4000; 0x4002 |
| 1.48.1 | as 1.44.0 |

Code changes:

- 1.24.8 to 1.32.15: adds 0x0011 (handler at `0xffe12ba8`) and 0x100c (`0xffe13236`); drops 0x3001 (1.24.8 handler at `0xffe13796`).
- 1.32.15 to 1.44.0: adds 0x4002, `general_req_controller_reboot` at `0xffe13d76` (named in the curated table).
- 1.44.0 to 1.48.1: no change.

Handler bodies, against 1.44.0 (normalized text, see the method):

- 1.48.1: all 39 handlers have the same text as 1.44.0.
- 1.32.15: 10 match (0x0001, 0x0009, 0x000b, 0x1001, 0x1003 to 0x1006, 0x100a, 0x2001). The other 28 differ; 0x4002 is absent from 1.32.15, so 38 codes are compared. Examples: 0x0011 keeps its frame at `-$c8(a6)` where 1.44.0 has `-$cc(a6)`; 0x1007 has `pea -$310(a6)` where 1.44.0 has `-$31c(a6)`. Frame offsets, not logic, are the first difference (established for the two examples).
- 1.24.8: only 0x100a matches. Several handlers are short stubs in 1.24.8: 0x0001 is `moveq #3,d4` then `bra`, where 1.44.0 has the `moveq #3,d0`, `move.l d0,-(a7)`, `jsr` sequence. The branch target of such a stub is not compared, so its handler text is cut short (established for 0x0001; the shared tail is unknown).

The request codes for other dispatchers, the command loop (code 0x0000 under task 3, for example) and the flash and peer forwarding paths, are not compared here.

## L1 general request codes, every set with the Origin 300 package

`scripts/l1_request_catalogue.py` runs the compare-chain interpreter of `version_diff.py` over the Fuel/PE package of each set that carries one: 6.5.22 to 6.5.30 and both patches, eleven sets in all (established). The sets 6.5.20 and 6.5.21 have a different first package and are not covered.

- [version-diffs/l1-request-catalogue.tsv](version-diffs/l1-request-catalogue.tsv): every accepted code in each set, with its handler address, a hash of the handler's normalised text, its line count, and how it compares with the same code in 1.44.0.
- [version-diffs/l1-request-changes.tsv](version-diffs/l1-request-changes.tsv): codes added or removed between consecutive sets, and codes whose handler text changes. A handler that only moved is not listed.

Scope: the general request chain only (task 6 in [l1/request-codes.tsv](l1/request-codes.tsv)). The command loop, the flash and power-bay tasks and the peer forwarding paths are not in these tables. Reply sizes are not extracted per handler here; the curated 1.44.0 rows state them.

The handler text is a literal comparison of the disassembly with addresses masked. A difference can be a real change or a register or frame-offset change in the same logic, and the tables do not separate the two. For 0x0001, 0x0002 and 0x0003 between 1.30.6 and 1.32.6, the first differing lines are register choices (`move.l d0,d5` against `move.l d0,d4`); the rest of those handlers is not read.

In every set, every handler except the 0x4000, 0x4001 and 0x4002 ones ends in an unconditional branch or jump to code that other handlers also use, and the code it reaches is not part of the compared text (established for all eleven sets, from the last instruction of each handler). The short ones only set up their parameters before the branch: in 1.44.0 the handlers of 0x0001, 0x0009, 0x000b, 0x000e, 0x1003, 0x100a, 0x2001 and 0x2005 are 14 lines or fewer, and 0x100a is two. For those, "same text" or "text changed" speaks only to the setup lines, not to what the shared code then does. 0x0001 in 1.24.8, 1.26.5 and 1.28.3 is two lines (`moveq #3` into a register, then the branch), so its change to a different register between 1.24.8 and 1.26.5 says nothing about the handler's behaviour. A change of this kind is a candidate to read, not a finding.

## L2 image

| Set | Kernel (decompressed) | Kernel bytes | cramfs offset | cramfs size |
|---|---|---:|---|---:|
| 1.24.1 | `2.4.7-sgil2` | 1,438,340 | 0xd4ff9 | 2,007,040 |
| 1.32.4 | `2.4.7-sgil2` | 1,438,340 | 0xd4ff8 | 2,043,904 |
| 1.44.0 | `2.4.7-sgil2` | 1,430,148 | 0xd521d | 2,052,096 |
| 1.48.0 | `2.4.7-sgil2` | 1,438,340 | 0xd4ff7 | 2,121,728 |

- The kernel banner is the same in all four (established).
- The 1.44.0 kernel is exactly 8,192 bytes shorter than the others (established).
- 1.24.1 to 1.32.4, the kernels have the same length and 7,644 of 1,438,340 bytes differ (established).
- 1.32.4 to 1.44.0 and 1.44.0 to 1.48.0 have different lengths, so no byte count is reported. Their 4 KB blocks, compared in order, match in 34 of 352 and 34 of 350 blocks (established, block counts only). The low count suggests the kernels are not aligned by a fixed offset (inferred); no finer comparison is made.

The cramfs trees are walked by `scripts/l2_extract.py`: every inode offset counts from a 512-byte pad that precedes the superblock, which is why a walk from the superblock fails (see [l2/image-layout.md](l2/image-layout.md)). The per-file differences between the four sets (sizes and which files are byte-identical) are in [l2/rootfs.md](l2/rootfs.md). No routine-level comparison of the daemon and libraries is made yet.
