# Origin 300 L1: what the console prints and answers

This note describes what the Origin 300 L1 firmware sends on its operator console, and what it answers, in each console state: at power-up, at the banner, at the idle prompt, for each command family and for error replies. It is written so that two controllers (the shipped firmware and any other implementation of the same console) can be compared transaction by transaction: a byte sent, the bytes returned.

## Scope and image

Everything below is read from the Origin 300 L1 1.44.0 ColdFire body (package 1, `Fuel/PE/O300 1MB`, body sha256 `9db44f3bb06ec90475035781766e1ca7e924f15a0ed215cf855c1f491275fdd1`, loaded at `0xffe00000`; see [l1/package-container.md](l1/package-container.md)). Addresses are first-bank addresses; the second bank is the same code `0x70000` higher. Strings were read at body offset = address minus `0xffe00000` and the command table (295 records of 68 bytes) was decoded from body offsets `0x1c0a0` to `0x20efc`; the last record starts at `0x20eb8`. Brick type character `4` (the Origin 300 board personality) is assumed unless a row says otherwise. Other packages and versions were not read for this note.

Grades follow [AGENTS.md](../AGENTS.md): established (read in the image, whole routine), inferred (reasoned from partial evidence), unknown. Each unknown names the software test that would settle it.

Terms: the "console" here means the L1's own operator serial port, called the system management port in the firmware's log texts. It is not the processor console, which the L1 relays when it is in console mode. The "text-command task" is the request endpoint that runs the same commands for host tools; it is covered in [l1/debug-task.md](l1/debug-task.md) and only touched here where a console reply differs.

Hints (not findings, from public manuals): the Origin 300 guide `007-4498-002` printed pages 181 and 184 show example command output; the controller guide `007-3938-006` printed pages 9 to 12 name the console subchannels and printed page 60 lists the valid brick types.

## 2. The line has two framings

The console runs in one of two framings, held in the word at `0x30005140+0x330`.

- Text framing (value 0, the value after boot): the read task tests the word against 1 at `0xffe3810c`; for any other value it branches to `0xffe381e6`, reads one byte through the UART read helper `0xffe36a90` into the buffer at `0x30005e10` and hands it to the console state machine at `0xffe378ac` (`0xffe381e6`-`0xffe3820c`). Established.
- Packet framing (value 1): the same UART is read as framed packets for host tools (`0xffe38116`-`0xffe38134`: the packet reader `0xffe790a8` with the callback `0xffe36a38`). A received byte `0x18` (control-X) while in text framing echoes the byte back and switches to packet framing (`0xffe3793e`-`0xffe379d6`; the switch reconfigures the UART client through `0xffe643cc` and `0xffe643e8`). The route back to text framing, and the exact packet format, are not covered here (see [l1/rs422-router.md](l1/rs422-router.md) and [l1/chunked-request-frames.md](l1/chunked-request-frames.md)). Echo and switch: established. Return to text framing: unknown; test: find stores of `0` to `0x30005140+0x330` and read the callers.

Output newline handling depends on the console state (section 3): in console mode (state 1) text goes out byte for byte; in the two L1 states every line feed in a message is sent as carriage return plus line feed (`0xffe36b22`-`0xffe36b92`, the two-byte string at `0xffe38869`). Established.

## 3. The console state machine

State word at `0x30005140+0x334`. Values and meaning (established from `0xffe378ac` branches and `0xffe36fc6`):

| State | Name used here | Entered |
|---|---|---|
| 3 | locked L1 prompt | at `management_port_init` (value `3` stored at `0xffe36fc8`) |
| 2 | escaped | from console mode on control-T (`0xffe37a3e`-`0xffe37a40`) |
| 1 | console mode | from state 3 on control-D (`0xffe37b60`); from state 2 after one command (`0xffe37c4a`) |

Transitions, one input byte at a time (all established unless stated):

1. State 3, control-D (`0x04`): if the brick type character is not one of a fixed set of 17 type characters (the set is compared at `0xffe37a88`-`0xffe37af6`; `4` is in it) the L1 prints `no console available on this brick` plus a line feed and stays. Otherwise, if the node-power test `0xffe4c2fc` does not return 1, it prints `WARNING: power appears off, console unavailable` plus a line feed. Then, in state 3, it prints a line feed, `entering console mode NAME, <CTRL_T> to escape to L1`, a line feed, and moves to state 1. NAME is the current console selection text built by `0xffe30dec` into the buffer at `0x30004f36` (format at `0xffe386d6`, call at `0xffe37b38`). For every type except `5`, `@` and `6` the routine first stores a one-space string (`0xffe31289`) and then appends a name that itself begins with a space: ` CPU0` to ` CPU3` or ` console` for subchannel 0 to 4, taken from bits 5 to 9 of the selection word at `0x30005140+0x9f4` (strings `0xffe312af`-`0xffe312c7`, appended with the string-append routine `0xffe7d2e8`), or ` subchannel %d` otherwise (`0xffe312a0`). NAME therefore starts with two spaces and the line reads `entering console mode   CPU0, <CTRL_T> to escape to L1` with three spaces after `mode`. Types `5`, `@` and `6` take another branch (`0xffe30e5e`-`0xffe30f00`, a printf into the buffer at offset 1) whose output was not decoded. The same text feeds the `returning to console mode` line (`0xffe37c28`) and the routing errors below. Established for type `4`, read from the code; not executed.
2. State 3, control-D when already in state 1 or 2: not applicable (state 1 forwards the byte to the processor, state 2 does only the warning check; see below).
3. State 1, control-T (`0x14`): prints a line feed, `escaping to L1 system controller`, a line feed, then the prompt string (section 4), clears the line buffer, moves to state 2. Any other byte in state 1 is sent to the selected processor console as console input through `0xffe37710`; on a routing failure the L1 prints a line built from the format `ERROR: can't route console input %s, %s` plus a line feed (`0xffe3881a`; built at `0xffe37796`-`0xffe377b4`). The first `%s` is the console name from `0xffe30dec` (two leading spaces, see transition 1, so the line starts `ERROR: can't route console input   CPU0, ` for subchannel 0). The second is an error text from `0xffe5b6b4`, which turns a numeric error code into text: `TEXT [errno N]` for code magnitudes 1 to 300, `Unknown Module %d, message = %d` for codes outside the module range, otherwise `MODULE:MESSAGE` from a module table at `0xffe5be20` (formats `0xffe5d912`-`0xffe5d956`). The individual texts per code were not enumerated. Two related errors come from the same family. A command that cannot be routed prints `ERROR: can't route command input, %s` plus a line feed (`0xffe38843`, built at `0xffe37878`; error text as above). A route that was accepted but never answered prints `ERROR: no %s response from %s, %s` plus a line feed (`0xffe387e7`, built at `0xffe376d4`-`0xffe376dc` by the routine at `0xffe375b4`): the first `%s` is `console` or `command`, the second the target's name (the console name for console input; another naming routine, `0xffe30be4`, for commands, not decoded), the third `TIMEOUT` when the 3000-tick wait (`0xbb8`, `0xffe375cc`) ends with the timeout code and `NUCLEUS` for any other failure of the wait. Established for the formats and call sites; the codes that reach each text are not enumerated. The brick-type-dependent routing is not covered here.
4. States 2 and 3, carriage return (`0x0d`) or line feed (`0x0a`): if the line buffer is non-empty it is copied into the history ring first (section 5). The L1 then echoes a bare line feed (`0xffe3870b`), submits the line to the command parser (section 6), and clears the line buffer. After that:
   - State 3: the prompt string is printed again; the state stays 3.
   - State 2: if node power is not on, the power warning is printed; then a line feed, `returning to console mode NAME, <CTRL_T> to escape to L1`, a line feed; state becomes 1. So an escape runs exactly one line, including an empty one, and then returns to the processor console.
   An empty line is not submitted (`0xffe377f6`-`0xffe377fc` returns zero before building a request), so an empty line prints only the echoed line feed and, in state 3, a fresh prompt.
5. States 2 and 3, backspace (`0x08`): if the buffer is non-empty, remove the last character and send the three bytes backspace, space, backspace (`0xffe38746`); if empty, nothing is sent.
6. States 2 and 3, control-P (`0x10`) or control-N (`0x0e`): history navigation (section 5).
7. States 2 and 3, any other byte: stored in the buffer and echoed as itself, up to the buffer limit. When the buffer is full (limit at `0x30005140+0x387`), the new byte replaces the last stored character and the L1 sends a backspace followed by the new byte, so the screen shows the replacement (`0xffe37d5a`-`0xffe37d98`). The buffer begins at `0x30005140+0x338`, so the room is `0x4f` characters; the exact accepted line length is therefore 79 characters (inferred from the two addresses; test: send 80 characters and read the echoed bytes).
8. Control-X (`0x18`) in text framing in any state switches framing (section 2).
9. Control-D in state 2: the byte reaches the same branch as in state 3 (dispatch at `0xffe37a20`-`0xffe37a2e` sends states 2 and 3 to `0xffe37a78`). It runs the brick-type test and, for a type in the set (`4` is), the power-warning test; the test at `0xffe37b2a` then skips the `entering console mode` text and the state change unless the state is 3. So in state 2 the only possible output is `no console available on this brick` (type outside the set) or the power warning (node not on). Established from the code; not executed.

Not echoed and not otherwise handled bytes: every byte other than the ones above is stored and echoed, including escape sequences, so arrow keys produce visible junk characters. Inferred from the absence of other compares in `0xffe37a78`-`0xffe37d98`; test: send `0x1b 0x5b 0x41` in state 3 and read the bytes returned.

## 4. Power-up and the banner

What the firmware prints, in the order it does it (established for the code path, inferred for what a terminal sees):

1. `main` (`0xffe10570`) calls `console_printf` with the format `L1 booting %s` plus a line feed and the version text `1.44.0` (`0xffe10586`-`0xffe10592`). Established. `console_printf` formats into a stack buffer and calls `0xffe59f00`, which appends the text to the L1 log ring (`0xffe5aed8`-`0xffe5aefc`, `0xffe59f00`-`0xffe5a17c`). That routine's callees are the clock read, string length, a semaphore, the ring writer and a checksum; no UART write was found in it. Conclusion: established that `console_printf` output reaches the log ring and not the serial line at the time of the call; this explains why `L1 booting 1.44.0` is the first entry the `log` command shows and why it does not appear at power-up on the wire. Inferred, not established: that no other path later drains the ring to the console (test: grep the listing for readers of the ring pointers at `0x300003a4+4`; only `log` at `0xffe5af04` was seen).
2. The management-port read task (`0xffe37f60`) opens its UART client and, if the flag word at `0x30000b24` is non-zero, sends the banner and clears the flag (`0xffe38070`-`0xffe38100`). The flag has the value 1 in the initialised data image copied to RAM at boot (data image at body offset `0x7f0e4`, flag at offset `0xb24`; copy described in [l1/board-boot-contract.md](l1/board-boot-contract.md)), and the one store of zero to it is the banner path. So the banner is sent once per L1 boot, before any byte has been received. Established for the code; the wire-level claim is inferred, because it depends on the write task running and a terminal being attached at the time. The text, with `\n` meaning line feed (and sent as carriage return plus line feed because the state is 3):

   ```
   \n\nSGI SN1 L1 Controller\n
   Firmware Image A: Rev. 1.44.0, Built 07/17/2006 18:20:38\n\n\n
   <prompt>
   ```

   The image letter is `A` when two words at `0x30000918+8` and `+0x10` are equal and `B` otherwise (`0xffe380a0`-`0xffe380bc`); what those words hold (the booted bank against the default bank) is inferred from the `flash status` text, unknown from this pass. The build stamp in the image is `20060717182038` (body offset `0x7a44c`); the format prints characters 4-5 as the month, 6-7 as the day, 0-3 as the year and then 8-9, 10-11, 12-13 as hour, minute, second, so the date prints as `07/17/2006 18:20:38`. Established arithmetic from the argument order at `0xffe380ba`-`0xffe380e2`; reading the stamp as year-month-day-hour-minute-second is inferred.
3. The prompt string (`0xffe36ec4`, stored at `0x300054cc`, which is `0x30005140+0x38c`): a prefix chosen by the stored brick type byte at `0x300002f8` (`T1-` for `1`, `T2-` for `2`, empty otherwise: `0xffe36eec`-`0xffe36f24`), then the rack, type letter and slot formatted as `%03.3d%c%02.2d` (`0xffe30a50`, format at `0xffe312d7`; rack from configuration item 1 and slot from item 2 through `0xffe59590`, type from the long at `0x30000b00`), then the literal `-L1>` (`0xffe36f5a`). When the rack value is 0 its three digits are overwritten with `-`, and when the slot value is 0 the two slot digits are overwritten with `-` (`0xffe30a90`-`0xffe30ac2`). The letter comes from the routine at `0xffe60f94`: a jump table of `0x3c` signed words at `0xffe60fb6`, indexed by the type character minus `0x23`. Type `4` (index `0x11`) goes to `0xffe6102e`. That code returns `a` for type `A`, `c` (`0x63`, `0xffe6106e`) for every type outside the set `5`, `@`, `O`, `B`, `F`, `H`, `L`, and other letters for the sets it does test; the result is passed through the case routine `0xffe7d4e0` (`0xffe610fc`). For type `4` the letter is therefore `c`, and the prompt is `NNNcSS-L1>`: with rack 1 and slot 1 it reads `001c01-L1>`; with rack 0 it reads `---c01-L1>` and with slot 0 `001c---L1>`. This agrees with the class alias table (section 6.1): its byte for `'4'`, at `0xffe21048`, is `c`. Established for type `4`. The example `001r08-L1>` seen in a sibling note is a router (type `D` or `R` selects `r`, `0xffe610e6`) and does not apply to the Origin 300 board.
4. The prompt is built once per boot. `0xffe36ec4` has one caller in the body, the call at `0xffe371c4` inside `management_port_init` (`0xffe36f74`-`0xffe37306`); a scan of the body for relative and absolute calls, tail branches and any 32-bit occurrence of the address finds no other reference, and `management_port_init` itself is called once, from `main` (`0xffe1062a`). The prompt buffer is read at `0xffe37a50`, `0xffe37c5e`, `0xffe380f6` (printing) and `0xffe2727e` (length), and written only at `0xffe36f48`-`0xffe36f68`. A change of rack, slot or type is stated by the firmware to take effect at the next L1 reboot (`brick rack set to NNN (takes effect on next L1 reboot/power cycle)` and the sibling texts), and nothing in the image refreshes the prompt, so the prompt text is unchanged until then. Established.

Display (not console): the front-panel display texts written during start-up (`  UNKNOWN   `, `BRICK TYPE!!`, `L1 running`, `L1 rebooted`; `0xffe106f2`-`0xffe10754`) are written to the two-line display, not to the serial line. Established by the callee name `display_text_write` (`0xffe5117c`).

## 5. History

Twenty entries of 80 bytes at `0x30005140+0x3ac` form a ring; the head index is at `+0x9ec` and a count at `+0x9f0` (`0xffe37b90`-`0xffe37bde`). On each submitted non-empty line the L1 stores it at the head, advances the head modulo 20 and increments the fill count up to 20. Control-P steps back one entry and control-N forward, erasing the visible line with backspace-space-backspace triples first, then loading and echoing the chosen entry (`0xffe37c9e`-`0xffe37d58`). Established for the ring and the erase-and-echo; inferred for the exact index arithmetic at the wrap (the code uses a signed divide by 20 and the stored remainder). The `history` command prints `History length: %d/%d` and a blank line, then one `%d: %s` line per entry (`0xffe19e40`). Test for the wrap: send 21 distinct lines, then control-P twenty-one times, and compare with the expected order.

## 6. Commands

The command table is a list of 295 records of 68 bytes (`0x44`) from `0xffe1c0a0`; the last record starts at `0xffe20eb8` and the table ends at `0xffe20efc`. Each record holds the command word list, argument types, a handler address, a brick-class string, a selector, a hidden flag and a help line. `0xffe61bd0` parses a line against the records; `help` (`0xffe17080` with the formatter `0xffe61658`) prints them. This section lists the replies that are fixed by the image. Replies that depend on hardware state (voltages, fans, sensors, eeprom, serial numbers, scan) are listed by command with their format strings only.

### 6.1 Parser replies (established)

- Leading white space is skipped. A line that is empty or only white space makes the parser return `-1201` and no text (`0xffe61c04`-`0xffe61c44`). From the console that case never reaches the parser (section 3.4).
- A line that matches no record: `ERROR: command not found.` plus a line feed, parser result `-1200` (`0xffe62018`; detail in [l1/debug-console.md](l1/debug-console.md)).
- A record that matched the words but whose arguments did not convert: the same `command not found` line, because later candidates clear the partial-match marker (debug-console.md). The text `ERROR: invalid arguments for 'CMD' command, try "help CMD"` (`0xffe62004`, formats at `0xffe620b0` and `0xffe62077`) is built only when a partial match survives to the end of the table.
- `help CMD` for an unknown name prints `ERROR: command CMD not found.` plus a line feed (code at `0xffe61a96`, format at `0xffe621be`).
- A record whose brick class does not include the stored type character produces `INFO: command not supported on this brick type` plus a line feed from the class guard at `0xffe140d4` (the text is copied at `0xffe14190`); some handlers print `command not supported on this brick type.` instead (`0xffe14de0`). The class strings use a letter alphabet mapped through a byte table at `0xffe21014`, indexed by the type character. The guard accepts a record when the class string contains the type character itself or its alias (`0xffe1413e`-`0xffe14170`); for type `4` the alias byte, at `0xffe21048`, is `c`, so a class string holding `4` or `c` accepts the Origin 300 board. Established for type `4`. The guard maps type `&` to `N` and type `Y` to `X` before the lookup (`0xffe14106`-`0xffe1411c`); the other table bytes were not decoded here.
- The word `~` before a first word in the guard string negates the test (`0xffe140f8`-`0xffe14104`). Established; the class string `~A` appears on `partdb`, `display` and the brick partition setter.

### 6.3 Commands with hidden or odd words

Command records marked hidden (flag word at record offset `0x40` equal to 1) are omitted from the short `help` list: the `let ... carnage ... begin`, `slipped ... mind` and `super ... sized ... please` word chains, many `env`, `fan` and `l1dbg` sub-forms, the `ioport force` forms, `pimm`, `serial` set forms, `eeprom dimm unsign`, `nvram read|write|scratch`, `router 6|8 port`, `b2b` and `l2`. Established from the table scan. The word chains are exact and all three are whole table records (word strings at body offsets `0x219c8`-`0x21a3a`, the sibling note [l1/usb-l2-revision.md](l1/usb-l2-revision.md) shows `let the carnage begin` typed at a prompt): `let the carnage begin` (record `0xffe1d008`, help line "turns security off"), `slipped my mind` (record `0xffe1d04c`, help line "forget previously used authenticators") and `super sized please` (record `0xffe1d090`, help line "change 6 port router into 8 port router"). All three are hidden and share the handler `0xffe1a878`, which tells them apart by the selector word of the record: 0, 1 and 2 in that order. Established from the table. The handler allocates an 80-byte reply buffer and clears its first byte, and none of the three selector paths writes to it (`0xffe1a888`-`0xffe1a966`), so none of them produces serial text of its own; whether an empty reply adds anything on the line is a property of the reply printer and was not read (unknown, test: execute the parser on `slipped my mind` and record the bytes). Each path first requires configuration item `0x11`, read through `0xffe59590`, to be 0, 1 or 2; it then changes stored settings through `0xffe58758` (selector 0: items `0x50` and `0xf`; selector 1: items `0x53` and `0x51`; selector 2: item `0x3d`, only when the time since the previous use, kept at `0x300009ac+0x1c`, is under 3 units). What those items mean was not decoded; the match between the help lines and the effects is therefore the firmware's own description, not independently established.

### 6.4 Catch-all

The words `fru`, `pci`, `prom` and `node` are registered as the last two table records: the bare words (`0xffe20e74`) and the words followed by the rest of the line (`0xffe20eb8`, argument marker 6). Both use the handler `0xffe141b4`, with the class string pointer `0xffe24911`, which points at an empty string. The handler passes that pointer to the class guard `0xffe140d4`. The guard looks the type character and its alias up in the class string with `strchr` (`0xffe7d304`); an empty string contains neither, so the guard fails for every type and stores the `INFO: command not supported on this brick type` line (copied at `0xffe14190`) in the reply slot passed down from the parser (that the slot is then printed is inferred from the sibling notes on the other guarded handlers; the printer was not read). Only a NULL class pointer passes (`0xffe140f2`), and this record's is not NULL. The handler ignores the guard's result and returns 0 (`0xffe141cc`-`0xffe141d6`). So these words always give `INFO: command not supported on this brick type` plus a line feed, whatever the stored type; the earlier reading that a passing type returns silently does not occur. Edge, established from the lookup code: `strchr` with a zero character matches the terminator, so a stored type byte of 0 would pass the guard and the command would then return silently; whether the byte can be 0 on a running controller is unknown (test: list the stores to `0x300002f8`). The sibling note [l1/console-command-tables.md](l1/console-command-tables.md) reads the same two records. The guard has 28 call sites (four absolute calls and twenty-four relative ones); other handlers pass their own class strings (section 6.1). A separate text `ERROR: unknown pci command.` exists (`0xffe11ca9`) in the PCI hook path.

## 7. Replies that never go to the console

Texts from `log_message` and `console_printf` (583 call sites; [l1/console-messages.md](l1/console-messages.md)) go to the log ring. The `log` command shows them and, when the `l1dbg printf` and `l1dbg console` switches are on, events carrying them are generated for the system side (`l1dbg` help lines: `enable/disable console tracking messages`, `enables/disables generating events on printf calls`). Whether any event reaches the operator's serial line is unknown; test: set `l1dbg console on`, trigger a log call, and capture the line.

## 8. Comparison checklist

To compare a second controller transaction by transaction, drive these in order and compare bytes exactly:

1. Reset the controller with the node off and record every byte on the console until idle. The expected sequence, if the banner is sent at task start, is section 4 step 2 (inferred as to wire timing).
2. Send a bare carriage return. Expected: one line feed (`\r\n` in states 2 and 3) and the prompt.
3. Send `version`. Expected: the line in section 6.2.
4. Send `nosuchcommand`. Expected: the echoed characters, `\r\n`, `ERROR: command not found.\r\n`, the prompt.
5. Send control-D with the node off. Expected: the power warning line, then `entering console mode ...`.
6. Send control-T. Expected: `\nescaping to L1 system controller\n` and the prompt; then one command; then `returning to console mode ...`.
7. Send `debug`, `debug 0x2a`, `log`, `history`, `flash status`.
8. Send 21 lines and navigate the history ring.
9. Send control-X and confirm the echo and the switch to packet framing.
