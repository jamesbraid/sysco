# The TCP link between MMSCs (`remote`)

The nine routines defined in the `remote` object of `mmscfw.bin`, IRIX 6.5.30 (MMSC 2.3). One MMSC runs a command on another by opening a TCP connection to the peer's address from the identity table ([identity-table.md](identity-table.md)), sending a one-line command and reading the reply line. Sizes count code up to the last `ret`.

## Tune values used

The tune table `ffscDefaultTuneInfo` (`0x12601c`, 39 entries of 16 bytes: name pointer, index, default, one more word) is copied into `ffscTuneInfo` by `ffscEarlyInit`; the live values are the dwords of `ffscTune` (`0x1e0678`) at 4 times the index. The names are the strings in the image. Timeouts are in microseconds: `timeoutSet` divides by 1,000,000 for seconds and scales the remainder, and `connectWithTimeout` is given the same split.

| Name | Offset | Default | Used by |
|---|---|---|---|
| `LISTEN_PORT` | +0x58 | 5678 | listener and connect |
| `LISTEN_MAX_CONN` | +0x5c | 25 | listener backlog |
| `CONNECT_TIMEOUT` | +0x54 | 3,000,000 | connect |
| `RI_LISTENER` | +0x30 | 100,000 | router reads the accepted descriptor |
| `RI_CONNECT` | +0x24 | 3,000,000 | user record read; reply to a connection command |
| `RI_REQ` | +0x34 | 1,000,000 | router reads a request line |
| `RI_RESP` | +0x38 | 1,000,000 | reads of reply data |
| `RO_REMOTE` | +0x44 | 3,000,000 | writes to a peer (user record, command, data) |
| `RO_RESP` | +0x48 | 1,000,000 | writes of a reply line |
| `RI_ELSC_MSG`, `RI_ELSC_RESP` and others | | | not used by this object |

The table was read in full (39 entries); the defaults for entries this object does not use are in the image and not repeated here.

## Wire format

- Transport: TCP, `socket(AF_INET, SOCK_STREAM, 0)`, destination the peer's IP address from its identity entry and the `LISTEN_PORT` value in network byte order.
- First, only if bit 0 of the peer's capability flags is set: a 112-byte (`0x70`) user record. Its first dword holds flags (bit 0 set when the record is valid, bit 1 set when a default destination string follows); then three dwords copied from the sending operator's record at offsets +0x18, +0x1c and +0x20 (+0x20 is the authority value the `RACKID` and `IPADDR` commands compare with 999); then from +0x20 of the user record a default-destination string (copied from operator record +0x3f, present only when the operator's flag at +0x24 bit 0 is clear). `userExtractUserInfo` builds it and `userInsertUserInfo` applies it on the receiver. The meaning of the first two copied dwords is not read (unknown).
- Then a command line. `remStartRemoteCommand` writes the text `R . B <bays> <command>` with `sprintf`, where `<bays>` is `*` when the destination byte for the rack has bit 7 set, otherwise the letters `U` and `L` (the two bytes at `ffscBayName`) for bits 0 and 1. The receiving router parses it with the same destination parser as a local command; that `.` means "this rack" at the receiver is inferred, the parser (`destParse`) was not read.
- The reply is a text line of the form `R<rack>:<text>`; for a request that will be followed by data it is `READY <n>` and then `n` raw bytes follow ([the routines below](#routines)). Message framing (the `msgRead` and `msgWrite` objects) was not read.

## Routines

- `remInit` (`0x12aaf8`, 83 bytes). Spawns task `tListen` (priority 100, options 0, stack 20,000, entry `remListener`). Returns 0, or logs "Unable to spawn remote request listener task" and returns -1. Only caller: `ffscInit`. Established.
- `remListener` (`0x12ac58`, 329 bytes). The body of the `tListen` task. It fills an `AF_INET` sockaddr with the port from `LISTEN_PORT`, in network byte order, and the wildcard address 0. Then socket, bind and listen(`LISTEN_MAX_CONN`); any failure is logged and the task exits with -1. The accept loop logs a failed accept and goes round again. Each accepted descriptor goes out as 4 bytes into the pipe `L2RMsgFD`, which the router watches; a short write logs a line saying the listener could not pass a message to the router. Debug bit 7 of the byte at `0x1e2338` (set when the byte reads negative as signed) turns on the a debug line announcing the listener is up, with its descriptor and a debug line for an accepted connection, with its descriptor messages. Established.
- `remAcceptConnection` (`0x12a8e8`, 461 bytes). The router calls it with a pipe descriptor, an output for the peer's rack ID and an output for user info. A negative descriptor returns -1. It reads 4 bytes from the pipe with `RI_LISTENER` as the timeout; a timeout, error or short read is logged and gives -1. Then `getpeername` on the descriptor and `identFindByIPAddr` on the peer address. An address missing from the table logs a rejection line for a peer whose address is not in the table, closes the descriptor and returns -1. Otherwise the peer's rack ID goes to the first output. When the peer's capability bit 0 is set, the 112-byte user record is read with `RI_CONNECT` (timeout, error and short read each return -1); when it is clear, the default record `userDefaultUserInfo` (112 bytes) is copied instead. Word +4 of the user-info output becomes -1, the line a debug line for an accepted connection, naming the rack, its address and the descriptor is logged under bit 7 of the debug byte, and the connection descriptor is returned. The router also checks for a return of -2, which asks it to re-evaluate its descriptors; the code as read never returns -2. Established.
- `remOpenConnection` (`0x12aef8`, 469 bytes). Takes a rack ID and a 112-byte user record. Rack `0xffffffff` is refused with a log line and -1. When `identFindByRackID` finds no entry, it logs a line saying no entry exists for the requested rack ID and returns -1. Otherwise it creates a TCP socket, fills in the peer address and the tune port, and runs `connectWithTimeout` with `CONNECT_TIMEOUT` split into seconds and microseconds. A failed connect logs a failure line for a connect to a remote MMSC, closes the socket and returns -1. When the peer's capability bit 0 is set, the 112-byte record goes out with `timeoutWrite` on `RO_REMOTE`; a timeout or short write closes the socket and returns -1. That write is a plain `write`, so the time limit does not apply to it. The descriptor is returned on success. Established.
- `remStartRemoteCommand` (`0x12b9e8`, 618 bytes). Arguments: user, command text, destination rack, destination table. Fills a user record from the user, sets operator-flag bit 4 (no reply wanted) if the user has no reply channel, opens the connection, stores the descriptor in the rack's command and reply message objects, builds the bay string and `R . B <bays> <command>`, sends it with `msgWrite` and `RO_REMOTE`. Success with a reply wanted leaves state 3 in the reply object, and with none wanted state 0; failures put "R<rack>:ERROR CONNECT (remStartRemoteCommand)" or "R<rack>:ERROR SEND" in the reply text and close the descriptor. On exit decrements `outConns` under `outConnsSem` and, when it reaches 0, gives `outConnsDoneSem`, so the router's fan-out waits for every spawned sender. Established.
- `remStartConnectCommand` (`0x12b568`, 505 bytes). Sends a command as above, then, if a reply is expected, waits with `msgRead` and `RI_CONNECT` for a reply whose text after the first `:` begins `READY`; that is a held-open connection and its descriptor is returned (and cleared from the reply object). Anything else is logged ("Connection request rejected"), the descriptor closed and -1 returned; timeout and bad-response replies are written as `R<rack>:ERROR TIMEOUT (remStartConnectCommand)` and `...BADRESP...`. Used by the commands that open a console on a remote rack (`cmdELSC`, `cmdFFSC`, `cmdRAT`, `cmdFLASH`). Established.
- `remStartDataRequest` (`0x12b7e8`, 224 bytes). `remStartConnectCommand`, then, when a size output is given, `sscanf("READY %d")` of the reply into it; a mismatch is logged "Invalid response to data request", the descriptor closed, -1 returned. Returns the descriptor. Callers: the log, environment and partition list and get commands. Established.
- `remSendData` (`0x12b2e8`, 640 bytes). The serving side of a data transfer: writes `READY <n>` as a reply line (with `RO_RESP`) and then `n` bytes to the connection with `RO_REMOTE`, in a loop until all are sent; failures put `ERROR CONNECT (remSendData)` or `ERROR WRITE: remSendData` in the reply text. Returns 0 or -1. Established.
- `remReceiveData` (`0x12b158`, 188 bytes). Reads exactly the requested number of bytes from a descriptor with `timeoutRead` and `RI_RESP`, looping over short reads; on error or timeout closes the descriptor, writes `ERROR READ (remReceiveData)` into the local rack's reply and returns -1; otherwise 0. Established.
