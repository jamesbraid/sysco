# PCF8584 I2C controller on the module bus

Each Hub reaches the module system controller (MSC, also called ELSC) through a PCF8584
I2C-bus controller on the management bus. The bus layout is in
[origin2000-module-management.md](origin2000-module-management.md); this page covers the chip.
Bit values and field codes are in [defs/pcf8584.toml](../defs/pcf8584.toml), with the generated
reference at [gen/docs/pcf8584.md](../gen/docs/pcf8584.md).

Unless a line says otherwise, the chip facts below are **inferred**: they summarise the public
chip layout, and the chip data sheet was not read in this pass. The Linux `i2c-algo-pcf` driver
states the address convention below, and it is the public check on it.

## Register selection

The data register is not one register. Four selections share one address on the Hub, chosen by the
serial-interface enable bit (ESO) with the register-select bits ES1 and ES2.

| ESO | ES1 | ES2 | Selected register |
|---|---|---|---|
| 0 | 0 | 0 | Own address |
| 0 | 1 | 0 | Clock control |
| 0 | 0 | 1 | Interrupt vector |
| 1 | either | 0 | Data |
| 1 | either | 1 | Interrupt vector |

ES2 still selects once ESO is set, and ES1 stops selecting. A model that treats "ESO set" as "data
register" gets the interrupt-vector case wrong.

The control bits used with this table are PIN at `0x80`, ESO at `0x40` and ES1 at `0x20`
(inferred). The position of ES2 is not stated here.

## Own address and transaction addresses

The own-address register holds the seven-bit address in its low seven bits. The chip shifts that
value left one bit onto the wire. Transaction addresses are written already shifted. Writing an
unshifted value puts the node on the bus one bit off. The Linux `i2c-algo-pcf` driver states the
same convention beside its own-address readback.

## Clock control

The clock-control register packs two fields.

- Main oscillator: `0x00` for 3 MHz, `0x10` for 4.43 MHz, `0x14` for 6 MHz, `0x18` for 8 MHz and
  `0x1c` for 12 MHz.
- SCL bus speed: `0x00` for 90 kHz, `0x01` for 45 kHz, `0x02` for 11 kHz and `0x03` for 1.5 kHz.

The Origin 2000 owner's guide describes the management link as 100 kbit/s. 90 kHz is the nearest
setting the chip offers. This is a family-level statement from the Origin 2000 guide, not a check
against the Origin 200, so it stays a hint.

## Bus liveness probe

**Established** from the disassembly of the IRIX 6.5.30 IP27 PROM payload (SHA-256
`c2c69bf33c375b43ec7ac511fab41ddf595be1b6838ae717e58a9a1273437fdd`), the early probe that asks
whether anything is on the bus:

- The probe reads the data register only. It never reads control or status and never checks
  bus-not-busy.
- It samples the low byte once, then re-reads until the byte differs from that first sample.
- The deadline is 5,000,000 units of the converted Hub counter. The firmware treats those units as
  microseconds, a nominal five seconds. The physical duration is not established.
- The caller discards the failure return. A controller that never answers therefore delays that
  processor for the whole deadline and nothing more.
- The address is formed in the explicit-node window: `0x9200000001a20000` plus `NASID << 32` for
  the data register, with control and status eight bytes higher. The Hub-local alias
  `0x9200000001220000` exists, but this probe uses the explicit-node form.

Consequence: a data register that returns a fixed value tells the probe that nothing is on the bus.
Any implementation of the controller has to keep the data register changing when the real
controller would send bytes.

## Interrupt output

The chip has an interrupt output, enabled by the ENI control bit. The Hub's slot-identity and
micro-controller status register carries an I2C interrupt bit, named in the public Linux and
OpenBSD headers for that register (inferred; its bit position is not given here). Whether any
guest enables ENI is not known.

## Left out

Facts whose only basis is non-public source are left out, as on the module-management page. That
covers the chip driver's initialization sequence and the controller's arbitration, grant and
address-phase behaviour.
