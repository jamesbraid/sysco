# System controllers beyond the L1 and L2

SGI built five generations of system controller. This repository started with the last two (the L1 and L2 of the Origin 300 and Origin 3000 era). This note covers all of them: what each serves, what runs it, what we hold and what we do not, and the reading jobs that follow. Findings that are not read from a shipped image are marked as hints, per [AGENTS.md](../AGENTS.md). No hardware is available and none is scheduled here.

Media are named by title. [../IRIX_FILES.md](../IRIX_FILES.md) lists the files and carriers; [firmware-versions.md](firmware-versions.md) lists the L1 and L2 sets; [inventory/images.tsv](inventory/images.tsv) has every held image with size, hash and version.

### What was found, and how

- The MMSC image header is a little-endian a.out with magic 0407, text 687,064 bytes, data 166,912, bss 123,288, a 94,884-byte symbol table and entry point 0x108000 (6.5.7 to 6.5.30 byte-identical). Its strings include a VxWorks boot line for a `pc486` target, the Wind kernel version 2.4, the `ns16550Sio` serial driver and VGA and EGA routines. This is read from the file; the CPU model within the 486 class is not.
- The symbol table names 602 object modules. The ones that matter for the controllers: `elsc` (the MSC client, 14 routines; read in [mmsc/msc-client.md](mmsc/msc-client.md)), `addrd` (rack-identity election, 71), `cmd`, `cmdadmin`, `cmdcfg`, `cmdctrl`, `cmdlog`, `cmdmode`, `cmdsrvc` (command interpreter), `flash`, `nvram` (six layout versions with upgrade routines), `log`, `identity`, `remote`, `route`, `partition`, `oobmsg`, `consenter`, `consleave`, `consroute`, `conssys`, `consuser`, and the display modules.
- Everest `sysctlrd`, its driver objects and `scmsg` exist from IRIX 5.0 to 6.5. The man page says the daemon runs power sequencing monitoring, front-panel LCD and CPU meter, retrieves sensor data and the controller's log RAM.

## Reader lanes, ordered by value to a machine that boots IRIX on Origin 200 and 2000 hardware

Each lane is one bounded job. A reader of vendor binaries writes in its own words, grades every fact, adds curated rows, and regenerates the tables ([AGENTS.md](../AGENTS.md)). Names below are the symbols in the shipped images.

1. **ELSC host request set.** Image: `6.5.30/usr/cpu/sysgen/IP27boot/elsc.o` (not stripped, debug info). Routines: `elsc_command`, `elsc_parse`, `elsc_process`, `elsc_msg_check`, `elsc_msg_callback`, `elsc_errmsg`, `elsc_init`, `elsc_version`, and the get and set families (`elsc_module_*`, `elsc_partition_*`, `elsc_domain_*`, `elsc_cluster_*`, `elsc_cell_*`, `elsc_bist_*`, `elsc_nvram_*`, `elsc_password_*`, `elsc_display_*`, `elsc_power_*`, `elsc_rpwr_query`, `elsc_system_reset`, `elsc_power_cycle`, `elsc_dip_switches`, `elsc_nic_get`, `elsc_lock`, `elsc_unlock`, `_elsc_hbt`). Output: one table of request text, argument form, reply grammar and the routine that sends it, plus the message framing and error mapping. Also the `_elscuart_*` UART path (`probe`, `init`, `poll`, `readc`, `getc`, `puts`, `putc`, `flush`, `gets`). Cross-check the same table in `6.4-origin` and `6.5.7` and list requests that were added. Read: [elsc-host-requests.md](elsc-host-requests.md).
2. **MSC client inside the MMSC.** Image: `6.5.30/usr/cpu/firmware/mmscfw.bin` (MMSC 2.3). Module `elsc`: `_elscInit`, `_elscSendCommand`, `_elscProcessInput`, `_elscCheckResponse`, `_elscPrintMsg`, `_elscUpdateDisplay`, `_routeDoAdminCommand`, `_msgNew`; module `cmdadmin`: `_elscSetPassword`; the mode switch routines `_cmdELSC`, `_ceEnterELSCMode`, `_clLeaveELSCMode`, `_csSysInELSC`, `_cuUserInELSC`, `_elscSendPassword`. Output: the MSC request and reply grammar from the controller's side, to be compared with lane 1. The load map and symbol tools of lane 4 exist: [mmsc/load-map.md](mmsc/load-map.md); `scripts/mmsc_aout.py IMAGE --disasm NAME` disassembles a routine by name.
3. **MMSC and MSC command catalogue.** Image: same 6.5.30 file. The command table in module `cmd` (`_cmdHELP`, `_cmdVER`, `_cmdSCAN`, `_cmdPWR`, `_cmdRACKID`, `_cmdNUMRACKS`, `_cmdPARTLST`, `_cmdPARTGET`, `_cmdPARTSET`, `_cmdPRINTENV`, `_cmdSETENV`, `_cmdLOG*`, `_cmdPASSWORD`, `_cmdFLASH`, `_cmdRESET_NVRAM` and the rest), with each command's argument grammar, permission rule and the strings it emits. Cross-check against the Origin2000 rackmount and Onyx2 rackmount owner's guides for the user-visible set. Output: a command table in `docs/mmsc/`.
4. **MMSC load map and symbols.** Establish the segment map of `mmscfw.bin` (where the data segment lands relative to the text at 0x108000, checked against data symbols and relocated references), write a symbol-import script for Ghidra and a capstone loader for the 7,907 nlist entries, and record the result with a byte check. Image: 6.5.30. Output: the shared tooling (`retools/ghidra/import/mmsc-aout/`, `scripts/mmsc_aout.py`) and the note [mmsc/load-map.md](mmsc/load-map.md). Done for all ten MMSC images held; the self-check passes on each.
5. **MMSC flash and NVRAM.** Image: 6.5.30 plus 6.5.5 and 6.5.6 (2.1, 2.2). Module `flash` (`_initFlash`, `_openFlashWindow`, `_clearFlashBlock`, `_writeFlash`, `_writeFlashBytes`, `_readFlash`, `_flashtest`), module `nvram` (`_nvramValidate`, `_nvramWriteHeader`, `_nvramIsValid`, `_nvramUpgrade1to2` through `5to6`, `_nvramPrintInfo`) and the serial download path (`_cmdFLASH`, `_cmdDOWNLOADER`). Output: flash window address, sector size, the six NVRAM layouts, the download protocol and checksum. Read `flashmmsc` in 6.5.30 (`mmsc_transact`, `do_grab`, `auto_transfer`, `ReadLine`, `AbortTransfer`, `CRCTab`) for the host half of the same transfer. Done: [mmsc/flash-nvram-download.md](mmsc/flash-nvram-download.md) (flash window, NVRAM objects and versions, XMODEM-CRC download, host tool).
6. **Rack identity election and the MMSC link.** Image: 6.5.30. Module `addrd` (71 routines: election start, end and timer, identity messages, rack-ID and IP-address conflict resolution), `identity`, `remote`, `route`, `oobmsg`. Output: the message formats and election rules between MMSCs, which a multi-rack Origin 2000 needs.
7. **Pre-container L1 layouts.** Images: `6.5.12` to `6.5.15` `l1.bin` (not parsed by the package reader). Derive the table layout from the four images and the first container layout (6.5.16), extend `scripts/sysco_tables.py` to parse them, and regenerate. Then compare the L1 version series 1.0.2 to 1.18.3 for request-code and package changes with the existing version-diff scripts.
8. **Everest host side and the old compression.** Images: `6.5/usr/etc/sysctlrd`, `6.5/usr/cpu/sysgen/IP{19,21,25}boot/sysctlr.o`, `6.5/sbin/scmsg`, with `usr/include/sys/EVEREST/sysctlr.h`. Output: the request set the daemon sends to `/dev/sysctlr`, the message layout in the driver, and the sensor and log record formats. Separately, work out the `inst` archive compression used by IRIX 5.0 to 6.2 media (compressed size and stored size are both in each `.idb` line, the stream starts with the same 16 bytes in every file) so the earlier builds can be extracted.
9. **`mmscd` and `sysctlrd` daemons.** Images: `6.5.30/usr/etc/mmscd`, `6.5/usr/etc/sysctlrd`. Output: the front-panel and CPU-meter protocol, the power-down and alarm handling sequence, and the files and signals each uses. Lower value to a machine model than lanes 1 to 3.
10. **Altix 330 and 350 L1 tie-down.** Images: the `Linux L1` packages in the 6.5.27 and later L1 sets. Read the cramfs file list and network scripts for a product name, tying the package to a model; no new image is needed.

Lanes 1 to 3 are readable now with the tools in the toolchain image. Lane 2 and lanes 3 to 6 need lane 4's loader or capstone scripting. None needs hardware.
