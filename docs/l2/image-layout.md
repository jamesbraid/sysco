# L2 image: container, kernel and root file system

Read from the L2 image of IRIX 6.5.30 (`/usr/cpu/firmware/sysco/l2.bin`, firmware 1.44.0, 2,924,652 bytes, sha256 `6bcfda07a24cb4d56850922dab17a98223abcd14221d307e3a8c3778434e8761`). The other three sets (1.24.1, 1.32.4, 1.48.0) were carved with the same script and have the same layout; where a value differs between sets it says so. Grades are those of [../../AGENTS.md](../../AGENTS.md).

## Carving it

`retools/tools/sysco/l2_extract.py l2.bin OUTDIR [--list FILE]` needs only the Python standard library. It writes `OUTDIR/kernel.bin` (the inflated kernel) and `OUTDIR/rootfs/` (the file tree). `--list` writes one row per entry: path, kind, mode, size, sha256, link target or device numbers. The 1.44.0 listing is [rootfs-1.44.0.tsv](rootfs-1.44.0.tsv). `retools/tools/sysco/l2_list.py ELF` makes an annotated PowerPC listing of one user-space executable or library: it names PLT and text-relocation targets, resolves constants built with `lis` plus `addi`, and shows strings. It uses capstone and pyelftools from the toolchain image.

## Layout of l2.bin (1.44.0)

| Offset | Contents | Grade |
|---|---|---|
| 0x00 | ASCII `ESTFBINR`, then big-endian words: 0x08 `0xfe000000` (load), 0x0c `0xfe2ca03f` (last), 0x10 `0xff000000`, 0x14 `0`, 0x18 and 0x1c repeat load and last, 0x20 `0xffffffff`, 0x24 `3` | established |
| 0x34 | string `SGI L2 Controller ROM 0.01` | established |
| 0x207c | string `SGI L2 Controller Boot Loader` | established |
| 0x4a218 | gzip stream, ends at 0xd501d, inflates to 1,430,148 bytes | established (inflated and measured) |
| 0xd501d | 512 zero-filled bytes, then the cramfs superblock at 0xd521d | established |
| 0x2ca01d | end of the cramfs (0xd501d plus the superblock's size field 2,052,096) | established |
| 0x2ca01d to end | 79-byte trailer: the build stamp `20060717113711`, the version string `1.44.0`, and a short table of big-endian words (`0xfe2c9ff4`, `0xfe2ca004`, `0xfe2ca030`, ...) | established as bytes; meaning of the words unknown |

So the image is boot loader, kernel and cramfs in one blob that the header places at flash address `0xfe000000`. The 44-byte header is not part of what the flash holds: the body starts at file offset `0x2c`, so an address `A` in the flash window is at file offset `A - 0xfe000000 + 0x2c`. The file offsets in the table above are file offsets; the addresses below are flash addresses. The boot loader is read in the next section.

### The boot loader

Read from 1.44.0 (`l2.bin`, sha256 above) with capstone in PowerPC big-endian mode; the instruction streams below were read in full unless marked. The 860 internal-register offsets follow the public MPC860 user's manual names and are a reading of the offsets, not something the image states.

There are two loaders, one behind the other, each a 256 KiB slot:

- **Stage 1, the ROM (flash `0xfe000000`; file `0x2c` to `0x4002c`).** Its text at offset 8 is `SGI L2 Controller ROM 0.01`. It has a vector table of 31 stubs (one per `0x100`, offsets `0x100` to `0x1f00`) and its code runs from the reset vector, `0xfe000100`. The reset code writes the internal-memory-map base register (SPR `0x27e`) with `0xfa200000`, writes `0x707a0900` to offset 0 of that block (the SIU module configuration register), `0x62000000` to offset `0x280` and `0x5040` to offset `0x284` (clock control and PLL registers), loads three cache-control registers with the invalidate and disable commands, and branches to `0xfe0041cc`. That routine (a) programs the memory controller: boot chip select 0 gets base `0xfe000001` and option `0xff800940` (an 8 MiB window at `0xfe000000`, stores at `0xfe004388` and `0xfe004394`), a 64-word table is written one word at a time to the memory-controller RAM array, and the mode and prescaler registers around it are set (`0xfe0042f0`-`0xfe0043a0`), (b) copies the `0x1f94` bytes of vectors and ROM head to RAM address `0x100` while XOR-summing them (`0xfe00441c`), (c) writes a short sequence to three registers of the internal block (offsets `0x200`, `0x300`, `0x320`) and to a byte-register device at `0xfa100000` (`0xfe004460`-`0xfe0044fc`; that device is the console UART, inferred from the banner printing; a busy-wait helper at `0xfe004500` turns a millisecond count into time-base ticks by dividing by 60, so it assumes a 60 MHz time base, established as a constant, the clock itself inferred), then sets `r1` to `0x3f0000`, `r2` to `0xdeadbeef`, and jumps to `0xfe001fa0`. That stub copies its C-compiled code (`0xfe004550` to `0xfe005db0`) to RAM `0x00e00000`, clears `0x00e01860` to `0x00e078cc`, sets the stack at `0x00e078cc`+`0x6000`-`0x100` rounded to 16 and jumps to `main` at `0x00e009ac`.
- **Stage 2, the boot loader (flash `0xfe040000`; file `0x4002c` to `0x4a218`).** The word at `0xfe040000` is not code: it is the flash address of the image record (below). Offset 8 repeats the ROM string, and `SGI L2 Controller Boot Loader` is at `0xfe041fa0`. Its reset-style entry is `0xfe040100`, with the same register set-up as stage 1; its code differs from stage 1.

**What stage 1's `main` does (`0x00e009ac`).** It prints a banner and `Validating L2 Controller Flash image....` on the console UART, then validates the image at `0xfe040000`. The address `0xfe040000` and the word stored there must both be word-aligned addresses inside the 4 MiB flash window (`0xfe000000` to `0xfe3fffff`); the word is taken as the address of the record. For this image the first word is `0xfe2ca00c`, an eight-word record near the end of the file: type/length halfwords `3` and `0x20`, the image start `0xfe040000`, two copies of the size `0x28a02c`, pointers to the build stamp `20060717113711`, the version `1.44.0` and a four-word table, and a final word `0x0721df60`. The check adds the 32-bit words of the record (the type-and-length word included when the type is above 2, left out for types 1 and 2) and requires zero; this record's words sum to zero (computed). The same word-sum rule appears in the L1 image record ([../l1/flash-nvram-and-image-records.md](../l1/flash-nvram-and-image-records.md)), where it protects the loader's 48-byte record; here it protects only the record, not the image bytes it describes (the size words are not used by stage 1's checks that were read). On a bad pointer or a nonzero sum it prints the offending address or sum and returns -1. On success it prints `Booting...`, copies the first `0x1f94` bytes of the image to RAM address 0 (vector area), and calls `0xfe040100` through the link register (established: `0x00e00a48`-`0x00e00a90`). If the call ever returns, or if the validation failed, it prints a box with `BOOT FAILED` and then the recovery text (`FATAL ERROR!!! Your L2 controller binary image is corrupted!!`, the serial-port recovery steps and the `l2recover` command naming `/usr/cpu/firmware/sysco/l2.bin`), stores `0xffffff80` at offset 4 of the internal register block (the system protection control register; read as the bus monitor enable with the watchdog left off, inferred from the bit layout) and spins (`0x00e009f4`-`0x00e00a44`).

**What stage 2 does.** Its reset code mirrors stage 1 (same SIU, clock and cache set-up), initialises the memory controller and vector area, then copies itself from `0xfe0444a0` (including the compressed kernel, up to flash `0xfe04a1ec`) to RAM `0x00700000`, clears `0x0070 5cb0` to `0x0070 efa8`, sets a stack, and calls a start-up routine and then a decompress routine (`0xfe0445f8`) with the loader's start (`0xfe041fa0`), its length in words and the board-information pointer it was given in `r11`. The strings are those of the public Linux/PowerPC "simple" boot wrapper: `Linux/PPC load:` followed by a command line (the loader holds a default fragment ending `=/dev/nfs rw`; it also polls the console for typed characters before it decompresses, so the line can probably be edited there, the polling loop is bounded and was not timed), `Uncompressing Linux...`, and `Now booting the kernel`, plus its zlib error texts, and it carries Motorola PCI/VPD helper strings that this board does not use. The decompress routine copies `0x1c` bytes from the pointer it received in its fourth argument to the RAM buffer whose address is the word at `0x00705c84` (a copy routine at `0xfe0447cc`, inferred from the call shape), reads the command line, calls an inflate routine as `gunzip(destination 0, limit 0x400000, source = the gzip stream, &length)` (`0xfe044f00`, a 4 MiB limit) and returns the buffer address. The start-up code then sets `r3` to that buffer address, `r4` and `r5` to the global words at `0x00705c88` and `0x00705c8c` (set by the decompress routine; under the Linux convention they are the initial RAM-disk bounds, not traced further here), `r6` to the command-line start, `r7` to the address of its terminating zero, clears the link register and returns, which transfers control to address 0, where the inflated kernel sits (established for the register set-up and the jump: `0xfe0445fc`-`0xfe044640`). The gzip stream itself is at flash `0xfe04a1ec` (file `0x4a218`).

The kernel's first five instructions save `r3` to `r7` into `r31` to `r27` ([the kernel entry](#the-kernel)); with the register set-up above, `r3` is the board-information buffer, `r4` and `r5` the RAM-disk bounds and `r6`, `r7` the command-line bounds, which is the public Linux 2.4 PowerPC boot-parameter convention (inferred from that match; the kernel's use of the registers was not read, and what the 28 copied bytes contain is not decoded here).

**Unknown after this read.** The meaning of the stage-1 vector stubs beyond the first reset (inferred: exception stubs that jump through RAM), the origin of the `r11` board-information structure that stage 2 receives (it is set by stage 1 or by the reset code; a first read of `0xfe040100` onward did not show where `r11` is loaded), and what the stage-2 memory-controller program contains. Test: trace the stores to the SIU registers and `r11` along the reset path of both stages on a board; or read stage 2's reset path one further level, which needs only the listings above.

### The kernel

The inflated image is a flat PowerPC binary, not an ELF. Its first word is `7c 7f 1b 78` (`mr r31,r3`), followed by moves of `r4` to `r7` into `r30` to `r27`; the loader's side of that hand-off is in [the boot loader](#the-boot-loader), and the kernel's own entry path is in [the next section](#the-kernel-entry-path). The version banner, at inflated offset 0xedcd8, reads `Linux version 2.4.7-sgil2 ... gcc version 2.95.2 ... #1 Tue May 23 12:45:01 CDT 2006` in 1.44.0 (established). Strings in the kernel show which hardware it has drivers for (established as strings; that the hardware is present is inferred):

- MPC8xx on-chip support: `init_8xx_ports() for SGI L2`, `wdt_mpc8xx_init` (watchdog), `cpm_iic_*` with `i2c-algo-8xx.o` (an I2C adapter on the communications processor), `fec` with a PHY probe (the fast Ethernet controller), and the on-chip serial ports;
- `rtc.c:set_rtc_time` (a real-time clock driver);
- `lcd137x: Epson SED%s LCD controller detected` and `SGI L2 (SED137x LCD controller) frame buffer device` (the display);
- a USB host stack (`usb-ohci.c`, `hub.c`) and an SGI driver the controller firmware source unit 68 for L1 controllers, whose ioctl interface is read in [daemon.md](daemon.md);
- RAM-disk support for a cramfs root (`RAMDISK: Compressed image found`).

No flash-chip or MTD-map string was found, although the root has `/dev/mtd0` to `/dev/mtd3` nodes. The daemon libraries reach the flash through `/dev/mem`, not through those nodes (see [daemon.md](daemon.md)).

### The kernel entry path

Read from the inflated 1.44.0 kernel (`kernel.bin`, linked at `0xc0000000`; addresses below are virtual). Names in brackets are the public Linux 2.4 PowerPC names for routines of the same shape (hints; the image carries no symbols). The sequence matches the public MPC8xx start-up (`head_8xx.S`, `setup.c`, `m8xx_setup.c`, `mm/init.c`) step for step, and each step below was read in the image.

1. **Reset-style entry, `0xc0000000` (established).** Saves `r3` to `r7` in `r31` to `r27`, clears `r24`, invalidates the TLB (`tlbia`), programs the MPC8xx MMU control, access-protection, effective-page and real-page registers (SPR `0x310` to `0x31e`, `0x230`, `0x238`) with fixed values, reads the internal-memory-map base register (SPR `0x27e`) and masks it to its top nine bits for one entry, and ends by writing `SRR0 = 0xc0002178` and `SRR1 = MSR | 0x30` and executing `rfi` (`0xc00000b8` to `0xc00000d0`). [`__start`, `initial_mmu`] The register values were not worked into a TLB map here.
2. **`0xc0002178` (established).** Loads `r2` with `0xc0117fe0` (the first task block, by its use as the stack base below), zeroes the words from `0xc015e000` up to `0xc01981d0`, sets `r1` to `r2 + 0x2000` (the task block is 8 KiB) and a back-chain word of 0, then calls `0xc01319dc` with `r3` to `r7` restored from `r31` to `r27`, then `0xc0132944` with no arguments. It then writes the physical address `0x00116000` (the page-table base) into SPR `0x31c` and does an `rfi` to physical `0x2208` with `MSR = 0x1002` (translation off); at `0x2208` (physical) it does `tlbia`, writes SPR `0x112` and `0x113` (`0x112 = 0`), and does a second `rfi` with `MSR = 0x1032` (translation on) to `0xc0131634` (`0xc0002208` to `0xc0002238`). [`start_here`, `load_up_mmu`]
3. **`0xc0131634` (established).** Prints the version banner (the pointer it loads from a data word leads to the `Linux version 2.4.7-sgil2` string) through the kernel print routine (`0xc0010640`), calls the architecture set-up (`0xc0131bdc`), prints "Kernel command line: %s", and then runs the usual initialisation chain. [`start_kernel`]
4. **Machine identification, `0xc01319dc` (established for the steps).** Saves the five boot registers, calls `0xc00091fc`, calls a hook through the machine-call table if one is registered, and calls the platform set-up (`0xc0132688`). It then looks for `mem=` in the command line buffer at `0xc0117000` and, if present, parses the number with an optional `k`/`K` (shift 10) or `m`/`M` (shift 20) suffix into the memory-limit word at `0xc015e0e4`. [`identify_machine`]
5. **Platform set-up, `0xc0132688` (established).** If `r3` is non-zero it adds `0xc0000000` to it (so the loader passes a physical address) and copies **28 bytes** from there to `0xc015ec74` with a string-move instruction pair. If `r4` is non-zero it stores `r4` and `r5` (also moved to virtual addresses) in two globals (the RAM-disk start and end). If `r6` is non-zero it writes a zero byte at `r7` (virtual) and copies the command line from `r6` to `0xc0117000`. It then fills the machine-call table at `0xc015e7f0` with 11 function pointers (slots `+0x00`, `+0x04`, `+0x10`, `+0x14`, `+0x1c`, `+0x20`, `+0x24`, `+0x2c`, `+0x30`, `+0x34`, `+0x44`) and zeroes ten others (`0xc0132740` to `0xc01327bc`). The table follows the layout of the public machine-call structure; which slot is which was matched only for `+0x44` (the memory-size hook that `MMU_init` calls) and `+0x48` (an optional debug hook that `MMU_init` calls with strings such as `MMU:enter`). [`m8xx_init`/`platform_init`]
6. **The 28-byte board-information block (established for the words used).** Word 0 at `0xc015ec74` has no direct access in the kernel text (a scan for `lis`-based addressing of the block found only the two uses below). Word 1 (`+4`) is the RAM size: the memory-size hook (`0xc013267c`) returns it and `MMU_init` clamps it with the `mem=` limit. Words 2 and 3 (`+8`, `+0xc`) are the processor and bus clock in hertz: the CPU-information routine (`0xc000a66c`) prints them divided by 1,000,000 under `clock : %dMHz` and `bus clock : %dMHz`, and the serial-port set-up (`0xc00a2630`) divides word 2 by 16 and by the baud rate to get a baud-generator divisor, with a 12-bit range check. Words 4 to 6 (`+0x10` to `+0x1b`) are not read; in the public board-information structure of the same name those bytes would be the Ethernet address and baud rate (hint, not matched here). This is the public `bd_t` prefix, not necessarily with its field names.
7. **`MMU_init`, `0xc0132944` (established).** Runs the hooks of the machine-call table, takes the RAM size from the memory hook, clamps it with the `mem=` limit and with a fixed maximum word, maps RAM, and then maps five I/O areas with the same call (`0xc000ba60`, which has the shape of the public `ioremap(phys, size)`, the third argument fixed at 2): `0xfa200000` (64 KiB; the internal memory map the loader sets, see above), `0xfa100000` (4 KiB; the console UART the loader prints to), `0xfa210000` (64 KiB, mapped twice), `0x10000000` (128 KiB) and `0xfe000000` (4 MiB; the flash window the daemon libraries reach through `/dev/mem`). The returned addresses are discarded, so the kernel relies on these being reachable at their physical addresses. What sits at `0xfa210000` and `0x10000000` is not named by the kernel here: inferred from the sizes that `0xfa210000` is a second 64 KiB register block next to the internal memory map and `0x10000000` an external device window; not read.

What this settles: the loader's `r3` must be a physical pointer to a block whose second word is the RAM size and whose third and fourth words are the processor and bus clocks in hertz; `r4`/`r5` and `r6`/`r7` bound the RAM disk and the command line. Unknown: the origin of that block (see "Unknown after this read" above), words 0 and 4 to 6, and the devices at `0xfa210000` and `0x10000000`. What would settle the devices: the drivers in the kernel that touch those windows (a read of the Ethernet, USB-host and LCD drivers' register bases), which was not done here.

### The cramfs

Standard cramfs fields, big-endian (established from the bytes): magic `0x28cd3d45`, size field 2,052,096, flags 3 (version-2 fsid and sorted directories), signature `Compressed ROMFS`, 1,177 blocks, 308 files, name `Compressed`. Two properties matter to anyone writing a reader:

1. The superblock sits 512 bytes into the image, and every offset inside it, including the size field's span, counts from the start of that 512-byte pad rather than from the superblock. Reading offsets from the superblock finds the root directory entries 512 bytes too early.
2. The CRC field (`0x873f5a16`) is not reproduced by a CRC-32 over the image with the field zeroed, over four spans tried (pad included or not; the stated size or the remainder of the file). Extraction does not need it. Unresolved.

File data is one zlib stream per 4 KiB block, with a table of end offsets in front, as in the public cramfs layout. A device node keeps its device numbers in the size field.

Totals for 1.44.0, from the listing: 69 regular files, 116 symbolic links, 88 character device nodes, 12 block device nodes, 1 FIFO and 21 directories (the root counts as the 308th entry). The tree is described in [rootfs.md](rootfs.md).

In 1.44.0 the small tools (`l2term`, `l2flash`, `l2dhcps`, `l2passwd`, `l2staticip`, `flashraw`) list `libscan.ppclinux.so` among their needed libraries, yet no such file is in the 1.44.0 cramfs, so as shipped they cannot start on that image unless the loader finds the library elsewhere. The 1.24.1 and 1.32.4 builds do not need it. The 1.48.0 file exports 253 dynamic symbols, 210 functions (one weak) and 43 data objects; the functions are named like a JTAG scan master (`jmstr_scan`, `jmstr_sel_sic`, `jmstr_sel_sic_multi`, `scancmd_*`, a vector-file section reader `readsection`) with an `enode_*` error-record set. None of the 1.44.0 tools imports a symbol that only a scan library could supply, so the dependency looks vestigial there. Established: the needed-library lists, the absence, the export names. Inferred: the role (names only; no routine read) and the vestigial reading.

The same holds in 1.48.0, where the library is present. Its own needed list is `libc.so.6` alone. The six tools above list it, and none of them has an undefined dynamic symbol that matches any of its 253 exports; no other ELF file in the 1.48.0 tree (the daemon, the other libraries, the other tools) imports one either. So no program in the image calls into the library, and the needed entry is a link-line leftover there too (established, from every ELF file's dynamic symbol table and needed list in the carved tree). What the library is for stays inferred from its export names.
