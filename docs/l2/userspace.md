# L2 user space: the contract the shipped programs expect

This note collects, in one place, what the programs of the L2 root file system ask of the kernel and of the far end of each link: how to unpack the image, every device node and what is done with it, the ioctl requests, how the daemon reaches non-volatile storage, vital-product data and the display, what each of its link modes expects at the other end, how it sees the L1 USB link, and what it replies to the partition service requests. It is written so that someone running the shipped programs under a user-mode PowerPC emulator, or building a stand-in for a node or a link, can work from system-call traces, link traffic and console output alone. The detail behind each row is in the other notes of this directory, linked where used.

Grades as in [../../AGENTS.md](../../AGENTS.md). Unless a row says otherwise, "read" means read in L2 1.44.0 (IRIX 6.5.30). Addresses are virtual addresses inside the named file (the daemon at `0x10000000`, `l2part` and `l2gui` likewise, the libraries from 0; the kernel at offsets of the inflated `kernel.bin`, where virtual address = `0xc0000000` plus offset, established from the printk string references). Routine names are the dynamic-symbol names where the file exports them and `sub_<address>` otherwise.

### Steps

Established (run on all thirteen). Needs Python 3 and nothing outside its standard library.

1. Take `l2.bin` from the product's install path above. Do not strip or alter it.
2. `python3 retools/tools/sysco/l2_extract.py l2.bin OUT --list OUT.tsv`.
3. `OUT/kernel.bin` is the inflated kernel: the first `1f 8b 08` in the file starts one gzip stream (at `0x4a218` in 1.44.0); the script inflates it with a gzip-window decompressor and notes where the stream ends.
4. The cramfs follows the gzip stream: the script searches forward from the stream's end for the cramfs magic (`28 cd 3d 45`, big-endian). Every offset inside this cramfs counts from 512 bytes **before** the superblock, so the script slices the file from `superblock - 512` and reads the root directory entry at `512 + 64`. A reader that counts from the superblock lands 512 bytes early. Stock cramfs tools were not tried; the byte order is big-endian, so a little-endian host's native cramfs reader is not expected to take it.
5. File data is one zlib stream per 4 KiB block, preceded by a table of big-endian end offsets; the script inflates each and trims to the inode's size.
6. Regular files are written with their modes. Symbolic links are created. A device node, FIFO or socket is **not** created; the script writes `<name>.node` beside it containing the mode and the device numbers (cramfs keeps a node's major and minor in the size field: major is `size >> 8`, minor `size & 0xff`). A user running the tree needs those nodes (or stand-ins, see section 3) made from the listing: `OUT.tsv` gives path, kind (`chr`, `blk`, `fifo`), mode and `major,minor`.
7. Check: `OUT/rootfs/etc/l2firmware_version` holds the version in the table above, and `OUT/rootfs/stand/sysco/bin/l2` has the size in the table.

The tree layout, boot sequence and the file groups are in [rootfs.md](rootfs.md).

### What the user-mode runs need besides the tree

All from [user-mode.md](user-mode.md), observed with a Debian-packaged user-mode PowerPC emulator and the 1.44.0 tree: a regular file standing in for `/dev/mem` (sparse, with the flash window at its end filled with `0xff`); an `etc/hosts` mapping the host name to `127.0.0.1`; the emulator's guest root prefix and library-path variable. Without the `/dev/mem` stand-in the daemon dies with a segmentation fault after printing its banner (observed, and explained by reading the start-up version lookup). The flash base the library maps (`0xfc000000`, then `0xfe000000`) fails under that emulator with `EOVERFLOW`; the observed workaround, patching those two words, is in the same note.

## 2. Programs and what starts them

Established from `/etc/inittab` and `rc.sysinit` ([rootfs.md](rootfs.md)): `inittab` starts `l2` with no arguments on runlevels 3 to 5 (respawned, with the console as its standard streams), `l2flash --l2 localhost` on 4 and 5, `l2gui --l2 localhost` and `l2part --l2 localhost` on 5 only; the default level is 5. With no argument the daemon's connection mode is USB (initial value 2 in `.data`). `l2part` is therefore the task-10 service and exists only at level 5.

### Semantics of `/dev/sgil1_N` as the program sees them

Read from the kernel driver (the controller firmware source unit 68 in the inflated kernel) and from `l1_read_usb` (`0x10006128`) and `l1_write_usb` (`0x10006dec`) in the daemon. Established unless marked.

- **Open.** Fails with `ENODEV` (19) when that slot is not connected. Otherwise allocates one 4 KiB receive buffer and one 4 KiB transmit buffer; out of memory is `ENOMEM` (12). A slot that is already open fails with `EBUSY` (16): the byte at `+0xd` of the slot record is the open flag, tested on entry and set before the buffers are allocated, so a second open is refused until the close clears it (kernel open routine `0x9d9c8` to `0x9db50`, tests at `0x9da20` and `0x9da60`). The control node has its own open routine (`0x9d0d8`, minor 104). No other failure was seen in the routine.
- **Close.** Resets the USB device (`SGI L1 device reset failed on close` is logged if the reset fails).
- **Write.** `write(fd, buf, n)` queues one USB bulk-out transfer and **returns `n` as soon as it is submitted**; it does not wait for the transfer. `n` must be at least 1 and at most 4096 (the transfer limit in the slot record), else `EINVAL`. The kernel copies the bytes, then **overwrites the first two bytes of the transfer with `n` as a big-endian 16-bit value** (`sth` at `0x9de98`) and submits it. Completion is seen by the next call: if the previous transfer is still pending, the next `write` sleeps for up to 300 ticks (`0x12c`; the tick rate is not read, so the time is not stated) for it, returns `-ERESTARTSYS` (512) if a signal arrives, and on a timeout logs `write timeout`, abandons it and fails with `ETIMEDOUT` (110). If the previous transfer finished with an error, the next `write` returns that error without sending and does not clear it (no store seen). A transfer whose completed length differs from the requested one logs `short write` and counts as error `EIO` (5) for the next call. Because a segment's first two bytes already hold its length ([router-packet.md](router-packet.md)), the overwrite changes nothing for packets the daemon builds. Established (kernel write routine `0x9dc3c` to `0x9df5c`, completion routines `0x9d7cc` and `0x9d834`).
- **Read.** The descriptor is read-ready (`poll`/`select` bit `POLLIN`) when a receive transfer has completed; `poll` itself starts the next receive transfer if none is pending. `read(fd, buf, n)` returns the **whole completed transfer** (one USB bulk-in transfer, at most 4096 bytes) or fails with `EINVAL` when `n` is smaller than the transfer, leaving the transfer in place for a retry with a larger buffer. With no completed transfer it returns 0 and logs `read not done`; after a failed transfer it returns the error once and goes idle; a zero-length transfer returns 0; after disconnect it returns `ENODEV`; a bad user buffer gives `EFAULT` (14). The daemon always reads into the packet buffer plus `0x10` with the segment size it expects (1024 for an ordinary segment; the reader is [router-packet.md](router-packet.md)).
- **Errors the daemon acts on** (`sub_100060ac`): `ENODEV` or `EINVAL` from a read or write is "device gone": the slot is closed (`[no device]`) and nothing is retried. Any other error increments a per-slot counter (kept at slot-table offsets `+0x40` read, `+0x44` write; the table has 0x48 bytes a slot at `0x100512b8`); when it passes 2 the daemon logs `closing … after multiple read errors` or `write errors`, resets the device (`sub_10004210(fd, 1)`) and closes the slot (`[rd error]`). A successful read zeroes the read counter. After an error below the threshold the read routine also issues the read-side reset `0x20005301` (`0x100062d4`); if that fails and the error is not "device gone", it issues the device reset `0x20005303` (`0x1000635c`) and reports a failure of that.
- **Packets larger than one write.** The router may build segments of up to `0x3000` bytes when both address words are of router form (the "local" case in [router-packet.md](router-packet.md)); a write above 4096 bytes would fail with `EINVAL` and the daemon would then close the slot. Whether the daemon ever builds such a segment for a USB device was not followed: open ([../open-questions.md](../open-questions.md)).

## 4. ioctls

All numbers are in PowerPC Linux encoding: the top three bits are the direction (1 none, 2 read, 4 write), the next 13 the argument size, then the type byte (`'S'` = `0x53`) and the request number. A user-mode emulator whose host is not PowerPC must therefore translate or handle them itself; the unknown type is not in a generic table (inferred; not tried). Established for every row from the call sites and the kernel handler (`0x9e280` to `0x9e460`, `0x9d3d0` to `0x9d560`).

| Request | Node | Direction, size | Argument and meaning | Issued by |
|---|---|---|---|---|
| `0x40045306` | `sgil1_cs` | read, 4 | writes a 32-bit big-endian integer, the driver revision. The kernel returns **2** in all thirteen images (section 1). The daemon stores it at `0x10043bc0`; a failed call sets 0. A revision of 0 or 1 makes `-usbpath` fail with a message. | `0x10004018`, `0x10004110` |
| `0xc0095307` | `sgil1_cs` | read-write, 9 | the 9-byte device record (below) for slot `index`, where `index` is byte 2 of the argument on input. Slots above 39 or not connected give `EINVAL` (22). An unknown request on either node returns the kernel-internal "no such ioctl" value `-515` (`-0x203`, `0x9d544` and `0x9e42c`), which the C library reports as `ENOTTY`.

The wrapper at `0x100041a8` skips the ioctl and returns 0 when the word at `0x10043bbc` is 0. Its initial value is 1.

**The 9-byte device record** (established from the formatter `sub_1000444c`, which prints it, and from the kernel, which fills it):

| Byte | Meaning | Grade |
|---|---|---|
| 0 | USB bus number | established |
| 1 | the number `P` of hub ports in the path, at most 6 (the kernel stops the walk after 6) | established |
| 2 | USB device address on that bus | established |
| 3 to 3+P-1 | port numbers from the root hub down, one byte each | established |

The formatter `sub_1000444c(record, form)` has three forms. Form 2 is `b<bus>;p<port>/<port>…` with no device number (for example `b1;p2/3`) and is the name `-usbpath` filters are compared with. Form 0 adds `;d<dev>` (`b1;p2/3;d4`) and is the name shown in `INFO: opened USB device at <path> (<node>)`. Form 1 is the long text `  bus: <b>  path: <p>/<p>…  dev: <d>`; the open routine formats it into a local buffer and does not store it in the slot record.

**The reset decision** (`sub_10004210(fd, also_device)`), established by reading the whole routine: with revision above 0 (the test is `revision > 0`, so revision 1 takes this branch too) it issues `0x5305`, then `0x5303` if `also_device` is nonzero; a failure of either returns -1. With revision 0 or less (the failed-call value): issue `0x5302`; if that fails log and issue `0x5303` (return 0 if it works, -1 if not); if it works issue `0x5301`; if that fails log and issue `0x5303` (same returns); if it works issue `0x5303` only when `also_device` is nonzero (-1 on failure). Open calls it with `also_device` 0 (`0x100049dc`); the error paths call it with 1. This corrects [daemon.md](daemon.md), which said revision above 0 issues `0x5305` alone.

## 5. NVRAM, VPD and the front display

**NVRAM.** The daemon holds a 16 KiB image in RAM and reads and writes it **through `/dev/mem`**, as flash: the block is at physical `0xfe3f0000` (old location `0xfe2e0000`), erased and reprogrammed by `libdrivers` on save. There is no NVRAM device node and no I2C access. The format (IPMI-style 8-byte common header, a 0x82c-byte internal-use area, then an event log), the key table and the load and save rules are in [daemon.md](daemon.md#nvram); a stand-in only needs the 4 MiB window with erased flash (`0xff`) as in [user-mode.md](user-mode.md), and with all-ones it creates default contents and saves them. Established.

**Vital-product data.** No program or library of the L2 root file system opens an I2C node, and none contains an EEPROM or VPD string beyond the record codec names (string search of `l2`, `l2part`, `l2gui` and each library, repeated here). The record codec (`FRUUnpackData` and friends) is called by the daemon only to detach and dump records it received (`FRUDetach` at `0x1000b424`, `FRUDumpAll` at `0x1000b44c`, no other call site in `l2`); a brick's VPD reaches the L2 as packet payload from the brick's L1 over the router. The boot loader (not read here) fetches the Ethernet address from an I2C EEPROM, per the kernel strings; user space does not. Established for the user-space statements; inferred that the L1 supplies the records (no request that fetches them was followed on the L2 side; the L1 request catalogue is in [../l1/](../l1/)).

**Front display.** The daemon does not touch the display. `l2gui` is a separate process that registers with the daemon as task 6 and draws into `/dev/fb0` with `mmap` (section 3); touch input arrives on `/dev/ttyS3`. The two `l2dsp` commands in the daemon (lock, debug) set daemon-side state; how it reaches `l2gui` is not followed (it would be a router event between task 6 and the daemon; unknown, in [../open-questions.md](../open-questions.md)). Established for the split.

## 6. What the link modes expect at the far end

The mode is chosen by argument ([daemon.md](daemon.md#starting-and-options)); the word at `0x10043b84` holds it (default 2). The dispatch table is at `0x10027d00`.

| Mode | Argument | What the daemon does | What the far end must do |
|---|---|---|---|
| 0 | `-noconn` | nothing | nothing |
| 1 | `-net` | listens on TCP port `bias + 0x232b` (9003 with bias 0) and on the Unix socket `/usr/tmp/UNIX_%04x` for that number (`sub_10007cc0`, `SocketExportInetConnection`, `SocketExportUnixConnection`), accepts each connection as one L1 port ("network") | connect to that port and speak the segment stream (below) |
| 2 | `-usb` (default) | section 8 | an OHCI-visible USB device as in section 8 |
| 3 | `-serial /dev/…` | open and set raw 8N1 RTS/CTS (section 3; the speed is not established there), then the handshake below | a serial peer that speaks the handshake and then PPP-framed segments |
| 4 | `-serial HOST [PORT]` | `connect` TCP to HOST and PORT (default 2345), then the same handshake over the socket (`SocketWrite`, `SocketRead`) | a TCP listener that behaves as the serial peer |
| 5 | `-l1sim`, `-l1sim_manual` | starts or awaits a simulator; reuses mode 1's listener | not used on a product |

**Handshake for modes 3 and 4** (read from `sub_10005614` and the code after `0x10005798`; this corrects the shorter account in [daemon.md](daemon.md)): after `PPPInit`, the daemon writes one byte `0x0d`, sleeps 2 seconds, writes one byte `0x18` (the two values are the initialised bytes at `0x10043bac` and `0x10043ba8`: `0d` and `18`), then **reads one byte at a time** until it gets `0x18`; any other byte is read and ignored, a read of 0 or an error is `FATAL: can't confirm L1 protocol`. On `0x18` it sets the socket to no-delay (mode 4 only meaningful; a failure is `can't set delay mode`), registers the port and from then on treats the stream as PPP-framed segments. A write of anything other than 1 byte is `FATAL: can't initiate L1 protocol`. The byte values are established; that `0x0d` then `0x18` is the L1's text-console escape into packet mode is inferred (the L1 side of this sequence is not read here).

**Framing.** Which reader a mode uses is the table at `0x100280a0`, indexed by mode minus 1 (entries decoded): USB uses `l1_read_usb` (`0x10006128`), modes 3 and 4 use `l1_read_ppp` (`0x100066b8`, `PPPRead`), modes 1 and 5 use the socket reader (`0x100067b0`). Established.

- Serial modes (3 and 4, the latter over TCP): HDLC-style async frames as in the public PPP framing standard, **without** the address and control bytes. Read in full in `libsys` 1.44.0: the writer `PPPWrite` (`0x9e60` to `0xa380`, with the per-byte check routine at `0x9c00` and the whole-buffer one at `0x9b10`) and the reader `PPPRead` (`0xa384` to `0xaaff`). Established unless marked.
  - **Context and the daemon's settings.** The daemon calls `PPPInit` (`0x9cf0`) at `0x100057e0` with a 0x100-byte output buffer, flag arguments 0 and 1 and a final argument `0x10`. `PPPInit` stores the second flag as "escape `0x0d`" (context `+0x2c`, set here) and the first as "escape `0x11` and `0x13`" (context `+0x28`, clear here). So **in the daemon's use XON and XOFF are not escaped** and a carriage return is.
  - **Writer.** One frame per call: flag `0x7e`; each data byte as is, or as `0x7d` then the byte xor `0x20` when it is `0x7e` or `0x7d` (always), `0x0d` (when the carriage-return flag is set) or `0x11`/`0x13` (when the XON/XOFF flag is set); the first data byte follows the flag directly. The frame check is the 16-bit PPP one: initial value `0xffff`, per byte `(fcs >> 8) xor table[(fcs xor byte) & 0xff]` with the 16-bit table at `0x142fc` (first entries `0000 1189 2312 329b`), computed over the data bytes before escaping. After the data it is complemented (`a110`) and sent **low byte first, then high byte** (the low byte is stored at `0xa120`, the high byte after a shift of 8 at `0xa134`; they are then copied out in that order by the same escape rule), then the closing flag `0x7e`. The output buffer is flushed through the caller's write function when the byte count plus 5 reaches the buffer size (`0xa05c` to `0xa06c`), and the closing flag is flushed last; a short write is reported through the error hook and returned, otherwise the return value is the data length.
  - **Reader.** Bytes outside a frame are reported once through the error hook (code -705, `-0x2c1`) and dropped; a `0x7e` opens or closes a frame. Inside a frame `0x7d` marks the next byte as escaped (xor `0x20`); a raw `0x0d` is an error (-704) only when the carriage-return flag is set, and `0x11` and `0x13` are plain data (the reader has no compare for them; an escaped one decodes through the ordinary `0x7d` rule). A closing flag with no bytes is ignored; an escape immediately before the flag is -703; a frame of one or two bytes is -702; otherwise the check runs over the data **and** the two trailing bytes in wire order (`0x9b10`, initial `0xffff`) and the frame is accepted only when the result is `0xf0b8`, the standard good-residue, else -700. That residue holds exactly when the far end sends the check low byte first, as above. A frame longer than the receive buffer grows the buffer only when the context's growth step (`+0x34`, the first stack argument of `PPPInit`) is nonzero (the call at `0xa848` carries a text relocation naming `realloc`; a null return is -706). The daemon passes 0 for it (the word stored at `8(r1)` before the call at `0x100057e0`), so in its use there is no growth: when the buffer is full the next two bytes are held aside (they may be the check bytes), and a third makes the reader report -701 (`-0x2bd`, `0xa90c`) through the error hook and drop the frame.
  - **What a far end needs.** Send `0x7e`, the segment bytes of [router-packet.md](router-packet.md) escaped as above, the check low byte first, `0x7e`. Do not send address or control bytes. Escape `0x0d` inside frames; escaping `0x11` and `0x13` is optional for the daemon's reader.
- Socket modes (1 and 5): the reader reads 2 bytes, converts them with `ntohs`, and reads that many bytes minus 2 into the buffer after the 2 length bytes (`0x100067fc` to `0x1000685c`): the first two bytes are a big-endian length that **includes themselves**, and the body follows. Established.
- USB: none; each transfer is one segment (section 8).

**Segments.** What travels is the segment of [router-packet.md](router-packet.md): wire bytes start with a 16-bit byte count (big-endian) and the first segment has bit 7 of byte 5 set, with the segment count in the low seven bits, counting down by one on each continuation to 1 on the last.

## 8. The L1 USB link as the daemon sees it

Established from `l1_open_usb` (`0x10003eec`), `sub_10004e8c`, `sub_10004680` and the kernel driver.

1. **Control node.** Open `/dev/sgil1_cs` read-only, issue `0x40045306`, register `sub_10004e8c` as the input handler, and call it once at once (`0x10004134`).
2. **Status read.** `sub_10004e8c` reads 0x28 bytes. A read of 0 logs `no devices`; negative logs the errno. Otherwise, for each slot `i` below the byte count, with `s` the byte and `state[i]` the daemon's slot state (table at `0x100512b8`, 0x48 bytes a slot): first pass, for every slot where `s` is 0 and the state is nonzero, set the state to 0 and run the close routine (`sub_10004bf8`, label `[driver]`); second pass, for every slot where `s` differs from the state and `s` is nonzero, set the state to `s` and run `sub_10004680(i)`. Because the kernel only returns 0 or 1, a slot is opened when its byte becomes 1 and closed when it becomes 0.
3. **Open a device** (`sub_10004680(i)`): when `-usbpath` is in force and the revision is above 1, issue `0xc0095307` with byte 2 = `i` to get the record for the slot and match its printed path against the filters (a form-2 string, compared with `strncmp` over the filter's length: any filter that is a prefix of the path matches, so `b1;p2` also matches `b1;p23`; the code after the compare tests the filter character at the path's length for the end of string or `/`, but it is reached only when the filter is as long as the path, where the compare has already forced equality, so that test never rejects. Read from `0x100047b0` to `0x10004870`, not run); then `open("/dev/sgil1_%d", O_RDWR)` (error: `ERROR: can't open %s, %s`); then, when the flag at `0x10043bbc` is nonzero, `0x40095304` for the record, format forms 1 and 0 into two local buffers, then `sub_10004210(fd, 0)` (a reset with no device reset on revision above 0). It prints `INFO: opened USB device at <path> (<node>)` with the form-0 path, copies the node name and the form-0 path into the slot record (`+4` and `+0x18`, `0x10004a64` and `0x10004a88`), stores the descriptor at `+0x38`, records the slot, adds the port to the configuration with type 2 (`L2CfgMAddPort`; a return of -1 is `ERROR: device is already in use.`), schedules a timeout of `0xb71b0` (750,000, unit not read) calling `0x1000d9a8`, and registers `0x100069b0` as the descriptor's input handler.
4. **Receive.** Whenever the descriptor is readable `0x100069b0` runs: it calls the router packet reader with the USB read routine, so each `read` returns one USB bulk-in transfer holding one segment with the layout above; the reader checks the first-segment flag and the down-count rule ([router-packet.md](router-packet.md)). Established for the call path; the byte checks are in the packet reader.
5. **Send.** The packet writer calls `l1_write_usb` once per segment with the segment's wire bytes (`IRouterWritePacket`, [router-packet.md](router-packet.md)); the kernel adds nothing but the two-byte stamp (section 3).
6. **What the daemon sends first.** No write follows the open itself (the open routine was read to its exits; inferred from its calls that nothing is written before the first timer). The timer armed at open (`0xb71b0`, callback `0x1000d9a8`, argument the slot number; read in full) is a **recurring request to the L1**, and it is the first thing the daemon sends. Each time it fires, provided the word at `0x10043c00` is nonzero (initial value 1) and the slot still has a descriptor, the callback builds one router packet with `IRouterMakePacket` and writes it to that slot through the mode's writer (`sub_10007478`, which dispatches on the connection mode):
   - destination word `0x0ffff00e` (the constant the callback stores on its stack at `0x1000d9c8` to `0x1000d9d0`), request class 0, request code 0 (inferred from the argument order of `IRouterMakePacket` against [router-packet.md](router-packet.md); the call also passes the constants 2 and 3, the 3 being the descriptor count), with **three descriptors**: an integer descriptor with value 6; a second descriptor that is a NUL-terminated string (type 9, length `strlen + 1`) holding a copy of the string setting number 3 of the daemon's NVRAM (`nvramGet(3)`, the 16-byte string at internal-use offset `+8`, which [daemon.md](daemon.md) infers is the system serial number) when that string is non-empty, or an integer zero when it is empty; and an integer zero.
   - It then re-arms itself with the period held at `0x10043d54` (a zero-initialised word in `.sbss`; set from `nvramGet(15)` at start-up `0x1000d6e0`, where the default NVRAM contents written at `0x1000d5d4` give 5, and by the option that stores to it at `0x100167a0`; 2 while the slot's port state word is not 2, see [config-request-reply.md](config-request-reply.md) section 4), the same callback and the same slot, and stores the timer handle in the slot record (`+0x3c`). The unit of the delay was not read.
   Established for the packet's construction and the re-arm. The daemon's own debug string for the timer is `cfg_ping_l1 (%s)` (`0x1002924c`, formatted at `0x1000dcb8`), and the packet-creation failure text calls it a configuration request, so a periodic ping of the L1 carrying the serial number is the daemon's own description, not only an inference from the shape; the same callback is armed for the serial modes (`0x10005b44`). the L1's handling of destination `0x0ffff00e` and code 0, the reply the daemon needs, and what the daemon does with it are read in [config-request-reply.md](config-request-reply.md). A second timer, armed by `sub_1000f710` with callback `0x1000f93c`, was not followed.
7. **Loss.** A status byte falling to 0, or `ENODEV` or `EINVAL` on an operation, closes the slot; other errors close it after the third in a row (section 3).

## 9. The reply to the partition-record requests

Tasks and codes here are read from `l2part` and its libraries in 1.44.0 (the three versions listed in section 1 share the code table). See [partition-task.md](partition-task.md) for the codes and the database record.

**Where `0x3001` to `0x3003` fit.** The stock boot firmware's partition fetch reaches the L2 as a request to controller type 1, task `0xa`. The codes `0x3001` to `0x3003` are the L1's multi-frame transport on the serial link between that firmware and the L1; the L1 consumes them and forwards an ordinary request. Seen from the L2:

- No L2 program contains a handler for `0x3001`, `0x3002` or `0x3003`. A search of the `ori`, `addi`, `li` and `cmpwi` operands of `l2`, `libmain`, `libRouter`, `libapi`, `libsys`, `l2part` and `partmgr` finds none in 1.24.1, 1.44.0 or 1.48.0; the only occurrences are in `libIRouter`, in the chunk reader and writer for **descriptor streams** (`IRouterConnectOS`, used by the client library when it talks to a device rather than the daemon). Established for the absence in those three versions.
- On those descriptor streams the L2 writes a 9-byte frame header (four zero bytes, the big-endian code `0x3001`, `0x3002` or `0x3003`, one byte, then the big-endian message length) and at most 118 payload bytes per frame ([partition-task.md](partition-task.md)). The L1 serial transport is the same layout with 113 bytes per reply frame (L1 datasheet figure; not re-read here). The two are different code, so the 118 and 113 are not a contradiction. Not on the USB link, where a segment is sent as-is (section 6).
- So a task-`0xa` request that arrives over USB is **not** framed: it is a normal router request whose code field (offset `0x22` of the segment record, `0x12` of the wire bytes) is the request code. What code the boot firmware puts there is **unknown** here (no boot firmware is part of these images); the handler answers codes 1 to 8 and any other code with result -3.

**The request.** Wire offsets are those of a segment's wire bytes (record offset minus `0x10`). The request's first argument descriptor is at record offset `0x24` (wire `0x14`): type in the low three bits of byte `0x24` (0 = integer, value in the word at `0x28`; otherwise the argument is fetched with `IRArg` from the payload), length halfword at `0x26`. The class byte at record `0x16` (wire `0x06`) is 0 for a request; the reply is sent only when it is 0.

**The reply** is built by the library's response path, established from `sn1SCSendRsp` and `IRouterResponseL3` (`libapi` `0xbc80`, `libIRouter` `0x3f6c`) and the common exit of `l2part` (`0x10001aa0`):

| class | 1 (response) | established |

## 12. Units of the timers

The daemon arms its timers with `EventAddTimeOut` from `libRouter`. Its arguments are the callback, the argument, a name, and a pair of deltas: the first is added to seconds and the second to microseconds. `EventCreateTimeOut` reads `gettimeofday`, adds the two deltas, and moves whole seconds out of the microsecond field when it passes 999,999 (0xf423f). Read in full at 0xa554 to 0xa6e4 of `libRouter`. Established.

| Timer | Call site | Seconds argument | Microseconds argument | Grade |
|---|---|---|---|---|
| First request after a device opens | 0x10004b34 (`l1_open_usb_device` timer) | 0 | 750,000 (0xb71b0), so 0.75 s | E |
| Recurring request to an L1 | 0x1000dc60 to 0x1000dcd8 (`cfg_ping_l1` callback, 0x1000d9a8) | the period in word 0x10043d54, which is NVRAM key 15 | 0 | E |

NVRAM key 15 is read at start-up (0x1000d6e0) and stored in the period word. It defaults to 5 (0x1000d5d4 and the default write just above it). A slot whose port record state word (the first word of the 0x1c-byte record, not the type) is not 2 uses 2 instead (0x1000dc8c); the state is 1 after the attach and 2 once a reply has been processed. So the period unit is seconds; the first re-arm after an open is 2 s, later ones 5 s once a reply has been processed and 2 s forever if none is ([config-request-reply.md](config-request-reply.md) section 4; the earlier reading of this word as the port type was wrong). The 750,000 first delay is microseconds (0.75 s).

The callback's own code does not wait for or record a reply; the reply is handled by a separate routine ([config-request-reply.md](config-request-reply.md)).

The IRIX `l2cmd` build (6.5.30) was read from its program headers, because its section table is cut. Its `main` (0x10006368 to 0x1000636c) passes the `--l2` host to a connect wrapper at 0x10007990, which is the same routine shape as `sn1SCInit`: it uses bias + 8000 (0x1f40) unless the device-mode flag word at 0x10049854 is nonzero, in which case it uses bias + 8002 (0x1f42) (established from the instructions at 0x100079b4 to 0x100079e8). The bias is read through the pointer at 0x1004926c. The file carries the variable name `IR_PORT_BIAS` and the text `biasing all network ports by %d`, so the bias comes from that variable (I; the code that reads it was not followed). The flag is set to 1 at 0x10007154, on the branch of the option parser at 0x100070d8 to 0x10007160 that follows a call returning zero; that call's target is an import whose name was not resolved, so the flag's meaning is inferred from the `--scdev` text beside it (I). With `--l2` alone the command port is therefore bias + 8000, which is the port the daemon's command service listens on. The connect path imports `socket` and `connect`; whether the socket is a TCP stream was not read (I). `l2cmd` passes no interface address: `main` gives the connect wrapper the host pointer and two zeros.

**Listener address.** `EnetServerInit` calls `SocketGetHostAddr` for the local host name. When that fails it logs `EnetServerInit: couldn't get IP address for local host` and returns with no error (0xecd8 to 0xed08). `EnetServerStart` takes the port number as its first argument and passes the validator and a zero to `RouterStartServer`; it does not pass the stored address (0xed24 to 0xedbc). Established from the calls. The socket bind address inside `libRouter` was not read, so whether a listener needs an interface address is unknown (U). The observed run in [user-mode.md](user-mode.md) needed a host-name entry for `127.0.0.1` to avoid a listener error, not an interface address.

**Start order.** `inittab` (see [rootfs.md](rootfs.md)) starts `l2` on levels 3 to 5, `l2flash` on 4 and 5, `l2gui` and `l2part` on 5, all respawned, with no wait or dependency between them. The partition service and the flash updater therefore do not need the daemon to be up first: each retries its connection every 5 s (strings above; `l2gui` prints `L2 Controller connect failed, retrying...`). What a display program that never registers does to the daemon is not traced: the daemon's `l2dsp` commands set daemon state and their delivery to task 6 was not followed (U).

## 14. Power-up mode and delay

Read from `bin/l2` (1.44.0).

- The power-up mode is NVRAM key 21 (0x15). A nonzero value selects `slow` (routers powered in series); zero selects `fast` (routers powered in parallel). The status command prints the mode with the words `parallel` and `series` chosen by the same bit (0x10014dc0 to 0x10014e24). Established.
- The inter-command delay is held in word 0x10043c4c. The `power` command help says it is in milliseconds (`delay is set to %d milliseconds`), and the stored value is the command's argument (0x10014dac). The delay is passed as the last argument of a per-router request (0x10013fa0). The queue, its runner, the sender and the order and spacing of both modes are read in [power-queue.md](power-queue.md); the delay defaults to 500 ms and is not saved to NVRAM. The R-brick's power-on serial-number check is an L1 behaviour and is not in these images (see the L1 notes).

## 15. The flash updater, the power queue and the open items (2026-11-02)

**The flash updater (`l2flash`, 1.44.0).** Its import list is `sn1SCInitL2App`, `sn1SCPkt`, `sn1SCReconnect`, `sn1SCParseCmdline`, `sn1SCUsage`, `FlashIRouter`, `IRouterFreePacket`, `LoggerDefaultMessage`, `syslog`, `fprintf`, `sleep` and `exit`. It imports no `flash_*` routine from `libdrivers`, so the program itself never maps `/dev/mem`. It registers as task 8 (established from the `li r5` before `sn1SCInitL2App`, see section 13) and then loops in `sn1SCPkt`, handing packets to `FlashIRouter` (a library routine whose name suggests it holds the flash handling; I, not read). What `FlashIRouter` does with each request code, and which code carries a flash image, was not followed (U). Its start-up retries and messages are in section 11. On a failed `sn1SCPkt` it prints `sn1SCPkt failed` and then `could not re-establish connection` (strings), and calls `exit`; the call site was not decoded because the calls go through stubs in its `.plt` (I). The status words of its replies (the open question on the `FLASH` reply `STATE` fields) were not read.

**Display program and start order.** `l2flash` does not wait for the display program. The daemon has no dependency on task 6: the daemon's `l2dsp` command sets its own state, and whether a task-6 client's absence changes any reply was not followed (U, as before).

**The power queue (`l2`, the `power` command).** Read in full in [power-queue.md](power-queue.md): `sub_1001f5e0` appends a (packet, wait flag, delay word) node to a FIFO, `sub_1001f6e4` removes it, and the runner `sub_1001c3ac` sends the packet, then waits for outstanding replies when the delay word is -1 or sleeps for that many milliseconds when it is positive. The earlier reading of the three calls per router in this section (a packet, a wait node, a delay node) is the serial case of that sender.

**R-brick power-on serial-number check.** Not in the L2 images. The L1 personalities for the R-brick (package 3 or 5) are not read (see [../coverage.md](../coverage.md)), so the check is unknown from this repository (U). Test: in L1 packages 3 and 5, find the R-brick power-up path (the power-on hook the brick-type table selects for the R-brick letter) and list its calls. The package 1 pre-power check is `0xffe52d18` ([l1/serial-number-requests.md](../l1/serial-number-requests.md)); locate its counterpart in each package by the same compare constants and report whether the R-brick power-up path reaches it. A call means the check exists and its required-letter field is read next; no call on any path means the R-brick powers on without a serial check in that package.

**Start order, reconsidered.** `inittab` order (section 13) still stands. Neither the flash updater nor the partition service waits for `l2` at boot. Each retries its own connection, so the only ordering dependency is the 5-second retry.
