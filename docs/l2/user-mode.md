# Running the L2 user space under a PowerPC user-mode emulator

Run against L2 1.44.0 (IRIX 6.5.30 `l2.bin`) with a user-mode PowerPC emulator (version 11.1.2 of the open-source Linux user-mode emulator packaged for Debian testing, unpacked with `dpkg -x` and run without installing). The L2 programs are 32-bit big-endian PowerPC Linux executables; the emulator runs one at a time and forwards system calls to the host kernel. Results below are observations of one run; where a statement rests on reading the code it says so. Grades as in [../../AGENTS.md](../../AGENTS.md).

## Recipe

1. Carve the image: `retools/tools/sysco/l2_extract.py l2.bin OUT` (see [image-layout.md](image-layout.md)). Copy `OUT/rootfs` to a private working directory; the copy is edited below and the firmware is never committed.
2. Make the flash window reachable. `libdrivers` opens `/dev/mem` and maps 4 MiB of it at a physical base taken from two words at `.rodata` `0x2a28` (`0xfc000000`, `0xfe000000`; see [libdrivers.md](libdrivers.md)). Observed: the emulator's `mmap` of that file at offset `0xfc000000` fails with `EOVERFLOW` (error 75), and the same call at `0x7c000000` succeeds; the likely cause is a signed 32-bit offset in the old-style guest call (not checked). In the private copy replace the two words with `0x7c000000` and `0x7e000000` (eight bytes, the only edit). The library then treats `0x7e000000` as a non-standard base and adds its offset compensation (observed message `flash memory detected at non-standard location 0x7e000000`), so callers' `0xfe3f0000` and `0xfe3e0000` land at the right place.
3. Provide the `/dev/mem` stand-in. The emulator's `-L` prefix also redirects guest file opens of absolute paths when the file exists under the prefix, so a sparse regular file of `0x7e400000` bytes at `<tree>/dev/mem` is what `open("/dev/mem")` gets. Fill the last 4 MiB with `0xff` (erased flash) and, if the flashed-version check should see something, write the payload of `l2.bin` (the file without its first 0x2c bytes, which are the file header) at its start: the check reads the header pointer at window offset `0x40000` ([config-request-reply.md](config-request-reply.md) section 5). A plain file is enough: every command cycle the driver writes lands as an ordinary store, and programming reads back what it wrote, so program and erase calls succeed without any flash command emulation (read from `flash_program` and `flash_seq_done`; the erase itself does not clear data in a plain file).
4. Give the tree `etc/hosts` with the host's name mapped to `127.0.0.1`: without it `EnetServerInit` reports `couldn't get IP address for local host` and every listener start prints a socket error.
5. Run with the tree as the library prefix (`-L`) and the loader search path set (`-E`): `ppc-user-emulator -L TREE -E LD_LIBRARY_PATH=TREE/lib:TREE/stand/sysco/lib TREE/stand/sysco/bin/l2 -noconn`. (Observed: `-L` alone fails with `libc.so.6: cannot open shared object file`.)

## What happens without the stand-in

With `/dev/mem` unreadable the daemon prints its banner and `flash_init: can't open /dev/mem`, then dies with a segmentation fault (observed). Reading explains it: the start-up version lookup (`sub_10003ca4`) calls `flash_read_addr`, which returns the `flash_init` error -2 as if it were a pointer, and `FlashValidateImage` rejects only -1 before it reads through the pointer. So `-noconn` alone does not reach the event loop; the open question in the earlier version of this file is answered: `nvramInit` would fall back to defaults (zeroed RAM image fails its header test and is reset, read in `0xc7f0` to `0xca04`), but the daemon never gets that far.

## Observed behaviour with the stand-in

Banner and warnings: `Current L2 version: ?.?.? (L2 emulator: 1.43.4)`, `Flashed L2 version: FLASH IMAGE IS CORRUPT!` (the validator did not accept the bytes at the flash address `0xfe040000` that it checks; the flash layout and the header it expects are read in [config-request-reply.md](config-request-reply.md) section 5, which also shows that the payload without its 0x2c-byte file header passes), `WARNING: No connections will be made to L1's (-noconn)`. With the stand-in filled with `0xff` the first start prints `NVRAM data detected at old flash location--moving to new location`, as the code at `0xdd7c` says it should for an all-ones new location.

Listeners (connect from the host and read): ports 8000, 8001, 8002, 8003, 9001, 9002, 9004 all open on first start, with the default port bias 0. 8001 and 8003 give the L2 command prompt (`?-127.0.0.1-L2>`); `help`, `version`, `rackid`, `sysname`, `date`, `serial`, `ip`, `smp`, `destination`, `l2dsp`, `dhcpserver` answer locally (rack ID 0, name and serial not set, `smp` lists console port 0 at 38400, modem port 1 at 38400 and the network session 16). `nvram`, `pbay` and `l2 ver` answer `ERROR: no L1s found to match that destination` because they are L1 commands. Ports 8000, 8002, 9002 and 9004 send an unsolicited 28-byte record on connect, `00 02 04 00 00 00 00 14 01 00 00 0f`, `L2`, NUL, `sgi`, NUL, `sgi`, NUL, `7f 00 00 01`, NUL (the two `sgi` strings and the leading bytes are not decoded). Port 9001 sends 8 bytes, `00 02 22 00 00 00 00 00`. That the 8003 and 9004 pair are the second ports of the 8001 and 9002 services follows from their identical replies.

Client programs: `l2part --l2 localhost` connects to 9002, logs `connection to localhost:9002 established` and stays up, so the task-10 service of [partition-task.md](partition-task.md) registers with the daemon. `partmgr` cannot be pointed at the daemon: its start-up calls `sn1SCUseSCDevice(0)` after parsing `--l2` (call at `0x10008630`), and that routine in `libapi` (`0xa654`) sets the device-mode flag and looks for `/dev/snsc/*c*` (observed: `Could not find an L1 Controller (/dev/snsc/*) to communicate with!`). Its option string `chlais:dux:Ff:m:p:b:r:e:` (read at `0x100013e0`) has no `n` or `v`, although the usage text lists them. So the partition requests of the PROM were not exercised; only the registration was.

## Not run

`l2term`, `l2flash`, `l2dhcps`, `l2passwd`, `l2staticip` and `flashraw` need `libscan.ppclinux.so`, which 1.44.0 lacks (the 1.48.0 tree has it); `l2gui` needs `/dev/fb0`. The USB mode of the daemon needs the SGI L1 kernel driver nodes, which the emulator cannot provide; `-serial HOST PORT` and `-net` modes were not tried.
