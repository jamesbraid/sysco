# Origin 300 L1 environmental reset and debug-switch reading

This note traces two commands in the selected Origin 300 L1 firmware.

## Checked source and public context

The selected 982,412-byte range of the IRIX 6.5.30 composite has SHA-256 `0c969f9e98c73826495dc37bff685b3403e248993ba92194a288333d9d42b2f4`. It identifies itself as L1 version 1.44.0, built 2006-07-17 for the Fuel/PE/Origin 300 family. Its ColdFire body has SHA-256 `9db44f3bb06ec90475035781766e1ca7e924f15a0ed215cf855c1f491275fdd1` and was analysed at `0xffe00000`, with reset vector `0xffe00400`. Bank-relative offsets are the locators below minus `0xffe00000`. Locators are read from the committed listing.

The public Origin 300 guide `007-4498-002`, printed pages 181 and 184, shows a debug command example and environmental status, respectively. The following conclusions are therefore scoped to the selected 1.44.0 image.

## `env reset` and the power-down countdown

The command interpreter registers a task-3 request endpoint and sends accepted text to its local command parser (`0xffe1aefc`, `0xffe1b0f8`). The `env` command table selects branch seven for `env reset` (command entry at bank offset `0x1d3c0`; handler `0xffe15528`, offset `0x15528`). That branch asks the environmental module to reconfigure, produces no command text, and returns the handler's success value. It does not check or return whether monitoring has been initialized. When initialization has not completed, the module's reconfiguration routine does nothing yet still lets the command handler return success (`0xffe2b798`, offset `0x2b798`). Thus a successful command response alone cannot prove that any live monitor or power-down timer was changed. Bad command syntax is handled by the common parser; the exact task-3 status value for each malformed form was not resolved here.

When initialized, reconfiguration takes the environmental lock, clears cached supply, fan and temperature warning/fault and work state, resets monitor-side state, reloads threshold settings, and reconfigures active monitors (`0xffe27e34`–`0xffe28176`, `0xffe2b798`–`0xffe2b80e`). It also sets the environmental power-down semaphore's count to one. The semaphore reset routine sets the count directly and clears waiting operations, rather than adding a token (`0xffe44098`–`0xffe44154`). The reset leaves the environmental-enable setting in place and resumes monitoring according to that setting. It does not directly issue a node power-on command. Whether reconfiguration succeeds on every fitted sensor, and how a failing sensor is reported to the remote command caller, remain unmeasured.

A countdown initially takes that semaphore without waiting. If it succeeds, the L1 emits a `0x4101` environmental event for each five-second step of its displayed 30-second countdown, waits 500 task-clock units, checks whether node power is still on, and tries the same semaphore again (`0xffe28178`–`0xffe282ba`). Restoring the count to one while the countdown is running makes its next semaphore take succeed. The worker then emits the `0x4102` abort event with diagnostic number `0x163` and exits without calling the environmental power-down action. If the node is already off at that check, it also exits with `0x4102` and diagnostic `0x163`, but through a different message branch. If neither condition occurs, the worker reaches zero, emits `0x4102` with diagnostic `0x164`, and calls node power down with environmental reason code four. These are separate conditions in the same worker, so the event code alone does not identify the cause of an abort.

An `env reset` during an active countdown therefore **cancels that countdown at its next check** in this image; it does not add a fixed delay to the same countdown. The firmware clears existing fault state as part of reset, so a still-faulty sensor may be detected again and start a new countdown. That subsequent path, including the interval between reset and a fresh fault event, has not been characterized.

## `debug` read, write and retention

The selected command handler accepts its parsed no-value branch as a read and its one-value branch as a write (`0xffe15214`–`0xffe1529a`; command entries at bank offsets `0x1cafc` and `0x1cb40`). In the write branch it stores the parsed value with the same settings accessor used by general-task request `0x1001`; request `0x0001` reads it with the matching accessor (`0xffe11e18`–`0xffe13e6c`, `0xffe15214`). Both command branches then read back the stored value and format one line with a four-digit hexadecimal switch word. The public guides show the operator forms `debug` and `debug <hex>` and the line's `0x` representation. The selected command table uses the parser's automatic numeric base for the value, so a complete decimal token, a leading-zero octal token or a `0x`-prefixed hexadecimal token is accepted; a token that is not fully numeric does not reach this handler (`0xffe61bd0`–`0xffe621e4`). The setter masks the word to 16 bits, so larger parsed values cannot persist in the switch field (`0xffe58758`–`0xffe587aa`, `0xffe59590`–`0xffe595ee`). The conversion routine recognizes a leading sign; its overflow handling is not yet read from the listing, so the result for overflow or negative input is unknown (route: read the routine at `0xffe61bd0` word by word; next: the same routine in 1.48.1). The handler itself does not reject them.

The settings accessor writes the switch field into the checksummed primary core settings record and refreshes its backup copy (`0xffe58758`–`0xffe5958e`). At firmware start the L1 maps that record from its NVRAM address region and validates its checksum. If the primary fails, it can restore the backup; if both are invalid it initializes default core data (`0xffe5a6a8`, `0xffe5a758`, `0xffe5a188`). This establishes persistence across a firmware restart **when the NVRAM contents remain valid**, rather than merely inferred survival from a console transcript. A guest node CPU reset or node power-down leaves the powered L1 running, so the current word remains available. An L1 processor reset runs the firmware-start path and restores the stored word subject to the primary and backup checks. The image does not identify the exact fitted NVRAM package, its battery condition, or a guaranteed retention time after mains power is removed. The older public 1.18.5 debug transcript is consistent with this behavior but cannot prove that version's storage layout is identical.

## Routes to settle the open points

- `debug` overflow and negative input, and the task-3 status for each malformed form: read the numeric-parse routine (`0xffe61bd0` to `0xffe621e4`) and the task-3 reply builder in full, then repeat the read in the 1.48.1 package whose layout matches this one.
- Persistence: read the settings validation and backup-restore routines (`0xffe5a188`, `0xffe5a6a8`, `0xffe5a758`) in full for the corrupted-primary, valid-backup case.
- The NVRAM part and its retention are not named by any image; the open-questions note carries the route.
