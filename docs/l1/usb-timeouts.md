# Origin 300 L1 1.44.0: four USB control decompiler timeouts

The four USB-area routines that time out in Ghidra's C generation are two first-bank functions and their relocated-bank copies. An instruction trace can settle the visible recipient, setup, software-state and error decisions, but cannot settle what a USB host receives from the lower device-controller callback. No new C text was recovered in this reading.

Its 982,368-byte ColdFire body at `0xffe00000` has SHA-256 `9db44f3bb06ec90475035781766e1ca7e924f15a0ed215cf855c1f491275fdd1`. Their listing, function-table and run-manifest SHA-256 values are respectively `7053bb92b2a82508786c957cf822ead2ceea9f50388bf6b44c23767b6589bc5f`, `153f7742bbc5a14f6c9ac7a3dd7667889d07abb2f24e3801055a18a4cc00aff7` and `260f026359f7585a81731fad5d34b9eaeebf64c0d623eb5a8d73f138e2edddcf`. All eight recorded full-pass hashes passed before this trace. The earlier control reading already binds the descriptor, endpoint and lower-controller claims to this image.

It ran with host `uv 0.12.1` as:

```sh
uv run --script tools/l1-analysis-repair/verify-timeout-instructions \
  .cache/l1-analysis/verified-final/0c969f9e98c7 \
```

It records 103 instructions and 336 bytes in each status handler (`0xffe6f6d0`–`0xffe6f820`, `0xffedf6d0`–`0xffedf820`) and 144 instructions and 436 bytes in each setup task (`0xffe6fb6c`–`0xffe6fd20`, `0xffedfb6c`–`0xffedfd20`). A matching shape does not prove which bank runs in an IP45 chassis.

## Status recipient and endpoint state

The status handler reads recipient bits 4:0 from the first setup byte. It branches to device at zero, interface at one, endpoint at two, and an error at any other value (`0xffe6f6e4`–`0xffe6f722`, `0xffe6f7b4`–`0xffe6f7dc`). The device branch stores status bit zero as one. The interface branch stores zero (`0xffe6f6fc`–`0xffe6f71e`). Neither branch reads the setup index or remote-wakeup software state. The [USB 1.0 standard request table](https://ethw-images.s3.us-east-va.perf.cloud.ovh.us/ieee/4/44/USB_1.0_Specification.pdf), PDF pages 174 and 176, identifies request zero as `GET_STATUS` and defines the device status bits and little-endian response.

The endpoint branch takes the low four bits of the now-swapped setup index as endpoint number and bit 7 as direction. It passes those values with the software controller slot to a lower endpoint-state query (`0xffe6f72e`–`0xffe6f75a`). The query maps endpoint zero to its control state, OUT endpoint one to a second state only when direction is clear, and IN endpoint two to a third state only when direction is set. Other endpoint numbers, directions or unavailable slots return errors (`0xffe6d92c`–`0xffe6d99e`). State two returns zero, state one returns error `-0x5e2` and any other state returns another error (`0xffe6d99e`–`0xffe6d9c0`). The handler maps zero to status bit zero clear and `-0x5e2` to status bit zero set. Other query results take its error path without building a status reply (`0xffe6f75e`–`0xffe6f7b2`). This establishes how the selected software formats active versus stalled endpoint state. It does not prove the controller's halt bit or whether an L2 host sees it.

On a recognized recipient, the handler swaps its two-byte status value to USB byte order and gives the send helper a maximum of two response bytes, the setup packet's advertised length, and the open control function (`0xffe6f7de`–`0xffe6f816`). The helper clips to the lesser of two and the advertised length, sends at most 64 bytes per lower call, alternates its two IN data-stage selectors, and fails on a mismatched lower return (`0xffe6f660`–`0xffe6f6be`). The constructed value would be `01 00` for self-powered or stalled status and `00 00` for clear status, subject to the advertised-length clip. The mirror handler calls its own relocated lower query and send helper (`0xffedf754`, `0xffedf80e`).

## Setup loop and dispatch result

The control task logs an unexpected entry argument but continues. It opens one control function, stores that handle, and exits that invocation if the open fails (`0xffe6fb78`–`0xffe6fbfe`). Once open, it repeatedly asks the lower read helper for a setup stage with a 64-byte buffer allowance and requires a return count of exactly eight (`0xffe6fc04`–`0xffe6fc20`). A short count, negative result or other mismatch goes to a diagnostic branch and then recovery. One negative value, `-0x5f1`, receives a distinct branch. another mismatch consults a lower object state before deciding whether to print a more specific warning (`0xffe6fc20`–`0xffe6fc54`).

After exactly eight bytes, the task byte-swaps the value, index and length words in place. It then uses direction bit 7 in the first setup byte to choose read or write dispatcher. A zero dispatcher return starts the next setup read. A nonzero return invokes a lower recovery operation and then loops again, even if the recovery itself reports an error (`0xffe6fc58`–`0xffe6fd12`). The recovery helper calls an indirect controller callback with an operation value, increments a software counter, clears work state and returns zero after its normal path without checking that callback's returned value (`0xffe6d624`–`0xffe6d66c`).

The read dispatcher accepts `GET_STATUS` (zero), `GET_DESCRIPTOR` (six), `GET_CONFIGURATION` (eight), `GET_INTERFACE` (ten) and `SYNCH_FRAME` (twelve) in this direction, using the [USB 1.0 request code table](https://ethw-images.s3.us-east-va.perf.cloud.ovh.us/ieee/4/44/USB_1.0_Specification.pdf) on PDF page 174 for those names. Zero calls this status handler, and six calls the descriptor builder. Eight, ten and twelve proceed directly to a common status-out call without writing request-specific data to the task's setup buffer (`0xffe6fa88`–`0xffe6fb2c`). The write dispatcher indexes a 24-byte data table at `0xffe6f948` for request numbers zero through eleven. The table is present in `unclassified.tsv` at `0xffe6f948`–`0xffe6f960`, SHA-256 `5f03c62ab2ca474d0c8821b395509f5ad5b8b4f36be62d4daceafdaccbc7e9f4`. It is twelve signed 16-bit branch offsets, not missing executable code. Odd requests `CLEAR_FEATURE` (one), `SET_FEATURE` (three), `SET_ADDRESS` (five) and `SET_CONFIGURATION` (nine) call their respective helpers. `SET_DESCRIPTOR` (seven) and `SET_INTERFACE` (eleven) go straight to the common status-in call, with no request-specific state write or OUT data read (`0xffe6f93e`–`0xffe6fa1c`). Even numbers and values above eleven reach the error path. The mirror table at `0xffedf948` has the same 24 bytes and relocated targets. These are selected software dispatch decisions. Setup type, recipient, index and length may still be checked by a lower layer.

The common status-in call asks the lower read helper for selector three and zero returned bytes. The common status-out call asks it for selector six with a 64-byte buffer allowance, then requires a zero return (`0xffe6fa1c`–`0xffe6fa4e`, `0xffe6fb2c`–`0xffe6fb60`). A nonzero lower result makes the dispatcher fail. In the read helper, the software object must be open under the current task and in an allowed state. It then calls the installed controller function indirectly and waits for its completion state (`0xffe6d4e4`–`0xffe6d5e8`). The same indirect callback serves the setup read and both generic status stages. The static selected image does not prove what a host sees when these requests construct no data: a zero-length stage, a stall, a timeout and callback-specific outcomes remain separate live possibilities.

## Controller path that remains unresolved

Before installing the visible controller callback, startup writes a scratch byte and reads a revision byte. If it reads `0x81`, it loads an alternate function pointer from RAM address `0x300006f4` and calls that function. Other revisions take the visible probe and callback path (`0xffe6db76`–`0xffe6dba6`, `0xffe6dbc4`–`0xffe6dbfe`). The callback's value and implementation are not in these four decoded routines. The controller-register reading keeps the revision and board-fitment limits explicit.
