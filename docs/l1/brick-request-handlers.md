# Request handlers of the general task that differ between the ColdFire packages

Read from the IRIX 6.5.30 `l1.bin` (L1 1.44.0). Package numbers and labels follow [personalities.md](personalities.md): 0 `Base 1MB image`, 1 `Fuel/PE/O300 1MB image` (the reference, "o300"), 2 `MIPS 2MB image`, 3 `Legacy 2MB image`, 5 `2MB image`. Addresses are first-bank body addresses. Grades follow [AGENTS.md](../../AGENTS.md). The code list of each package and the handlers added by packages 3 and 5 are in [personalities.md](personalities.md); this note covers the shared codes whose handler differs from the o300 one.

Method. Each package's dispatcher was run symbolically over every code from `0x0000` to `0x4fff` (compare chains, the two 16-bit jump tables) to get the handler address of every code; the results agree with the o300 rows of [request-codes.tsv](request-codes.tsv). A handler runs from its entry to the next handler entry. Each handler was disassembled in all five packages and compared with the o300 one after masking registers, frame offsets, RAM addresses and branch targets, and the differing instructions were read against the listing. Handlers that came out identical after masking (`0x0001`, `0x0005`, `0x0009`, `0x000b`, and in package 3 also `0x1002`, `0x1004`, `0x1005`) are not described again.

## What every handler shares

Established from the o300 dispatcher (`0xffe11e18`), the package 3 dispatcher (`0xffe11258`) and the package 5 dispatcher (`0xffe3eecc`).

- The request frame is passed to the dispatcher as argument 0 (kept in `a3` in packages 0 to 3, in `a2` in package 5). The byte at +0x20 is the word count including the code. Word `k` has a tag byte at +0x24+8k (only its low 3 bits are tested) and a value at +0x28+8k; a zero tag means the value is in the frame, any other tag means the value is fetched with the argument routine (o300 `0xffe79344`, package 3 `0xffea83ec`, package 5 `0xffeaa324`) called with the frame and the word index. The word at +0x1c is the sender: negative gives index `0xff`, otherwise bits 11 to 5.
- The reply is built in two stack buffers by a status writer (o300 `0xffe388c8`, package 3 `0xffe45bec`, package 5 `0xffe46f64`: stores the status and sets the field count to 1) and an integer writer (`0xffe388ec`, `0xffe45c10`, `0xffe46f88`). The three writers have the same bodies. A handler that has no reply on success leaves the buffers untouched and falls into the common exit, which sends them.
- A shared status code, as in [personalities.md](personalities.md): `-100` (`0x9c`) too few words, `-104` (`0x98`) absent or empty, `-105` (`0x97`), `-106` (`0x96`) hook or lifecycle failure, `-107` (`0x95`), `-108` (`0x94`) not available on this brick type, `-101` (`0x9b`) no handler.
- A code with no handler in the package takes the default path. In the o300 package it tests the word at block+8 of the RAM hook block at `0x30000990` and, when it is set, calls it with the frame and the two reply buffers, otherwise replies `-101`. Package 3 does the same with block `0x300010fc` and offset 4; package 5 with block `0x30001334` and offset 4.

## Packages 0 and 2 against package 1

Established for all 39 shared codes, from a byte comparison of every handler. Package 0 and package 2 run the same instruction stream as package 1 in every handler: every differing byte lies inside a 32-bit absolute operand. Each `jsr` target is the routine that the routine pairing ([personality-diffs/routines.tsv](../personality-diffs/routines.tsv)) matches to the o300 callee (a different routine never replaces a callee), and the other operands are RAM words that moved. The moved RAM words are:

| o300 word | Package 0 | Package 2 | Used by |
|---|---|---|---|
| `0x30000990` request hook block | `0x30000964` | `0x30000fe4` | `0x0006`, `0x0007`, `0x2002` to `0x2004`, `0x4002` and the default path |
| `0x30001f20` board descriptor block | `0x30001e30` | `0x3000281c` | `0x0008`, `0x0010` |
| `0x3000015c` | `0x30000130` | `0x30000730` | `0x000a` |
| `0x30005038` | `0x30004f48` | `0x30005ad4` | `0x1007`, `0x100b` |
| `0x300009b0` | `0x30000984` | `0x30001004` | `0x4000` |
| `0x30000928`, `0x30003eb8`, `0x30003ee0` | `0x300008fc`, `0x30003dc8`, `0x30003df0` | `0x30000f24`, `0x30004884`, `0x300048ac` | `0x4002` |

Package 2 also moves every string pointer (its literal pool is 0x2350 bytes higher). What differs between the three packages is therefore only what the called routines and the hooks installed in the hook block do for the brick type. The brick types each package initialises are in [personality-board-init.md](personality-board-init.md). The entries below name package 0 and 2 only where something beyond the table applies.

## Entries

### Identity and addressing

- **`0x0002` and `0x0003`** (o300 `0xffe11ffc`, package 3 `0xffe11488`, package 5 `0xffe3f160`; one handler, the code selects the extra field). Inputs: the code only; no word-count test. Board accesses: persistent settings 2 and 1 (the bay and the rack, through the setting reader), the brick-type accessor, the port-tag routine and the runtime slot `0x2a` plus the port tag (package 5 reads slot `0x1b` plus the tag; see [brick-request-handlers-detail.md](brick-request-handlers-detail.md)). Reply: 0, then an integer `rack << 6 | bay`; for `0x0003` a second integer, the brick-type character reported for the port. In o300 the character is the local type, except that type `8` (`0x38`) reports `7` when the subtype byte routine returns 4, and type `=` (`0x3d`) reports `#` when the low byte of the slot value is zero. Packages 3 and 5 keep only the `=` rule: the `8` case and the subtype routine are gone. Established (all three bodies read in full). Package 0 and 2: same as o300.
- **`0x0004`** (o300 `0xffe122a8`, package 3 `0xffe11714`, package 5 `0xffe3f3ec`). Inputs: the code only. Board accesses: a per-node serial routine or the brick serial routine, chosen by the type character. Reply: 0 then the serial text; `-104` when the routine returns null. o300 takes the per-node routine for types `6` and `@` and the brick serial routine otherwise. Package 3 takes the per-node routine (`0xffe6b3d0`) for `@` only and the brick serial routine (`0xffe6b4a8`) otherwise. Package 5 takes the per-node routine (`0xffe7a214`, which also receives a second argument, a register that the dispatcher prologue loads) for `,` `-` `.` `@` and `}` and the brick serial routine (`0xffe7a314`) otherwise. In packages 3 and 5 the `-104` status is set before the common reply path; in o300 it is set at the shared inventory code. Established for the type lists and the call shapes; the routines behind the callees were not read, so what each serial is stays as in [functions.tsv](functions.tsv).
- **`0x0008`** (o300 `0xffe12848`, package 3 `0xffe11cb6`, package 5 `0xffe3f990`). Inputs: the code only. Board accesses: tests the board descriptor word at +0xe0 (package 3 +0xe4, package 5 +0xec; blocks `0x30001f20`, `0x30002b90` and `0x30003404`) and, when it is set, calls it with one zero argument and takes the result as the text; otherwise reads persistent setting `0xd` (the system serial). Reply: 0 then that text; `-104` when its length is zero. Established; the three bodies have the same shape, only the descriptor field offset and block address move.
- **`0x000a`** (o300 `0xffe128f2`, package 3 `0xffe11d60`, package 5 `0xffe3fa3a`). Inputs: the code only. The brick-type character selects the source through a jump table over the character minus `0x30` (package 5: minus `0x24`). Board accesses: persistent settings `0x2a` to `0x2f`, the per-port record routine (ports 1 to 4) and RAM word `0x3000015c` (package 3 `0x30000878`, package 5 `0x30000914`). Reply: 0, one integer, then the integer of setting `0x2b`. The port-record path takes the port tag (0 to 3), picks record 1 to 4 and setting `0x2a`, `0x2b`, `0x2e` or `0x2f`, and the integer is that setting when the RAM word is nonzero, otherwise the record's word at +0x30 when the record's first word is nonzero, otherwise 0. In o300 the table sends types `0 3 4 5 6 7 8 9 @ A B C F H L O Q` to a second chain and every other type reads setting `0x2a`; the chain reads setting `0x2b` for types `0`, `7`, `8` and `Q`, setting `0x2a` for `9`, and takes the port-record path for the rest. Packages 3 and 5 have no second chain: the table sends the types `0 3 4 5 6 7 8 9 @ A B C F L M O Q |` (package 3) or `$ , . 0 3 4 5 6 7 8 9 @ A B C F L M O Q { }` (package 5) to the port-record path and every other type reads setting `0x2a`. Package 5's record routine is `0xffe44c30`, a 40-byte routine against the 24-byte one in o300. Established for the tables, both chains and the three port-record paths.
- **`0x000c`** (o300 `0xffe12090`, package 3 `0xffe114fc`, package 5 `0xffe3f1d4`) and **`0x000d`** (`0xffe1220c`, `0xffe11678`, `0xffe3f350`). Inputs: the code only. Board accesses: the per-port record routine (four calls for `0x000c`, two for `0x000d`). Reply: 0 then, for each port, two integers. Package 3 differs only by the record routine's address (`0xffe32174`); package 5 calls `0xffe44c30`, a routine of a different shape (40 bytes against 24 for the o300 one: it returns no record for an index outside its table). The package 5 handlers read the same record fields and `0x000d` has no `=` rule; established for all three packages, with the package 5 body read in full and the record routine described in [brick-request-handlers-detail.md](brick-request-handlers-detail.md).
- **`0x000e`** (o300 `0xffe12a4c`, package 3 `0xffe11ed8`, package 5 `0xffe3fbcc`). Inputs: the code only. Reply: 0 then one integer, the link index the request arrived on (o300 a tag byte computed by the dispatcher). Package 5 prepends a test of its type character against `,`, `}`, `.` and `$`, which sets a register, and a call of `0xffe7a2fc`; both outcomes continue at the same instruction (the `ble` after the call targets the next instruction, and `0xffe7a2fc` is `moveq #1,d0; rts`), so neither changes the reply. Established.
- **`0x000f`** (o300 `0xffe12a78`, package 3 `0xffe11f44`; absent in package 5). Reply: 0 then two integers copied from the lifecycle state words. Package 3's callee `0xffe6346c` is the paired routine of the o300 one (same 28-byte body). Package 5 has no handler: the code takes the default path. Established.

### Records and scan data

- **`0x0006`, EEPROM read** (o300 `0xffe12526`, package 3 `0xffe1198e`, package 5 `0xffe3f66e`). Inputs: at least five words (`-100` below five): word 1 and word 2 are the record index source and the area selector (`0` to `4`, otherwise the chain ends in `-104`), words 3 and 4 follow. Board accesses: o300 resolves the record number through the hook word at block+0 of the request hook block (`0x30000990`), called with the sender index and word 1, then calls the record-count and record-present routines; a missing record gives `-104` and an index past the count `-105`. Reply: status 0, the number of bytes left after the window, then a binary field holding the window (not four integers; the four words after the code are inputs; details and the area table in [brick-request-handlers-detail.md](brick-request-handlers-detail.md)). Package 3 and package 5 call no hook: they call a local routine (package 3 `0xffe10f9c`, package 5 `0xffe3ec20`) that reads the brick-type byte (RAM `0x30000a5c` in package 3, `0x30000be0` in package 5) and maps the arguments to a record number. For type `5` (`0x35`) indices 0 and 1 are returned unchanged and an index of 2 or more gives the value the tag routine returns for the first argument times 22 plus the index. For type `O` (`0x4f`) a 100-entry table gives: indices 0 and 1 unchanged, 2 and 3 `0xff`, 4 to 13 the record numbers 2 to 11, 14 and 15 `0xff`, 16 to 21 the numbers 12 to 17, 22 to 97 `0xff`, 98 and 99 the numbers 18 and 19. Every other type returns the index unchanged (the `0xff` result belongs to type `O` only). The record routines take an extra zero argument in packages 3 and 5. Package 5's map has the same jump table; it multiplies the port-tag byte directly where package 3 first calls `0xffe2f294`. Established for all three packages.
- **`0x0007`, EEPROM format** (o300 `0xffe1236a`, package 3 `0xffe117d2`, package 5 `0xffe3f4c8`). Inputs: at least two words (record index). Board accesses: as `0x0006` (hook word at block+0 in o300, the local type map in packages 3 and 5), record count and presence routines, and the log line `EEPROM not present` on a missing record. Reply: 0 then the record kind, and for kind 1 eight more integers (three area sizes, the constant 8, then four check words), for kind 2 two more (size and check word), so nine integers for kind 1 only. Same difference as `0x0006`; the word-count test is `-100` below two words in all three. Established for all three packages (package 5 and o300 read in full, layout in [brick-request-handlers-detail.md](brick-request-handlers-detail.md)).
- **`0x0010`, processor masks** (o300 `0xffe12acc`, package 3 `0xffe11f98`, package 5 `0xffe3fc66`). Inputs: none. Board accesses: o300 and package 3 read the processor count (`0xffe52414`, `0xffe66310`; `-108` when it is zero), take the mask-word count from the board descriptor (+0x88, package 3 +0x8c; 1 when zero), allocate and clear two arrays of that many words, and for each processor index i set bit (i mod d) shifted left by descriptor +0x78 (package 3 +0x64) in word i / d of the first array when routine `0xffe52424` is nonzero for i, and in the second array when `0xffe52464` is; d is 4 shifted right by the same field. Reply: 0, the word count, the processor count, then one pair of words per array entry, and both arrays are freed. Package 5 reads the count through `0xffe6e3c8`, the word count at descriptor +0x90 and the shift at +0x68, and in addition prints `REQ: slab%d %d CPUs, %d nodes` and per-node presence and enable words through the console printer when the trace flag word is set; its handler is 688 bytes against 368. Established for o300 and package 3, and for package 5 read in full: its reply has two shapes by type character (`,` `}` `.` `$` get one mask pair chosen by the port tag; every other type gets all pairs), see [brick-request-handlers-detail.md](brick-request-handlers-detail.md).
- **`0x0011`, scan record** (o300 `0xffe12c3c`, package 3 `0xffe12108`, package 5 `0xffe3ff16`). Inputs: none. Reply: 0 then a 64-byte binary field, or `-106` and the status when the scan fails. Packages 3 and 5 differ in stack offsets and in the order of two register moves; the callees (`0xffea2e28` and `0xffe9b4e0` in package 3, `0xffea4c34` and `0xffe99e40` in package 5) are the routines the pairing matches to the o300 ones. Established as a relocation of the o300 body.
### Settings and the console

- **`0x1001`, write debug switches** (o300 `0xffe12dfc`, package 3 `0xffe122ca`, package 5 `0xffe400d8`). Inputs: one integer; reply 0. Calls the setting writer with setting 3. The writer is a different routine in each of packages 3 and 5 (`0xffe6eb98`, `0xffe72de8`); both are paired with the o300 one at about half similarity, so the persistent store may differ. Established for the call shape; inferred that the stored setting is the same.
- **`0x1002`, console subchannel** (o300 `0xffe12e40`, package 3 `0xffe1230e`; no handler in package 5). Same body in package 3 apart from the callee (`0xffe34784`). Established.
- **`0x1003`, console volunteer** (o300 `0xffe12e9c`, package 3 `0xffe1236a`; none in package 5). Package 3 runs the same stream as o300; its callees `0xffe32174` and `0xffe348b0` are the paired module-record and console-owner routines. Established.
- **`0x1004` and `0x1005`, display line** (o300 `0xffe12ec2`, package 3 `0xffe12390`, package 5 `0xffe4011c`). Inputs: one text; `-100` below two words, `-102` if the word is not text. Calls the display writer (package 3 `0xffe64f4c`, package 5 `0xffe63cf8`). Established; same stream as o300 in packages 3 and 5.
- **`0x1006`, partition set** (o300 `0xffe12f20`, package 3 `0xffe123ee`, package 5 `0xffe4017a`). One integer; setting writer with setting 0xe, then the setting reader and the module-update routine (package 3 `0xffe336a4`, package 5 `0xffe46188`, the latter 320 bytes against 264). Reply 0. Established for the call shape; the package 5 update routine differs in body and was not read.
- **`0x1007`, event subchannel set** (o300 `0xffe12fd8`, package 3 `0xffe124a6`, package 5 `0xffe40232`). Inputs: one integer (`-100` below two words). Builds a tag from the sender and the value with the tag builder (o300 `0xffe349a8`, package 3 `0xffe2f2d4`, package 5 `0xffe3cab4`), stores it at +0xc of the state block (o300 `0x30005038`, package 3 `0x30005a44`) and writes setting `0x13`. Package 5 stores the tag combined with the sender shifted left 16 at +8 of its block (`0x30006d0c`), reads the argument again and, when the debug flag word is set, prints a one-line trace through the console printer before writing setting `0x13`. Reply 0. Established.
- **`0x1008`, two-bit setting set** (o300 `0xffe12f7e`, package 3 `0xffe1244c`, package 5 `0xffe401d8`). One integer; setting writer with setting `0x12`; reply 0. Same difference as `0x1001`. Established for the shape.
- **`0x1009`, panel control** (o300 `0xffe13060`, package 3 `0xffe1252e`, package 5 `0xffe4030a`). Two integers; selector 0 to 2 else `-105`; calls the indicator routines (`0xffe54414`, `0xffe543f0`, `0xffe54450` in o300; `0xffe68270`, `0xffe6824c`, `0xffe682ac` in package 3; `0xffe71518`, `0xffe714f4`, `0xffe71554` in package 5). Same instruction stream. Established.
- **`0x100a`, event subchannel clear** (o300 `0xffe131b2`, package 3 `0xffe12680`, package 5 `0xffe4045c`). No reply; calls the clearing routine (`0xffe2fb0c`, `0xffe3d4c0`; 91 percent similar to the o300 one). Established for the call shape.
- **`0x100b`, PROM version report** (o300 `0xffe131bc`, package 3 `0xffe1268a`, package 5 `0xffe40466`). Inputs: exactly three integers (`-100` otherwise): word 1 is a number printed last as `PR`, word 2 the first `%x` (major) and word 3 the second (minor); they are packed as word 2 (low byte) << 24, word 3 (low 16 bits) << 8, word 1 (low byte) and stored in runtime slot `0x2a` plus the sender's port tag (package 5: `0x1b`) (slot setter `0xffe546d4`, package 3 `0xffe68530`, package 5 `0xffe717dc`). The handler then prints a line of the form `N%d: PROM %x.%x (PR %d)` through the console printer (unconditionally in o300), and, when the tag stored at +0xc of the state block (RAM `0x30005038`; package 3 `0x30005a44`) is not -1 and whose port tag equals the sender's port tag, clears the event subchannel. No reply on success. Package 5 reads the stored tag at +8 of its block (`0x30006d0c`), passes its slot setter a constant first argument whose result is not tested, and prints the line only when the trace flag word at `0x3000139c` is set. Established for all three packages.
- **`0x100c`, per-processor setting** (o300 `0xffe132ca`, package 3 `0xffe12798`, package 5 `0xffe4057c`). Exactly two integers; calls the per-processor setter (`0xffe52680`, `0xffe6657c`, `0xffe6e6bc`; package 5's takes three arguments, the first the constant zero, and is 34 percent similar). The index argument is the port tag times 4 plus word 2, masked to a byte, and the value is word 1 masked to a byte, in all three. Established for the handlers; the package 5 setter body was not read.

### Lifecycle and board hooks

- **`0x2001`, system reset** (o300 `0xffe1335a`, package 3 `0xffe12828`, package 5 `0xffe40610`). No reply on success; `-106` and a status on failure. o300 and package 3 call the reset routine with reason 3 (`0xffe4ef74`, `0xffe63790`). Package 5 calls through the RAM hook word `0x30000900` with reason 6. Established.
- **`0x2002`, `0x2003`, `0x2004`, PCI operations A, B, C** (o300 `0xffe1336c`, `0xffe13406`, `0xffe134bc`; package 3 `0xffe1283a`, `0xffe128d8`, `0xffe12992`; package 5 `0xffe40624`, `0xffe406c2`, `0xffe4077c`). Inputs: at least three words including the code (`-100` otherwise, and `-100` when the hook is not installed for `0x2002`), word 1 and word 2 as bytes (bus and slot). Board accesses: a hook word in the request hook block: o300 offsets `0xc`, `0x10`, `0x14` of block `0x30000990`; package 3 offsets 8, `0xc`, `0x10` of block `0x300010fc`; package 5 offsets 8, `0xc`, `0x10` of block `0x30001334`. o300 calls the hook with the two bytes; packages 3 and 5 call it with a third argument (zero in package 3; a register loaded by the dispatcher prologue in package 5). `0x2002` replies with the hook result as the status; the other two reply `-106` on a nonzero result and nothing on success. Established for the hook offsets and argument counts; what each hook does is set by the board and is in [board-boot-contract.md](board-boot-contract.md).
- **`0x2005`, power down** (o300 `0xffe13570`, package 3 `0xffe12a4c`, package 5 `0xffe40836`). Calls the power-down routine with reason 3 (o300 `0xffe4c554`, package 3 `0xffe60ea4`; the latter 572 bytes against 584); `-106` on failure, nothing on success. Package 5 calls through the RAM hook word `0x3000093c` with reason 6. Established.
- **`0x2006`, third lifecycle action** (o300 `0xffe1359c`, package 3 `0xffe12a7a`, package 5 `0xffe40866`). o300 calls the lifecycle routine with 3 and replies `-106`, then the result as an integer, when it is nonzero; packages 3 and 5 reply `-106` only (the integer reply is gone) and call `0xffe61548` and `0xffe69a30`, package 5 with reason 6. Established for the reply layout; which action it is stays unknown.
- **`0x2007` and `0x2008`, expander read and write** (o300 `0xffe135de`, `0xffe136bc`; dropped in packages 3 and 5, which send them to the default path). Established for o300: the brick-type character selects the expander index: types `8`, `9` and `Q` select index 13, type `A` index 8, and every other type, including `4`, replies `-108`. `0x2007` needs exactly one word (`-100` otherwise) and `0x2008` exactly three (`-100` otherwise), then they call the checked read routine (`0xffe65cb4`) or the update routine (`0xffe65b3c`) on that expander. Packages 0 and 2 run the same code; they initialise other types, so only the types in the list above reach an expander on them.

### Inventory and restart

- **`0x4000`, inventory** (o300 `0xffe137e8`, package 3 `0xffe12aa8`, package 5 `0xffe40894`). Reply: 0 then one text field per record, each line `<n>,<kind>,...` with the record kind read from the record area: `IPMI,...`, `JEDEC,...` and `PIROM,...` forms, with `OKAY`, `DISABLED`, `NOT_PRESENT`, `ERROR,<text>`, `N/A` and `UNKNOWN` words. Package 3 is the o300 routine with the same formats (1,478 bytes against 1,422) and RAM word `0x30001114` for its hook. Package 5 drops the `JEDEC` formats (its memory text is built by `0x4004`), prints each line as `%d,%s%s,` (an extra string) and takes the record count through two routines, `0xffe7a2fc` (constant 1) and `0xffe911a4`. Established for the format strings and the handler boundaries; the per-field parsing was not followed end to end, so the meaning of each `%02X` field is inferred.
- **`0x4002`, controller reboot** (o300 `0xffe13d76`, package 3 `0xffe1306e`, package 5 `0xffe40f3e`). No reply. Each logs a line, then calls the reboot routine with a RAM word (o300 `0x30000928`) and 1. Package 3 uses `0x30001094` and the paired reboot routine `0xffe699a0`; package 5 uses `0x300010c0` and `0xffe786fc`, which the pairing does not match to the o300 routine. Established for the sequence.
