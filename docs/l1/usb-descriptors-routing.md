# Origin 300 L1 1.44.0: USB descriptors and routing

It describes tables and control flow in that image, not a verified USB enumeration on an IP45 board. It supplements the USB firmware reading. The L1 management port is distinct from the IO-8 PCI OHCI guest ports (Origin 300 User's Guide 007-4365-002, printed pages 10–12 and 67).

The body loads at `0xffe00000`; addresses here refer to the first bank.

## Descriptor tables: observed software

The standard control-request dispatcher sends an 18-byte device descriptor from `0xffe6fd20` and a 32-byte configuration tree from `0xffe6fd32` (`0xffe6f820`–`0xffe6f8e2`). The device table declares USB revision 1.00, a 64-byte control endpoint, device revision 1.00, one configuration and three device-level string indexes. The image contains vendor and product identifiers, but this note does not reproduce them. Device-level class and subclass values are all-ones while the protocol field is zero. These are declared bytes, not a fitted-controller identification.

The configuration tree has one nine-byte configuration descriptor, one nine-byte interface descriptor and two seven-byte endpoint descriptors. It declares one interface, configuration value one, alternate setting zero and two endpoints. The endpoints are **bulk OUT endpoint 1** and **bulk IN endpoint 2**, each with a 64-byte maximum packet and a zero polling interval (`0xffe6fd32`–`0xffe6fd52`). The interface class and subclass are zero and its protocol is all-ones. The configuration and interface refer to two further string indexes. The power field is zero; two feature bits are set in the configuration-attributes field, whose bit 7 is clear. A [USB-IF USB 1.1-derived configuration descriptor table](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf) says bit 7 must be set, while this image declares USB 1.00. That is a standards-version conflict, not evidence of L2 rejection. Host acceptance needs an actual enumeration transcript. None of these descriptor values proves which controller chip or revision is populated on Origin 300.

The string-descriptor selector indexes six pointers for each of two language selections and rejects an out-of-range index or unmatched language (`0xffe6f158`–`0xffe6f1f8`, table at `0xffe6fe94`). The pointer arrays are initialized in RAM from the image's data area; their contents address the descriptor objects in the selected bank. One selection corresponds to the image's language descriptor and the other is a zero-language selection. I did not establish why the language descriptor's identifier differs from the common US-English identifier, or what an L2 host accepts. The string contents are intentionally omitted.

The control dispatcher recognizes standard descriptor, address, configuration, interface, status and endpoint-halt requests (`0xffe6f158`–`0xffe6fcf8`). The exact table above gives the declared logical endpoints. It does not by itself determine controller FIFO mapping, interrupt assignment, USB transfer timing or whether the host ever configured the function.

It selects device, interface or endpoint from the setup packet's recipient bits. The device branch returns a self-powered status bit; the interface branch returns zero. The endpoint branch takes the endpoint number and direction from the request's index field, queries the configured endpoint state, and maps that state to the halt-status bit. A configured endpoint outside the accepted states returns an error rather than a fabricated status.

The second timed-out routine is the control task (`0xffe6fb6c`–`0xffe6fd1e`), created during USB initialization (`0xffe6f080`–`0xffe6f158`). It warns when its launch argument count is unexpected but continues. It opens the device's control function; an open error is reported and ends that task invocation. Otherwise it repeatedly reads eight setup bytes. A short read, reset indication or control-stage error goes through its recovery/error path, which returns to the setup-read loop rather than fabricating a successful request. For a complete setup packet, it converts the three multi-byte request fields from USB byte order for the ColdFire code, chooses the read or write request dispatcher from the direction bit, then waits for the control stage before the next setup packet (`0xffe6fbfe`–`0xffe6fd16`). The exact reset-to-reopen timing and an L2 host's retry behavior were not established. The short routine immediately before the GET_STATUS handler (`0xffe6f6c8`–`0xffe6f6ce`) returns without using the debug-label pointers passed by several nearby control branches; those labels alone do not prove that a diagnostic was logged. The selected bank has `0x70000`-shifted counterparts, but the trace above is confined to these two first-bank bodies.

## Controller probe: observed software, chip inference

The probe reads an eight-bit revision at offset `0x18` from a controller-base pointer and performs a scratch-register readback at offset `0x1b` (`0xffe70968`–`0xffe70a98`). Revision values with high nibble one proceed; three low-nibble patterns take the quiet path, while the other patterns under that high nibble produce a warning. Other high nibbles return an error. The scratch loop writes every even test value from zero through 252, reads each back, and stops on the first mismatch. Successful probing precedes the reset/control/read/write task setup (`0xffe70a98`–`0xffe70ad8`). This supports a **USS-820-family register-layout inference** from the firmware, but not an exact Agere/LSI part, revision or populated board count. An Agere-authored USS-820D revision 4 data sheet is mirrored online, but only its front page was checked: it identifies a USB device controller, not the probe offsets or the fitted IP45 chip. Those remain unverified as chip specifications.

Its external-bus capability is consistent with, but cannot prove, a discrete USB device controller on the fitted IP45 board.

## Packet framing and route ownership

The USB receive task passes its device read callback to the packet-stream parser and then delivers reconstructed packets to the ordinary L1 router (`0xffe2d3b4`–`0xffe2d49a`, `0xffe790a8`–`0xffe792a8`). The parser reads in 256-byte chunks and assembles a packet object across reads, checking a marked first segment and continuation count. The send path passes queued router packets through the corresponding stream writer (`0xffe2d65c`–`0xffe2d844`, `0xffe792a8`–`0xffe79340`). I did not decode USB wire bytes or observe an L2 host transfer.

On USB open, the task attempts a catch-all request/response registration only when a separate runtime guard is clear (`0xffe2d23e`–`0xffe2d2a4`). That registration targets a nonlocal address class and both request and response slots. The router's nonlocal catch-all branch writes the new registration without an occupied-slot check (`0xffe777ce`–`0xffe7791e`); its local-address branch does reject occupied slots (`0xffe77762`–`0xffe777ba`). Thus a successful USB registration can overwrite an existing nonlocal catch-all, while a set guard skips the attempt entirely. The USB task logs other registration failures and continues. Its first open function becomes the event destination and attempts an event registration (`0xffe2d2de`–`0xffe2d34a`). On loss, it withdraws its own catch-all route when its open-state conditions allow, closes the function and may reassign the event destination to a still-open second instance (`0xffe2d4b2`–`0xffe2d61a`). The guard is the word at offset `0x18` of the peer-link record at `0x30004d70`. Established in package 1 (1.44.0): the only store to that word is the `move.l` of 1 at `0xffe2dc3a`, inside the peer initializer, which first clears the record's `0x84` bytes (`0xffe2dc10`–`0xffe2dc1e`), fills the `0x34` bytes from offset `0x1c` with `0xff` (`0xffe2dc22`–`0xffe2dc2e`), and then sets the word, unconditionally on every path through the routine. The other routines that load the record address (entries at `0xffe2e358`, `0xffe2e5d4`, `0xffe2e894`, `0xffe2f0cc`, `0xffe2f31a`, `0xffe2f482`, `0xffe2f4ce` and `0xffe31d0c`, each read to its end, contain no store through the register that holds it; the `pea.l` at `0xffe2eab8` hands the record to the router's send routine `0xffe78e0c`, which was read and does not write offset `0x18` of its first argument either; the network-mode routine at `0xffe533f8` does not name the record or the word at all. So the guard is set once, at boot, and is never cleared. The boot task calls the initializer before it creates the USB task (`0xffe106ae` or `0xffe106b6`, then the USB creator at `0xffe106c2`), except for brick types `9` and `A`, whose jump-table slot goes straight to `0xffe106c2` ([personalities.md](personalities.md#what-the-boot-task-does-with-it)). Consequence, established for the order and inferred for the initial value (RAM is assumed zero where nothing has written it): on an Origin 300 (`4`) and on every other type in package 1 except `A`, the guard is already 1 when the USB task opens its function, so the USB task never installs a catch-all, and the catch-all is the one the peer initializer chose by brick type ([rs422-router.md](rs422-router.md)); only on a package-1 brick of type `A` does a USB open register one. Inferred: the `network usb` and `network 422` setting does not act through this guard, since its routine never names it. Whether the USB task's own per-function route (the module-record word at `+0x58`, see [power-reset-cbrick.md](power-reset-cbrick.md)) is the only way an L2 reaches the brick over USB on these types is unread. Unknown for other packages: the same read has not been made in packages 0, 2, 3 and 5.

The Origin 300-applicable L1/L2 Controller Software User's Guide 007-3938-001 lists the L1's USB slave port for communication with upstream system controllers (printed page 3) and describes `network usb`/`network 422` selection (printed page 64). The Origin 300 with NUMAlink Module User's Guide 007-4498-002 shows an L2 and USB hub in a multi-chassis/module configuration (printed pages 10–13 and 83–91). The ordinary one- or two-chassis layout does not need that module or L2 (Origin 300 User's Guide 007-4365-002, printed pages 36–41). The late L1/L2 guide 007-3938-006 describes Altix-specific service examples; this paragraph does not use it to infer Origin 300 topology. These public topology facts do not establish that a particular IP45 board has two populated USB device controllers or that an L2 was attached.
