# General-task request handlers re-read where the first comparison left them inferred

Read from the IRIX 6.5.30 `l1.bin` (L1 1.44.0). Package numbers and addresses follow [brick-request-handlers.md](brick-request-handlers.md): package 1 is the Origin 300 reference ("o300"), package 3 the `Legacy 2MB image`, package 5 the `2MB image`. Addresses are first-bank body addresses. Packages 0 and 2 run the o300 instruction stream in every handler, so an entry that names o300 holds for them with the moved RAM words of that note. Every handler below was disassembled from entry to its exit in the package named, and each callee named by address was disassembled as far as the entry says.

The notes in [brick-request-handlers.md](brick-request-handlers.md) and [personalities.md](personalities.md) graded several package 5 handlers inferred because their bodies are restructured. They are read here to the end. Where this note contradicts them, the entry says so and the older text is corrected.

## What the package 5 dispatcher sets up for every handler

Established, from the dispatcher at `0xffe3eecc` read to the jump on the code (`0xffe3f01c`).

- The frame is in `a2`. The sender word at +0x1c gives register `d5`: `0xff` when its top bit is set, else bits 11 to 5. The routine at `0xffe3c8a8` turns `d5` into a one-byte port tag (it calls the type accessor `0xffe79e60` and passes both bytes to `0xffe3c2f8`); the tag is kept in `d2`. The type character is kept in `d3`.
- Runtime slot `0x1b` plus the port tag is read with `0xffe71914` into `a3`. o300 and package 3 read slot `0x2a` plus the tag (`0xffe547d0`, `0xffe6862c`), so the "slot `0x2a`" of the identity entry in [brick-request-handlers.md](brick-request-handlers.md) is the o300 and package 3 slot only.
- `d4` is zero in this build: the dispatcher computes it from frame byte +0x17 only when `0xffe7a2fc` returns more than 1, and that routine is `moveq #1,d0; rts`. The handlers below that pass `d4` as an argument therefore pass zero.
- The word at `0x3000139c` is the trace flag; a handler that prints a trace tests it with `tst.l (a5)`.

## Records, scan data and the memory-record table

- **Per-port record routine** (o300 `0xffe31f00`, package 3 `0xffe32174`, package 5 `0xffe44c30`). One argument, the port record index. o300 and package 3 return the table pointer in a RAM word (`0x30000aa4`, `0x30001248`) plus 0x70 times the index, with no range test. Package 5 returns zero when the index is negative or not below the count held at +4 of its table header (`0x30001370`, pointer at +0, count at +4); otherwise the pointer plus 0x70 times the index. Established, all three bodies read in full. The two package 5 attached-port handlers below do not test for the null return.
- **`0x000c`, attached ports 1 to 4, package 5** (`0xffe3f1d4`). Inputs: none. Board accesses: the record routine for indexes 1, 2, 3 and 4 in that order. Reply: status 0, then for each record two integers: the word at +8 shifted left 6 ORed with the word at +0xc, then the word at +0x10. The second integer is the character `#` (`0x23`) in place of a `=` (`0x3d`) when the low byte of register `a3`, the runtime slot value the dispatcher read, is zero. Same instruction pattern as the o300 and package 3 handlers except the record routine. Established (read in full); the earlier grade for package 5 was inferred.
- **`0x000d`, attached ports 5 and 10, package 5** (`0xffe3f350`). As `0x000c` with two calls, indexes 5 and 10, and no `=` to `#` rule: the second integer is always the word at +0x10. Same index pair in o300 (`0xffe1220c`) and package 3 (`0xffe11678`). Established (read in full).
- **`0x0006`, record area read, all packages** (o300 `0xffe12526`, package 3 `0xffe1198e`, package 5 `0xffe3f66e`). Inputs: at least five words including the code (`-100` otherwise): word 1 is the record number source, word 2 the area (0 to 4), word 3 the byte offset, word 4 the byte count. Board accesses: the record number comes from the request hook word at block +0 in o300 (called with the sender index and word 1), and from the local type map in packages 3 and 5 (`0xffe10f9c`, `0xffe3ec20`; the same 100-entry jump table in both, read for both here. Type `O`: indexes 0 and 1 unchanged, 4 to 13 give 2 to 11, 16 to 21 give 12 to 17, 98 and 99 give 18 and 19, every other index (2, 3, 14, 15, 22 to 97, and 100 or more) gives `0xff`. Type `5`: indexes 0 and 1 unchanged, 2 and above give the port-tag value times 22 plus the index (package 3 takes the tag from `0xffe2f294`, package 5 uses the byte the dispatcher derived directly). Every other type returns the index unchanged, not `0xff`). The record table is read through `0xffe6aed0` and `0xffe6aee8` in o300 (`0xffe911a4` and `0xffe911c8` in package 5, group 0): a record absent gives `-104`, a record number not below the count `-105`. Area 0 needs record kind 1 and returns the 8 bytes inline at record +8; area 1 needs kind 1, returns the buffer at +0x18 with size +0x14 after checking the word at +0x10 is zero; area 2 the buffer at +0x24, size +0x20, check +0x1c; area 3 the buffer at +0x3c, size +0x38, check +0x34; area 4 needs kind 2 and returns the buffer at +0xc, size +8, check +4. A wrong kind gives `-104`, a nonzero check word `-107`, an area above 4 `-105`. An offset not below the size gives `-105`. Reply: status 0, one integer (the bytes left after the window, zero when the window was cut at the end of the area), then, when the window is not empty, one binary field of the window. Established for o300 and package 5 (both read in full and the same apart from the lookups); package 3 has the same area offsets (`0x14`, `0x20`, `0x38`, `8`) and checks. **The reply is not four integers**: the four words after the code are inputs. The `four ints` in the earlier entry and in [request-codes.tsv](request-codes.tsv) is corrected here.
- **`0x0007`, record format, package 5** (`0xffe3f4c8`). Inputs: at least two words including the code (`-100` otherwise); word 1 is the record number source. Board accesses: the local type map with the sender's port tag (`0xffe3ec20`), then the record table group 0 through `0xffe911a4` and `0xffe911c8`; absent gives `-104` (and logs `EEPROM not present`), not below the count `-105`. Reply: status 0, then the record kind (word at +0). For kind 1 the reply continues with the words at +0x14, +0x20, +0x38, the constant 8, then +0x10, +0x1c, +0x34 and +4, nine integers in all counting the kind; for kind 2 with the words at +8 and +4, three integers in all; any other kind ends after the kind. These are the area sizes (areas 1 to 3, then area 0's 8) followed by the per-area check words of `0x0006`. o300 (`0xffe1236a`) has the same reply layout, read in full here. Established. The older text that described nine integers for every kind is corrected.
- **`0x0010`, processor masks, package 5** (`0xffe3fc66`). Inputs: none. Board accesses: the processor count from `0xffe6e3c8` (zero gives `-108`), the descriptor at `0x30003404` (word at +0x90 is the mask-word count, 1 when zero; word at +0x68 is the shift `s`), two word arrays of that many words cleared with the allocator `0xffe759ec` and the clearer `0xffeae414`, and for each processor `i` below the count the predicates `0xffe6e3d8(0,i)` and `0xffe6e418(0,i)`; with `q = 4 >> s`, a true predicate sets bit `(i mod q) << s` of word `i / q` in the first (`0xffe6e3d8`) or second (`0xffe6e418`) array. Reply, by type character: for `,` `}` `.` and `$` the reply is status 0, the integer 1, the processor count divided by the word count, then the two words at the port tag index of each array; for every other type (the compare against the constant-one routine `0xffe7a2fc` always takes this path) status 0, the word count, the processor count, then one pair of words per array entry. When the trace flag word is set it first prints `REQ: slab%d %d CPUs, %d nodes` and one `REQ: slab%d N%d  pres=0x%04x, ena=0x%04x` line per entry (the `SL REQ` forms for the first reply shape). Both arrays are freed. Established (read in full, both reply shapes). The earlier grade for package 5 was inferred.

## Settings and the console

- **`0x100b`, PROM version report, package 5** (`0xffe40466`). Inputs: exactly four words including the code (`-100` otherwise). Word 1 low byte, word 2 low byte and word 3 low 16 bits pack as `word2 << 24 | word3 << 8 | word1` in the same layout as o300. The slot setter is `0xffe717dc(0, 0x1b + port tag, packed)`; the dispatcher already passed three arguments and its result is not tested. **The line `N%d: PROM %x.%x (PR %d)` is printed only when the trace flag word is set** (package 3 and o300 print it unconditionally). It prints the port tag, the top byte, the middle 16 bits and the low byte of the packed value. Then, when the word at +8 of `0x30006d0c` is not -1 and the port tag of that value (`0xffe3c8a8`) equals the sender's port tag, it calls the event subchannel clear routine `0xffe3d4c0`. No reply on success. Established. The note that the slot setter takes an extra argument whose result is tested is wrong; the extra argument is the constant zero and the result is dropped.
- **`0x100c`, per-processor setting, package 5** (`0xffe4057c`). Inputs: exactly three words including the code (`-100` otherwise). Word 2 is read as a full word, word 1 as its low byte. Calls `0xffe6e6bc(0, (port tag * 4 + word2) & 0xff, word1 & 0xff)`; o300 (`0xffe132ca`) and package 3 (`0xffe12798`) call their setters with the last two of those arguments only. No reply on success. Established for the handler; the setter body was not read.
- **`0x0002` and `0x0003`, package 5** (`0xffe3f160`). The runtime slot behind the `=` to `#` rule is `0x1b` plus the port tag in this package; see the setup section. The rest of the entry in [brick-request-handlers.md](brick-request-handlers.md) stands.

## Lifecycle

- **`0x4002`, controller reboot, package 5** (`0xffe40f3e`). No reply. Logs the line `L1REQ_REBOOT requested...` with `0xffe74520`, then calls the reboot routine `0xffe786fc` with the first argument 1 and the second the word at `0x300010c0`. o300 pushes the same two words in the same order (`0xffe56654(1, [0x30000928])`). Established.

## Request codes that only packages 3 and 5 have

- **`0x3001`, memory record signature, package 3** (`0xffe13108`). Inputs: at least three words including the code (`-100` otherwise). Only the types `5`, `@`, `O`, `B`, `F`, `L`, `M` and `|` pass; every other type, and an empty hook word at `0x30001114`, give `-101`. Word 1 and word 2 are read as full words and passed as `hook(0, word1, word2, 0)`. The status is 0 when the result is positive, `-106` otherwise, then the result as an integer. Established. The hook at `0xffe3b690` was read as follows: it takes the selector from its second argument and for selector 0 reports status text, for 1, 2 and 4 walks the memory-record table (`0xffe90bf0`, `0xffe90c14`) and edits each record of kind 2 whose size is at least 0xa0 (`-2` below that), and returns the selector minus 4 for every other selector (3, 5 and above), which the handler turns into `-106` for 3 and into status 0 with integer 1 for 5. For selectors 1, 2 and 4 it first stamps revision 2 at record +0x80, the bytes 3, 4 at +0x81, +0x82, 8 at +0x87, 1 at +0x90, `0xc1` at +0x92 and clears +0x93 to +0x96, then: selector 1 stores the 32-bit value (word 2) big-endian at +0x83 to +0x86 and eight check bytes at +0x88 to +0x8f, selector 2 clears those twelve bytes, selector 4 stores the low byte of word 2 at +0x91. Last it stores the negated byte sum of the 0x17 bytes from +0x80 at +0x97 and writes 0x18 bytes from +0x80 back through `0xffe91bcc`; a failed write returns `-4`. Selector 0 was not read past the type test. Established for the stamp, the three edits and the write-back; the check-byte formula is the one given for package 5 below.
- **`0x3001`, memory record signature, package 5** (`0xffe40fd8`). Inputs: at least three words including the code (`-100` otherwise). Types accepted: `5`, `@`, `O`, `B`, `F`, `L`, `M`, `$`, `,`, `}`, `.` and `{`; every other type gives `-101`. Word 1 (the selector) and word 2 (the value) are read as full words. Unlike package 3 there is no hook word: the handler calls the routine at `0xffe7f3b8` directly with `(0, selector, value, 0)`. The status is 0 when the result is zero or positive (package 3 needs a positive result), `-106` when negative, then the result as an integer. Established.
- **The record routine behind `0x3001` in package 5** (`0xffe7f3b8`, 2,740 bytes, read in full). Arguments: a record pointer, the selector, the value, and a text buffer. Jump table of six entries at `0xffe7f3e8`: selector 0 to the status text, selectors 1 to 4 to one record walk, selector 5 to the usage text; any selector above 5 returns itself with no other effect (the handler then reports it as the result integer with status 0). The record table is group 0 of `0xffe911a4`; each record is 0x78 bytes: kind at +0, error word at +4, size at +8, data pointer at +0xc. Established.
  - **Selectors 1 to 4, common walk.** For each record whose presence test `0xffe911c8` passes and whose kind is 2 and error word zero: a size below 0x100 returns `-2`, a first data byte above 0x80 returns `-3`. Counts the record. Data byte +0x80 selects what is cleared (revision 1 and 2: 0x16 bytes from +0x92; revision 3: 0x28 bytes from +0x80 only when its checksum test fails; others: 0x28 bytes from +0x80), then stamps +0x80 = 3, +0x81 = 5, +0x82 = 4, +0x87 = 8, +0x90 = 1, +0x92, +0x97 and +0x9c = 4, +0xa1 = `0xc1` and clears +0xa2 to +0xa6. After the selector's edit it stores the negated byte sum of the 0x27 bytes from +0x80 at +0xa7 and writes 0x28 bytes from +0x80 back through `0xffe92284`; a failed write returns `-4`. A successful walk returns the count of records visited. Established.
  - **Selector 1.** Stores the value big-endian at +0x83 to +0x86 and eight check bytes at +0x88 to +0x8f. With `t0..t3` the value bytes, high first, and `s0..s3` the data bytes at +0x5f to +0x62: +0x88 is `~((t0 >> 4) | (s0 << 4))`, +0x89 is `(s0 >> 4) | (t0 << 4)`, and so on in pairs for `t1,s1`, `t2,s2`, `t3,s3` (the even byte complemented, the odd byte not). Established.
  - **Selector 2.** Clears +0x83 to +0x86 and +0x88 to +0x8f. Established.
  - **Selector 3.** Stores the low byte of the value at +0x91. Established (package 3 does this under selector 4).
  - **Selector 4.** Writes nothing back for a record unless `0xffe6a4c0(group)` is nonzero and the 0x28-byte sum from +0x80, taken after the common stamping, is zero (a further test that applies only when the group count exceeds 1 never runs, because the count is the constant 1). Adds 1 to the big-endian counter at +0x93 to +0x96, reads the clock with `0xffe7a804` and stores its 32-bit result big-endian at +0x98 to +0x9b. Established; what the counter counts is unknown.
  - **Selector 0, status text, written to the buffer.** In order: a type outside the `0x3001` list writes `N/A      --`; revision at +0x80 above 3 `REVERR   --`; a failed checksum test (0x18 bytes for revision 2 and below, 0x28 for revision 3) `CSUMERR  --`; all four bytes +0x83 to +0x86 zero `UNSIGNED`; the eight check bytes differing from the selector 1 formula applied to the stored value and the serial bytes `FORGERY `; otherwise the stored value converted by `0xffe7e708` and formatted `%m/%d/%y` through `0xffe7dbdc`, which makes the value a time stamp. Then, for revision 2, a space and the byte at +0x91 as `%02x`, and for any other revision ` 00`. Established.
  - **Selector 5, usage text.** A type outside the list writes `N/A        N/A       N/A      \n`; a first data byte above 0x80 `DIMM manufacturer uses > 128 locations\n`; a nonzero 0x28-byte sum `checksum error - act: %d, exp %d\n` (the printed actual value is the byte at +0xa8, the expected value the negated 0x27-byte sum; the writer puts its checksum at +0xa7); otherwise `%8d.%1d ` with the counter divided by 10 and its remainder, then the time stamp from +0x98 to +0x9b as `%m/%d/%y`, or `N/A` when it is zero. Established.
  - The record layout, and the time-stamp reading of +0x83 to +0x86, are read from this one routine and its caller `0x4004`; what the fields are called by the maker is unknown.
- **`0x3002`, FRU scan, package 5** (`0xffe41132`). Inputs: none read. Calls the hook word `0x300013cc` (installed with `0xffe2d460`) with the frame's word at +0x1c, which is the sender word, not the first request argument as the earlier entry says, and replies the result as the status. Established for the call. The hook (read in full) uses the state block at `0x30007050`: if it has already run (word +0xc nonzero) it returns -1; it allocates a group array (`0x18` bytes per group, group count from the constant-one routine), for type `5` a `0xd8` byte sub-entry block and for type `O` a `0x6c` byte one (other types allocate none), calls `0xffe48de4` for those two, reads the clock into +0xc, then calls, with the group index and the sub-entry index, the function pointer stored at +0x68 of each 0x6c-byte sub-entry that has one and sums the results; it returns 0 when state word +8 is zero at the end and -1 otherwise. What the sub-entries scan is unknown.
- **`0x3003`, FRU scan reset, package 5** (`0xffe4115a`). Replies status 0 first, then calls the hook word `0x300013c8` (installed with `0xffe2d2c8`) with no arguments and ignores the result. The hook frees the buffers held at +0x1c to +0x30 of the state block `0x30007050` and in every sub-entry, clears the group array, sets the state word +8 to 1, clears +0xc, and frees and clears the three buffers at `0x300011ac`, `0x300011b0`, `0x300011b4`. Established (read in full). Undoes `0x3002`.
- **`0x3004`, FRU report, package 5** (`0xffe4117a`). Replies status 0 first, then calls the hook word `0x300013dc` (installed with `0xffe2d730`) with the current field count and the reply buffer, and takes the hook's result as the new field count. The hook, when the pointer at `0x300011ac` is set, calls `0xffe82ca4` with the count, the buffer and two words from that block (+0 and +0xc) and returns its result, else it returns the count unchanged. Established for the call shape; `0xffe82ca4` was not read.
- **`0x4004`, DIMM text, package 5** (`0xffe40c2a`). Inputs: none. Board accesses: group 0 of the memory-record table (`0xffe911a4`, count at its return; group count from the constant-one routine), per record `0xffe91314` for a name string and `0xffe911c8` for presence. For each record of kind 2 it builds one text field and adds it to the reply with `0xffe47078`; records of any other kind produce no field. The text is `<index>,<name>,` and then one of `JEDEC,NOT_PRESENT` (record absent), `JEDEC,ERROR,<text from 0xffe91200 of the error word at +4>` (error word nonzero), or `JEDEC,OKAY,` followed by, from the data buffer at +0xc: the bytes at +0x40 to +0x47 as `%02X`, the bytes at +0x5f to +0x62 as `%02X` (24 hex digits in a run), a comma, the 18 bytes at +0x49 to +0x5a copied as characters when the class test `0xffeae7c0` (mask `0x57`) passes and as spaces otherwise, a comma, the bytes at +0x5b and +0x5c (as characters when the byte at +0x40 is not a comma and both pass the class test, otherwise as `%02X%02X`), a comma, the byte at +9 as `%3d.%-2d,` (high nibble, low nibble), and then the status text of selector 0 of the `0x3001` routine for that record. Established for the text layout. Hint, not confirmed in an image: those offsets match the manufacturer, part number, revision, serial number and cycle time bytes of the public serial-presence-detect layout for DDR memory modules (JEDEC Standard No. 21-C).
