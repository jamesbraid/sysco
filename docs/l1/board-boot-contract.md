# Origin 300 L1 1.44.0: what the processor and board must provide

Everything here is read from L1 1.44.0, package 1 (`Fuel/PE/O300 1MB image`, composite offset `0xefdd0`, body sha256 `9db44f3bb06ec90475035781766e1ca7e924f15a0ed215cf855c1f491275fdd1`, loaded at `0xffe00000`). Addresses are in the first of the two program copies; the second is `0x70000` higher. The note describes what the software does, so that a machine hosting the unmodified image can be judged from its own register-access log, with no listing needed. Register meanings come from the MCF5206e User's Manual, revision 1 (chapter 8 for the system integration module, chapter 9 for chip selects, chapter 10 for timers and chapter 11 for the on-chip UARTs); the manual says what a register does, the image says what the software writes.

Grades follow [AGENTS.md](../../AGENTS.md): established means the whole routine or table was read and the statement follows; inferred means a reasoned reading, with the reasoning given; unknown names what would settle it.

## Reset entry and early initialisation order

- **Vector table at body offset 0 (established).** Word 0 is the initial stack pointer `0x301017fc`, word 1 the reset entry `0xffe00400`. The other 254 words point into a run of 254 `bsr.w` instructions at `0xffe0042c`-`0xffe00820`, one per vector, all branching to one routine at `0xffe00824`. That routine derives a vector number from the return address and ends in a `halt` word (`0x4ac8` at `0xffe0083e`). So an exception taken before the real vector table is installed stops the processor.
- **Reset entry, in order (established, `0xffe00400`-`0xffe0042c`).** (1) Write `0x30100001` to the RAM base control register (`RAMBAR`, `movec` register `0xc04`), putting 8 KB of on-chip SRAM at `0x30100000`. (2) Set the stack pointer to `0x30101800` and the status register to `0x2700` (supervisor, interrupts masked). (3) Call the loader at `0xffe00a80` with the module base `0x10000000` as its first argument. The loader never writes `MBAR`; it reads the reset-status byte at `0x10000040` through that address while `MBAR` is still unwritten, so on silicon that read is an external bus cycle. A machine that makes `MBAR` valid at reset reads a real reset-status register there instead; the two agree after power-on and after a watchdog reset (see the watchdog entry below).
- **Retained boot record (established, `0xffe00a80`-`0xffe00b26`).** A 0x4d8-byte record lives at `0x30101990`, marked by the word `0xa1b2c3d4`. If the marker is absent the loader zeroes the record, writes the marker, a version word 1 and the length `0x4d8`. It stores the `MBAR` argument at record offset 8. Then it reads the reset-status byte: when bit 5 (watchdog reset) is clear it clears the record's image-pointer word (offset `0x10`); when set it keeps a previously recorded image whose address lies in `0xffe00000`-`0xffefffff`, word aligned, and whose metadata checks pass. With no recorded image it scans the table below.
- **Image choice (established, `0xffe00994`-`0xffe00a7c`).** The pointer table starts at `0xffe01000` and ends at the first all-ones word (here the third word) or at `0xfff00000`. The loader walks the table backwards. For each entry it masks the low byte, checks alignment and range, and sums the 48-byte metadata record the entry points to; a nonzero 32-bit sum rejects the entry. A set low bit in the table word forces that entry to be used at once. Otherwise it compares the build-stamp strings of the candidates byte by byte as signed characters and keeps the one that compares greater; equal stamps keep the one met first, which is the later table entry. In this package both copies carry the stamp `20060717182038`, so the copy at `0xffe80000` (second table word) wins unless the retained record names the other.
- **Handing over (established, `0xffe00840`-`0xffe008aa`).** The loader copies 1 KB from just after the chosen entry's first pointer to `0x30100000`, loads that address into `VBR`, and calls the entry address stored in the record (`0xffe10b02` or `0xffe80b02`). If it returns, or if no candidate passed, execution reaches a `halt` word (`0xffe00b1c`).
- **Program entry (established, `0xffe10b02`-`0xffe10ba4`).** In order: `RAMBAR` again, stack `0x30101800`, status register `0x2700`, `MBAR` `0x10000001` (base `0x10000000`, valid), then the board set-up routine (`0xffe54b0c`) with the base as its argument, `VBR` `0x30100000`, a cache invalidate (`CACR` `0x01000000`) and enable (`CACR` `0x80000000`), and the start of the real-time kernel (`0xffe4264c`) with its heap beginning at `0x300061d8 + 1000`.
- **Board set-up order (established, `0xffe54b0c`-`0xffe54bde`).** `0xffe54960`: `SIMR` `0xc0`, `IMR` `0xfffe`, the interrupt control registers, `PAR` `0x0071`, byte at `MBAR+7` cleared. `0xffe549d8`: chip selects (next section). Parallel-port data direction cleared. Vectors copied from flash `0xffe10004` (1 KB, skipping the stack word) to `0x30100000`. `0x30000c38`-`0x300061d8` zeroed. `0xc38` bytes of initialised data copied from flash `0xffe7f0e4` to `0x30000000`. Finally the timer routine is run from its RAM copy at `0x30000260` (next sections).
- **Kernel start order (established, `0xffe4264c`, `0xffe10570`).** The kernel initialises its tables, starts the main task, and that task (`0xffe10570`) in order: prints the banner, registers the board (`0xffe55254`), runs `0xffe55198` (which first opens the four-channel UART through `0xffe54be0`, then probes the USB controllers), initialises the parallel-port scan interface (`0xffe71d90`), reads settings 1 and 2 to form the rack and bay identity, starts the request router and the general (task 6), command (task 3), loopback (task 18), flash (task 16), peer-link, management (task 2) and node-link (task 5) services, then selects the board personality (see [board identity](board-records.md)).

## Chip selects, DRAM and the memory map

The set-up routine at `0xffe549d8` (established) writes the following, as 16-bit address (`CSAR`), 32-bit mask (`CSMR`) and 16-bit control (`CSCR`) triples at `MBAR+0x64`/`+0x68`/`+0x6e` for `CS0` and a stride of 12 bytes after that. The table is this routine's complete write set.

| Select | Base | Mask register value | Control | Read as | Grade |
|---|---|---|---|---|---|
| `CS0` | `0xffe00000` | `0x001f0000` (2 MB), rewritten `0x000f0000` (1 MB) when the first 1024 words at `+0` equal the first 1024 words at `+1 MB` | `0x1183` | 16-bit port, internal acknowledge, 4 wait states | established |
| `CS1` | `0x20000000` | `0` (64 KB window) | `0x1143` | 8-bit port | established |
| `CS2` | `0x30000000` | `0x00070000` (512 KB), rewritten `0x00010000` (128 KB) when the probe below fails | `0x0983` | 16-bit port, 2 wait states | established |
| `CS3` | `0x40000000` | `0` | `0x0953` | 8-bit port; only when a USB controller is counted (`0xffe55198`) | established |
| `CS4` | `0x50000000` | `0` | `0x095f` | 8-bit port, quad UART; not programmed for brick letter `G` | established |
| `CS5` | `0x60000000` | `0` | `0x0953` or `0x095f` | second USB controller, or second quad UART for letter `6` | established |
| `CS6`, `CS7` | cleared (`0xffe549d8` loop) | | | `PAR` bits 3:0 `0001` give these pins to the write enables | established |

- **Size probes (established).** Flash: the routine compares 1024 words at `0xffe00000` with the same number at `0xfff00000`; equal means a 1 MB part (the upper half mirrors the lower). RAM: it saves the word at `CS2` base `+0x1fffc`, clears it, writes all ones at `+0x7fffc`, and if the cleared word is still zero it takes 512 KB (end `0x30080000`), otherwise it cuts the mask to 128 KB (end `0x30020000`) and the size/end are stored at `0x300002ec`/`0x300002f0`. A board with 512 KB of RAM at `CS2` takes the large branch; one with a 128 KB window that aliases takes the small one.
- **DRAM and default memory (established).** Every DRAM controller register is cleared and `DMCR` is cleared: no DRAM and no default-memory responder exist. The program's own address validator accepts only `0xffexxxxx`, `0x200xxxxx`, `0x300xxxxx` and `0x301xxxxx` (`0xffe56388`).
- **`MBAR`/`RAMBAR` after set-up (established).** `MBAR+0x03` (`SIMR`) `0xc0`; `RAMBAR` `0x30100001`; the stack and the boot record occupy `0x30100000`-`0x30101e68`, inside the 8 KB SRAM.

Flash carries two copies of the program (`0xffe10000` and `0xffe80000`), a pointer table at `0xffe01000` and the loader at the base (established). The composite package table is in [package-container.md](package-container.md).

## Processor clock (inferred)

The code never reads a clock; four constants agree on 48 MHz. (1) The on-chip UART divisor routine takes a software clock constant of 12,000,000 for the quad UART and 48,000,000 for an on-chip channel (`0xffe62fd4`, constant `0x02dc6c00` = 48,000,000 divided by 16 times the baud rate). (2) Timer 1 reference `0x752f` (30,000 counts) with a divide-by-16 prescale gives a 100 Hz tick at 48 MHz. (3) The M-Bus divider `0x13` is divide-by-480, 100 kHz at 48 MHz. (4) Timer 2 with reference 1 on the undivided clock toggles its output every two clocks, 12 MHz at 48 MHz, equal to the quad UART's assumed input clock. A different clock keeps the image running but changes the tick rate, baud rates, M-Bus speed and watchdog period together. Unknown: the fitted oscillator; no image states it.

## Interrupts (established for the writes, inferred where noted)

`0xffe54960` writes the interrupt control registers `ICR1`-`ICR15` at `MBAR+0x14`-`+0x22`, and `PAR` selects encoded interrupt-level inputs (bit 6 set), so all seven external levels are available:

| Register | Byte | Meaning | Handler (vector) |
|---|---|---|---|
| `ICR1`-`ICR7` | `84 88 80 90 80 98 9c` | external levels 1 to 7 autovectored (bit 7 set); the level fields are reserved for external sources | vector table entries 25 to 31 |
| `ICR8` (watchdog) | `1d` | level 7, priority 1 | none installed; the watchdog is set to reset, not interrupt |
| `ICR9` (timer 1) | `94` | level 5 autovector | `0xffe10ff4` (vector 29) |
| `ICR10` (timer 2) | `80` | level 0, never interrupts | none |
| `ICR11` (M-Bus) | `99` | level 6, priority 1 | M-Bus completion handler |
| `ICR12` (UART 1) | `1a` | level 6, priority 2, vectored (`UIVR` `0x42`) | on-chip UART 1 handler |
| `ICR13` (UART 2) | `00` | not used | none |
| `ICR14`, `ICR15` (DMA) | `09`, `0a` | level 2 | none; no access to the DMA registers occurs anywhere |

Devices behind the external levels: the quad UART at `CS4` takes level 4 (the driver installs `0xffe63d44` in RAM vector 28 and unmasks `IMR` bit 4, `0xffe636b0`); a second quad UART at `CS5` for letter `6` takes level 3 (vector 27, `IMR` bit 3); USB slot 0 at `CS3` and slot 1 at `CS5` take the level passed to the USB driver at start-up (2 and 3 respectively, `0xffe55198`; `ICR3` is rewritten `0x8c` for slot 1, `0xffe55212`). Which line the fitted board routes to which external pin is inferred from those software levels; no image names a board net. Levels 1 and 7 have vectors but no handler install was found; unknown which parts, if any, drive them.

## Instruction set: the MAC module is never used (established)

The MCF5206e has a MAC module (manual section 1.3.2) and the image never uses one. The retained linear listing contains 20 words whose first nibble is `0xa`, all inside the 256-entry CRC table at `0xffe62a4c`-`0xffe62c4c` (the table is data); none of them decodes as an instruction in the listing. The only `movec` forms the image executes address `RAMBAR` (`0xc04`), `MBAR` (`0xc0f`), `VBR` (`0x801`) and `CACR` (`0x002`). The image uses the ISA_A integer set (including the 32-bit divides, 376 sites in the body, and `extb`), `movec`, `halt`, `rte` and `sr` access in supervisor mode.

## Idle loop and `STOP` (established)

No `stop` word (`0x4e72`) exists at any even offset in the 982,368-byte body. The scheduler's idle path (`0xffe41336`-`0xffe41356`) lowers the interrupt mask in `sr` to the level held at `0x30003e4c`, then spins reading two RAM words (`0x30003d48`, `0x30003d24`) until one is nonzero. Timer 1's level-5 tick (and any other interrupt that readies a task) breaks the spin. The CPU is therefore always running, with a 100 Hz tick at the inferred clock; the image never idles in a `stop`, and `halt` is reached only on the failure paths named above and in the restart entry below.

## Watchdog, reset cause and restart

- **Arming (established, `0xffe562d4`, called from the main task at `0xffe1076a`).** When the RAM flag at `0x3000030c` is nonzero (its initial value in the image is 1; the routine clears it), the routine writes `SYPCR` (`MBAR+0x41`) `0xfe`: software watchdog on, reset (not interrupt) on timeout, prescaler on, both timing bits set, bus monitor on with timing `10`. The register is write-once. It then writes `SWIVR` (`+0x42`) `0` and services with `0x55` then `0xaa` at `SWSR` (`+0x43`). At the inferred 48 MHz clock the period is 2^24 system clocks = 0.35 s (manual table 8-6); a 256-clock bus monitor applies to external cycles.
- **Servicing (established).** `0xffe5630c` loops writing the `0x55`, `0xaa` pair every 20 kernel ticks; the main task's start-up wait and several other task loops write the pair as well (for example `0xffe107ac`). `PAR` bit 7 is set only for the RTS2/RSTO pulse during the timer routine (`0xffe7f344`), so the `RSTO` output is not asserted by the image on a watchdog reset.
- **Reset cause (established, `0xffe565b4`-`0xffe56652`).** The kernel reads `RSR` (`MBAR+0x40`), records bit 5 as "the last reset was a watchdog reset" at record offset `0x1c`, and writes the value back to clear it. If the bit was set and the record's saved word is zero, it calls a routine (`0xffe563c0`) that follows saved frame pointers and stores a backtrace of return addresses, with small negative markers, into the record from offset `0x28`. The routine reads memory only and touches no device (established); that the stored trace is for later diagnosis is inferred.
- **Restart behind `reboot_l1` (established, request `0x4002` at `0xffe13d76`, restart routine `0xffe56654`).** The request logs the line "controller reboot" and calls the restart routine with reason 1 and the requested image pointer (the RAM word `0x30000928`). The routine calls `0xffe6d38c` (interrupt shutdown for the on-chip peripherals), makes sure the boot record is valid, stores the reason word at `0x30101800`, arms the watchdog if still disarmed (`0xffe562d4`), and checks `SYPCR` bit 7. If the watchdog is not enabled it executes `halt` (`0xffe566bc`). Otherwise, for reason 1, it stores the image pointer and its complement over the first two words of the vector copies at `0x30100400` and `0x30100000` and into the record's image-pointer word (offset `0x18`), masks all interrupts (`0xffe411ca` with `0x700`) and spins (`0xffe5670c`). With nothing servicing it the watchdog expires, the chip resets, `RSR` bit 5 reads set, and the loader above takes the recorded image. Established: that chain of stores and loop. Inferred: that the stored vector words only make the stale RAM vectors unusable; their purpose is not stated by the code. A different reason value takes the backtrace branch instead (`0xffe566e6`), then returns for the value `0x3e6` (`0xffe5671c`, a request to record a trace) and spins for any other value. A host that keeps the watchdog from expiring leaves `reboot_l1` hanging with interrupts masked.
- **Reset-status read at the loader (established for the image side, hint for the chip side).** The loader passes `0x10000000` as the base of its reset-status read (`0xffe0041e`, test at `0xffe00ac8`), but nothing before that read writes `MBAR`: the only `movec` in the loader (`0xffe0040c`) loads `RAMBAR` (register `0xc04`), and the first write of `MBAR` (register `0xc0f`, value `0x10000001`) is in the kernel entry at `0xffe10b2e` (second copy `0xffe80b2e`), after the loader has chosen its copy. The public MCF5206e user's manual (revision 1, sections 8.2 and 9.3.2, and the register summary in chapter 9) says that system reset clears the `MBAR` valid bit, that an access is claimed by an internal peripheral only while that bit is set, that `CSAR0` and `CSMR0` reset to zero, and that `CS0` is asserted for every access except CPU-space and internal-peripheral accesses until `CSMR0` is first written. The loader never writes `CSMR0` before the read (its chip-select set-up is in the kernel), so the read at `0x10000040` is an external byte read answered through `CS0`, that is, by the boot flash. The flash is the only device behind `CS0`, and the flash image holds `0xff` at offset `0x40` (body offset `0x40` of package 1, read from the image), so bit 5 reads set. Section 6.11 of the same manual says a software watchdog timeout acts as a normal reset that resets the internal registers, so the same decode applies after the watchdog restart that sets the retained-record path (see the restart entry above): bit 5 is read from flash, not from `RSR`, and reads set because the flash byte is `0xff`. Consequence: on the fitted board the loader's test sees a watchdog reset on every start, hard or watchdog, and the retained record's own marker and checks decide whether a recorded image is kept (the `0xa1b2c3d4` test above). Inferred, not shown in an image: that the flash chip decodes the low address bits of the bus directly, so the read lands on offset `0x40` of the flash array; the offset-to-array mapping rests on the board wiring, which no image states. A read that returns the flash byte at offset `0x40`, or any value with bit 5 set, gives the loader's behaviour; a read that returns the `RSR` reset value (`0x80`, bit 5 clear) takes the other arm and clears the retained image pointer, which also reaches the same table scan on a cold start but would drop a recorded image after a `reboot_l1`.
- **Source for the decode (hint).** The MAME model of this chip (`src/devices/cpu/m68000/mcf5206e.cpp`) keeps the register window off until bit 0 of `MBAR` is set and has its reset-status register at offset `0x40`, which agrees with the manual and with the readers in the image (the loader at `0xffe00ac8` and the kernel at `0xffe565b4`). The manual, not that model, is the cited source for the statements above.
