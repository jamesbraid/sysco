# Origin 300 L1 1.44.0 board-record validation

The selected Origin 300 L1 firmware validates the board EEPROM's common header and each nonempty board area before its general request handler serves those bytes. This note records the observed validation rule. The fitted EEPROM part remains a separate question. The visible normal IP45 startup path loads or invalidates board records before the general request task starts; later indirect refresh calls remain untraced.

Addresses below refer to its first flash-bank copy. Which bank executes on a fitted board is unverified.

At `0xffe6ba58–0xffe6bc02`, the board reader reads eight header bytes and accepts that header only when the low byte of the sum of all eight is zero. The checksum helper at `0xffe5b3a4–0xffe5b3ca` accumulates byte values, and the caller compares its byte result with zero. A mismatch records a header error and skips area loading. The corresponding published Origin 300 EEPROM dump is in SGI *Origin 300 System with NUMAlink Module User's Guide* `007-4498-002`, printed pages 181–182. Its two shown board headers and six nonempty areas each have a byte sum of zero modulo 256. The example does not prove all fitted board revisions.

The reader then considers four area classes: chassis, board, product, and internal-use. Their header offsets are encoded in eight-byte units. For an area with a nonzero offset, the helper at `0xffe6b89c–0xffe6ba58` reads its eight-byte prefix, derives the declared area length in eight-byte units, and accepts the extent only if its end is strictly less than the configured EEPROM capacity. An area ending exactly at that capacity is rejected by the selected software. A zero area length or out-of-range extent leaves that area unavailable. For a valid nonempty extent, it reads the complete declared area and accepts its contents only when the low byte of the byte sum over that area is zero. A failed area checksum records an invalid state and discards the area's RAM copy. The internal-use class has a special length interpretation when its first byte is zero.

The M-Bus startup and request trace follows the normal continuing IP45 branch: after DIMM probes and a temporary node-board read, the board callback scans all six registered records before starting the general request task. A present board record with a bad common-header checksum stores an invalid header status and leaves unread areas unavailable. A valid `0x0006` request for its header, chassis or board area then answers minus 107: the stored status check precedes the offset bounds. A failed first IO8 read can also leave that entry present with read-error status and answer minus 107 for a valid board-area request. A failed early DIMM probe clears that entry's presence, so its request answers minus 104. An area checksum failure is a startup/read-time state change, not a checksum calculation performed on every host `0x0006` request. Minus 107 alone cannot identify a bad checksum.
