# C-brick L1: `power`, `reset`, requests addressed to an L2, and the RS-422 peer links

Reads the IRIX 6.5.30 `l1.bin` (L1 1.44.0, sha256 `c355c542554a41b23b69dca4c201c566e8352e8f9fb870d2365c74cdd8ab0c0f`). A C-brick (brick-type character `C`, `C (IP35)`, see [personalities.md](personalities.md)) is served by two ColdFire packages whose supported-brick strings contain `C`: package 0 `Base 1MB image` and package 2 `MIPS 2MB image`. The reading is of package 0 (body sha256 `3c8a7aa93eb38502289cf0c2921ea91e6800228005bd8abd67425ce615f7b364`, 982,376 bytes, loaded at `0xffe00000`, so its image starts at container offset `0x68`), through a linear listing made with the same decoder settings as [disasm/](disasm/README.md) (capstone 5, 68040 mode). That listing is 17 MB and is not committed. Addresses are first-bank addresses of package 0. Every routine in the first table was compared whole with packages 1 and 2 (code and RAM addresses masked, immediates such as error codes kept): the instruction streams are identical, so every finding below holds for the Origin 300 body and for the 2 MB package as well, apart from the data they use (supply tables, board hooks). The first table gives the addresses in all three.

Grades as in [../../AGENTS.md](../../AGENTS.md): E established (routine read in full), I inferred, U unknown. A locator written `` (`mnemonic` at 0x...) `` names the instruction at that address in the package 0 listing. The linear decoder mis-decodes a few jump tables and data words; where a cited address is one of those the text says so.

The questions behind this note were what a C-brick L1 does with a request addressed to an L2 that is not there, whether its `power` and `reset` commands reach another C-brick, how `*` resolves its targets, and what a first `pwr d` does. No L2 is assumed anywhere below.

## 1. A task-3 request addressed to an L2 (`0x1ffff003`) with no L2 attached

Answer: an error reply, router code minus 1 with detail 8, sent back to the request's source. Nothing is forwarded, nothing is run locally, no request falls back to this L1's own task 3, and the request is not dropped silently. E for package 0 and for the compared ranges of packages 1 and 2. One exception on a C-brick, which has a USB function that opens without a host: for a short stretch of each one-second cycle of the USB task the route word is -1, a request in that stretch goes to the USB write queue, and it gets a detail 9 error (or, once five USB writes have failed, no reply); see "When the word is not 0" below.

The path, step by step:

- **The word.** `0x1ffff003` is the destination the `l2` console command loads (`move.l` at 0xffe14ab4, mode word 2 at `move.l` at 0xffe14ab0). Low five bits 3: task 3, the command interpreter. Bits 12 to 31, `0x1ffff`, are the "module" field the router compares; the top nibble, 1, is the address type the catch-all switches on. E.
- **Not local.** The router (`lsr.l` at 0xffe788a0, `cmp.l` against the local identity at 0xffe788a8 and against `0xffff` at `cmp.l` at 0xffe788c0) takes the local task table only for the local identity or `0xffff`. `0x1ffff` is neither. It then walks the remote list (`0xffe78922` to `0xffe78954`); no routine in the boot, USB or config paths read registers a remote entry for `0x1ffff` (I: the registrations seen are the catch-all and the local tasks). With no match it takes the catch-all slot (`movea.l` at 0xffe7895a, RAM `0x30001ae0`). E.
- **The catch-all of a C-brick.** The peer-link initializer (`0xffe2dba4`) tests the brick-type character against the I/O-style set `I X Y P G N & # = E V` (compare chain `0xffe2e1d8` to `0xffe2e21e`). `C` is not in it, so it takes `beq.w` at 0xffe2e222 and registers `0xffe2eb60` for address `0x0fffe000` (`pea.l` at 0xffe2e2e4, `move.l` at 0xffe2e2ee, `jsr` at 0xffe2e2f8), which the registration routine files in the catch-all slot (`cmp.l` at 0xffe7791e). The I/O-style bricks register `0xffe2edfc` instead. [rs422-router.md](rs422-router.md) read the Origin 300 body, where the same `0xffe2eb60` is the compute-brick catch-all. E.
- **Type 1.** `0xffe2eb60` extracts the top nibble (`lsr.l` at 0xffe2ebb8) and jumps through a 16-word table (`jmp` at 0xffe2ebce; the table at `0xffe2ebd2` is mis-decoded by the linear listing; read from the bytes, scaled by 2, types 1 and 2 go to `0xffe2ebf2`, 3 and 6 to `0xffe2ec8c`, 4 to `0xffe2ecb2`, 5 to `0xffe2ed00`, 14 and 15 to `0xffe2ec78`, the rest to `0xffe2ed1a`). The entry at `0xffe2ebf2` is `move.l #$ffff,d7` (bytes `2e3c 0000 ffff`; the listing shows an `ori.l`). Because the destination's bits 12 to 27 are `0xffff`, it goes on to `0xffe2ec1c` and, for a request (byte `0x16` of the packet is 0), calls the route chooser (`bsr.w` at 0xffe2ec7a). E.
- **No L2 route.** The route chooser fetches the record of module 0, this brick (`jsr` at 0xffe2e8f6), and reads the word at `+0x58`. That word is the L2 route: `-1` means an L2 is attached to this brick and the route is not yet known (the request is put on a queue, `jsr` at 0xffe2e912, and no reply is made yet); `0` means no L2; a positive value is the peer slot (1 or 2) that leads to an L2. For a request and a word of 0 it loads `-1608` (`move.l` at 0xffe2e96e), sends a routing-error reply through the response routine `0xffe78f5c` (`jsr` at 0xffe2e982), writes the log text `B2B: no receiver (REQ)` (string `0xffe2f910`), frees the packet and returns the code. The response routine builds the reply as code minus 1 with detail byte `1608 mod 100 = 8` (negate, divide by 100, remainder: `neg.l` at 0xffe78fb2, `moveq` at 0xffe78fb4, `divs.l` at 0xffe78fb6) addressed to the request's source word. E.
- **When the word is not 0.** Writers of the word: `move.l` at 0xffe2d362 stores `-1` in the USB task right after it opens its USB function ("registered as remote"), `clr.l` at 0xffe2d5cc clears it when that task's read fails and it closes the function, and `move.l` at 0xffe32380 stores slot 1 or 2 when the record of a peer brick shows an L2 behind it. A C-brick has one USB function (its descriptor sets the USB count to 1 at `move.l` 0xffe45524), so the task runs from boot (`jsr` at 0xffe106c2, creator `0xffe2d000`, task `0xffe2d1c4`, which logs `USB%d: waiting on open`, `opened`, `registered as remote`). It does not need a host to open. With no host, the next read fails at once: the lower read returns -1506 or -1505 while the function's state byte is not 2 (`subq.l` at 0xffe6e39c; state 2 is reached only by a host configuring the device, I), the stream reader maps that to -1612 (`move.l` at 0xffe79298, reader `0xffe791f8`), and the task takes its error path (`0xffe2d4b2`): unregisters, closes the function, clears the word to 0 (`clr.l` at 0xffe2d5cc), waits 100 ticks (`jsr` at 0xffe2d5ec) and reopens. So the word is `-1` for the short stretch between reopening and the next failed read and 0 for the rest of each 1 s cycle (E for the cycle, I for the host-less read failure and for the share of time). A request that arrives in the `-1` stretch is queued to the USB write queue instead (`jsr` at 0xffe2e912); the USB write task dequeues it, the lower write fails the same way, and the stream writer answers a request with router code `-1609` (detail 9, `pea.l` at 0xffe79446, `bsr.w` at 0xffe79450) and frees it. The write wrapper (`0xffe2d8c0`) counts failed lower writes in the word at `0x300009f4`; after five it skips the write and reports success, so later requests in that stretch are dropped without any reply (E for the mechanism; the count also rises for failed event and response writes, and falls back to 0 only on a successful USB read, so by the time a host asks it may already be five, I). With a host attached and configured the word stays `-1` and the L2 receives the request.
- **What the reply carries.** Header `0x20` or-ed with the request's subchannel, code `-1` (`ff ff ff ff`), detail 8, no count byte: the "iRouter error" form already recorded in [rs422-router.md](rs422-router.md) for type 4. Detail 10 (`-1610`) is a full USB write queue (`B2B: send to queue error (REQ)`, `move.l` at 0xffe2e952) and needs the `-1` stretch above. E for the code and detail, I for the frame bytes (the serializer was read for the Origin 300 body).
- **The `l2` console command.** `l2 <text>` builds a one-target list with the same word `0x1ffff003` and mode 2, so the executor sends it through the same router and gets the same error reply; the collector then prints a line that starts with the brick name, then `ERROR: (3)` and says the request could not be sent to the target (string `0xffe26ee1`, the reply-error branch at `0xffe1b928`). E for the branch and string, I for the exact arguments.

Consequence for a host that loops a partition-id query and `p <id> pwr d` to `0x1ffff003`: every such request gets the router error and nothing else; the L1 never turns it into a local `* pwr d`. That fallback would have to be the host's own. E.

## 2. Plain `power down`, `power up` and `reset` against the other C-brick

Answer: none of the three forwards a command to the other C-brick. They act on this L1's own brick. What does cross the link is the power-state notice (a configuration event) that `power up` and `power down` publish, and a `*`, `ctc` or `cti` prefix, which forwards the rest of the line as a task-3 text request. E for the handlers and the routines they call (direct callees read; none sends a packet), I for what the other L1 does with the notice.

### The handlers are local

- `power up`, `power up hold`, `power down` share `0xffe19740`. After the brick-set guard (`bsr.w` at 0xffe1975c) and a supply-table check it dispatches on word 1 of the record: 0 calls the local power-up with the record's second flag (`jsr` at 0xffe197e0; 1 for `power up`, 0 for `hold`) and reason 1, 1 calls the local power-down with reason 1 (`jsr` at 0xffe197f0). It writes output only on error. E.
- `reset` and `reset hold` (`0xffe1988c`) first test the all-supplies-on state (`jsr` at 0xffe198a0, `subq.l` at 0xffe198a6): anything but "all on" prints `ERROR: power appears off.` and returns -1. Otherwise `reset` calls `0xffe4f324` (`jsr` at 0xffe198e4) and `reset hold` calls `0xffe4f2f0` (`jsr` at 0xffe198f4). Those routines log `reset (COMMAND)` or `reset hold (COMMAND)`, drive the board's reset lines through hooks and delay (`reset` asserts, waits 10 ticks, releases); neither builds a packet. E.

### Local power-up sequence of a C-brick (`0xffe4cb4c`)

In order, for `power up` (reason 1; type `C`). The environment monitor (`0xffe2b8d4`, the module whose log literal is `Env.c`) is told the phase around the supply walk (`jsr` at 0xffe4ccc2, helper `0xffe2be58`, phase 2, just after the reset hold):

1. A board hook (`jsr` at 0xffe4cb90) can veto: log `System failed pre-power check`, return 0, nothing powered. E for the veto, U for the hook's body (installed by board code).
2. The serial-number pre-power check (`jsr` at 0xffe4cbbc). Its failures print `Brick serial number mismatch`, `System serial number mismatch`, `Brick disabled`, `System serial number invalid format` or `No system serial number assigned` on the display (`jsr` at 0xffe4cc2c) and return the error. E.
3. Log `power up (COMMAND)` (or `power up hold (COMMAND)`) (`jsr` at 0xffe4cc66), display `Powering Up` (`jsr` at 0xffe4cc9a), hold the node in reset (`jsr` at 0xffe4ccb8, `0xffe4f2f0`).
4. Walk the power table `0x300000fc` upward. The C-brick table is the 20-record table at `0xffe457c4` registered by the board initializer (`jsr` at 0xffe4544e). Every record that is enabled and whose pin byte is not `0xff` is switched on (`bsr.w` at 0xffe4cec2, routine `0xffe4c76c`), in table order, with a 25-tick delay after each (`moveq` at 0xffe4cf2a, `jsr` at 0xffe4cf2e). The records that carry a pin are 0 (pin `0x0b`, no name), 1 `PIMM0 VCPU`, 2 `PIMM1 VCPU`, 3 `DIMM`, 4 (pin `0x09`, no name), 10 `PIMM0 SRAM` and 15 `PIMM1 SRAM`; which are enabled depends on the fitted modules (the enable flags are written by board code, U). A supply that fails to switch on makes the routine call the power-down with reason 5 and return the error (`bsr.w` at 0xffe4ced2). E for the order and delays, I for the record names (strings next to the table).
5. A 100-tick delay (`moveq` at 0xffe4cf40, `jsr` at 0xffe4cf44), then a board hook and a phase change of the environment monitor (`jsr` at 0xffe4d030, helper `0xffe2be6c`, which stamps the time and calls `0xffe2b8d4` with 4).
6. Normal `power up` only: a 50-tick delay (`moveq` at 0xffe4d14e, `jsr` at 0xffe4d152), then release of the node's reset (`jsr` at 0xffe4d15e, `0xffe4f324`). For `power up hold` the delay and the release are skipped and the node stays in reset. The 50-tick delay applies to the brick types that map to `0xffe4d14e` in the table at `0xffe4d10a` (read from bytes: `0 3 4 5 6 7 8 9 @ A B C F H L O Q`); I, P, R and the other types go straight to the release. E.
7. If nothing failed: record-0 power state := 1 (`jsr` at 0xffe4d17a, routine `0xffe33268`, which also publishes the power-state notice, below), display `Powered Up` (`jsr` at 0xffe4d18e). Otherwise display `Power Up Error`. E.

The tick is the 100 Hz timer tick (I, from [power-bay-link.md](power-bay-link.md) and [board-boot-contract.md](board-boot-contract.md)), so a C-brick takes 0.25 s per enabled supply, then 1 s, then 0.5 s before the reset release. The routine has no call into the power-bay task or its UART (none of its callees to two levels does either); the bay is read by its own task and is not sequenced here (I).

### Local power-down (`0xffe4c904`)

For a C-brick, at once and in this order (E):

1. No deferral (section 4). Log `power down (COMMAND)` (`jsr` at 0xffe4c9de, skipped for reason 5), display `Pwring Down` (`jsr` at 0xffe4c9fe), environment-monitor phase 3 (`jsr` at 0xffe4ca08, helper `0xffe2bea4`), node held in reset (`jsr` at 0xffe4ca12, `0xffe4f2f0`).
2. Switch the supplies off in reverse table order (loop `subq.l` at 0xffe4ca5c to `bpl.b` at 0xffe4cac2), no delay between them.
3. Display `Powered Down` (`jsr` at 0xffe4caea) or `Power Down Error`, environment-monitor phase 4 (`jsr` at 0xffe4cb12, helper `0xffe2beb8`), which also **clears the registered event subchannel** (`jsr` at 0xffe2bec6 to `0xffe3517c`: the subchannel word becomes -1 and the persisted setting is cleared), record-0 power state := 0 (`jsr` at 0xffe4cb1a, routine `0xffe33268`), a 40-tick delay (`jsr` at 0xffe4cb32) and a board hook.

### What crosses the peer link

- **Power-state notice (I for the receiver, E for the sender).** `0xffe33268` changes the word at `+0x34` of the record of module 0 and, only when it changed, calls `0xffe33060` with kind 4 (`bsr.w` at 0xffe3328c). `0xffe33060` builds a packet from the brick's rack, bay and that word and hands it to the event sender `0xffe79084` (`jsr` at 0xffe33200). The peer-link initializer subscribed the event handler `0xffe2efe8` to all events (`0xffe2e29a` branch, `jsr` at 0xffe2e2a8). For an event addressed to task 14 (configuration exchange) that handler, for a brick with no ring set up, copies the packet to peer slot 1 and slot 2 when open (loops at `0xffe2f2a0` and `0xffe2f308`; forwarding routine `0xffe2eeec`). Order on the link: the notice goes out after the local power state flips (after the supplies, for both power-up and power-down). It is informational for the module table; the other L1's reaction was not read (U).
- **`*`, `ctc`, `cti`.** `ctc` (record `0xffe1c890`) is peer slot 1, UART 3 (the `C` group of the initializer's jump table, `moveq` at 0xffe2dda2, `move.l d0,(a3,d7.l)` 0xffe2ddd0 and `$20(a3)`; the same group as `4`, `0`, `7`, `8`, `Q`); `cti` (record `0xffe1c918`) is slot 9, UART 4. The handler refuses a closed slot with `ERROR: <name> doesn't appear to be active` (string `0xffe243c3`). With the slot open, the executor builds a task-3 text request carrying the rest of the line, source `0x0ffff003`, and queues it to the slot's writer with a 100-tick wait (`jsr` at 0xffe1b2e8). The peer runs the text and answers with code 0 and its output fields. E for the sender side, I for the peer.

## 3. What `*` resolves to, and the order of `* power up`

- **Target list (E).** `*` (`0xffe14acc`) walks the module table by index from 0 (`jsr` at 0xffe14b46) and adds one target for every valid record (`moveq` at 0xffe14b62 for mode 2, `or.l` at 0xffe14b86 for task 3): address = (rack in bits 18 to 27, bay in bits 12 to 17) with task 3, so the type nibble is 0. Duplicates (same rack and bay) are dropped (`0xffe14ba0` to `0xffe14bc0`, count `addq.l` at 0xffe14bc6). Module 0 is this brick. With no L2 and no peer record the list has one entry, this brick, and `* cmd` runs `cmd` locally and prints the brick name and `:` before the output. How records 1 and up get filled without an L2 (peer notices, I; the L2's configuration reply, E in [../l2/config-request-reply.md](../l2/config-request-reply.md)) was not read (U).
- **Order of sending (E).** The executor (`0xffe1b0f8`) starts at the last target and counts down to 0 (`subq.l` at 0xffe1b20c; loop `subq.l` at 0xffe1b59c and 0xffe1b59e, `bpl.w` at 0xffe1b5a2). A target whose module field equals this brick's is parsed and run at once (`jsr` at 0xffe1b3ae). Any other target gets a task-3 request built and delivered through the router (`jsr` at 0xffe1b4da); the send is not waited for. So `* power up` hands every remote request to the router first, highest table index first, and runs this brick's own `power up` last, at index 0, taking the seconds of section 2. Remote L1s start when their request arrives, so the powering of different bricks overlaps; the table order is the only order the C-brick imposes. No brick type is compared anywhere in this loop, so there is no fixed "C, then I, then R, then P" order in this L1 (E). Which peer slot a remote request leaves by comes from the module table (module indices 1 to 4 to slots 9 to 12, higher indices to slots 1 and 2: `divs.l` loop at `0xffe2ed58` to `0xffe2edb4`, E; what the indices stand for in a given cabling is U). The C-brick has only two peer slots, 1 (`ctc`, UART 3) and 9 (`cti`, UART 4), so `*` leaves it on those two only. The R-brick opens no RS-422 peer port ([power-reset-ibrick-rbrick.md](power-reset-ibrick-rbrick.md)), so with no L2 neither `*` nor `cti` reaches an R-brick (E for the R side, I for the cabling). An I-brick is reached on slot 9 and has no auto power-up task, so it powers only when a `power up` text reaches its own L1.
- **Collecting replies (E).** After the loop the executor receives replies in arrival order with a wait value of `0x44c` (1,100 ticks, 11 s; `pea.l` at 0xffe1b5ba, `jsr` at 0xffe1b5c6) per receive. For each reply it appends `<name>:` and the reply text, or ` ERROR: (1)`, `(2)` or `(3) could not send request to <name>` for send failures and error replies, or ` ERROR: no response from <name>` for a timeout. The overall result is 0 or -1 by whether any target failed.
- **Per-brick differences (E for this routine).** Every L1 runs the same shared power-up routine, driven by its own supply table, so what differs is the table, the wait after the first supply (250 ticks for type `A`, 100 ticks for `6`, 25 for everything else: `move.l` at 0xffe4cef2, `moveq` at 0xffe4cf04 and 0xffe4cf2a) and the 50-tick delay before reset release (type set above). The R-brick, P-brick and I-brick tables were not read. With an L2 attached, power order and spacing come from the L2, which sends `power up` to each brick's L1 and holds the queue: see [../l2/power-queue.md](../l2/power-queue.md).

## 4. First `pwr d` and the event subchannel

Answer: with no event subchannel registered there is no deferral for any brick type. `pwr d` powers the brick down at once and prints nothing on the console. Even with a subchannel registered, a C-brick never defers. E.

- The test is in the local power-down (`jsr` at 0xffe4c91e, routine `0xffe35164`, which returns 1 unless the subchannel word at RAM `0x30004f54` is -1). When it returns 0 the code goes straight to the power-down body (`beq.w` at 0xffe4c926 to `0xffe4c9c6`).
- When it returns 1, the type character must also be `9`, `A` or `Q` (`add.l` at 0xffe4c92e, `subq.l` at 0xffe4c932, `add.l` at 0xffe4c938), and the reason must be 1, 2 or 4. Then, the first time (flag at `+0x1c` of the power block, set by `move.l` at 0xffe4c9bc), the routine sends event code `0x8000` with a one-line text asking the operator to repeat the `pwr d` command (reasons 1 and 4) or to press the power button again (reason 2), through `0xffe27944` (`jsr` at 0xffe4c9b0), whose log flag also appends the text to the log ring, and returns 0 without powering down. The second request finds the flag set and powers down. `C` (0x43), `I` and the Origin 300's `4` are not in the type set, so the deferral belongs to the workstation-style bricks only. The routine is instruction-for-instruction the same in package 1 (`0xffe4c554`), package 0 and package 2, so a deferred first `pwr d` cannot be taken from the Origin 300 image either: no image of 1.44.0 defers it for a C-brick, an I-brick or an Origin 300.
- What a `pwr d` prints on the console: nothing. The command handler (`0xffe19740`) leaves the output buffer untouched when the power-down returns 0. The effects are the log entry `power down (COMMAND)` (the log writer `0xffe5a92c` appends to the log ring; it is not a console print, I for its identity from the ring pointers it advances), display line 2 `Pwring Down` then `Powered Down`, and the event-subchannel clearing of section 2. The reply to a task-3 `pwr d` is code 0 with the usual module-name field. I for that reply shape (the executor, read in the Origin 300 body).

## 5. Automatic power-up after mains

- **Which bricks (E).** The boot code creates the auto power-up task (`jsr` at 0xffe1075e, creator `0xffe2ff88`) only for the brick types `C 3 5 4 A 6 9 7 8 0 Q @ O B F H L` (compare chain `0xffe2ffc2` to `0xffe30032`), and only when persistent setting `0x32` is nonzero (`jsr` at 0xffe30044, `beq.w` at 0xffe3004e). `I` and `R` are not in the list ([power-reset-ibrick-rbrick.md](power-reset-ibrick-rbrick.md)); a C-brick is. What the setting holds at first power-on is U.
- **Countdown (E for the arithmetic, I for the time).** The task entry (`0xffe30130`) sets a step count from the type: 2 for `A`, 18 for `C` and the other letters of the list (the bytes at 0xffe301f0 are `70 12 24 80`, `moveq #$12,d0` and `move.l d0,(a2)`; the linear listing shows an `ori.w` at 0xffe301ee that swallows them), 12 for the rest. It logs `auto power up countdown initiated`, prints an `INFO:` line that gives the seconds left (5 times the count), and then loops: sleep 500 ticks (`move.l` at 0xffe30230 loads `0x1f4`, `jsr` at 0xffe3023a), test for a user abort (the abort form of the auto-power-on command, record `0xffe1c230`; log `auto power up aborted, user abort`), for the setting having been cleared (`auto power up aborted, nvram changed`) and for an L2 among the module records (`auto power up aborted, L2 detected (%d)`), and prints the `INFO:` line again. At 100 Hz a C-brick waits 18 steps of 5 s, 90 s, unless it is aborted (I for the tick rate).
- **The action (E).** At the end it logs `auto power up initiated`, prints an `INFO:` line saying the system is powering up, and builds one task-3 request to `0x0ffff003` (this L1's own command interpreter) with the text `* power up` (`move.l` at 0xffe30524, string `0xffe3072c`), injects it into the router as a packet from itself (`jsr` at 0xffe3058c) and waits for the reply with no time limit (wait value -1, `jsr` at 0xffe305a0). The `*` of that text is the handler of section 3, so an automatic power-up orders the bricks exactly as a typed `* power up` does.
