# Origin 300 L1 router and serial-link reading

This note describes software paths in the selected Origin 300 L1 firmware.

## Source identity and locators

The image is the Origin 300 L1 1.44.0 body described in [package-container.md](package-container.md) (build stamp `20060717182038`, loaded at `0xffe00000`, reset vector `0xffe00400`). Addresses are first-bank; subtract `0xffe00000` for a body offset. Locators are read from the committed listing.

## Two different serial paths

On boot the image initializes the address router, then the processor-facing Bedrock link, then the brick-to-brick link for the Origin 300 brick-type value `4` (`0xffe10570`, bank offset `0x10570`). The Bedrock link offers a processor port in PPP-framed mode or a configured raw-byte mode. Its framed receiver classifies header type 0 as a request and type 2 as console output. Requests carry a destination and typed fields. Responses, console input and events leave through the Bedrock link's output queue, where the frame serializer chooses the source subchannel and the PPP sender for a framed port. This is software multiplexing of management requests and console traffic over the processor UART, separate from the RS-422 peer ports (`0xffe34598`, `0xffe34774`, `0xffe35634`, `0xffe35864`, `0xffe358cc`, `0xffe35c08`, `0xffe35f24` to `0xffe35f60`). Bank offsets equal the low six hex digits of these addresses. The image alone does not establish the processor UART's electrical path through Bedrock or a mandatory baud divisor.

The peer-link initializer uses the Origin 300 brick-type value `4` to assign UART device 3 to peer slot 1 and UART device 4 to peer slot 9. These device numbers are software UART API selectors. The image does not show which connector net each selector reaches. The module starts separate read and write tasks for each configured slot and uses its own PPP contexts and queues. Its request receiver is registered as the router's fallback for destinations that are neither the controller's concrete type-0 identity nor the all-local-sentinel type-0 identity (`0xffe2dba4`, especially the brick-type switch and the registration near the end, and `0xffe78314` for router initialization). The chosen fallback is the compute-brick variant for brick type `4`.

## Type-4 request on a normal one-chassis boot

The fallback reads controller type 4 from the destination, rewrites the type to 0 for forwarding, and chooses peer slot **9**. For its task-5 tagged form it adds the decoded port index to 9. An ordinary type-4 general-task request uses slot 9 directly (`0xffe2eb60`, bank offset `0x2eb60`). It does not dispatch type 4 to the local general task. The forwarding function calls the slot-open predicate, which is true only while both the read and write software handles for that slot are nonzero (`0xffe2e88c`, `0xffe2ea3c`).

If slot 9 is closed when the request reaches forwarding, the L1 builds a router error response and frees the request. If both handles are open, the L1 queues the rewritten request for the peer writer. A successful enqueue produces **no immediate response**. The writer later sends it as a PPP-framed serial packet. The enqueue helper distinguishes a full queue or timeout from other enqueue failures: the former returns an internal error that would encode router detail 11, while the latter returns one that would encode detail 10. The type-4 forwarding caller replaces either nonzero result with the generic error before building the Bedrock-side reply. Thus both failures produce a router-error response with **detail 10** on this path. A full queue also leaves a queue-full log entry. The helper and caller branches are at `0xffe78c7c` and `0xffe2ea3c`. The response detail is computed at `0xffe78e0c` (bank offsets `0x78c7c`, `0x2ea3c`, `0x78e0c`). The slot-open predicate is at `0xffe2e88c`, and the peer writer is at `0xffe2e5c0`.

The image fixes the conditional behaviour: the chosen software slot is 9, configured to UART device 4 on the Origin 300 branch. Whether the slot is open in a live system depends on the UART open routine's result, which this note does not read (see the open question on the peer UART open routine). The read task repeatedly tries to open its configured UART, and the write task repeatedly tries to open its own handle. A failed open leaves the predicate false. Receive or send failure closes the corresponding handle, resets its PPP context and restarts opening. After more than five consecutive failures the read task waits 100 ticks and the writer waits 200 ticks. The writer also waits 100 ticks between open attempts. It reports serial send failures through the L1 console but does not synthesize a request reply after a queued packet fails to transmit (`0xffe2e344`, `0xffe2e5c0`, `0xffe2e88c`). The L2 route state is likewise not proved by this type-4 path.
