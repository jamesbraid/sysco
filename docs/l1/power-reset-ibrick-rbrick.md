# I-brick and R-brick: what `power up`, `power down` and `reset` drive, and what reaches them

Read from the IRIX 6.5.30 `l1.bin` (L1 1.44.0, sha256 `c355c542554a41b23b69dca4c201c566e8352e8f9fb870d2365c74cdd8ab0c0f`), ColdFire package 0 (`Base 1MB image`, supported-brick string `CIPXYN&?RG`), first bank, load address `0xffe00000`. Package 2 (`MIPS 2MB image`) carries the same code for these two letters; where a locator is given for package 2 it was matched by byte pattern and the surrounding routine read, and where it is not given the package 2 body was not compared (inferred equal). The I-brick is brick letter `I`, the R-brick letter `R` ([personalities.md](personalities.md)). Both letters are in packages 0 and 2 only; packages 3 and 5 do not list them. Grades follow [AGENTS.md](../../AGENTS.md): E established, I inferred, U unknown. "Tick" is the unit of the firmware's delay routine `0xffe40e54`; its length in time was not read (U).

## Common machinery (E)

- **Command entries.** `power`, `power check`, `power up`, `power up hold`, `power down`, `reset` and `reset hold` have no brick filter (entries `0xffe1e9c4` to `0xffe1eba0`, handlers `0xffe185b8`, `0xffe19740`, `0xffe1988c`; read with [../../scripts/l1_command_table.py](../../scripts/l1_command_table.py)), so both letters accept them from any request source. The commands that send onward (`*`, `<id>`, `ctc`/`nia`, `cti`/`iia`) list the types allowed to issue them, and neither `I` nor `R` is in any of those lists (`0xffe1c0dc` to `0xffe1c95c`): an I-brick or R-brick L1 cannot forward a command.
- **Power handler `0xffe19740`.** First flag word 0 calls the power-up routine `0xffe4cb4c(arg, 1)` (the second flag word, 1 for `up` and 0 for `up hold`), 1 calls the power-down routine `0xffe4c904(1)`.
- **Reset handler `0xffe1988c`.** It first calls the supply-state routine `0xffe4c6ac`, which returns 1 when every supply with an enable bit is on, -1 when some are, 0 when none is. Anything but 1 prints "ERROR: power appears off." and fails (`0xffe198a0`-`0xffe198c8`). Otherwise flag word 0 calls the reset routine `0xffe4f324(1)` and 1 calls the reset-hold routine `0xffe4f2f0(1)`.
- **Supply table** (24-byte entries, header at `0x300000fc`: base, count, per-entry enabled bytes). Byte +2 is the expander index (`0xff` means no enable bit), byte +3 the bit mask. **Enable polarity.** `0xffe4c4bc` returns 1 only for supply type `0x17`; for every other type "on" is the bit **clear**: power-up clears the bit (`0xffe4c76c` to `0xffe65f1c`) and power-down sets it (`0xffe4c894` to `0xffe65ef8`). `0xffe65e84(index, mask, value)` is the masked expander write; `0xffe65ef8` is it with value = mask, `0xffe65f1c` with value 0. Each expander write sends the whole shadow byte once ([ip45-io-expanders.md](ip45-io-expanders.md) for the descriptor format).
- **Cold start applies the descriptor values.** After the board tables are registered, `0xffe4a83c` runs the sanity routine `0xffe4a7b0`; when it returns nonzero, `0xffe6664c` writes every expander once with its applied value OR its input bits (`0xffe6657c`). `0xffe4a7b0` returns nonzero at once when the RAM word at `0x301019ac` is clear (`0xffe566e8`; the start-up code logs "L1 running" for clear and "L1 rebooted" for set, `0xffe10720`-`0xffe10754`). That word is read at `0xffe566ee` (and its second-bank copy) and no instruction in the package stores to its absolute address (E for the reads, I that a clean power-on leaves it clear). Otherwise `0xffe4a7b0` checks that the expanders agree with a running brick (logging "power supplies ON, fans are OFF" and similar texts) and only a disagreement makes it nonzero.
- **Serial-number check before power-up.** `0xffe4cb4c` calls `0xffe530c8` first, for every letter except `A` and unless persistent setting `0x50` is nonzero. It compares the stored brick serial number with the one in the board record, rejects a disabled number, a malformed system serial number (first character one of `L M N P R`, a digit `0` to `3`, then six digits) and a system serial number different from the one in the first module record, with the error codes `-0x834` to `-0x838` and the texts around `0xffe53ff1`. The check is identical for `I` and `R`. The R-brick rule in the router datasheet is this routine (E for the routine; which settings a given machine holds is not read).
- **No automatic power-up task.** The task that sends `* power up` after start is only created for `C 3 5 4 A 6 9 7 8 0 Q @ O B F H L` (`0xffe2ff88`, list at `0xffe2ffc2`-`0xffe30030`; package 2 `0xffe35760`, same list). `I` and `R` are not in it.

## I-brick (letter `I`)

**Board tables (E).** Letters `& I N P X Y` share the descriptor initialiser `0xffe4676c` (package 2 `0xffe4c7e4`): USB count 0, reset-hold hook `0xffe47ddc` at descriptor `+0x98`, reset-release hook `0xffe48370` at `+0x9c`, no power-down hook (`+0x70`) and no power-up veto (`+0xd8`). The registration routine `0xffe46028` takes the `I` branch at `0xffe4606a`: 13 expanders at `0xffe467e8`, 9 supplies at `0xffe468f4`, then (second dispatch `0xffe46584`) a one-entry reset table at `0xffe46a0c` registered by `0xffe47ed8`.

| Expander (index, M-Bus address) | Applied value | Use here |
|---|---|---|
| `POWER ENABLE` (0, `0x70`) | `0xff` | all supply enables, active low |
| `XBRIDGE CONTROL` (5, `0x48`) | `0xd4` | reset lines, bits 0, 1 and 3 low at start |

Supply enables in `POWER ENABLE`, in table order: mask `0x01` (supply type 8, the 48 V entry), `0x04` (type 9, named `12V BIAS`), `0x08` (type `0x0f`), `0x10` (type `0x10`), `0x40` (type 9), `0x20` (type `0x11`), `0x80` (type `0x12`). Together `0xfd`; bit `0x02` drives no supply. Two further supplies, `3.3V aux` and `5V aux`, have no enable and are only monitored: they stay up with the L1.

**What the I-brick does at mains (E for the code path, I for the flag).** With the flag word clear the cold start writes `POWER ENABLE = 0xff`, which with active-low enables is every supply off, and `XBRIDGE CONTROL = 0xd4`, which holds the three reset bits low. No power-up task exists for `I`. So the brick's L1 comes up with its supplies off and its bridges in reset, and `power check` reports power off, until a `power up` request reaches it.

**`power up`** (`0xffe4cb4c`; E): the serial-number check; the reset-hold routine; each enable bit cleared in table order with 25 ticks after each (`0xffe4cf2a`), after the check `0xffe4b6cc(0xff)` (first supply only, while all are off); 100 ticks; a node-reset helper that does nothing for a brick with no registered compute nodes (I); "Powered Up". Plain `power up` then calls `reset` (`0xffe4f324(5)`, `0xffe4d15e`; the jump table at `0xffe4d10a` sends `I` straight to it), so the bridges come out of reset. `power up hold` skips that call and the reset stays asserted.

**`power down`** (`0xffe4c904`; E): letters `9 A Q` take a deferred "issue `pwr d` again" path; `I` does not. It logs `power down (<reason>)`, shows "Pwring Down", calls the reset-hold routine, then sets the enable bits of the supply table **in reverse order**, one expander write each, and shows "Powered Down" (`0xffe4c9c6`-`0xffe4cb4a`). So `power down` cuts the seven switched supplies (`POWER ENABLE` returns to `0xff` except the unused bit) with the bridges already in reset; it leaves the two aux supplies and the L1 running.

**`reset`** (E). Hold (`0xffe47ddc`, via `0xffe4f29c`) is `0xffe65e84(5, 0x0b, 0)`: bits 0, 1 and 3 of `XBRIDGE CONTROL` (M-Bus address `0x48`) driven low. Release (`0xffe48370`, the `I` arm at `0xffe48432`, via `0xffe4f144`) writes bits `0x34` of the same expander from two inputs, then, only when the supply-state routine is nonzero: 10 ticks, bits `0x0b` := `0x0a`; 10 ticks, bits `0x0b` := `0x0b` (bit 0 comes up last). The `0x34` value has bit `0x04` set when module record 1 holds a neighbour (or a global flag at `0x30000130` is set) and setting `0x2a` is nonzero, and bit `0x10` likewise for record 2 and setting `0x2b` (`0xffe48432`-`0xffe484ee`); the two records are the "attached brick on port A / port B" slots, so these bits are I as an enable for each host port. `reset` is hold, 10 ticks, release (`0xffe4f324`). Whether the three reset bits are the bridge chips' resets or other board resets is not named in the image: the expander is called `XBRIDGE CONTROL`, so I for the bridges (U for which chip pins). A processor-side pulse sequence on parallel-port pins (`0xffe7219c`) is gated by the word at `0x30000044` and by bit 7 of a board byte (`0xffe4f17e`); what sets them for an I-brick is U.

**Which link a request arrives on (E for the tables, I for the cabling).** The I-brick has no processor link (the peer-link routine `0xffe34774` returns at once for `I`, `0xffe34968`) and no USB (count 0). Its router maps slot 9 to UART device 3 and slot 10 to device 4 (`0xffe2dd48`; package 2 `0xffe33520`). Devices 3 and 4 are the RS-422 peer ports (107,142 baud, software flow control; `I` is in that group in packages 0 and 2, table at `0xffe5524e`/`0xffe756b2`, see [quad-uart-and-serial-links.md](quad-uart-and-serial-links.md)). The console is on port 5 (`I` is in the console group). A C-brick maps slot 1 to device 3 and slot 9 to device 4 (`0xffe2dda2`); its `cti`/`iia` command is slot 9 and `ctc`/`nia` slot 1 (flag words 9 and 1 in the entries `0xffe1c918`, `0xffe1c890`, tested by the slot-open predicate `0xffe2e88c` at `0xffe14fda`). Its `*` handler (`0xffe14acc`) walks the module records (0x70 bytes each from `0x30000a78`, count at `0x30000a7c`, accessor `0xffe31f00`), forms one address per record from the record's rack and slot words and sends the command text there through the router. So a C-brick `* power up` reaches an I-brick as a router packet on the RS-422 peer link, from a C slot (1 or 9) to an I slot (9 or 10); which C slot meets which I slot is cabling and is U. The command works only for a brick that has a module record, which the neighbour handshake fills (not read; U for the handshake).

**Summary.** An I-brick at mains is off with its bridges held in reset (E code path, I for the clean-start condition). It powers only when its own L1 receives `power up`: from its console, or from a C-brick over the RS-422 peer link (`* power up` or `cti power up`), or from an L2. Nothing in the I-brick image powers it by itself.

### I-brick `XBRIDGE CONTROL` bit by bit (package 0, 1.44.0)

Every bit use below is read from the routines named; the expander (index 5, M-Bus address `0x48`, name `XBRIDGE CONTROL`, applied value `0xd4`, input-bit mask 0, so all eight bits are outputs) carries no per-bit label in the image. The only labels are the log literals quoted. The reset table entry for the `I` brick (`0xffe46a0c`) holds the `XBRIDGE CONTROL` index (5) in byte 0, a second expander index (4) in byte 1, then the setting numbers `0x2a` and `0x2b` and the module-record numbers 1 and 2 as word pairs (bytes `05 04 00 00 00 00 00 2a 00 00 00 2b 00 00 00 01 00 00 00 02`), so the port-A and port-B enables read exactly those settings and records; the routine that reads both back at start-up (`0xffe47cd4`, source literal the controller firmware source unit 38) logs "Error reading XBridge control IOExp status" and "Error reading Port control IOExp status". E.

| Bit | Mask | What the firmware does with it | Grade |
|---|---|---|---|
| 0 | `0x01` | Reset group member. Driven low by reset-hold (`0xffe47ddc`, call `0xffe65e84(5, 0x0b, 0)`), released last: release writes `0x0a` to the group, 10 ticks later `0x0b`. Low at cold start (`0xd4`). | E for the writes, I that low is asserted (hold drives it low, release raises it) |
| 1 | `0x02` | Reset group member, released with bit 3 in the step before bit 0. Low at cold start. | E, as above |
| 3 | `0x08` | Reset group member, released with bit 1. Low at cold start. | E, as above |
| 2 | `0x04` | Not in the reset group. Release writes it set when module record 1 (a neighbor on host port A) is valid and persistent setting `0x2a` is nonzero, or when the global word at `0x30000130` forces it (`0xffe48446` to `0xffe48466`); a word at `0x3000012c` can force both enables clear (value 1) or both set (values 2 and 3) (`0xffe484a2` to `0xffe484dc`). Set at cold start (`0xd4`). | E for the condition; I that it is the enable of host port A |
| 4 | `0x10` | The same for record 2 (host port B) and setting `0x2b` (`0xffe4847e` to `0xffe4849c`). Set at cold start. | E, I as above |
| 5 | `0x20` | Clock-source select. The helper `0xffe480a4` decides it from the two host ports and release writes it with bits 2 and 4. The reader `0xffe47fd8` tests this one bit (`0xffe66044(5, 0x20)`) and returns the character `A` (`0x41`) when it is set and `B` (`0x42`) when it is clear; the helper's log text is "Neither port is okay for UST clock selection". Clear at cold start. | E for the bit and the A/B reading (reader read in full), I for the electrical meaning (what UST stands for is not stated in the image: U) |
| 6, 7 | `0x40`, `0x80` | Never written by reset hold or release in this package. Both are 1 in the cold-start value. | E for not written here, U for use |

How the helper picks a port (`0xffe480a4`, read in full). For each of host ports A and B it reads the port-control expander through `0xffe4f8d0`; a read error logs "Error reading port A status" or "... port B status" (strings `0xffe48750`, `0xffe48770`) and counts that port's status bit 0 as clear. A port is "ok" when its module record is valid and the record's brick-type word (`+0x10`) is one of `C 3 5 4 A 6 9 7 8 0 Q @ O B F H L` (compare chain `0xffe48150` to `0xffe481e6`; the same letters as the auto power-up list), or when this brick's own type is `%` (`0x25`) and `0xffe2d178(port)` is nonzero (`0xffe481f2` to `0xffe48206`). Only A ok gives `0x20`; only B ok gives 0. Both ok: with setting `0x2c` nonzero the result is `0x20` unless A's status bit 0 is clear and B's is set; with it zero the result is 0 unless B's status bit 0 is clear and A's is set. Neither ok: log, then `0x20` if setting `0x2c` is nonzero, else 0. So bit 5 chooses between the clocks arriving on host ports A and B. E for the logic, I for "clocks arriving": the image names only "UST clock selection".

What this does and does not settle. The three reset bits are written only as a group and have no individual name, so the image does not say which chip input each reaches. The expander is `XBRIDGE CONTROL`, the second expander named in the entry (index 4) is read back with it at start-up, and the other bits of the same byte are port enables and a clock select, so the three reset bits are board controls of the XBridge (I). Whether they are the chip's power-on reset, a warm-reset or link-reset input, or a PCI-side reset is U. Nothing in the firmware distinguishes them beyond the order of release (bits 1 and 3 together, then bit 0 ten ticks later) (E).

## R-brick (letter `R`)

**Board tables (E).** Initialiser `0xffe4a330` (package 2 initialiser matched at `0xffe693e8`): USB count 1, reset-hold hook `0xffe49fe0`, release hook `0xffe4a1b4`, no power-up veto. Registration `0xffe4a234`: 8 expanders at `0xffe4a3bc`, 5 supplies at `0xffe4a460`, one reset entry at `0xffe4a5d0`.

| Expander (index, M-Bus address) | Applied value | Use here |
|---|---|---|
| `POWER CONTROL` (0, `0x72`) | `0xff`, input bits `0xe0` | supply enables (active low) and bit `0x08` below |
| `ROUTER CONTROL` (2, `0x46`) | `0xf1` | reset lines and the router-type nibble |
| `PORT HA/BC/DE/FG CONTROL` (3 to 6, `0x48` to `0x4e`) | `0xd5`, `0xdd`, `0xdd`, `0x5d` | per-port control |

Supply enables in `POWER CONTROL`: `0x01` (type 8, 48 V) and `0x04` (type `0x0f`); the other three supplies are monitored only.

**Cold start (E for the writes).** Same rule as for the I-brick: `POWER CONTROL = 0xff` (both supplies off) and `ROUTER CONTROL = 0xf1` (the bits `0x0d` read `0x01`, the same value reset-hold writes). No power-up task for `R`. The R-brick is therefore off and in reset until a `power up` request reaches it.

**`power up` / `power down`** use the same routines as the I-brick (E). Power-up clears `0x01` then `0x04` in turn with 25 ticks after each, then runs the router-port helper `0xffe50b74(port, 3)` for ports 0 to 5 (`0xffe4cfc0`-`0xffe4cfe0`; I that these are the six router ports), then `reset` as above. Power-down holds reset and sets the two bits in reverse order. The serial-number check applies.

**`reset`** (E). Hold (`0xffe49fe0` through `0xffe49f88`): `ROUTER CONTROL` bits `0x0d` := `0x01` and `POWER CONTROL` bit `0x08` cleared. Release (`0xffe4a1b4` through `0xffe4a060`): `ROUTER CONTROL` bits `0xf0` := persistent setting `0x3c` (low nibble, shifted left four; a value outside the three accepted ones is replaced by `0xf` and stored) , which is the router type, so a type change takes effect at the next release; then only if the supply-state routine is nonzero: 10 ticks, `POWER CONTROL` bit `0x08` set; 10 ticks, `ROUTER CONTROL` `0x0d` := `0x09`; 10 ticks, `:= 0x0d`; 10 ticks, `:= 0x0c`. Which pins bit `0x08` of `POWER CONTROL` and the three `ROUTER CONTROL` bits are is U (named only by the expander labels).

**Does a C-brick `*` reach it with no L2? No (E for the R side, I for the C side).** The `R` letter is absent from the peer-link group (table `0xffe5524e` in package 0, `0xffe756b2` in package 2): the RS-422 ports 3 and 4 are never opened, and the router init has no slot mapping for `R` (its arm is `0xffe2de0a`, which adds nothing). The only external links `R` opens are the console (port 5), the node link (port 6, the processor/router side, [rs422-router.md](rs422-router.md)), on-chip UART 1 (power-bay link) and one USB device port, which needs a host. A C-brick's `*` goes out only on its router slots 1 and 9, so there is no listener on the R side and no path. An R-brick takes `power` and `reset` requests only from its own console or from a USB host, which in these systems is an L2.
