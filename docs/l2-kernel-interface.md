# L2: what the user-space programs need from the kernel and the board

This note is the kernel side of the L2 contract. [l2/userspace.md](l2/userspace.md) already lists every device node the programs open, every ioctl, the `/dev/mem` flash window, the NVRAM and partition-database addresses, the L1 USB link as the daemon sees it, and the failure paths of the opens. This note does not repeat those. It adds what they rest on: how the boot loader hands over to the kernel, the physical windows and on-chip blocks the kernel maps, which kernel facilities exist and which are absent, which kernel driver backs each node, the system-call surface of each program, the PCI and USB chain that must work before an L1 can be seen, the display and reset paths, and an ordered list of what has to hold for the daemon to reach the point where it registers an L1.

Everything is read from the L2 1.44.0 image (IRIX 6.5.30, `l2.bin`, sha256 `6bcfda07a24cb4d56850922dab17a98223abcd14221d307e3a8c3778434e8761`). The kernel is the gzip stream at file offset `0x4a218`, inflated to 1,430,148 bytes (`kernel.bin`, sha256 `b2f8aa846a2c...` in the first 12 digits). The inflated image is flat PowerPC code linked at virtual `0xc0000000`; an address below is the virtual address, and `kernel.bin` offset = address - `0xc0000000` (the same convention as [l2/userspace.md](l2/userspace.md)). The kernel has no symbols, so routine names below are my descriptions. Disassembly used capstone's 32-bit big-endian PowerPC decoder; every address was read in the listing.

Grades are those of [../AGENTS.md](../AGENTS.md). A fact taken from a public source and not seen in the image is written as a hint with its source. The boot loader that runs before the kernel is read in [l2-board-contract.md](l2-board-contract.md); this note cites that note and the wrapper addresses in it, and re-read the hand-off code itself in the 2026-11-10 review (section 13). Public sources named: the Linux 2.4 PowerPC 8xx platform, MBX board and driver sources (the kernel's own banner says 2.4.7; the tagged public tree read here is 2.4.0, and the host-bridge record layout was compared against the later 2.6.12-rc2 header, which adds one field), the MPC860 user manual and the Tundra QSpan documentation. The two manuals are not held (the reference search service was unreachable in the review), so register names and reset values that come from them are recalled, not checked, and are marked as hints.

Other versions: the same constants (the `ioremap` argument loads, the USB match word, the OHCI id table, the QSpan base, the panel names) occur as byte patterns in the kernels of all twenty other held L2 images from IRIX 6.5.13 on; the 6.5.12 kernel is an older build that lacks the QSpan, panel and OHCI-table patterns. That is graded inferred for those images: nothing but the patterns was compared.

## 1. Hand-off from the boot loader to the kernel

The kernel's first word is `mr r31,r3` at `0xc0000000`; it saves r3 to r7 and sets up the memory-management registers by hand (the standard 8xx start code). The platform-init routine at `0xc0132688` then reads the five registers as follows. Established.

| Register | Meaning | Read at | Grade |
|---|---|---|---|
| r3 | physical address of the board-information block; if nonzero, 28 bytes are copied from `r3 + 0xc0000000` to `0xc015ec74` | `0xc01326bc`, `0xc01326c0` | established |
| r4, r5 | physical start and end of an initial RAM disk, stored plus `0xc0000000` at `0xc015e428` and `0xc015e42c` | `0xc01326cc` to `0xc01326e0` | established |
| r6, r7 | physical start and end of the kernel command line; a zero byte is stored at the end address, then the text is copied to `0xc0117000` | `0xc01326ec` to `0xc0132704` | established |

The addition of `0xc0000000` shows that the loader passes **physical** addresses and that physical 0 is where the kernel is linked (virtual `0xc0000000` is physical 0). Established.

**Board-information block (28 bytes copied).** Offsets are those the kernel reads; the names are the public 8xx names for the same slots (hint). The last column is what the loader stores into the block (wrapper addresses, established; see [l2-board-contract.md](l2-board-contract.md) sections 2 and 7B).

| Offset | Use in the kernel | Evidence | What the loader stores |
|---|---|---|---|
| `+0x00` | no reader found | none | 0 (wrapper `0x704be4`) |
| `+0x04` | memory size in bytes; returned as the amount of RAM by the platform's end-of-memory hook (`0xc013267c`) and then capped by a `mem=` option | `0xc0132680`, `0xc01329b4` to `0xc01329d4` | `0x01000000`, 16 MiB (`0x704be8`) |
| `+0x08` | core clock in Hz; printed in MHz as "clock", and the divisor for the decrementer (`/16`) | `0xc000a684`, `0xc013250c` | `0x02faf080`, 50,000,000 (`0x704bec`) |
| `+0x0c` | bus clock in Hz; printed in MHz as "bus clock" | `0xc000a680` | the same 50,000,000 (`0x704bf4`) |
| `+0x10` to `+0x15` | the Ethernet address; the fast Ethernet driver copies six bytes from here into its station-address field, one byte per loop pass with an incrementing pointer (so `+0x14` and `+0x15` are read as address bytes 4 and 5) | `0xc013c26c` to `0xc013c2a8` | six bytes of tag 8 from the I2C EEPROM at address `0xa4`, copied one at a time (`0x704c28` to `0x704c8c`) |
| `+0x18` | console baud rate; compared against a table of 20 baud values at `0xc012ca68` (0, 50, 75, 110, 134, 150, 200, 300, 600, 1200, 1800, 2400, 4800, 9600, 19200, 38400, 57600, 115200, 230400, 460800), the matching index being used as the terminal baud code. The loop compares 21 words, because the word after the last value is also 0, so index 21 means "not found"; the code then falls back to code `0xd` (9600 baud) | `0xc013bf6c` to `0xc013bfb0` | `0x9600`, which is 38,400 written in hexadecimal digits, so index 15 (`0x704bc8`, `0x704bd4`) |

No kernel instruction loads the `+0x00` word, and none loads `+0x16` or `+0x17`; the earlier statement that nothing read `+0x14` was wrong, because the Ethernet driver reads the address through a moving pointer and an immediate-offset scan does not see it. The only routines that form the block's address are platform init, the cpu-information routine, the serial console set-up and the Ethernet driver. Established for the offsets read; the field names are hints. The 28-byte copy ends at `+0x1b`, so no later field of a longer public layout reaches the kernel.

The loader supplies, before the daemon can run: memory size, both clocks, the MAC address and the console rate (all established from the wrapper stores above). The image header's note that the loader fetches the MAC address from an I2C EEPROM ([l2/userspace.md](l2/userspace.md) section 5, from kernel strings) is confirmed by the wrapper; the kernel itself has no way to read an EEPROM (section 3). Which address in the wrapper's RAM the r3 value points at is inferred: the tail routine returns the variable at wrapper `0x705c84` (initial value `0x70ee8c`) and the final jump leaves r3 unchanged (`0x7009e8` to `0x7009ec`, `0x7000c0` to `0x700104`).

**Hand-off registers as the loader sets them.** The final stub (wrapper `0x7000c0` to `0x700104`) loads r4 and r5 from the wrapper variables at `0x705c88` and `0x705c8c`, the command-line start into r6 (variable at `0x705c6c`, a buffer at `0x70eea8`) and its end into r7 (found by scanning for the terminating zero), clears the link register to 0, writes `0x0c000000` to SPR `0x230` and executes `blr`, which branches to address 0 with translation off. That fits the physical addresses the kernel adds `0xc0000000` to. Established. The loader copies the ramdisk (the cramfs from flash) into RAM before this stub (call at `0x7007ec`) when the range between the flash constants `0xfe0d4ff1` and `0xfe2c9ff1` is non-empty; the range is a compile-time constant of about 2.0 MB, so that branch is always taken. Inferred for the copy destination and for r4/r5 being RAM addresses (the arithmetic at `0x7007d8` to `0x700814` was followed once, not exhaustively).

**Command-line options the kernel understands** (the `__setup` table, 24 entries of option string and handler at `0xc015d160` to `0xc015d21f`; each row is the option string and the handler address). Established. The table also holds `profile=`, `ro`, `rw`, `kbd-reset`, `netdev=` and `ether=`, which the rows below name only in passing.

| Option | Handler | Note | Grade |
|---|---|---|---|
| `root=` | `0xc01310fc` | the kernel prints the standard "append a correct root= option" message if the root cannot be opened (`0xc0135208`) | established |
| `mem=` | parsed in `0xc01319dc` | caps RAM; accepts `k` and `m` suffixes | established |
| `noinitrd`, `ramdisk_start=`, `load_ramdisk=`, `prompt_ramdisk=`, `ramdisk=`, `ramdisk_size=`, `ramdisk_blocksize=` | `0xc0137904` to `0xc0137a10` | RAM-disk handling | established |
| `console=`, `panic=`, `reserve=`, `memfrac=`, `profile=`, `debug`, `quiet`, `l2cr=` | generic | | established |
| `wdt_8xx=` | `0xc0137648` | software watchdog switch (section 8) | established |
| `pci=` | `0xc01394ac` | PCI options | established |
| `video=` | `0xc013a234` | the generic frame-buffer option: it first handles `scrollback:`, then compares the text against the name of each registered frame-buffer driver followed by a colon and hands the remainder to that driver's own setup routine. The only registered driver is `sgil2fb`, whose setup routine is `0xc013aecc` (section 7). So the panel choice is `video=sgil2fb:color` or `video=sgil2fb:mono` | established |

The initial command line is empty in the image (`0xc0117000` is zero in the file), so the root device, console and panel come from the loader. **What the loader passes**, read in the wrapper (`0x700838` to `0x70099c`): the base text is `root=/dev/ram` when the ramdisk range is non-empty (it always is, see above; the alternative text is a network root, `root=/dev/nfs rw`, never chosen here), then the fixed text ` panic=5 ` (string at `0x705348`), then whatever the operator types on the console during a polling loop of up to 1,999 passes of the delay routine (`0x7008c8` to `0x700970`; the real length of that window depends on the unresolved tick length, so the usual figure of about two seconds is not established). There is no `video=`, `console=` or `wdt_8xx=` text. Established for the fragments and the order; the branch choice rests on the constant range check (inferred, arithmetic only). Consequences: the greyscale panel is used unless the operator types an option (section 7); a kernel panic restarts the processor after five seconds through the reset path in section 8 (the restart-on-timeout behaviour is the public kernel's, hint); no console is named, so which port the kernel console uses is the console set-up's default (section 11, item 1). The kernel can find a cramfs in a RAM disk (it prints "cramfs filesystem found at block"), and the 512-byte pad before the cramfs superblock ([l2/image-layout.md](l2/image-layout.md)) is compatible with the public cramfs reader, which accepts its superblock at offset 0 or at offset 512 (hint: Linux 2.4 `fs/cramfs/inode.c`). Which of the two the kernel's RAM-disk detector expects was not read.

## 2. Windows and on-chip blocks the kernel maps

During early memory-management setup (`0xc0132944`, called right after platform init) the kernel makes six calls to its I/O-remap routine (`0xc000ba60`, which tail-calls `0xc000ba84` with the "uncached" flag value 2). Before the kernel's memory initialisation has finished the routine returns the physical address as the virtual address, because the variable that bounds "descending" allocations (`0xc015e098`) is never written in the image text and so stays zero (read in `0xc000bb48` to `0xc000bb5c`). So these are one-to-one mappings. Established for the calls and the arguments; inferred for the one-to-one result (it rests on the variable never being stored, found by scanning every store with that offset).

| Physical base | Length | What it is | Evidence |
|---|---|---|---|
| `0xfa200000` | `0x10000` | the on-chip register block of the MPC860-family processor (the kernel's own interrupt, serial, timer, clock, watchdog, real-time-clock, I2C and Ethernet code all address it) | the section 4 users below; `0xc0132a1c` |
| `0xfa100000` | `0x1000` | a byte-wide board register block: the ROM stage and the wrapper write it (`l2-board-contract.md` section 7D; wrapper `0x704bac` to `0x704bbc`). The same address and role are the public MBX board's control and status block (`MBX_CSR_ADDR` in `include/asm-ppc/mbx.h`, mapped in `arch/ppc/mm/init.c`; hint). After the mapping the kernel image has no use of the returned pointer that was found, and no user-space program forms the address. What each bit does on this board is unknown | `0xc0132a28`; scan of `lis` immediates in the kernel and in every ELF file of the tree |
| `0xfa210000` | `0x10000` | the PCI bridge's own register window (section 6); its address is also the initial value of the pointer the config-cycle routines load (`0xc012f2d0`) | `0xc0132a34`, `0xc012f2d0` |
| `0x10000000` | `0x20000` | the LCD controller: display memory from the base, registers in the last `0x20` bytes (section 7) | `0xc0132a40`; the LCD set-up at `0xc013ab10` |
| `0xfe000000` | `0x400000` | the flash window, the same 4 MiB the daemon maps through `/dev/mem` | `0xc0132a4c` |
| `0xfa210000` | `0x10000` | mapped a second time | `0xc0132a54` |

Separately, the PCI host set-up (`0xc01327d8`) maps `0x80000000` with length `0x20000000` (512 MiB) the same way (`0xc0132828` to `0xc0132830`) and stores the result in the host-bridge record. **This window is the PCI I/O-space window, not memory space.** The six stores at `0xc0132818` to `0xc013283c` fill the record at offsets `+0x10` (0), `+0x14` (`0xff`), `+0x18` (the mapped address), `+0x1c` (`0x80000000`), `+0x20` (0) and `+0x24` (the configuration-access table), which are, in that order, the first and last bus numbers, the virtual and physical I/O base, the PCI-memory offset and the operations pointer of the public PowerPC host-bridge structure (hint: `struct pci_controller` in `include/asm-ppc/pci-bridge.h`; the 2.4.7 header is not held, and the 2.6.12-rc2 header differs by one extra field after the bus numbers, which the stores do not fit, so the match is inferred). A memory offset of 0 means the kernel treats PCI memory addresses as CPU addresses one for one. The public MBX board map agrees: `PCI_ISA_IO_ADDR` is `0x80000000` (512 MiB) and `PCI_ISA_MEM_ADDR` is `0xc0000000` (512 MiB), and the public QSpan boot code says the processor address decides the cycle type, I/O at `0x80000000` and memory at `0xc0000000` (`arch/ppc/mbxboot/qspan_pci.c`; hint). The memory window the controllers use is therefore the one at `0xc0000000` (section 6). Established for the call and the six stores; inferred for the role.

The kernel never touches the flash window itself and has no flash driver (section 3); it maps it so that the window exists. The user-space mapping through `/dev/mem` is an independent `mmap` of the same physical range ([l2/libdrivers.md](l2/libdrivers.md)). Whether `/dev/mem` can map `0xfc000000`, the first base `libdrivers` tries, and what a load from an unpopulated address does is unknown (section 11, item 8).

## 6. The PCI and USB chain that must work before an L1 is seen

This is the part of the boot the daemon cannot influence. It is why `/dev/sgil1_cs` reads all zeros when it fails.

**PCI host.** The kernel's PCI host set-up (`0xc01327d8`) allocates one host-bridge record and prints "Can't alloc PCI controller structure for QSpan PCI" on failure (established; the name is the kernel's own string). It sets bus numbers 0 to `0xff`, the physical I/O window base `0x80000000` (record `+0x1c`), the mapped window from section 2 (`+0x18`), a PCI-memory offset of 0 (`+0x20`) and the configuration-access routine table at `0xc011a1fc` (`+0x24`). Established for the stores; the field names are inferred as in section 2.

Configuration cycles (the six routines at `0xc000a78c` to `0xc000a8b8`, with the worker routines at `0xc000a934`, `0xc000aa0c`, `0xc000aae4`, `0xc000abac`, `0xc000ac78`, `0xc000ad44`) work like this. Established from `0xc000abac` and `0xc000ad44` and the address builder at `0xc000a8f4`:

1. The bus number must be at most 7 and the device-and-function byte below `0x80`; anything else returns the standard "device not found" status `0x86`.
2. With interrupts off, the routine sets bit `0x1000` in the bridge register at offset `0x800` of the bridge window.
3. It stores the configuration address word at offset `0x500`: bus number in bits 16 to 23, device and function in bits 8 to 15, the register number with its low two bits cleared, and bit 0 set when the bus number is nonzero (a type-1 cycle).
4. Data moves through offset `0x504` of the bridge window: a 32-bit store or load for a word, and for bytes and halfwords at `0x504 + ((register xor 3) & 3)` (byte) or the equivalent for a halfword, which is the big-endian lane of the little-endian register. There is no software byte swap, so the bridge swaps in hardware (inferred from the absence of swap instructions).
5. It clears bit `0x1000` of offset `0x800` again.

Offsets `0x500` and `0x504` are the configuration-address and configuration-data registers of the bridge window in the public Linux QSpan code, which names them exactly so (hint: `arch/ppc/kernel/qspan_pci.c`, read in the review; established match of the offsets). Offset `0x800` has no name in that code. The public kernel file uses it not at all; it toggles a board-control bit (`BCSR2_QSPACESEL`) around each configuration cycle on the RPX board instead, and the public MBX boot code writes the 32-bit word at `0x800` (`qptr[512]`) once at start-up with `0x000c0003`. The wrapper writes `0x000c1013` there ([l2-board-contract.md](l2-board-contract.md) section 7C), and the kernel sets and clears bit `0x1000` of it around each cycle. So the kernel's toggle plays the part of the RPX board bit, which is a reasoned reading (inferred); the register's name and the meaning of the bit are unknown (bridge manual not held). The wrapper's other bridge writes follow the same public boot code value for value where the words overlap (`+0x004 = 0xf9000147`, the variant for external bus arbitration; `+0x00c = 0`; `+0x104 = 0x80000000`; `+0xf00 = 0x01000000`), which identifies the bridge family further (hint) but gives no register meanings.

**OHCI.** The USB host driver's PCI id table is at `0xc015cee8` and has two entries (established): vendor `0x1022` device `0x740c` with the driver-data bit that selects the "AMD756 erratum 4 workaround" message, and a class entry for class code `0x0c0310` (serial bus, USB, OHCI) for any vendor. The probe (`0xc013b388`) requires a nonzero interrupt line in the device record ("found OHCI device with no IRQ assigned"), takes the first memory region of the device, maps it with `ioremap`, and calls the controller set-up (`0xc013b158`), which requests the interrupt, resets the controller, waits in a ten-step delay loop, and starts it. The controller therefore needs: a PCI function that answers configuration reads, a memory region, and a working interrupt line. **The loader programs both functions before the kernel starts.** It accepts PCI devices 4 and 5 on bus 0 only when the first configuration dword is `0x580111c1` or `0x580211c1` (vendor `0x11c1`, device `0x5801` or `0x5802`), writes and reads back base register 0, and writes the interrupt line byte: device 4 gets base `0xc0000000` and line 8, device 5 gets base `0xc0001000` and line `0xa` (wrapper `0x704c9c` to `0x704cc0`, routine `0x704944`). Established. The kernel's own id table matches by class code, so the kernel does not depend on those vendor and device numbers. The two bases lie in the memory window at `0xc0000000` (section 2), not in the I/O window at `0x80000000`. **Unknown:** whether the kernel keeps those bases or reassigns them, which processor interrupt input lines 8 and `0xa` become, and the USB topology (section 11, item 3).

**Hub and device enumeration.** The standard Linux 2.4 hub driver (strings `hub.c: ...`) walks ports and gives devices numbers; the kernel stops a device path at six hubs ([l2/userspace.md](l2/userspace.md) section 4, the 9-byte record). Whether an external hub sits between the root hub and the L1 connectors, and how many root ports there are, is unknown.

**Class driver match.** [l2/userspace.md](l2/userspace.md) section 10 records the match as a descriptor word, one configuration, one interface and a bulk-out then bulk-in pair. The exact test in `0xc009e4b8`, which this note adds, is: the device descriptor word at `+0xbc` of the device record equals `0x065e1234` (vendor `0x065e` and product `0x1234`, as the L1's descriptor in [l1/protocols.tsv](l1/protocols.tsv) row 6 shows); the byte at `+0xc5` (configuration count) is 1; the configuration has one interface; the probe's interface argument is 0; that interface's setting has two endpoints; the first endpoint's address-and-attributes word masked with `0x8003` equals 2 (OUT, bulk) and the second's masked with `0x8003` equals `0x8002` (IN, bulk). It then takes the first free entry of a 40-entry slot table of `0x88` bytes at `0xc0195384` (free means the first word and the byte at `+0xd` are both zero, `0xc009d62c`), fills it, allocates two URBs, logs "SGI L1 connected, minor: %d device: %d.%d" and sets the change flag that makes `sgil1_cs` readable (`0xc009d5c8`). Established. A forty-first device is not claimed (the allocation routine returns -1 and the probe returns 0).

## 7. The display

Established from the frame-buffer set-up at `0xc013ad74` and the LCD controller routine at `0xc013ab10`; the first sentence of each point is established, any extension is marked.

- The controller is an Epson SED1375-family part. The routine prints "SED1375" unconditionally (the 1374 string is also in the image but is not selected by the code read), display memory starts at physical `0x10000000`, and the register block is the top `0x20` bytes of a `0x20000`-byte decode, at `0x1001ffe0`. The frame buffer's start (`0xc015e4bc`), size (`0xc015e4c0`) and line length (`0xc015e4c4`) are variables set at `0xc013ab2c` to `0xc013ab68`.
- Two panels are built in, as records at `0xc012bcf8` (a Hantronix 320 by 240 4-bit greyscale panel, 160 bytes per line, 38,400 bytes) and `0xc012bd14` (a Hantronix 320 by 240 8-bit passive colour panel, 320 bytes per line, 76,800 bytes). The line length is `width << log2(bpp) / 8`, the size is line length times height (`0xc013ab4c` to `0xc013ab64`). The pointer to the active record is initialised in the image to the greyscale record (`0xc012f5f0` holds `0xc012bcf8`). The option is `video=sgil2fb:color` or `video=sgil2fb:mono`: the setup routine `0xc013aecc` is the `setup` field of the single frame-buffer driver record at `0xc0159a08` (name pointer `sgil2fb`, init routine `0xc013ad74`, setup routine `0xc013aecc`), reached from the `video=` option handler (section 1). It splits the text after `sgil2fb:` at commas and compares each piece with `color` and then `mono`, five bytes each, so the terminator must match; a match replaces the record pointer with the colour or the greyscale record (`0xc013af08` to `0xc013af58`). The text `SED137X` is not an option: it is only the identification string copied into the frame-buffer information record (`0xc008e0e0` to `0xc008e0ec`). Established. The wrapper passes no such option (section 1), so unless the operator types one the greyscale panel is used (established for the loader's text; the operator window can change it).
- The controller's registers are loaded from the panel record (`0xc013abb8` to `0xc013acd0`): register `+1` is packed from record bytes `+0x11` to `+0x15`; register `+2` from bytes `+0x10` and `+0x16` to `+0x19`; register `+3` gets 3; register `+4` gets width/8 - 1; registers `+5` and `+6` get the low and high bytes of height - 1, and `+0x12` and `+0x13` repeat them; register `+8` gets record byte `+0x1a` and `+0xa` gets `+0x1b`; register `+0x19` gets `0x1e`; the remaining registers from `+7` to `+0x1c` that are stored get zero. The per-panel bytes are in the records (greyscale: `+0x10..+0x1b` = `02 00 00 00 / 00 01 01 00 / 01 00 1e 3b`; colour: `03 03 01 00 / 00 01 01 00 / 00 00 10 01`); the meaning of each register is the manufacturer's and was not mapped here.
- The routine also writes a zero byte to `0x1000ffe0` (a display-memory address, not a register) at `0xc013ab7c`, and then fills `0x9600` (38,400) bytes of display memory from a table at `0xc01226f8`, byte by byte with a per-byte bit transformation (`0xc013acd8` to `0xc013ad58`). That count is the greyscale panel's frame size. Established for the loop bounds; the transformation and the table's picture are not decoded. The purpose of the single byte store is unknown.
- Frame-buffer attributes: start `0x10000000`; length equal to the size variable above; the panel record's byte `+0x10` (log2 of bits per pixel: 2 for the greyscale panel, 3 for the colour panel) is tested against 1 (`0xc013ae18` to `0xc013ae38`): a field at `+0xbc` of the frame-buffer record is set to 0 when it equals 1 and to 3 otherwise, and in the otherwise case a halfword at `+0xd0` is set to 1. By position these are the visual (0 monochrome, 3 pseudo-colour) and a colour-map length; both built-in panels take the otherwise case, so both report a palette visual, which is the branch of `l2gui` that skips the true-colour check and uses `FBIOGETCMAP` and `FBIOPUTCMAP` ([l2/userspace.md](l2/userspace.md) section 3). The offsets in the frame-buffer information record are matched to the public 2.4 layout from the position of each store, so the visual and length fields are inferred, not established. The `mmap` length `l2gui` passes is therefore the panel's size rounded up to a page: 40,960 bytes for the greyscale panel and 77,824 for the colour panel (inferred; this fills the gap [l2/userspace.md](l2/userspace.md) section 3 leaves for the length).
- The touch port `/dev/ttyS3` is the fourth on-chip SCC; the kernel treats it as an ordinary terminal and has no touch-panel driver (no string; inferred role as in [l2/userspace.md](l2/userspace.md)).

## 8. Reset, halt, watchdog, clock and I2C

- **Reset, halt and power-off are the same action.** The platform's three hooks for restart, power-off and halt (stores at `0xc0132774` to `0xc0132790` into the platform record at `0xc015e7f0`) are `0xc000a5e0` and two thin routines (`0xc000a624`, `0xc000a648`) that call it with 0. `0xc000a5e0` sets bit `0x80` in the register at offset `0x284` of the on-chip block, clears the machine-check-enable bit of the machine-state register, and then reads the byte at offset `0x28c`; if the processor survives it prints "Restart failed" and loops. The sequence is the one the public 8xx code uses to force a checkstop reset by touching an unimplemented register (hint: Linux 2.4 `m8xx_setup.c`; `0x284` is the PLL, low-power and reset control register in the MPC860 manual, recalled). So `/sbin/reboot` (the daemon's `init 6` and `/sbin/reboot` calls), `halt` (`init 0`) and the `poweroff` binary all end in a processor reset; nothing powers the L2 down. Established for the code; the register names are hints.
- **Watchdog.** The wrapper never writes the system protection control register on a normal boot. The only write of `0xffffff80` to it (flash `0xfe004f78` to `0xfe004f84`) is on the failure path after an image-check failure or a return from the second stage, so it does not decide the kernel's view. The wrapper does write the service key pair `0x556c` and `0xaa39` to the service register (offset `0xe` of the on-chip block) in its console-wait loop and around the kernel decompression (`0x7008cc` to `0x7008d8`, `0x7009a4` to `0x7009d4`), which suggests it expects the watchdog may be running (inferred). So the state the kernel finds is the chip's reset state. Established for the stores; the reset state is unknown (MPC860 manual not held). `wdt_mpc8xx` (`0xc0137500`) reads the system protection control register at offset `+4`; if the software-watchdog enable bit (`0x4`) is clear it prints "SWT not enabled by firmware" and the driver does not start. If set, it loads the maximum timeout, sets two more bits (`0x3`), services the watchdog with the key pair `0x556c` and `0xaa39` at offset `0xe`, starts a kernel timer, and registers the misc device. No L2 program opens `/dev/watchdog`; that the kernel timer is what keeps servicing it is inferred (the timer callback at `0xc007f5e8` was not read), as is the meaning of the bits `0x3` (reset on timeout and a prescaler, from the MPC860 manual as recalled). The register accesses are established. The loader does not enable the watchdog (established); whether the chip comes out of reset with it armed is unknown (section 11, item 2). The option `wdt_8xx=` can switch it off, and the loader does not pass it.
- **Real-time clock.** The hooks at `0xc000a5ac` and `0xc000a5d4` read and write the on-chip clock (section 4). `rc.sysinit`'s `hwclock --hctosys` and the daemon's `date` command (`hwclock -u --systohc`) go through `/dev/rtc`. The kernel also writes the clock-source and decrementer set-up (`0xc01324f0`) into the register at offset `0x280` with its key at `0x380`. Established for the stores; the register names are hints.
- **I2C.** The adapter and `/dev/i2c-0` exist; no client driver (no EEPROM, no sensor) is present, and no program opens the node ([l2/userspace.md](l2/userspace.md) section 5). So in 1.44.0 **no vital-product data is read by the kernel or by user space**; the board's own EEPROM is read only by the boot loader (256 bytes at I2C address `0xa4`, tag 8 for the MAC address; [l2-board-contract.md](l2-board-contract.md) section 7B). Established for the kernel, the tree and the loader.

## 9. What the daemon needs, in order, to register an L1

The daemon's registration is the call `L2CfgMAddPort` with type 2 inside the open of a slot ([l2/userspace.md](l2/userspace.md) section 8, step 3), and the port becomes usable when a reply to the first configuration request has been processed ([l2/config-request-reply.md](l2/config-request-reply.md)). This list says what must hold underneath, step by step, and who provides it. Grades are per step; "established" means read in the 1.44.0 image.

1. **Loader to kernel.** Physical addresses in r3 to r7 as in section 1, with the board block holding memory size, clocks, MAC address and baud rate; a RAM disk range holding the cramfs, or a root given by `root=`. Provider: the boot loader, which sets r3 to r7 as section 1 states, passes `root=/dev/ram` and copies the cramfs into RAM as the ramdisk. Established for the registers and command line; the copy destination is inferred.
2. **Kernel up.** Memory-management set-up maps the windows of section 2; the on-chip block must be at `0xfa200000`. Provider: the reset code and the ROM stage set the on-chip block base to `0xfa200000` and program the chip selects (the table in [l2-board-contract.md](l2-board-contract.md) section 5, established), including the windows of section 2.
3. **Console and `init`.** The kernel opens `/dev/console` (link to `ttyS1`) and execs `/bin/init`; the serial console set-up uses the baud from the board block. Established (strings "unable to open an initial console", "No init found").
4. **`rc.sysinit`.** `tmpfs` mounts, `mount -a` (`proc`, `usbdevfs`), `hwclock`, `l2passwd`, `l2staticip`, loopback and default route. These can fail without stopping boot; `usbdevfs` must exist as a file system type for `/proc/bus/usb` but the daemon does not use it. Established ([rootfs.md](l2/rootfs.md)).
5. **Daemon start (`inittab` entry `l2`).** `/dev/mem` must be openable and the flash window must be mappable and readable, or the daemon dies in its version lookup ([l2/user-mode.md](l2/user-mode.md)); a semaphore key must be creatable (`semget` works with System V IPC in the kernel); the sockets in section 3 must exist. Established for the dependencies; the cause of the early failure is read in [l2/user-mode.md](l2/user-mode.md).
6. **USB.** PCI configuration cycles through the QSpan bridge (section 6) must answer for the OHCI function; the OHCI function must have a nonzero interrupt line and a memory region; the controller must reset and the root hub must report a connected device; the device must enumerate with the descriptor shape in section 6. Provider: the loader programs the bridge, the two USB host controllers' base registers and interrupt lines before the kernel starts (section 6, established); the kernel runs the configuration cycles, the OHCI driver and the class driver.
7. **Class driver.** The probe of section 6 claims the device, assigns it a slot, and raises the change flag.
8. **Daemon opens `/dev/sgil1_cs`, reads 0x28 status bytes, opens `/dev/sgil1_N` and registers.** From [l2/userspace.md](l2/userspace.md) section 8.
9. **Request and reply.** The first request goes out 0.75 s after the open, to the L1, over the bulk-out endpoint; the reply arrives on the bulk-in endpoint; the port state becomes 2 ([l2/config-request-reply.md](l2/config-request-reply.md)).

The Ethernet controller, the PHY, the display, the watchdog, the real-time clock and I2C do not appear in this chain. A missing Ethernet address affects the network listeners and the partition and flash-update clients (they connect to `localhost` over loopback); it does not affect USB registration.

## 11. Unknowns and the software test that settles each

Items 1 to 4 and 7 of the first version are settled or narrowed by the loader read ([l2-board-contract.md](l2-board-contract.md)); what remains of them is stated here.

1. **Which serial port the kernel console uses when no `console=` text is passed** (the loader passes none, section 1). Test: follow the console set-up at `0xc013bf48` and the console registration in the 8xx serial driver to the port index it takes when the console option is absent; compare with the `/dev/console` link to `ttyS1`.
2. **The reset state of the software watchdog enable bit.** The loader does not enable it (section 8). Test: read the MPC860 manual's reset value for the system protection control register and the hard-reset configuration word rules; the kernel tests bit `0x4`, so that decides between "SWT not enabled by firmware" and a started watchdog.
3. **The interrupt inputs behind PCI interrupt lines 8 and `0xa`, whether the kernel keeps the loader's base registers, and the USB topology (root ports, any external hub).** Test: follow the kernel's PCI device set-up that reads the interrupt line and the 8xx interrupt-number translation to the `request_irq` of the OHCI driver; check whether the PCI resource assignment re-writes base register 0; count ports from the root-hub descriptor routine (`hub.c` strings, power-on-to-power-good print).
4. **What each bit of the byte-wide block at `0xfa100000` does on this board.** The mapping origin and the writers are known (section 2). Test: compare the loader's byte sequence (offset 0: `0x00` then `0x80`; offset 3: `0x18`; offset 1: `0x0e`, `0x0f`, `0x0e`) with the public MBX board register definitions; a bit-for-bit match to named bits would grade them, a mismatch leaves the block as an SGI-specific control register.
5. **Whether a failed bind of the Unix-domain path is fatal, and whether the default USB mode ever binds it.** Test: read the callers of the address builder at `libRouter` `0xd078` and the error path after `bind`; find which of them the USB-mode start-up calls.
6. **What `l2gui` does when its font files are absent.** Test: in `l2gui`, find the `fopen` of the paths under `/usr/local/microwin/fonts/` and read what follows a null return.
7. **Whether an operator-typed `video=sgil2fb:` option is ever used in production.** The default is greyscale (section 7). Test: none by software; the wait window length also depends on the unresolved tick length (item 12).
8. **What a load from an unpopulated address does, for example the first flash base `0xfc000000` that `libdrivers` tries.** Test: read the 8xx machine-check vector at `0xc0000200` and its handler to see whether a user-mode machine check becomes `SIGBUS`; read `libdrivers`' probe at `0x17fc` to `0x19b4` to see which access it makes.
9. **The register meaning of the LCD controller's writes and the byte store at `0x1000ffe0`.** Test: compare the register offsets and bit packing at `0xc013abb8` to `0xc013ac9c` with the SED1375 manual; the manual is not in the held references.
10. **The QSpan register name and bit meaning of offset `0x800` bit `0x1000`, and the translation the bridge applies between processor `0xc0000000` and PCI memory addresses.** The kernel's PCI-memory offset of 0 is read (section 2); the hardware side is not. Test: compare the wrapper's bridge writes (board contract section 7C) with the bridge's user manual; a match of the image translation register to base `0xc0000000` would settle the one-for-one claim.
11. **Whether the kernel's host-bridge record layout is the 2.4.7 `pci_controller` exactly.** Test: read the 2.4.7 header (not held) or find a consumer of record `+0x1c` or `+0x20` in the kernel, such as the I/O base routine, and see which field it treats as the I/O physical base.
12. **The real length of a loader delay unit (the time base tick).** Settled by the clock and PLL decode in the board contract (its unknown about the time-base tick), not here.

## 13. Review (2026-11-10)

An independent reader checked the first version of this note (commit `d75bbd5`) against `l2.bin`, the inflated kernel, the loader and the public Linux 2.4 sources and reported six problems. Each was re-checked here by disassembling the same bytes (capstone, PowerPC big-endian; the image hash and the kernel hash are the ones in the opening paragraph, and the inflated kernel was regenerated from the gzip stream at file offset `0x4a218` and compared byte for byte).

| Finding | Outcome | Where it landed |
|---|---|---|
| The window at `0x80000000` is the PCI I/O window, not memory space, and the controllers sit at `0xc0000000` and `0xc0001000` | **Upheld.** The six stores into the host-bridge record match the public host-bridge structure field for field (first bus, last bus, virtual and physical I/O base, memory offset, operations); the public MBX map and boot code say the same. The role is graded inferred (the exact 2.4.7 header is not held), the stores established. The loader assigns both controllers' bases and interrupt lines | sections 2, 6, 9, 10; unknown 11 |
| The loader is already read; unknowns 1 to 4 and the "provider unknown" lines are settled by the board contract | **Upheld for 1, 3 and the providers; partly for 2 and 4.** Hand-off registers, board-information stores, command line, PCI set-up and EEPROM MAC are confirmed in the wrapper. The command-line branch the reviewer did not trace (`root=/dev/ram`) was traced: the choice rests on a compile-time constant range, so it is always the ramdisk text | sections 1, 8, 9, 11 |
| `SED137X` is not the option | **Upheld.** The panel choice is `video=sgil2fb:color` or `video=sgil2fb:mono`; the string `SED137X` only fills the frame-buffer information record's identification field. The reviewer put the driver record at `0xc0159a0c`; that is the init routine word, the record starts at `0xc0159a08`. The `__setup` table has 24 entries; the missing ones are listed | sections 1, 7 |
| Board-information offsets contradict each other | **Upheld.** The Ethernet driver reads six bytes from `+0x10` with an incrementing pointer, so `+0x14` and `+0x15` are read; the immediate-offset scan missed it | section 1 |
| Baud table | **Upheld.** 20 values, 21 words compared, the unmatched case falls back to the 9600 code `0xd` | section 1 |
| `0x800` is not "the miscellaneous register" of the public QSpan code | **Upheld.** The public kernel file never uses it; the public MBX boot code writes it once as a bare word, and the wrapper's other bridge words repeat that code's values | section 6; unknown 10 |

Rejected or narrowed:

- **The loader's SYPCR write does not make the watchdog unarmed by firmware.** The reviewer read the store at flash `0xfe004f78` as a normal-boot write with the enable bit clear. It is reached only after the image-header check fails or the second stage returns, as the board contract already states (its own review withdrew the opposite claim). On a normal boot the loader never writes the register, so the chip's reset state decides, and it is unknown. The loader does service the watchdog, which hints that it may be running.
- **`0xfa100000` is not settled.** The kernel mapping and the public MBX address match, and the loader's writes are established, but the byte sequence matches no named bit of the public block in an obvious way and the kernel never uses the pointer, so the block stays a board control register of unknown bit meaning.
- **The two-second operator window is not established.** The loop is 1,999 passes of a delay routine whose unit depends on the unresolved tick length.
- **"PCI memory maps one for one"** is established only as the kernel's assumption (offset 0); whether the bridge translates `0xc0000000` that way is open (unknown 10).

Also corrected without a reviewer finding: the new table in section 1 records what the loader stores in each slot; the opening paragraph now cites the board contract.
