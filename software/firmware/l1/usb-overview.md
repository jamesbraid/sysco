# Origin 300 L1 1.44.0: management USB reading

It describes what that firmware can do. It does not establish which USB device-controller revision is fitted to an Origin 300 board, how many such controllers are populated, or that an L2 is present in a particular chassis. The L1 management USB port is separate from the IO-8's PCI OHCI controller and the guest's two USB ports. The Origin 300 User's Guide labels the rear management connector `USB L1 port` and lists the ordinary USB ports separately (007-4365-002, printed pages 1, 10–12, 67 and 73–74).

## Evidence and limits

The image is the Origin 300 L1 1.44.0 body ([package-container.md](package-container.md)); its first program bank loads at `0xffe00000`. Addresses below refer to the first bank. The program has a second, partly relocated bank beginning `0x70000` later; the image does not settle which bank runs at boot.

The Origin 300-applicable controller guide calls the L1 USB connection a **slave port** to upstream controllers (007-3938-001, printed page 3). The Origin 300 with NUMAlink Module guide places a USB hub and L2 controller in systems with a NUMAlink module, and shows the module/hub-to-L2 cabling (007-4498-002, printed pages 10–13 and 83–91). Its layout is product-specific: a one- or two-chassis Origin 300 needs neither that module nor an L2 (007-4365-002, printed pages 36–41; 007-3938-001, printed pages 11–16). The `usb` operator-command examples in the later 2005 controller guide are explicitly limited there to Altix 3000 service use; they prove the family command's format, not an Origin 300 USB-chip population (007-3938-006, printed page 111).

Hint: the MCF5206E User's Manual (printed chapters 6 and 12) describes an external peripheral bus and no integrated USB controller. The USB device controller is therefore a separate part, and no image names it. The USS-820-family inference comes from this image's probe behaviour (see [usb-controller-registers.md](usb-controller-registers.md)).

## Does this L1 run Linux?

The selected **Origin 300 L1 1.44.0 range** has positive evidence of Nucleus Plus, not a Linux boot path. Its first words form a ColdFire reset-vector table with an initial stack pointer and reset entry, then its reset path initializes memory and creates a main task (`0xffe00000`–`0xffe00400`, `0xffe00400`–`0xffe10570`). This range names **Nucleus** and **Nucleus Plus** in fatal-error and status texts (`0xffe387d7`, `0xffe57545`–`0xffe57618`, `0xffe5d8da`), and its timer, semaphore, task and interrupt paths call that embedded RTOS's services (`0xffe40bc0`–`0xffe42550`, `0xffe6e818`–`0xffe6ea9e`). The composite also contains gzip data labeled `kernel` near offsets `0x565180` and `0xabb6d4`, with CramFS images near `0x5f887c` and `0xb94770`, in other packaged ranges. Those signatures prevent an OS claim for the composite as a whole; their contents and target roles were not determined here. Public controller and topology guides distinguish the L1 from a separately cabled L2 (007-3938-001, printed page 3; 007-4498-002, printed pages 10–13). This Nucleus conclusion says nothing about the L2 or other L1 revisions.

## Bring-up and USB role

The L1 boot sequence calls a USB setup routine after local packet routing is initialized (`0xffe10570`–`0xffe10720`). Setup reads a per-brick count and returns if it is zero. It warns when the count exceeds two, initializes per-instance state, a shared write queue and semaphore, a write task, then creates receive tasks for instance zero and, when configured, instance one (`0xffe2cf94`–`0xffe2d176`). This is a multi-product firmware capability, not a count of controllers on IP45 hardware. Each receive task waits for its USB function to open before declaring it available (`0xffe2d1c4`–`0xffe2d230`).

The lower layer has a probe consistent with a USS-820-family device controller: it reads a revision value and tests a scratch register before installing the device callbacks (`0xffe70968`–`0xffe70ad8`). An invalid revision pattern or failed scratch test is a setup error. It then creates reset, control, read and write work, registers the interrupt path, resets the function and starts control handling (`0xffe6e818`–`0xffe6ea9e`). The reset/control path accepts standard USB device requests: device, configuration and string descriptors; address and configuration changes; interface/status queries; and endpoint halt control (`0xffe6f158`–`0xffe6fcf8`). That is evidence that the L1 is the USB **device** presented for enumeration by an upstream host. The declared USB revision and attributes are in [usb-descriptor-fields.md](usb-descriptor-fields.md); host acceptance and the fitted controller revision and FIFO allocation are open.

The USB status path formats per-instance disconnect and bus-reset counters, then three logical endpoint rows named control, read and write with state, status, stalls, errors and timeouts (`0xffe6df18`–`0xffe6e0b8`). The public `usb` example prints the same columns (007-3938-006, printed page 111). Its shown counters and states come from an Altix 3000 example; they are not reset defaults for Origin 300.

## Management packet transport and routing

When the USB function opens, the receive task attempts a catch-all request/response destination with the L1 packet router only when a runtime guard is clear, then attempts an event path. It records the first open USB function as the event destination (`0xffe2d23e`–`0xffe2d34a`). The catch-all targets the nonlocal destination space rather than a new local task, and the router's nonlocal branch can overwrite an existing catch-all (`0xffe777ce`–`0xffe7791e`). Thus normal Bedrock-to-L1 requests still terminate at local task handlers, while foreign addresses and L2-directed traffic may take USB when that route is registered.

The USB receive task passes its bulk-function read callback to the router packet-stream parser; its write task passes queued router packets to the matching stream sender (`0xffe2d3b4`–`0xffe2d49a`, `0xffe2d65c`–`0xffe2d844`). The USB callbacks hand raw transfer-buffer bytes to and from the device lower layer (`0xffe2d85c`–`0xffe2d8bc`, `0xffe2d8c0`–`0xffe2d918`, `0xffe6d7c4`–`0xffe6d8b4`, `0xffe6e220`–`0xffe6e3d4`). The router parser assembles linked packet segments from those bytes and checks its first-segment marker and continuation count; the sender writes each packet segment through its callback (`0xffe790a8`–`0xffe79340`). No PPP flag, escape or frame-check call appears in this USB callback-to-stream call tree. Thus the selected firmware's USB route uses router packet segmentation rather than the Bedrock PPP wrapper.

On a read error, reset or disconnect, the task withdraws its catch-all only if the other configured USB function is not open, then closes its own function and clears its open state (`0xffe2d4b2`–`0xffe2d58e`). USB withdrawal passes a zero comparison argument to the router unregister routine (`0xffe2d4c8`–`0xffe2d4d0`, `0xffe77c40`–`0xffe77d82`). For a matching nonlocal key, the static-slot branch can clear without comparing callbacks, and the linked-route branch skips that comparison when given zero (`0xffe77cd0`–`0xffe77d4a`). A later different callback under the same key is therefore not guaranteed to survive USB withdrawal. The route state at loss remains unknown without the live key and callback fields. With two configured instances, the event destination can move to the still-open one; with none, it is cleared (`0xffe2d522`–`0xffe2d546`). The task waits, then attempts to open again and rechecks the catch-all guard (`0xffe2d5e8`–`0xffe2d61a`, `0xffe2d23e`–`0xffe2d2a4`). This is event-destination failover and conditional route withdrawal in firmware, not proof of a second populated Origin 300 USB controller or request replay. The write task chooses an open function for request/response/event packets and drops packets when no destination is open (`0xffe2d73a`–`0xffe2d816`).

## Interaction with RS-422 peers and operator commands

The visible first-bank boot paths call the RS-422 peer initializer before USB setup (`0xffe106ae`–`0xffe106c8`). That initializer clears its state record, then sets the field at `0x30004d88` to one before it starts the peer ports (`0xffe2dc0a`–`0xffe2dc44`). The USB open task tests that same field and attempts nonlocal catch-all registration only when it is zero (`0xffe2d23e`–`0xffe2d2a4`). The field is at offset `0x18` of the state record at `0x30004d70` (cleared at `0xffe2dc10`, set to one at `0xffe2dc3a`; the only absolute-address use of `0x30004d88` in the body is the test at `0xffe2d23e`). No later store exists: the record pointer's other users and the mode setting were read, and none stores to it ([usb-descriptors-routing.md](usb-descriptors-routing.md) has the list and the consequence for the catch-all). Peer forwarding remains separate (`0xffe2e88c`–`0xffe2edfc`).

The L1's `network` command reports the current management-network mode. `network usb` and `network 422` force USB or RS-422 and disable autodetection; a changed setting is stored in nonvolatile memory and needs an L1 reset to take effect (Origin 300-applicable guide 007-3938-001, printed page 64; firmware `0xffe53400`–`0xffe54230`). That controls the management path, not the IO-8 guest USB controller. The operator's `usb` command asks for the three-endpoint status table described above; the public late-revision guide marks its service use as Altix-specific. They provide probes but do not prove that those transitions occurred on a stock Origin 300.
