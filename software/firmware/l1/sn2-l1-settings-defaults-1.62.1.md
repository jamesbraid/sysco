# The ARM L1 1.62.1 settings record: how it is initialised, what setting 3 holds by default, and who changes it

The node firmware's first question to the L1 (request `0x0001`, [sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md)) is answered with the value of non-volatile setting 3, the debug switches. This note records where that value lives in the ARM L1, what a blank or reset L1 holds there, and which commands and requests change it, so an emulated L1 can answer as an unconfigured one would. Grades follow [AGENTS.md](../../../AGENTS.md).

Source: the `Linux L1 image` (package 4) of `l1-1.62.1.bin`, its `/stand/sysco/bin/l1`: ARM, 1,999,676 bytes, SHA-256 `22cb62871e447a394acbd662f4f49f3146580afec93839953b37a5354545bfc5` ([sn2-l1-1.62.1-packages.md](sn2-l1-1.62.1-packages.md)). The program keeps its routine names in its dynamic symbol table; addresses are virtual addresses (base `0x8000`). Everything below was read as disassembly, nothing was run. String addresses are virtual addresses too.

## Where the settings live

**Established (read in full: `nvramInit` `0x2c5ac` to `0x2d51c`, the repair routine `0x2d51c` to `0x2dc3c`, the header rebuild `0x2dca0`, `nvramGet` `0x2ff74`, `nvramSet` `0x2dda8`, the flush routine `0x2c490`).**

- The settings are a 0x2000-byte image in RAM (`0x32e2a8`), loaded at start from the file `/work/l1_NVRAM` and written back whole (seek to 0, write 0x2000 bytes) after every `nvramSet`. `/work` is a YAFFS flash partition (`/etc/fstab`, [arm-linux-boot-scripts-and-flash-tools.md](arm-linux-boot-scripts-and-flash-tools.md)), so the values survive a power cycle. The file is opened read-write with create (flags `0x1042`, mode `0666`); a read error only logs "Can't initialize L1 NVRAM from file". A missing or empty file therefore leaves the image all zero, which fails the header check below and takes the blank path.
- Integrity is a byte-sum rule, no magic number: the routine at `0x60eac` adds a region's bytes and the caller wants zero; `0x60f18` stores the two's complement. Header: 8 bytes at the image start, byte 0 high nibble non-zero, byte 1 (offset of the first record in 8-byte units) non-zero, byte 7 the checksum. Record 1: `0x3cc` bytes at `8 * header[1]` (checksum at `+0x3cb`), mirror copy at `+0x3cc`. Record 3: `0xb4` bytes at record 1 `+0x7e0` (byte 0 = 3, checksum `+0x893` from the image's record base), mirror at `+0x894`. Record 2: `0x24` bytes at `+0x798` (byte 0 = 1), mirror at `+0x7bc`. The record version is the high nibble of record byte 0; the current version is 10, versions 1 to 9 run an upgrade chain (jump table `0x2c7dc`) that rewrites older layouts.
- This is not the ColdFire layout: the ColdFire record is `0x70` bytes with the version in the low nibble of a big-endian first byte ([settings-window-blank-image.md](settings-window-blank-image.md)). The setting numbers are shared (the ARM getter has 0xd0 entries against 0xb3), the byte positions are not assumed equal.
- **Setting 3 (established).** `nvramGet(3)` (table entry for key 3 at `0x303b4`) loads the little-endian 32-bit word at record `+0x1c`, shifts it right by 8 and zero-extends to 16 bits: bits 23:8 of that word, that is bytes `+0x1d` (low half) and `+0x1e` (high half). `nvramSet(3, v)` (`0x2e298`) replaces bits 23:8 with the low 16 bits of `v`, then recomputes the checksums, refreshes the mirrors and writes the file (`0x2fe78` to `0x2ff68`). The result is always 0 to `0xffff`.

## What a blank or reset image holds

**Established.**

- **Blank, zeroed, erased or corrupt header.** `nvramInit` checks the header (`0x2c718` to `0x2c75c`); a failed sum, a zero version nibble or a zero offset byte calls `0x2dca0`, which zeroes the 8 header bytes, stores version 1 (byte 0 `0x10`), offset 1 and the checksum, logs "checksum Error - common header initialized", sets the record pointers and calls the record initialiser `0x2d51c` directly.
- **The record initialiser takes each record independently** (`0x2d51c`): a valid primary (sum zero and a non-zero version) is kept; otherwise a valid mirror is copied over it (log "nvram checksum error - core data invalid, using backup copy"); otherwise the record is zeroed and rebuilt from the defaults below (log "nvram checksum error - initializing core data."). Records 2 and 3 are handled the same way. When record 1 passed as it stood but its version nibble is not 10, the tail of the routine (`0x2db70` to `0x2dc38`) rewrites the nibble to 4, clears the 7 bytes at `+0x3c4`, logs "Rebooting L1 to clear up NVRAM revision confusion" and restarts the L1; a blank image does not take this branch.
- **Defaults of record 1.** The whole `0x3cc` bytes are zeroed first (`memset`, `0x2d5c8`); then only these stores are made (read in full, `0x2d5d8` to `0x2d760`): byte `+0x00` version 10 in the high nibble (value `0xa0`); `+0x20` = 5; `+0x04` bits 1, 2 and 3 set (`0x0e`); `+0x11` = 0; `+0x17` ends as `0x3f`; `+0x21` ends as `0x30`; `+0x2e` = `0x7e`; `+0x9a` = `0x40`; checksum at `+0x3cb`; mirror copy. Start-up then raises setting `0x11` to 2 if it is below 2 and setting `0x3d` to 2 if it is 0 (`0x2d16c` to `0x2d1a8`). The record-3 and record-2 rebuilds zero their bodies and store their version bytes (3 and 1) and checksums.
- **No default is written to `+0x1c`, `+0x1d`, `+0x1e` or `+0x1f`.** A scan of `nvramInit`, the header rebuild and the record initialiser for any access at those four offsets finds none, so after a rebuild they are zero. **Setting 3 is 0 on a blank or reset ARM L1, so request `0x0001` is answered with status 0 and the integer 0** (bit 11 clear). The ColdFire image's default is also zero for the same reason ([settings-window-blank-image.md](settings-window-blank-image.md): every byte not listed is zero, and `+0x1c` is not listed); its `debug` command reads and writes the same 16-bit field ([debug-console.md](debug-console.md)).
- **Mirror recovery matters.** A record whose primary fails the sum but whose mirror passes is restored from the mirror, so a partly damaged image keeps its previous setting 3; only an image with no valid copy goes to zero.

## Who changes setting 3

**Established (constant-key call-site scan of the whole program for `nvramSet` and `nvramGet` with key 3; each site read).**

- **Console `debug`** (handler `0xd2780`, command records at `0x180420` and `0x180464`, help text "get virtual debug switches" and "set virtual debug switches"; behind `SMPCmdCheckBrickType` for the module's brick type). With no value it reads setting 3 and prints "debug switches set to 0x%04x"; with a value it calls `nvramSet(3, value)` at `0xd2838`, reads it back and prints the same line. The value is the console's integer, truncated to 16 bits by the setter.
- **Request `0x1001`** from the node (handler at `0xcae2c`, `nvramSet(3, value)` at `0xcae94`; it needs at least two arguments, the second an integer or an immediate argument, and replies status 0). So the node firmware can store a debug word into the L1 as well as read one; whether the SHub 1 PROM ever sends it was not checked.
- **Request `0x0001`** reads it (`0xc8b78`, reply status 0 and one integer).
- A diagnostic compare (`0xeab84`, "debug switch mismatch: 0x%x") reads it against an expected value; it does not change it.

**Other writers, and whether the node can reach them.** Read in the same program (`/stand/sysco/bin/l1` of package 4, SHA-256 `22cb62871e44...`, nothing run).

- **Computed keys (established for the sites, inferred for the reach).** Of the 184 `nvramSet` call sites, 13 pass a key that is not an immediate: `bladeEnable` and `bladeDisable` (`0xb4` plus an index), `powerSetMarginValue` and `powerSetMarginState` (`0x82` and `0x14` plus a byte index), `promIceDisable` (`0x6c` plus an index), `pcixOverrideSpeed` (`0xaa` plus an index), `cpuEnable` (`0x58` plus an index), `_parse_cpu` (two sites, `0xd2c5c` and `0xd6378`, key taken from a console command record) and the generic handler below. Each of the first seven adds a base of at least `0x14` to a non-negative index, so none can produce key 3. The `_parse_cpu` keys come from console command data and were not enumerated.
- **Console `nvram write <offset> <byte>` (established).** `nvramWrite` (`0x31bcc`) has one caller, the `nvram` command handler (`0xdc4f4`), so the byte write exists only as a console command. It can overwrite `+0x1d` or `+0x1e` directly; the checksums are repaired by the next `nvramSet`.
- **Text commands from the node (inferred).** The node can send a text command to task 3 (code 0, one string; [sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md)). `SMPCmdIRouter` (`0xddf0c`) takes the string and calls `SMPCmdLibrary` (`0xdcbf8`), which hands it to `CmdProcess` (`0x10f4b8`), the same command processor the serial console uses. Neither of the first two routines tests where the request came from, and the `debug` handler (`0xd2780`) tests only the brick type. So a node that sends the text `debug <value>`, or `nvram write ...`, should change setting 3. The command table lookup and any privilege check inside `CmdProcess` were not read, which is why this is inferred, not established.
- **Generic handler `0xae68c` (established for the code path; the node cannot reach it, inferred for the whole link).** It checks that argument 3 is 1, then calls `nvramSet(argument 4, argument 5)`. It is called only at `0xaa454`, in `L1CfgProcessEvent` (`0xaa310`) for event code `0x66`. `L1CfgProcessEvent` is called from `L1CfgIRouter` (`0xaa4e4`), which accepts a class 2 packet only if its source word's task is 14, the configuration task, from `EvtIRouter` (`0x9de04`, which turns a request addressed to task 1 into an event and forwards it only when the source task is 4 or 14), from the configuration task's own registration for all events (`0xa2510`), and from `B2BEventMesh` (`0xb0dc8`). The sender is the configuration task itself: `L1CfgEventNVRAM` (`0xad0fc`, nine call sites) builds the event with code `0x66` and the arguments 1, key, value, and sends it through the event router (to the configuration task itself and, by the mesh path, to other L1s; the second part is inferred). A frame from the node cannot make that packet: `syscom_process_inbound_request` and `syscom_process_inbound_event` (`0xc2284`, `0xc271c`) build the packet themselves, with the source word set to the SysCom task (5) and the class set by the call (`IRouterRequest` class 0, `IRouterEvent` class 2), and the event code of a node class 2 frame is the constant 0 (`0xc2b48`). The reach from a peer L1 over the brick-to-brick link is by this path and was not traced further, so whether a peer can set key 3 on this L1 is **unknown** here.
- **Answer for an emulator.** A node can set key 3 with request `0x1001` (established, above) and, by the text command path, probably with `debug`. The generic `0x66` event path is for peer L1s, not the node link. An emulated L1 that wants to stay faithful should accept `0x1001`; it need not model the event path.

**Inferred.** The L1 itself shows no use of the value apart from the sites listed in this section.

**`nvram reset` does not reset it (established for the handler, inferred for what the called routines write).** The console command `nvram reset` ("return L1 settings to factory default", handler `0xdc2e8`, case 0) prints "Changing NVRAM values to default settings" with a table (environmental monitoring on, temperature monitoring on, margin normal, syscom protocol ppp) and performs exactly: `EnvAuto(1)`, `EnvTemp(1)`, one call through a function pointer (`0x3315c0`, argument 2) and `nvramSet(8, 1)`. It stores no key 3. Forcing the blank path instead means removing or corrupting `/work/l1_NVRAM`. The refresh script in the boot-scripts note does not do that (established, script re-read in the package 4 CramFS): it copies `/work/*` to `/tmp`, unmounts `/work`, erases its flash partition, mounts it again and copies the files back, so a plain file such as `l1_NVRAM` survives. Its `cp` has no recursive flag, so only top-level files come back.

## What an unconfigured L1 reports

- Request `0x0001`: status 0, one integer, 0, unless a `debug` command or a request `0x1001` has stored something since. **Established** for the 1.62.1 Linux L1 image from the code above. For a particular deployed Altix L1 the stored value is **unknown**: only a read of that machine or a published log would show whether it was ever set. The sysco notes hold no such capture.
- The node firmware tests bit 11 of the value; zero takes the interconnect-discovery branch rather than the skip (the SAL boot-sequence page of the chips repository states what that branch does on a node with no NUMAlink peer).

## Not settled

- The upgrade chain for record versions 1 to 9 (jump table `0x2c7dc`): only its lack of any access at `+0x1c` to `+0x1f` was checked.
- Settings 61 and `0x11` in the ARM getter (table entries `0x30860`, `0x3050c`) were not read; the fix-ups assume the setting numbers match the ColdFire table.
- Whether anything on the node side sends request `0x1001`.

## Review

Independent review of sysco commit `6ee9e7e` (this page, the changes it made to [sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md), the questions list and the directory index), examined at that revision. The reviewer wrote none of it. Method: `/stand/sysco/bin/l1` carved from package 4 of `l1-1.62.1.bin` with this repository's CramFS reader (container SHA-256 `b4b5634949a9...`; program 1,999,676 bytes, SHA-256 `22cb62871e44...`, both match), decoded with the toolchain image's ARM decoder over the whole text segment, with literal-pool loads and symbol names resolved. The program's `.bss` starts at `0x1b2608` and the image buffer (`0x32e2a8`) lies inside it, so the buffer is zero until the file is read. Nothing was run.

**Confirmed (re-read in the binary).**

- The accessor. `nvramGet` (`0x2ff74`) indexes a table of `0xd0` entries by key minus 1; the entry for key 3 is `0x303b4`: load the pointer `nvramIUA` (`0x1b56d0`), load the word at `+0x1c`, shift right 8, mask to 16 bits. `nvramSet` (`0x2ddd4` table, key 3 entry `0x2e298`) replaces bits 23:8 with the low 16 bits of the value, then runs the flush tail (`0x2fe78` to `0x2ff68`: the three checksums, the three mirror copies, `0x2c490`, which seeks to 0 and writes `0x2000` bytes).
- The layout. `nvramInit` loads `/work/l1_NVRAM` (flags `0x1042`, mode `0x1b6`) into `0x32e2a8` after zeroing it, reads `0x2000` bytes, and sets the header pointer to the buffer start; the header test is the byte-sum routine (`0x60eac`, the sum of the bytes, low byte tested for zero; `0x60f18` stores the two's complement) over 8 bytes, a zero high nibble in byte 0 or a zero byte 1 calls `0x2dca0`. The record pointer is the buffer plus 8 times header byte 1. Record 1 is `0x3cc` bytes (checksum `+0x3cb`, mirror `+0x3cc`), record 3 `0xb4` bytes at `+0x7e0` (byte 0 = 3, checksum `+0x893`, mirror `+0x894`), record 2 `0x24` bytes at `+0x798` (byte 0 = 1, mirror `+0x7bc`). The version is the high nibble of record byte 0, current value 10; the jump table at `0x2c7dc` has ten entries, 1 to 10, and entries 1 to 9 fall through one into the next.
- The blank path. A zero image has a zero byte sum, so the header test that rejects it is the zero version nibble; `0x2dca0` zeroes 8 bytes, stores `0x10`, offset 1 and the checksum (byte 7), logs "checksum Error - common header initialized", sets the record pointer and calls `0x2d51c`. In `0x2d51c` a primary with sum zero and a non-zero version nibble is kept; else a mirror with the same property is copied over it; else the record is zeroed (`0x2d5c8`) and rebuilt. The stores of the rebuild (`0x2d5d8` to `0x2d760`) are exactly those on the page: `0xa0` at `+0`; `+0x20` = 5; `+0x04` ORed with 2, 4 and 8; `+0x11` = 0; `+0x17` ends `0x3f`, `+0x21` ends `0x30`, `+0x2e` ends `0x7e`, `+0x9a` = `0x40`; checksum and mirror copy. The tail (`0x2db70` to `0x2dc38`) is as described: only when record 1 was neither rebuilt nor restored, and its nibble is not 10.
- No default at `+0x1c` to `+0x1f`. A scan of every instruction of `nvramInit`, `0x2d51c` and `0x2dca0` finds no load, store or address computation at those offsets; the memsets cover `+0x48` (`0x50` bytes), `+0x3c4` (7 bytes) and the record 3 body. The upgrade chain's per-version fix-ups store at `+0x04`, `+0x11`, `+0x12`, `+0x17`, `+0x2e`, `+0x2f`, `+0x46`, `+0x48` to `+0x97`, `+0x3c4` to `+0x3ca`, `+0xec` and `+0xf0`, none at `+0x1c`. Every use of the buffer, the header pointer or the record pointer by address is inside `0x2c000` to `0x31fff` (the settings module); outside it only the getter, setter, read, write and init routines are called.
- Start-up then raises setting `0x11` to 2 if it is 0 or 1 and setting `0x3d` to 2 if it is 0 (`0x2d16c` to `0x2d1a8`), as stated.
- Writers by literal key 3, found by scanning all 457 call sites of `nvramGet` and `nvramSet`: set at `0xcae94` (request `0x1001`, reached from the compare chain at `0xc8924`; needs at least two arguments counting the code, reads the second as an immediate or through `IRArg`, replies status 0) and `0xd2838` (the `debug` handler, `0xd2780`, which writes then reads back and prints the "debug switches set to 0x%04x" line); gets at `0xc8b78` (request `0x0001`, dispatched at `0xc8810`), `0xd2810`, `0xd2840`, and `0xeab84` and `0xeaba0` (the diagnostic compare and the message that prints the stored value). The `debug` handler pointer appears in two command records at `0x180448` and `0x18048c`.
- `nvram reset` (`0xdc2e8`, case 0): `EnvAuto(1)`, `EnvTemp(1)`, a call through `powerMargin` (`0x3315c0`) with argument 2, `nvramSet(8, 1)`; no key 3. The page's reading of which setting the called routines write is correctly graded inferred.
- Flash versus code. The only code that fills the image is `nvramInit`'s read of the file; nothing in the container's CramFS (all files of both ARM packages searched for the file name) carries or creates `/work/l1_NVRAM` except the `l1` programs themselves, `rc.sysinit` does not touch it, and `/work` is the third YAFFS partition in `fstab`. A fresh partition therefore has no file, `open` with create makes an empty one, and the image stays zero. That a factory process might write a non-zero file into `/work` is outside the package and is what the page's "unknown for a deployed L1" covers.
- The sn2-prom-link and questions-list edits made with this commit agree with the page; the links resolve.

**Mechanical fixes made in this review.** None.

**Findings not fixed.**

1. The last paragraph of "Who changes setting 3" says the work-partition refresh script "erases the `/work` partition and so has that effect" (forces the blank path). The script, as the linked boot-scripts note describes it, copies `/work/*` to `/tmp`, erases the partition and copies the files back, so it preserves `l1_NVRAM`. Removing or corrupting the file is the only forced-blank route the page supports.
2. "Nothing else writes setting 3" (inferred) is incomplete in a way that matters to the sentence. Besides the literal-key sites, the console has `nvram write <offset> <byte>` (the same handler `0xdc2e8`, the case that calls `nvramWrite` at `0xdc4f4`), which stores one byte at any offset of the image (`0x31bcc`, offsets up to `0x1fff`) with no checksum update until the next `nvramSet` rewrites the sums; and a generic handler (`0xae68c`, called from a dispatch at `0xaa454`) takes a flag, a key and a value from the packet's arguments 3 to 5 and, when the flag is 1, calls `nvramSet(key, value)`; which request reaches it was not traced. Either can change the field. Neither affects the blank-image default.
3. The record 2 rebuild is described as storing its version byte and checksum. It also stores four words at `+0x79c` to `+0x7a8` from the log-region pointers (`0x2da34` to `0x2da8c`). Irrelevant to setting 3.
4. The open of `/work/l1_NVRAM` also logs on failure ("Can't open L1 NVRAM file ...", `0x2c66c`), apart from the read-error log the page names; both leave the image zero. A second file, `/work/l1_NVRAM_slots`, exists by name; the `nvramSlot*` routines presumably own it (inferred) and were not read here.
5. The page reads the upgrade chain only for accesses at `+0x1c` to `+0x1f` (stated in "Not settled"); that scan is confirmed above, so the unchecked part is only what the chain does to the other fields.

**Cleared scope.** The location, layout and integrity rules of the image, the blank-image path and its stores, the default of setting 3 (0, hence request `0x0001` answers status 0 and integer 0) for a blank, zeroed or erased image, the accessor and setter, the `debug` command and request `0x1001` as writers, the `nvram reset` finding. Not cleared: the sentence about the refresh script (finding 1), the claim that nothing else writes setting 3 (finding 2), and what a deployed L1's flash holds.
