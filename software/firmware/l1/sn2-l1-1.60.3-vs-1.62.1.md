# The ARM L1 1.60.3 against 1.62.1: the node-facing protocol is the same code

A second build of the Altix L1 controller firmware is held: `l1-1.60.3.bin`, from the `snxsc_firmware` 1.60.4 package of the Altix ICE system-tools disc 3.23 (x86_64 host tools). This note compares its `Linux L1 image` program with the reviewed 1.62.1 build, with the node link in mind: what an emulated L1 must answer for the Altix 350 node firmware ([sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md)). Grades follow [AGENTS.md](../../../AGENTS.md).

**Result.** The ARM `l1` program of 1.60.3 has byte-for-byte the same code, read-only data (apart from four version strings), initialised data and symbol table as 1.62.1. Every address, request handler, table, default and error code recorded for 1.62.1 holds unchanged for 1.60.3. The 1.60.3 build is not independent evidence for any 1.62.1 reading, and it adds no request, brick type or reply.

The package layout is the same as 1.62.1's (three ColdFire, two ARM Linux); package labels and supported-brick strings are character for character equal.

**Established** (section-by-section byte comparison of the two `l1` programs after carving package 4 with this repository's CramFS reader, `find_cramfs` and `cramfs_entries`):

- `.text` (1,295,272 bytes at `0x20de4`), `.plt`, `.init`, `.fini`, `.data` (18,852 bytes), `.hash`, `.dynsym` (1,400 exported functions, same names, addresses and sizes), `.dynstr`, the relocation tables, `.got` and the section sizes: identical.
- `.rodata` (296,844 bytes): eight bytes differ, the four copies of the version literal (`1.60.3` against `1.62.1`, at `0x15d1d3`, `0x176517`, `0x17bf7b` and `0x193fc7`). The `l1` program's `0x0005` firmware-revision handler parses one of them, so the only change a node can see is the three integers that request returns.
- `.comment` (the compiler and source-identifier strings, 284,802 against 284,811 bytes) and the ELF section-table offset are the rest of the file difference. The source identifiers of the linked modules are equal except `Revision.h` (CVS 1.1689 of 2008-09-30 in 1.60.3, 1.1690 of 2008-10-09 in 1.62.1) and the file dates of `IP73.c`, `IP73.h`, `Env.c`, `main.c`, `monitor.c`, `SMPCmd.c` and `SMPCmd_2m.c`; the revision numbers of every module other than `Revision.h` are equal. So the two builds are one source revision stamped twice.
- The strings of the two programs differ only in those version and date strings (a few dozen lines, all source-identifier dates).

The rest of the package 4 CramFS (537 entries each, same paths): `l2`, `libapi.armlinux.so` (7 bytes) and `busybox` (28 bytes) differ by small runs, the kernels by 108 bytes of the same size (build stamps), and nothing is added or removed. Package 2 (legacy ARM, 2.4 kernel): the `l1` program is the same length with 68 differing bytes. **Not read:** those differences, and ColdFire packages 0 (`NL3R 1MB`, 220,627 bytes differ) and 3 (`2MB`, 621,781 bytes differ), which are not the SN2 node path; package 1 (`Legacy 2MB`) differs in 52 bytes. The ColdFire differences are therefore open (unknown) for Origin 3000 use.

## How it was read

Ghidra (language `ARM:LE:32:v4`, the `0x8000` load segment of 1.60.3's `l1` as a flat image seeded with the 1,400 exported names) was the reading tool, through `retools/tools/re-run --ghidra-export`. The exporter's ELF loader accepts only MIPS, so the flat mode was used and the names seeded from the dynamic symbol table by a local change to the exporter that is not committed. Decompiled: `L1ReqIRouter` (`0xc8388`), `PPPWrite` (`0x10df80`), `PPPRead` (`0x10e490`), `PPPDecode` (`0x10eeb4`), `syscom_process_inbound_request` (`0xc2284`), `syscom_process_outbound_response` (`0xc3f64`) and `IRouterResponse` (`0x10ac40`). Decompiler output is navigation: constants below were checked against the bytes, and the byte equality of the two programs is what carries each "identical" row, not the decompiler. The addresses are the same in both builds.

## 1. The node link

**Established, identical in both builds** (same bytes; read again in 1.60.3's Ghidra output):

- **Framing.** `PPPWrite` (`0x10df80`) starts and ends the frame with `0x7e`, starts the check value at `0xffff`, and sends a payload byte of `0x7e` or `0x7d` as `0x7d` and the byte xor `0x20`. `PPPDecode` (`0x10eeb4`) and `PPPRead` (`0x10e490`) undo the escape and test for the frame flag. The 256-entry table at `0x198134` and the residue `0xf0b8` are in the same bytes.
- **Reply layout.** `syscom_process_outbound_response` (`0xc3f64`) builds byte 0 as `0x20` plus the subchannel index, the status in bytes 1 to 4, the argument count in byte 5 and the arguments after; the error shape is status `0xffffffff` followed by the packet's error code. The running-length tests against `0x80` in that routine (compare `< 0x80`) are the 127/128-byte limit of [node-link-sn1-vs-sn2.md](node-link-sn1-vs-sn2.md): an integer is added only while the length stays at most 127 and a string or raw block is tested without its tag byte.
- **Request entry.** `syscom_process_inbound_request` (`0xc2284`) and the packet entry `0xc2c58` are unchanged; request code `0x3001` to `0x3003` still go to the chunk assembler `0xc4ab0` first, so the open item about how those codes reach rows of the compare chain is also unchanged ([sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md), Not settled).
- The node's 127-byte clamp is on the node side and is not in this program.

## 3. Request `0x100b`

**Established, and the same as 1.62.1: on the success path there is no reply.** In 1.60.3's decompiled `L1ReqIRouter`, the routine clears its reply-count word (`local_2b4`) at entry. The `0x100b` branch (the comparand is the word `0x100b` at `0xc9410`) tests that the request's argument count byte (packet `+0x20`) is 4. If it is not, it calls `ARG__START` with `-100` (`0xffffff9c`). If it is, it rebuilds the PROM version word from three integer arguments (argument 2 shifted left 24, argument 3 masked to 16 bits and shifted left 8, argument 1 masked to 8 bits), stores it with `vramSlotSet`, optionally logs it (`nvramLogFinsert`, the `PROM %x.%x (PR %d)` text), and calls `SysComEventDisable` when the packet's slab equals the stored one. It never calls `ARG__START` or the integer and string reply routines. The shared tail (`LAB_000cf198`) calls `IRouterResponse` (`0x10ac40`) only if the reply-count word is non-zero, so a four-argument `0x100b` produces no frame.

This is the same reading as 1.62.1 and cannot differ, because the routine bytes are equal. **1.60.3 is therefore no evidence for a reply path.** It does give a second, independent reading by a different tool of the same code (the 1.62.1 reading used a disassembler and an interpreter), and that reading agrees with "no reply". The conflict with the node side stays: the node's request path times out when no reply arrives and then calls the node-reset routine (the chips repository's `software/firmware/snprom/l1-requests.md` states a model must reply to every request, including `0x100b`); that is a statement about the node firmware, not about this L1, and 1.60.3 does not touch it. Not settled by either L1 build: whether the real node call for `0x100b` ever waits (the chips page's node-side reading and the 1.62.1 page's "the node routine does not check the outcome" need reconciling).

## 4. Settings defaults and the DIMM request

- **Setting 3 (reply of `0x0001`).** Identical: `nvramGet` (`0x2ff74`), `nvramSet`, `nvramInit` (`0x2c5ac`) and the record initialiser (`0x2d51c`) are in the byte-equal `.text`, and `.data` is equal, so a blank or reset image holds 0 and request `0x0001` returns status 0 and the integer 0, as [sn2-l1-settings-defaults-1.62.1.md](sn2-l1-settings-defaults-1.62.1.md) records. Same default record stores (`0xa0`, `+0x20` = 5, `+0x04` = `0x0e`, and the others listed there).
- **`0x0006` (DIMM and board EEPROM).** Identical: the device-id to table-index routine (`0xc7664`: id 0 to 0, 1 to 1, 4 to 7 to 2 to 5, 8 to 13 to 6 to 11, 16 to 21 to 12 to 17, 98 to 18, 99 to 19, any other -1), the `OpusTio_eepromCfg` table (`0x16550c`) in `.rodata`, the checks in order and their codes (-104 not present or a type or area mismatch, -105 index, selector or offset out of range, -107 parse failed, -100 too few arguments) and the 256-byte SPD buffer with its sum check. [sn2-dimm-spd-request.md](sn2-dimm-spd-request.md) applies to 1.60.3 unchanged.

## 5. Brick types, and the ICE disc

**Established, identical.** `brickInitBrickOps` (`0x214fc`) and its jump table (`0x21528`) are in the equal `.text` and `.rodata`, and the supported-brick strings are equal, so every type letter in the table of [sn2-l1-1.62.1-packages.md](sn2-l1-1.62.1-packages.md) maps as before: type `F` (Opus TIO) to `OpusTio_BrickOpsInit` (`0x3cc74`) with the IP57 hooks, and the 1.62.1 letters `$ , Z . - { }` (the 1932 and 191010 chassis, Daytona, Quad Dense Router, IP71, 1955 chassis) are already in 1.60.3's string. The `IP73`, `IP75` and `IP81` configuration tables that [sn2-brick-packages.md](sn2-brick-packages.md) ties to Altix 4700 are present in 1.60.3 with the same names and addresses.

**Nothing new for ICE bricks.** The L1 program has no string naming an ICE brick. The only whole-word `ice` strings are the `promIce` console messages (the PROM in-circuit-emulator control, "not available for this brick type"), which are in 1.62.1 as well. So the disc's name does not correspond to a new brick family in this L1, and which brick an Altix ICE rack uses is not answered by this firmware (unknown).

## What this changes

- The conclusions of [sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md), [sn2-dimm-spd-request.md](sn2-dimm-spd-request.md) and [sn2-l1-settings-defaults-1.62.1.md](sn2-l1-settings-defaults-1.62.1.md) stand for 1.60.3, and the 1.60.3 image can be used wherever 1.62.1 is cited for the ARM `l1` program.
- Open for the 1.62.1 side, unchanged: the `0x100b` reply conflict with the node's reading, the order of the first requests, and `0x3001` to `0x3003`.
- Not compared: the ColdFire packages (0 and 3 differ widely), the `l2` programs, and the L2 image `l2-1.60.0.bin` of the same container disc.
