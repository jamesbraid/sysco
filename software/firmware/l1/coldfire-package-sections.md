# Origin 300 L1 1.44.0 package sections and boot candidates

The selected IRIX 6.5.30 package contains a ColdFire reset region and two loader candidates. The reset region has an explicit two-entry pointer table. Both pointed candidates pass the package's own additive metadata check. These facts identify where the boot code can look. The image alone does not say which flash bank runs.

## Checked section anchors

| Body offset or address | Checked contents | Limit |
|---|---|---|
| `0x000000`–`0x0003ff` | The first two big-endian words give an initial stack pointer `0x301017fc` and reset entry `0xffe00400`. Later words in this interval point into early reset code. | This is the packaged vector region. Unknown: how address zero is mapped at reset; the image holds no chip-select setup before the reset entry (routes: the reset code to `0xffe00b38`, the candidate entries; next: the MCF5206E reset-state description in the public manual). |
| `0xffe00400`–`0xffe00b38` | Decoded early reset and loader path. It initializes RAM, checks a retained candidate pointer under a branch condition, and otherwise scans the flash pointer table. | The retained-candidate test at `0xffe00ac8` reads the byte at offset `0x40` from its first argument (`0x10000000` in the reset call at `0xffe00426`) and tests bit 5; inferred, from the public MCF5206E manual's register map, that offset `0x40` is the reset status register and bit 5 the software-watchdog reset flag, so a watchdog restart can reuse a retained candidate. The reset code writes no MBAR value before this read; how the register is reachable at that point is unknown. |
| `0xffe01000`–`0xffe0100b` | Two aligned entries point to `0xffe10000` and `0xffe80000`. The third word is all ones. Every subsequent measured word up to `0xffe10000` is all ones. | The two entries are present in this package. |
| `0xffe10000` and `0xffe80000` | Each candidate starts with a pointer to its metadata record, then the initial stack pointer and a candidate entry address. The entries are `0xffe10b02` and `0xffe80b02`. | These are loader candidates; which one runs is unknown from the image. |
| `0xffe7fd1c`–`0xffe7fd4b` and `0xffeefd1c`–`0xffeefd4b` | Each 48-byte record starts with type word four and length word `0x30`. Each has 12 big-endian 32-bit words whose sum modulo `2^32` is zero. | This is the firmware's record check, not a whole-bank checksum or proof that flash was programmed correctly. |

The candidate starts are `0x70000` bytes apart. Corresponding code and data after their first 64 KiB show matching content with address-bearing words adjusted between the candidates. That correspondence supports two related images. Of the 98,304 words after the first 64 KiB, 87,068 are identical, 6,937 differ by exactly `0x70000` and 4,299 differ otherwise. It does not show that either copy is a complete flash-bank dump. The selected body stops at `0xffeefd5f`, 20 bytes after the second 48-byte metadata record. It does not extend to the loader's `0xfff00000` upper search bound. Spans the listing cannot place need pointer or control-flow evidence before classification (see [unclassified-regions.md](unclassified-regions.md)).

## What the boot branch establishes

The loader scans aligned table words from `0xffe01000` toward `0xfff00000` until an all-ones terminator, then considers entries in reverse order. For an entry, it first checks that the entry and its first pointed word are aligned and within `0xffe00000`–`0xffefffff`. It uses the pointed word as a metadata address. A record with type below three skips its first four bytes for the sum. These two type-four records include all 48 bytes. A nonzero 32-bit sum rejects the candidate. The original package bytes give zero for both records. The table entries have their low flag bit clear. The branch can retain a candidate based on a text field in the metadata. The two measured records point to the same build stamp and version. Those fields are the published `20060717182038` and `1.44.0` values, not evidence of a distinct later bank.

Before that scan, the reset path can accept a saved candidate pointer in RAM when a flag and range checks permit it. The branch validates that candidate's metadata too. After choosing a candidate, another routine copies 1,024 bytes from just after its first pointer into RAM at `0x30100000`, sets the vector base there and calls the candidate entry. This establishes a loader pointer consumer and an execution path for a valid candidate. It does not establish how a fitted board maps flash at reset or which candidate was selected during a real boot. Routes to settle which candidate runs: read how the update tool writes and selects the two banks (the `flashsc` image-selection routines in [package-container.md](package-container.md)), diff the loader candidates against the other 1.44.0 ColdFire packages, and compare the reset behaviour that the public MCF5206E manual and the MAME MCF5206E core give for the chip-select and reset-status registers the loader reads.
