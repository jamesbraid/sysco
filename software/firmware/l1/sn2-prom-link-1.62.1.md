# The node-to-L1 link of an Altix node in L1 1.62.1: framing, requests, and what the node firmware asks at boot

An Altix node's firmware (the PROM, which also answers the kernel's console and controller SAL calls, [sn2-controller-host-protocol.md](sn2-controller-host-protocol.md)) talks to the L1 over a serial channel that the node chip provides. This note records that link from the L1 side, so that a machine model can answer the node authentically: the byte framing, the frame header, the argument encoding, which requests the L1 accepts, and which of them the node firmware sends. Grades follow [AGENTS.md](../../../AGENTS.md).

Sources, all disassembled (no code was run):

- **L1 side.** The `Linux L1 image` package of L1 1.62.1 (package 4 of the container in [sn2-l1-1.62.1-packages.md](sn2-l1-1.62.1-packages.md)), its `/stand/sysco/bin/l1`: ARM, 1,999,676 bytes, SHA-256 `22cb62871e447a394acbd662f4f49f3146580afec93839953b37a5354545bfc5`. The program exports its routine names. For comparison the same program of L1 1.44.0 (`Linux L1 image`, SHA-256 `b33154e53b00531623db6ff365e80b1c1825bc9427961c59fdc132c24f0c819e`).
- **Node side, cross-check only.** The SAL runtime component (FIT type `0x12`, gzip, 918,824 bytes expanded, IA-64) of the SHub 1 firmware `shub1snprom.bin` of snprom 10.54 (SAL 5.04). Only the request-building call sites and the framing routine were read; the node firmware as a whole belongs to the chips repository's SN2 firmware page, which this note does not change. Addresses below with no package named are in that component.

The addresses of the L1 routines are in the Linux L1 `l1` program's load image (`0x8000` base).

## The channel

**Established** (`SysComConfig`, `config` at `0xbf570`, `init` at `0xbfdfc`, `uartOpen`). The L1 keeps a table of "SysCom" channels, one per serial or scan-chain device. A brick type registers its channels with a small table (`<brick>_SysComCfg`, 24-byte entries; for example `IP63_SysComCfg` is `0x700, 1, 2, 0x4fff, 8, 4`, `Daytona_SysComCfg` two entries `0x400, 1, 2, 3, 1, 2` and `0x401, 1, 2, 7, 1, 2`). The second word of an entry selects the mode: **1 or 3: framed (PPP) channel**, which allocates a PPP codec (`PPPInit` with a 256-byte buffer); **0: raw channel**, whose input goes to `syscom_process_inbound_data` and is forwarded as console characters (below). The first word is stored as the channel's device number; a UART device is opened as `SCC-<n>` (`uartOpen`). The meaning of the other words was not read.

**Established** for the Opus TIO and NL4R router families: the node chip's UART is reached through the scan chain, not a serial wire. `TIOSysComInt` and `NL4R_SysComInt` call `SysComJTagReadReady`, which calls `JTAG_UART_read`; `JTAG_UART_write` and `JTAG_UART_read` access the chip's test data registers named `WR_SYSCOM` and `RD_SYSCOM` (`JChip_TDR_Raw`, `jtag_comm.c`), packing the bytes with the bit-reversal masks `0x55555555`, `0x33333333` and `0x0f0f0f0f`. The rest of the bytes pass through the same PPP codec as a wire. For the node families whose entries carry no `SysComCfg` table (Opus TIO, Dorado, Gemini, IP67 and IP69, the families with an IP57 configuration) which channel mode each uses was not read (unknown); the ColdFire `Legacy 2MB` and `2MB` packages use the processor's own UART for a SHUB node ([sn2-brick-packages.md](sn2-brick-packages.md)).

On the node side (SHub 1 build), the UART driver (`sc_uart_*`, for example `sc_uart_rxintr` and `sc_uart_txintr`) addresses the UART at the literal `0x8000000ffed40000 | nasid << 38` plus eight bytes per register, the same eight-byte stride as the PROM's own UART accesses (established: the immediates `+0x00` to `+0x38`). The chipset table also holds two accessors for the same window: `sc_shub_dev_reg` forms `0x8000000ffed40000 | nasid << 38` plus the register index shifted left by 6 (a 64-byte spacing), and `sc_shub_dev_reg_offset` forms `0x7fed40000` plus the index shifted left by 3. No call from the `sc_uart_*` routines to either was found; the callers of the table slots that were found are in the scan-chain, TIO and router code. So 8 is the register spacing of the UART as the UART driver uses it; what the `<< 6` accessor serves is not settled (unknown). `sc_shub_uart_divisor` returns 1; an `sc_tio_*` set drives the TIO's UART and an `sc_nl4r_*` set the router's. The register layout belongs to the SHub reading, not to this note. The L1 and node ends were read independently and agree on the framing below.

## Framing: HDLC-style byte stuffing with the PPP FCS-16

**Established** at both ends (`PPPWrite` at `0x10df80`, `PPPRead`, `PPPDecode`; node side `l1sc_fill_sendbuf` at `0x52fe0`, `l1sc_receive` at `0x53b80`).

1. A frame starts and ends with the flag byte `0x7e`.
2. Between the flags go the payload bytes, then the 16-bit frame check sequence. Any payload or check byte equal to `0x7e` or `0x7d` is sent as `0x7d` followed by the byte xor `0x20`. The L1's writer also escapes `0x11` and `0x13` (XON, XOFF) when its flow-control option is on, and `0x0d` when a second option is on (both options are fields of the channel; the SysCom channels are created with both off, see [node-link-sn1-vs-sn2.md](node-link-sn1-vs-sn2.md)). The receiver undoes `0x7d` escapes.
3. The check is the PPP FCS-16: initial value `0xffff`, reflected polynomial `0x8408` (the 256-entry table at `0x198134` in the Linux L1 program equals the generated table, entries `0x0000, 0x1189, 0x2312, 0x329b, ...`), the final value complemented and sent low byte first. The reader tests the residue `0xf0b8` (`PPPRead`, literal `0xf0b8`). There is no address and control prefix (`0xff 0x03`) and no protocol field: the payload begins directly with the frame header below.
4. A payload is at most 127 bytes: the node firmware's frame writer clamps the length to 127 (`l1sc_fill_sendbuf`), which agrees with the 127-byte `CHUNKSIZE` of the kernel's subchannel driver. Larger messages are sent in chunks (request codes `0x3001` to `0x3003`, below).

## Console input frame (L1 to node)

**Established** (Ghidra, ARM 1.62.1 `l1`, SHA-256 `22cb6287...bfc5`; node side in the chips repository, `software/firmware/snprom/l1-requests.md`, "Console input"). `FUN_0009d1e0` (one caller, `SMPLibrary`) builds a task-5 request with the typed character as one immediate argument; `syscom_process_outbound_request` (`0xc31dc`) turns it into a frame whose payload is two bytes: the header `SysComGetSubc(tag)` with the class bits clear, then the character. `PPPWrite` adds the flags, escapes and FCS-16. The tag is `slab * 32 + subchannel` for brick type `F`, and the console target is set by `SMPConsoleSubchannel` (`0x9c9d0`) from the node's last class-2 frame header (`header & 0x1f`; `syscom_process_inbound_event`, `0xc271c`), except that a slab whose recorded subchannel is 4 takes priority. So the header is the node's console index (4 for the remote console) and the PROM's receiver accepts it. Brick type `?` sets `0x40` in the header and appends LF after CR; those frames would be rejected for indices 0 to 4. No batching: one frame per character. That is the framed form; when the slab record's mode word at `+4` is 0, `syscom_process_outbound_request` instead sends the bare character as a single byte through the channel's own write routine, with no header and no FCS (read, not run; what sets the word was not traced). The mapping `SysComGetSubc` for type `F` is the `tag mod 32` branch of `0xc11d4` (read, not run).

## Frame header and argument encoding

**Established** from the L1 receive path (`syscom_process_inbound_packet` at `0xc2c58`, `syscom_process_inbound_request` at `0xc2284`) and the node's request builder (`sysctl_cmd_construct_req` at `0x4f8a0`):

| Byte | Content |
|---|---|
| 0 | bits 7:5 the **class**, bits 4:0 an index. Class 0: request; class 2: event; any other class is not processed by the packet entry. The L1 writes a response with `0x20` in this byte (class 1). |
| 1 to 4 | a 32-bit big-endian address word. The node firmware builds it from `0x0ffff000` (`sysctl_cmd_open` passes `0xffff000`) and the destination task number; every numbered request it builds is to task 6, and its text command goes to task 3 (see the request table below). The L1 passes the word through `SysComSetTasknum` to derive the 7-bit tag it puts in bits 5 to 11 of the packet's source word (inferred for the L1 use). |
| 5, 6 | the 16-bit big-endian request code |
| 7 | the argument count; absent when the request has no arguments (the PROM's builder omits it, and the frame is then 7 bytes) |
| 8 on | the arguments, in order |

**A request with no arguments has no count byte (established, both ends).** The L1's `syscom_process_inbound_request` (`0xc2284`; `0x83ac4` in 1.38.4, same code) reads byte 7 only `if (7 < length)` (length excludes the check bytes) and otherwise takes the count as 0. It reads the code from bytes 5 and 6 without a length check, and nothing between the PPP reader (which needs more than 2 bytes with the check) and this routine enforces a minimum, so a 7-byte frame such as `7e 05 0f ff f0 06 00 03 69 27 7e` (request `0x0003`) is a valid request with no arguments. The code is stored as the request's argument 0, so the argument total the handlers see is the count plus one and the `-100` test at entry (total zero) cannot fire for a well-formed frame. Reply payloads (before the check bytes): `0x0002` is 11 bytes (`20|subchannel`, `00 00 00 00`, `01`, `00` + `rack << 6 | bay`); `0x000e` is 11 bytes (`01`, `00` + the slab; handler `0xca214`, slab is the source tag's `SysComGetSlab`; the blade workaround applies only to types `,`, `}`, `.` and `$` or a brick with more than one slot). The 0x0003 reply is 16 bytes: `20|subchannel`, `00 00 00 00`, `02`, `00` + word, `00` + type (handler `0xc8bb8`, shared with `0x0002`).

The node's builder writes the same fields without the first byte (word, code, count, arguments) into a buffer; the class and index byte is supplied by the frame writer (`l1sc_fill_sendbuf`'s fourth argument).

An argument starts with a type byte: **`0x00`**, then a 32-bit big-endian integer; **`0x01`**, then a NUL-terminated string; **`0x80 | n`**, then `n` raw bytes (`n` up to 127, "indirect"). This is the encoding the kernel's event parser expects ([sn2-controller-host-protocol.md](sn2-controller-host-protocol.md): types `0x00`, `0x01` and `0x80 | length`), so the event record the kernel sees is the node-to-L1 argument encoding with the code and count in front.

A response carries the status first (bytes 1 to 4 of the frame, see below): 0 on success and a negative number on failure; the integer, raw-byte or string results follow. Status values read in `L1ReqIRouter`: `-100` (at entry, when the packet's argument count at `+0x20` is zero; the response routine iterates over the same field), `-101` (unknown request code, after an optional extended-request hook), `-104` (no serial number; request `0x0008`, and other handlers too, for example `0x0004`) and `-106` (request `0x0013` when the blade state check fails). The response header is described under [What the ARM L1 sends back](#what-the-arm-l1-sends-back-for-the-nodes-early-requests-l1-1621-opus-tio-and-ip57-personality): byte 0 is `0x20` plus the subchannel and bytes 1 to 4 are the status, not an echo of the request.

Messages longer than one frame use request codes `0x3001` (start), `0x3002` (next segment) and `0x3003` (continuation): `syscom_process_inbound_request` sends these three codes to a separate assembler (`0xc4ab0`). Their layout in this L1 was not read; the ColdFire L1 uses the same three codes with a segment count in byte 7 and a data length in bytes 8 and 9 ([chunked-request-frames.md](chunked-request-frames.md)); that the ARM L1 does the same is inferred from the shared codes.

## Where requests go

**Established** (`IRouterRegisterFunction` and `IRouterRegisterQueue` call sites, address word `0xffff0NN`): the L1's request router delivers a request to the task whose number is in the low bits of the destination word. Registered tasks: 1 `EvtIRouter` (events), 2 `SMP` (holds `SMPSystemConsole` and `SMPConsoleSubchannel`), 3 `SMPCmd` (text commands), 5 and 21 `SysCom` (outbound to the node), 6 `L1ReqIRouter` (general requests), 14 `L1CfgIRouter` (configuration), 18 `LpbkIRouter` (loopback), 20 `APwr`, 23 `RouteIRouter`, 24 `BkDr`, plus `FlashInit` and the scan-packet task. These are the same task numbers as the ColdFire L1 (general 6, command 3, loopback 18, management 2, node link 5), so a node firmware that addresses task 6 reaches the same request family on either L1.

## What the node firmware sends

**Established** (the call sites of `sysctl_cmd_construct_req` in the SAL runtime): every numbered request below is addressed to task 6 and built as (code, argument count, arguments). The one exception is the text command, the last row, which goes to task 3. The "Arguments" column below counts words in the node's builder (an integer or string is 2, a raw block 3), not arguments: the SN1 PROM's builder does the same ([node-link-sn1-vs-sn2.md](node-link-sn1-vs-sn2.md)), and 8 for `0x0006` is the four integers the L1 handler reads (inferred for the SN2 builder). The PROM version report `0x100b` is sent from `sysctl_init` (SAL_B `0xffa90f5c` and `0xffa9115c`, in the flash SAL_B rather than the runtime component read first): three ints, the first constant 1 and two bytes of the PROM's version data. The ARM L1 checks the count and sends no reply.

The node firmware's own probe of the controller (`sysctl_probe`, 16 instructions in this build) compares `cpuid[2]` with the simulator signature `0xaeeeeeee8badbeef` and returns 0 or 1 without a call; it sends no request. An L1 therefore does not need to answer anything for the probe in this build.

## The first exchanges, as a contract for an emulated L1

What the L1 must do for the node firmware of this build, in dependency order. The order among the identity queries is **unknown**: the node caches them and fetches each when a SAL call or the boot path needs it; the L1 side cannot show the order because it answers whichever arrives.

1. **Channel and framing.** A framed channel to the node: frames as above, flags, escaping and FCS-16. A read error from the codec is logged as `SCC-<n> read error (PPP)`; no acknowledgement or retransmission frame was seen at this layer (inferred: none is defined by the code read).
2. **Board identity** (all to task 6; reply: status 0 then the values):
   - `0x0003`: `rack << 6 | bay` (an integer) and the brick type character (an integer), from settings 1 and 2 and the identity routine's result.
   - `0x0008`: the system serial as a string; status `-104` if none is set.
   - `0x0013`: the slot of the node (and `-106` if the blade is not in a state to answer).
   - `0x000e`: the slab number. `0x0012`: the node maximum. `0x0015`: the sharing mode (setting `0xcc & 0x7f`). `0x0009`: the partition (setting 14).
   - `0x0010`: processor presence and enable, per node.
3. **Power and reset state.** There is no numbered request for it in the table, and none from the node in the list above. The text-command path is not closed (its `fru reset` strings have no reference found), so "no power or reset request" holds for numbered requests only. The strings "Reset request sent to system controller" and "Request for system reset failed" are LED display-code descriptions in the exported table `chipset_common_ledlist`, not requests. The L1 holds the node in reset and releases it itself (the `IP57_ResetHold` and `IP57_ResetRelease` routines, [arm-ip57-configuration-control-1.40.5.md](arm-ip57-configuration-control-1.40.5.md)); the node firmware finds itself running after the release, so a model that starts the node firmware at all has already completed the L1's release sequence. Not asked and not answered: the last-reset reason (`0x000f` is absent from this L1).
4. **Console selection.** There is no console request in this L1. The L1 learns the console from the data: a class-2 frame from the node (`syscom_process_inbound_event`) makes the L1 call `SMPConsoleSubchannel` with the sender's slab and subchannel (which sets the system console and tells the configuration task through `L1CfgEventConsoleSubchannel`) and forwards the frame to the management task as an event (`IRouterEvent`); a raw-mode channel (`syscom_process_inbound_data`) forwards its bytes as one string argument of an event, on subchannel 4. The node firmware's `l1sc_send` passes the immediate `0x42` to the frame writer where the header byte goes, and `l1sc_receive` has no header compare against `0x44` (the `0x44`, `0x53` and `0x66` immediates near the console routines are lock tags, inferred): the node's console output is class 2 (`0x40 | index`) and its console input is class 0 (see "Console input frame" below). The console characters in a class-2 frame are the frame's payload (the L1 copies them as one string argument, `ARG__STRING`). The L1 side of the kernel's `SN_SAL_SYSCTL_EVENT` is `0x1007` above.
5. **Event delivery.** After `0x1007` the L1 persists the subchannel (setting `0x13`) and pushes environmental events to the node as class-2 frames in the argument encoding the kernel parses ([sn2-controller-host-protocol.md](sn2-controller-host-protocol.md)).

An emulated L1 for the Altix 350 therefore needs: the framed channel and the task-6 requests in steps 2 and 5 plus the clock (`0x200e`, `0x200d`) and the display (`0x1005`); it does not need the PROM-load, FRU, inventory or scan requests, and may answer them `-101`.

## What the ARM L1 sends back for the node's early requests (L1 1.62.1, Opus TIO and IP57 personality)

Read from the Linux L1 program (`/stand/sysco/bin/l1`, the addresses above; the program was carved from package 4 with this repository's CramFS reader and matches the SHA-256 in the first section). Grades: established where the whole routine named was read.

**The reply frame on the wire (established, `syscom_process_outbound_response` `0xc3f64`, read in full; this replaces the earlier inference that the reply echoes the request's address word and code).** The PPP payload of a reply is:

| Byte | Content |
|---|---|
| 0 | `0x20 | subchannel`: class 1 in bits 7:5, the subchannel index in bits 4:0. The index is `SysComGetSubc` of the tag the request left in the packet (`SysComSetTasknum`, `0xc132c`, called from `syscom_process_inbound_request` with the request's own byte 0 bits 4:0); the pair is inferred to return the request's subchannel index unchanged (the table behind them was not read) |
| 1 to 4 | the status, big-endian 32-bit: argument 0 of the reply |
| 5 | the argument count, counting the arguments after the status |
| 6 on | the arguments: integer `0x00` + 4 bytes big-endian; raw bytes `0x80 | n` + n bytes; string `0x01` + NUL-terminated text. The running length includes the class byte and an integer is added only while it stays at most 127; a string or raw block is tested without its one-byte tag, so a reply can reach 128 bytes with the class byte ([node-link-sn1-vs-sn2.md](node-link-sn1-vs-sn2.md), maximum payload row). A larger reply sets an overflow flag and the arguments after that point are dropped |

There is no address word and no echoed request code in a reply. A reply whose packet carries a nonzero error code is sent as status `0xffffffff` followed by that code in four bytes, with no argument count (nine bytes). This is exactly the shape the node's reader wants: the node strips byte 0, then reads the status in bytes 0 to 3, the count in byte 4 and the arguments from byte 5 (`sysctl_cmd_interpret_resp`, the chips repository's SN2 boot-sequence page), so the two ends agree on byte positions (L1 end established; node end read in the same routine). In the L1's own request records the request code is argument 0, so the argument count the L1's handlers test is the request's argument count plus one.

A handler that never calls `ARG__START` sends no reply at all (`IRouterResponse` is skipped when the reply's count word is zero, `0xcf198`). The PROM-version report `0x100b` is such a handler on its success path: it checks that the request carries three arguments (count 4 with the code), prints the PROM version, and returns without a reply; with a different count it replies -100. The node sends this request and waits for a reply it does not get; what the node does when none comes is under [The 0x100b reply](#the-0x100b-reply).

**Reply bodies (status 0 in every row; arguments after the status).**

| Request | Reply arguments | Source of the values | Grade |
|---|---|---|---|
| `0x0001` | one int: the debug-switch word | non-volatile setting 3 (`nvramGet(3)`) | established, in full |
| `0x0003` | two ints: `rack << 6 | bay`, then the brick type character | settings 1 and 2; `brickGetType()`; for `=` the character `#` unless a per-slot flag is set | established, in full |
| `0x0013` | for brick types other than `,` `}` `.` `$` with one slot (the Opus TIO letter `F` with a single slot): two ints, 0 then the brick type character | `brickNumSlots`, `brickGetType()` | established for the branch, inferred that `F` has one slot |
| `0x000e` | one int: the requester's slab | `SysComGetSlab` of the request's tag (the blade workaround applies only to types `,`, `}`, `.` and `$` or a multi-slot brick) | established for the code, inferred for the value (0 for the one node on the channel) |
| `0x0009` | one int: the partition | non-volatile setting 14 | established, in full |
| `0x0015` | one int: the sharing mode | non-volatile setting `0xcc`, masked to 7 bits (mask from the earlier reading) | inferred |

**Module type (established for `F`, inferred for the Altix 350).** The type letter comes from `brickGetType`; the program's brick-family switch (`brickInitBrickOps` `0x214fc`, jump table at `0x21528`) maps `F` to `OpusTio_BrickOpsInit` (`0x3cc74`), and that routine installs the `IP57_CpuPresent`, `IP57_CpuEnable` and `IP57_CpuDisable` hooks and the name string `TIO`. Request `0x0003` returns that letter (0x46) as its second int and `0x0013` returns it as its second int; the first int of `0x0003` is `rack << 6 | bay` from settings 1 and 2. That a base Altix 350 compute module is the `F` brick is inferred (the IP57 configuration tables are carried by exactly the Opus TIO, Dorado, Gemini, IP67 and IP69 families, and Opus TIO carries a PCI-X bus and slot configuration); the ColdFire `O` alternative in the earlier note is not served by this ARM program.

### Request `0x0006`, board and DIMM EEPROM read (`L1ReqIRouter` `0xc9658` to `0xc9dd8`, read in full)

The request carries four ints: device id (argument 1), selector (2), byte offset (3) and length (4); it needs more than four arguments including the code or it replies -100. The reply is status, then one int and one raw-byte argument.

1. **Device id to table index (`0xc7664`, read for `F`; indexes the slot's EEPROM table).** Id 0 gives index 0 (INTERFACE), id 1 gives 1 (NODE), ids 4 to 7 give 2 to 5 (CPU 0A, CPU 0C, CPU 0A S, CPU 0C S), ids 8 to 13 give 6 to 11 (DIMM0 to DIMM5 L), ids 16 to 21 give 12 to 17 (DIMM0 to DIMM5 R), id 98 gives 18 (RISER), id 99 gives 19 (IO10). Every other id gives -1 and fails as not present. The names and per-entry type codes (1 FRU record, 3 CPU, 0 CPU sensor, 2 DIMM, 4 power supply) are in `OpusTio_eepromCfg` (`0x16550c`, eleven rows of two 12-byte entries). The power supply entries (20, 21) have no device id. So the node's DIMM ids 8, 16, 9, 17, 10, 18, 11, 19, 12, 20, 13, 21 are present on an Opus TIO brick and ids 14, 22, 15, 23 (the fourth bank) are not: twelve DIMM slots (established for the mapping, inferred that every one of them holds a DIMM).
2. **Checks, in order.** `eepromIsPresent` false: -104. `eepromIsPresent` is also false for an index at or above the slot's entry count, so that case gives -104 too; the separate -105 test for it is not reachable. Selector above 4: -105.
3. **Selectors.** The L1 keeps one 120-byte record per table entry. Selector 0 (record type 1): the 8-byte common header, copied raw. Selector 1 (type 1): chassis information area. Selector 2 (type 1): board information area. Selector 3 (type 1): the fourth area slot (the multi-record area; the product area slot is never served). Selector 4 (type 2): the DIMM's raw serial-presence-detect bytes. A record whose type does not match the selector, or whose area slot is absent, gives -104; a record whose parse failed gives -107.
4. **Record layout (established for the offsets read; sizes are in bytes, inferred).** Type 1 records are an IPMI FRU: the common header is read first (8 bytes) and checked with `ipmiCheckCSum` ("EEPROM header checksum error"), then the area offsets in header bytes 2 to 5 select four areas, each stored as (error, size, pointer) at record offsets `+0x10`, `+0x1c`, `+0x28`, `+0x34`. Type 2 records hold a 256-byte buffer read from the DIMM's EEPROM (`0x12e5c0`), checked against its own checksum byte (the sum of bytes 0 to 62 must equal byte 63; "SPD checksum error" on failure; the full DIMM request is in [sn2-dimm-spd-request.md](sn2-dimm-spd-request.md)), size at `+8`, pointer at `+0xc`.
5. **Reply.** Status 0; then an int: the number of bytes of the area left after this chunk (area size minus offset minus length, floored at 0); then a raw-byte argument of `length` bytes from the area at `offset`, shortened if the area ends first (a length of zero sends no bytes). An offset at or above the area size gives -105. The node asks for at most 64 bytes per request.
6. **What the node's parsers need in the bytes** (the chips repository's SN2 boot-sequence page): for a DIMM, SPD bytes 5, 9, 18, 23, 25, 29, 31 and 42 of the first 48; for the board and chassis areas, version, length in 8-byte units, a checksum that makes the whole area sum to 0, and `0xc1`-terminated type/length-coded fields in the IPMI order (chassis: type, part number, serial number; board: language, manufacture time, manufacturer, product name, serial number, part number, FRU file id, custom fields).

**The PROM's I/O-discovery read (device id 98).** SAL_B asks `0x0006` with the integers 98, 2, 0 and 64 once per PIC widget when the type letter it holds is `o`, and then at offsets 64, 128 and so on while the bytes-left integer is not 0 (the chips repository, `software/firmware/snprom/l1-requests.md`, "Request `0x0006` in I/O discovery"). In this program id 98 is table entry 18 (RISER), selector 2 its board information area. A present, parsed record gives status 0, the bytes left and the raw bytes; a clear presence flag gives -104; a present flag whose boot-time read of the EEPROM header failed gives -107 (see the review). The PROM treats any negative status as "no EEPROM info" and carries on; only silence is fatal for it. Established for the handler. An `F` L1 holds type `f` in the PROM, which asks for id 1, so this id-98 path is reached only by an L1 that reports `O`.

## The 0x100b reply

The question: the node firmware sends `0x100b` as its first request and waits for a reply frame; does the real L1 answer it? **Answer: no frame of any kind comes back (established), so the node's wait for it times out (established). What the node does after the timeout is corrected in [Resolution](#resolution-of-the-0x100b-conflict): the first reading here, that the node carries on, was wrong; the boot processor parks.** Both earlier readings were partly right: the L1 sends nothing, and the node does wait. A sentence above and in the review that said the node's reply read "expects none" was wrong on that point and is corrected here.

**Node side (SAL_B of snprom 10.54, Ghidra export plus objdump cross-check; established).**

- `sysctl_init` (`0xffa90e60`, and a second copy at `0xffa91060` reached by a jump at `0xffa912bc` that differs in the address word, `0x4ffff000` instead of `0x0ffff000`) opens a slot (`0xffa819c0`), builds the request with `0xffa81f40` (task 6, code `0x100b`, three integer arguments, so a count byte of 3 and a 4-byte integer after each type byte `0x00`), sends and waits with `0xffa82c10`, closes the slot (`0xffa81e40`), and on success decodes the reply with `0xffa82270`.
- `0xffa82c10` is a 16-byte wrapper that loads the timeout `0x2dc6c0` (3,000,000 ticks) and tail-jumps to `0xffa82a10`. Nothing in the call path skips the wait for `0x100b`: the only bypass is the simulator signature test on `cpuid[2]` (`0xaeeeeeee8badbeef`), which returns -24 without sending. The wait itself (`0xffa82730`) polls the slot's reply-ready byte (slot offset `+529`) until it is set or the deadline passes. On the deadline it returns -24 (the reply-ready byte was still 0); with the byte set it decodes the frame. The tick unit of the timer routine `0xffa0da70` is inferred to be one microsecond, so the wait is 3 seconds ([below](#what-could-end-the-wait-the-l1s-frame-sources-enumerated)); the count 3,000,000 is exact.
- On -24 the send-and-wait routine calls the node-die routine `0xffad2cb0` with `0x8d` (`0xffa82bf8`) before it returns -24 to its caller. **Corrected, see [Resolution](#resolution-of-the-0x100b-conflict):** an earlier edit of this bullet said the routine returns, because its own `br.ret` at `0xffad2dec` is reached. That read stopped one call too early. The call at `0xffad2dbc` into `0xffa9fc70` does not come back for the boot processor.
- `sysctl_init` returns the -24 and its caller at `0xffa1f62c` ignores the result (the next instruction returns), but on the boot processor the die routine has already parked it, so that code is not reached on the timeout path. The second copy is entered through the thunk at `0xffa912b0`, which has no direct caller (unknown who reaches it).
- What the node does with a reply, if one came: the decoder `0xffa82270` reads the status (4 bytes) then the count byte and its arguments; it is called with zero expected arguments, so a status-0 frame with a zero count would be accepted. No reply is the L1 behaviour, so this decode is not reached on a real brick.

**L1 side (L1 1.62.1 `l1`, read with an ARM disassembly of the load image; established unless marked).** Every path from the received frame to the outbound response for code `0x100b`:

1. `syscom_process_inbound_request` (`0xc2284`) parses the frame into an argument list whose argument 0 is the request code (`ARG__START` at `0xc23d8`), so the argument count it passes on is the frame's count plus one. A call to the optional capture hook `SysComCaptureInput` (a global that is a pointer, called with the frame; its return is ignored) precedes the routing. It then calls `IRouterRequest` (`0xc2664`). It sends no reply of its own, and if routing fails it only logs.
2. `IRouterRequest` (`0x10aafc`) builds a packet and calls the routing routine `0x109af8`. That routine, for a destination registered as a function (`L1ReqInit`, `0xc82d0` to `0xc82e4`, registers `L1ReqIRouter` as the request function of router id 6), calls it directly in the same task, with the packet, and discards its result (`0x10a150` to `0x10a164`). So there is no queue, no other task and no deferral.
3. `L1ReqIRouter` (`0xc8388`) is a big switch; the `0x100b` case is `0xcb474`. The packet's argument count is at `+0x20`. A count of 4 (the code plus three) is the only value that takes the work path: it builds the version word from the three integers, calls `vramSlotSet`, logs through `nvramLogFinsert`, and, when a stored slab is set and `SysComGetSlab` of it equals the slab byte kept in the handler's frame, calls `SysComEventDisable`. None of those starts or sends a reply (`SysComEventDisable` at `0xc4a84` is 44 bytes: it writes one global and calls one other routine, `0x2dda8`, a setting store whose first 0xd8 bytes contain no call; it is not a router routine, and the reply path needs the reply count word that only `ARG__START` sets). Any other count calls `ARG__START` with -100, which is the only reply.
4. Both branches jump to the common tail at `0xcf14c`. The tail sends a reply only if the reply count word at `fp-0x2b0` is non-zero (`0xcf198`); `ARG__START` (`0x9df34`) is the only thing that sets it to 1, and the work path never calls it. It then frees the request packet (`IRouterFreePacket`, which has no send call).

The node firmware's own `0x100b` request carries three integers, so its count is 4 and it takes the work path. A different argument count would produce a status -100 frame, but the node firmware does not send one.

**Conclusion for an emulated L1 (established).** For `0x100b` with three arguments send no bytes back. Do the L1's side effects only: record the version and run the `SysComEventDisable` step when its slab test passes. For any other argument count the reply is the ordinary status frame: a reply of status -100 and no further arguments: byte 0 is `0x20` plus the subchannel, then `ff ff ff 9c`, then the argument count 0 (inferred from the reply layout above; `ARG__START` records only the status). The node firmware never sends a wrong count, so this frame is not needed for it. Remaining unknown: what completes the node's wait on a real brick (see [Resolution](#resolution-of-the-0x100b-conflict)). The L1's behaviour is silence; the node's behaviour on silence is a park, so a model that is silent here makes the PROM stop at its first request.

## Resolution of the 0x100b conflict

The chips repository's review said the node-die routine `0xffad2cb0` parks the boot processor; this page said it returns. **The chips reading is right for the code (established). This page's reading was wrong.** Both sides were re-read in Ghidra (ARM `l1` of 1.62.1, retools ARM support, and the IA-64 export of `shub1snprom.bin`), with `ia64-linux-gnu-objdump` as the cross-check for every branch below.

- **The node does not return from the die routine on the boot processor (established).** `0xffad2cb0` ends by calling `0xffa9fc70(nasid, 0, 0)` (`0xffad2dbc`), and only then reaches its `br.ret`. `0xffa9fc70` does the two register accesses the chips page describes (the node reset request and a scratch-word update), then, because its third argument is 0, compares the local node number (`0xffa0dcf0`, a read of a local register) with the argument at `0xffa9fe0c`; with a zero second argument it calls `0xffa9fba0(nasid, slice)` at `0xffa9fe60`. That routine repeats both tests, and the processor's own slice is the one in `cr.lid`, so for the boot processor it calls `0xffaeb7c0` (`0xffa9fc5c`). That routine sets a per-processor bit (`0xffa0eae0`), does an `rfi` to `0xffaeb8b0`, calls PAL index 3 (cache init) and then loops on PAL index 29 (halt light) at `0xffaeb8d0`; the loop's own branch goes back to the call. Nothing in that path returns. The simulator signature on `cpuid[2]` is the only bypass, and it also stops the request being sent.
- **The L1 sends nothing for a three-argument `0x100b` (established, re-read).** `syscom_process_inbound_request` (`0xc2284`) turns the frame's count byte 3 into four arguments by adding the code as argument 0 (`ARG__START` first), so the node's request has the count 4 that the handler requires. The node's request builder `0xffa81f40` is called with argument-word count 6, which is three integer arguments, so the -100 reply path is not taken. The destination word `0x0ffff006` is the local wildcard (`0xffff` in bits 31:12 matches the constant at `0x10a17c`) with task 6, which is the function registered by `L1ReqInit`. The handler never calls `ARG__START`, and the router tail sends only when the reply-count word is non-zero. The PPP reader (`PPPRead`, `0x10e490`) only de-frames; no layer from the serial port to the handler sends an acknowledgement. The ColdFire packages' handlers for `0x100b` (see [brick-request-handlers.md](brick-request-handlers.md)) also send no reply on success, so no L1 package read here answers it.
- **What the node accepts as a reply (established from the receiver).** The receive state machine `0xffa87830` marks a slot done by incrementing its reply-ready byte (slot offset `+529`) after the frame's CRC residue test (`0xf0b8`, `0xffa89de0`). The test is on the CRC and the header byte's slot number only. It does not look at the request code or the body. Any good frame whose header byte is the open slot's (`0x20 | n` or `0x40 | n`, `n` = 5 plus the processor slice) completes the wait.
- **Candidates closed (established).** An L1 that replies by some path (a generic acknowledgement, the PPP layer, another task or subchannel) was not found in the ARM program. A different argument count does not occur. The node does not skip the wait on a real brick: the only bypass is the simulator signature.

### What could end the wait: the L1's frame sources, enumerated

Read in Ghidra over the whole `l1` program (2,141 decompiled routines, the 28,516-byte `L1ReqIRouter` decompiled on its own), with a capstone disassembly of `0xc8388` to `0xc8460`, the `0x100b` handler `0xcb474` to `0xcb6b0` and the router tail `0xcf14c` to `0xcf2ec`. The node's wait on slot `n = 5 + slice` (slice = `cr.lid` bits 26:23, `0xffa819c0`) completes on a good-CRC frame whose header byte is `0x20 | n` or `0x40 | n` while slot `n` is open (receiver `0xffa87830`: the in-use byte at slot offset `+0x210` is tested before the data bytes are stored, the reply-ready byte at `+0x211` is incremented after the `0xf0b8` residue test).

**Every byte the L1 can send to the node leaves through four routines (established).** The only callers of `PPPWrite` in the program are `syscom_process_outbound_request` (`0xc31dc`), `syscom_process_outbound_event` (`0xc3748`), `syscom_process_outbound_response` (`0xc3f64`) and the chunked-response routine `0xc5a78`; the first three also call the channel's raw write function for scan-chain channels. A routine that starts a frame on its own, such as a status, heartbeat or link-up frame, would have to be one of these callers, and none is.

| Writer | Header byte | Fires when | Can it land in the `0x100b` window? |
|---|---|---|---|
| response, `0xc3f64` and chunked `0xc5a78` | `0x20 \| subchannel` (subchannel from the 7-bit tag in bits 5 to 11 of the request's source word) | an `IRouterResponse` for a request that carries a reply: only after `ARG__START` (`0x9df34`) | not for `0x100b`: the handler never calls it (below). Replies for other requests do not exist yet: the node has sent nothing else |
| event, `0xc3748` | `0x40 \| subchannel` of the event word `SysCom+8` (global `0x3326e4`, `+8`) | an event packet addressed to task 4 (`EvtIRouter` `0x9dd34`; producers include `EvtPrintf`, `EnvEvent` and `L1CfgUpdate`, and which of them address task 4 was not traced) **and** the event word is not -1. A four-argument event is dropped unless its fourth argument is 0 or equals setting `0xe` | only if the event word is set; see next paragraph |
| request, `0xc31dc` | `subchannel` (class 0), or `0x40 \| subchannel` for brick type `?` | a console character the L1's own console input path hands to task 5 (`FUN_0009d1e0` from `SMPLibrary`, `0x9bed4`, one request per typed character; carriage return becomes CR LF only for brick type `?`) | no: needs a person typing on the L1 console, and the subchannel is the console's |

**The event word is -1 after every L1 start and after node power-down (established).** `SysComConfig` (`0xc0584`) stores -1 into it, and restores it from setting `0x13` only when `exceptionIsSoftReset` is true and the stored subchannel index is 4 or more. Writers: `0x1007` sets it (`0xcb094`; the handler replies status 0), `0x100a` clears it, `0x100b` clears it when the sender's slab equals the stored slab (`0xcb474` path, `SysComGetSlab`), and `EnvPowerDownDone` (`0xbec9c`) clears it; two more callers in the environment code (`0x73730`, `0x74060`) were not read. So after a cold start or a node power cycle no event can reach the node before the node itself has sent `0x1007`, and the node sends that after `0x100b`. The one path that makes the L1 send a frame the node did not ask for is a stale event word: an L1 soft reset, or a node reset with no power-down in between, after an OS had registered a subchannel. The kernel's event subchannel is opened from the same slot numbering as the PROM's (`sysctl_subch_open`, then `0x1007` naming it; the slot index itself was not read in the kernel path, so that match is inferred), so an environment event would then carry `0x40 | n` and satisfy the open slot. That is a warm-restart accident, not a design, it needs an event inside three seconds, and it cannot occur on first power-up.

**Nothing in the node's own earlier traffic prompts a frame (established).** Before `0x100b` the node programs its UART and sends no byte (chips `software/firmware/snprom/l1-requests.md`, "The link start before the first request": no sync, no hello). A console frame from the node (class 2, `0xc271c`) makes the L1 call `SMPConsoleSubchannel`, `vramSlotSet` and `IRouterEvent` for its own management task; nothing in that path writes to the node.

**The `0x100b` handler itself sends nothing (established, re-read).** The reply-count word `fp-0x2b0` is cleared at `0xc83a8`; the count-4 path of `0xcb474` calls `vramSlotSet`, `nvramLogFinsert` and, on the slab test, `SysComEventDisable` (`0xc4a84`: one global store and `nvramSet(0x13, 0)`), then branches to the tail, where `0xcf198` skips the reply because the word is still 0. `IRouterRequest` (`0x10aafc`) and the router (`0x109af8`) call the handler directly and discard its result, and `IRouterFreePacket` (`0x1092f4`) sends nothing. The chunk assembler `0xc4ab0` is reached only for codes `0x3001` to `0x3003`.

**Other builds (established for ARM, not read for ColdFire).** The ARM `l1` of L1 1.44.0 (package 6 of the IRIX 6.5.30 container, SHA-256 `b33154e5...0c819e`) has the same `0x100b` handler (`0xc1d50` to `0xc1f40`): the count-4 test, `0xfde7c` argument reads, `0x818a0` (`vramSlotSet`), the `PROM %x.%x (PR %d)` log, `0xb7e54` (`SysComGetSlab`) and `0xbb818` (`SysComEventDisable`), and no call to `ARG__START` (`0x958d4`) except in the count-not-4 branch. The ColdFire handlers send no reply either ([brick-request-handlers.md](brick-request-handlers.md)); whether the ColdFire L1 initialises its event word differently from -1 was not read, so for a ColdFire Altix 350 brick the stale-event paragraph above is not checked. The ARM builds 1.38.4 and 1.40.5 have it too ([arm-prom-version-request-1.38.4-1.40.5.md](arm-prom-version-request-1.38.4-1.40.5.md)). **The tick unit (inferred).** The node's timer `0xffa0da70` returns the SHub real-time-clock count (`0x81_101c_0000`) times a period read from `0x81_1006_0280` (bits 13:4, times 10, plus 10), shifted right 3, times `0x20c49ba5e353f7cf` (0.128 of 2^64, high half) and shifted right 4, which is the product divided by 1000. The delay routine `0xffa0db90` inverts it (`ticks * 1000 / period`). Read as a period in nanoseconds, a tick is one microsecond and the `0x2dc6c0` wait is 3 seconds. The register's meaning was not read from a manual, so the unit is inferred.

**Conclusion (grade: the frame is unknown).** Nothing in the L1 1.62.1 program, or in the 1.44.0 handler, sends a frame that could end the node's first wait on a cold start: no response (the handler sends none), no event (the event word is -1), no console frame (needs typing), and no periodic, heartbeat or link-up frame exists. The one frame that could satisfy the slot is an event with header `0x40 | n` on a stale event word, which needs a previous OS session and cannot be the cold-boot path. So what completes the wait on a real brick on first power-up is **unknown**, and the code read says a silent L1 parks the node. Real boots of SAL 4.65 and 4.80 (next paragraph) show that on real machines the wait does end. Two readings remain open, neither supported by code: the real bricks ran an L1 build that does answer `0x100b` (none of the ARM builds 1.44.0, 1.60.3, 1.62.1 and none of the ColdFire packages read does), or the PROM image read here is not the one those bricks booted. A ColdFire-fitted Altix 350 module would not change this reading unless its event word starts set.

**Real boots against this reading (added 2026-11-15).** The chips repository's `software/firmware/snprom/l1-requests.md`, section "Real boots and the other PROM builds", has the evidence and the tables; the points that bear on the L1 are:

- *Real hardware passed this wait (inferred: console logs and an owner's statement, not a read of shipped code).* Published Linux console logs from a Prism (SAL 4.65, snprom 10.15) and an SGI SHub 1 test system (SAL 4.80, snprom 10.30) start at the EFI banner, so the PROM finished. An Altix 350 owner reports SAL 4.56 (snprom 10.6). All three builds send `0x100b` through a send-and-wait that calls the die routine on a missing reply, and the die chain in each is the 5.04 one (node reset write, node and slice test, halt loop). The same holds for every held SHub 1 build from SAL 4.55 to 5.04 (23 builds). Builds up to SAL 4.43 send the request through a plain send-and-wait without the die call, so a silent L1 only cost them 3 seconds.
- *The park is not state-dependent (established for SAL 5.04 and 4.90, the two builds re-read in review).* On the boot processor the die path reads only the SHub ID register's node field, `cr.lid`, and the state object's nasid; no master flag or per-slice record, and no scratch-word value that decides a branch (it writes back a scratch word with bits 29:26 cleared). Its register store, `0x1_0001_0000_0000` to offset `0x1_2000_0000`, is the same value and register offset as SAL_A's "PAL early self-test failed" store, reached through a different address window. So a real first boot whose wait times out reaches the halt routine.
- *Therefore, on the machines in the logs, the wait ended.* The L1 builds read here (ARM 1.44.0, 1.60.3, 1.62.1; the ColdFire handlers) answer nothing and have no other frame source on a cold start, so none of them is the L1 those machines ran, or the frame that ended the wait was not one of the sources enumerated above. Every SHub 1 PROM from 4.33 on prints "Check L1 firmware version. Must be at least 1.37.25" for an unrelated feature (port set-up), which puts the L1 of those machines at 1.37.25 or newer. The ARM 1.38.4 and 1.40.5 readings in this repository reach that range, and their `0x100b` handlers send no reply either ([arm-prom-version-request-1.38.4-1.40.5.md](arm-prom-version-request-1.38.4-1.40.5.md)).
- *Which L1 an Altix 350 carries is not established.* The Altix 350 guide (007-4660-001) and the L1 and L2 guide (007-3938-005) show prompts such as `001c01-L1>`, the display text "L1 running" and the L1 message list, and name no firmware version, processor or brick type letter. ColdFire `O` and ARM `F` are both in the 1.62.1 container.
- *ColdFire event word.* In package 5 of the IRIX 6.5.30 container (L1 1.44.0) the word at `0x30006d14` (offset 8 of the `0x30006d0c` state block) has two direct references: a test (`0xffe3d4d4`, which compares it with -1) and the clear routine (`0xffe3d4ec`, which stores -1 and calls the NVRAM setter with `0x13`). No direct store of a power-on value was found, and no direct jump to the clear routine was found, so the initial value, and with it the stale-event path for a ColdFire Altix 350, is unread. Established for the two references; unknown for the initial value.

**For a model.** The L1's behaviour for `0x100b` with three integers is silence (established for ARM 1.44.0, 1.60.3 and 1.62.1). A model that wants the PROM to boot must complete the node's wait some other way. The least-assumption frame is status 0 and a zero argument count with header byte `0x20 | n`, so the payload is `20+n 00 00 00 00 00` (`n` = 5 plus the boot processor's slice). For `n` = 5 the wire frame is `7e 25 00 00 00 00 00 68 66 7e`; for 6, 7 and 8 the two FCS bytes are `15 6a`, `3e 6e` and `b7 53` (FCS computed here, residue `0xf0b8` checked, no escaping needed). It is an approximation, not a recorded L1 behaviour, and a model should mark it as one.

**(a) Stale event word.**

- *Cold start: cannot fire (established, both builds).* `SysComConfig` stores -1 in the event word and restores it from setting `0x13` only if `exceptionIsSoftReset` is true and the restored subchannel is 4 or more. `exceptionIsSoftReset` tests the boot variable `HW_LAST_RESET` against `soft` (inferred meaning: the last reset was a processor soft reset, not a power-on). 1.38.4 does the same in the tail of `SysComInit` (a store of -1 at `0x83600`, then `nvramGet(0x13)` under the soft-reset test, kept if the signed word is above 3, `0x83620` to `0x83638`). Ghidra's decompile of the jump table omits that tail, which is why the earlier reading took 1.38.4's gate to be open from the start. Brick types that take the table's default case (`0x836c0`) skip the tail and start no outbound task, so they have no SysCom writer at all.
- *Warm restart: passes the acceptance rule, but the window is the time before the first request is handled (established for the order, inferred for the size).* A stored word with subchannel 5 to 19 gives an event header `0x40 | subchannel`. If that equals the open slot `n` and the frame leaves on the PROM's channel, the receiver takes it. The frame leaves on the channel of the word's slab, and the `0x100b` handler clears the word when that slab equals the slab the request arrived on, which is the PROM's channel. So the PROM's own first request removes the subscription. The frame could land only between the PROM opening slot `n` and the handler running, and only if an environment event falls in that interval. A word with another slab sends to another channel, so it cannot reach this PROM. The compare uses the slab and ignores the slot (channel group) in the word's high half; a different group is a different UART, so that does not change the answer. Two more routines clear the word after `SysComReset` on a port-down path (`0x73730`, `0x74060`, the environment callers left unread before), so a node power-down clears it as well.
- Grade: cannot end the wait on a cold boot (established); on a warm restart, practically no (inferred).

**(b) Request-writer frame for brick type `?`.**

- *The frame (established).* For `brickGetType() == '?'` the writer sends `0x40 | subchannel`, the character, and a line feed after a carriage return, and skips the `powerStatusSlot(slot) == 1` condition. 1.38.4's request writer has no `?` branch: it sends the bare subchannel byte (class 0) and needs the power test.
- *Acceptance (established, from the receiver reading in the chips page).* `0x40 | n` for `n` = 5 to 19 is accepted when slot `n` is open, so the frame would complete the wait if the console target's subchannel equalled the PROM's slot. The subchannel comes from the console target word (`L1Cfg(0)+0x14`, copied into the destination by `SMPInit`); its value was not determined: unknown.
- *Cold boot with no input: cannot fire (established).* It is the per-character path in the first table row. `?` is a wrapper type that carries the real brick type in a subtype letter (the same letters as the console connect list); which product that is was not established.

**Result.** No frame from either build ends the wait on a cold boot (established for 1.38.4 and 1.62.1; 1.40.5, 1.44.0 and 1.60.3 were not re-enumerated). The stale-event path is closed by the handler itself and the `?` path needs console input. What a real brick did stays unknown, and the least-assumption reply above stays an approximation.

## Request `0x0006` in the ColdFire L1 (type `O`), 1.62.1 package 3

Read in Ghidra (`68000:BE:32:Coldfire`, flat load at `0xffe00000`) from package 3 (`2MB image`, string `O5#=?`) of `l1-1.62.1.bin`. Addresses below are that package's. The same code is in package 1 (`Legacy 2MB image`; handler `0xffe13a02`, device table `0xffe5152c`) and in package 5 of the IRIX 6.5.30 container (L1 1.44.0; addresses in the last bullet). Grades follow [AGENTS.md](../../../AGENTS.md).

### The handler (established)

- **Dispatch.** The general-task dispatcher is at `0xffe3f9d4`; codes `0x00` to `0x13` go through a table of 16-bit relative offsets at `0xffe3fc78`, and code `0x0006` lands on `0xffe402c8`. The handler is a block inside the dispatcher, not a function of its own. It needs at least five words including the code (`-100` otherwise): word 1 device id, word 2 selector, word 3 byte offset, word 4 byte count. A tagged word is fetched with the argument routine `0xffea855c`.
- **Id to table index** (`0xffe3f6b8`, called from `0xffe40304`). For brick type `O`: 0 to 0, 1 to 1, 4 to 7 give 2 to 5, 8 to 13 give 6 to 11, 16 to 21 give 12 to 17, **98 gives 18, 99 gives 19**, every other id gives `0xff` (read as an unsigned byte). This is the same map as the ARM `F` one. Type `5` takes a different rule (tag times 22 plus the index).
- **Device table** (22 entries of three words: bus-and-address-and-size word, record kind, name; table at `0xffe55fd0`, registered at `0xffe55ae2` with count `0x16`). Entry 0 INTERFACE bus 0, address `0xa4`; entry 1 **NODE bus 2, address `0xa0`, size `0x200`, kind 1 (IPMI FRU)**; entries 2 to 5 CPU 0A, CPU 0C, CPU 0A S, CPU 0C S (bus `0x12`, `0x80` bytes, kind 3 for the first two and 0 for the S pair, so every selector answers `-104` for them); 6 to 17 DIMM 0 to 5 L and R (`0x100` bytes, kind 2); **18 RISER bus 3, address `0xa8`, size `0x200`, kind 1; 19 IO9 bus 3, address `0xac`, size `0x200`, kind 1** (the ARM table has IO10 here); 20 and 21 PS 1 and PS 2 (bus 4, `0xa0` and `0xa2`, kind 4). The top nibble of the bus byte picks a second-level channel, the low nibble the first-level one.
- **Checks, in order** (`0xffe4038c` to `0xffe403b6`): presence byte of the mapped index (`0xffe8efe8`; false for an index at or past the count, which includes `0xff`) gives **`-104`**; then the selector dispatch. Selector 0: kind must be 1 (else `-104`), record status word at +4 nonzero gives `-107`, returns the 8-byte common header at +8. Selector 1, 2 and 3: kind must be 1 (else `-104`), the area's status word (+0x10, +0x1c, +0x34) nonzero gives `-107`, the area buffer and size are at (+0x18, +0x14), (+0x24, +0x20) and (+0x3c, +0x38). Selector 4: kind must be 2, status +4 nonzero gives `-107`, buffer +0xc, size +8. A selector above 4 gives `-105`. An offset not below the area size gives `-105`. The `-105` for an index past the count cannot be reached, as in the ARM handler.
- **Reply** (`0xffe405cc` to `0xffe4060a`; writers `0xffe48034`, `0xffe48058`, `0xffe48098`). Status 0 (an integer field), then an integer: the area size minus offset minus count, or 0 when the window reaches or passes the end of the area; then, only if the clipped window is not empty, one raw-byte field (type 9) copied from the area buffer at the offset, clipped to the end of the area. Three fields in all, the same shape the PROM reads in 64-byte chunks.
- **Statuses.** `-100` (`0xffffff9c`), `-104` (`0xffffff98`), `-105` (`0xffffff97`), `-107` (`0xffffff95`).

### How the records and presence flags come to be (established, ordering inferred)

- **Registration** (`0xffe8ede8`, called from the type-`O` board initialiser `0xffe55a80`). Allocates a presence byte per entry **filled with 1** and one 120-byte record per entry. Nothing is read yet. The initialiser is reached from the boot task `0xffe10570`: the identity routine `0xffe7b404`, then the descriptor setup (`0xffe55cd8`, chosen for type `O` by `0xffea8b9c`), then the call through the descriptor's board-init word at `0xffe105c0`. The general task is started later in the same routine (`0xffe3f840` is the nearest candidate; its body was not read), so decoding before the first request is inferred, not traced.
- **What clears a flag** (`0xffe8ef28`, the only writer of 0). In the type-`O` board code (`0xffe54d94`): PS 1 (index 20) and PS 2 (21) from bit 2 of expander 3 and 4 input bytes; **RISER (18) and IO9 (19) when bit 1 of expander 0's input byte is set (the log line is "Riser not present")**; IO9 also when the riser EEPROM's product text is `2U_AGP_RISER` (a graphics riser, "Opus Graphics Brick"), or when its probe fails; the CPU and DIMM entries from the node-board presence code (`0xffe57ec4`, `0xffe57a68`). **NODE (1) and INTERFACE (0) are never cleared**: their flags stay 1.
- **What is probed at boot.** `0xffe8f2cc` sets a flag to 1, reads 8 bytes at offset 0 and clears the flag if the read fails (a NAK, status `-0x194`, is swallowed silently; other failures are logged "Error probing"). It runs for IO9 (when a non-graphics riser is present) and for the DIMM entries. The riser (18) is only read, into a local buffer, to learn its subtype; its flag is untouched.
- **Decode** (`0xffe905c8` per entry, all entries by `0xffe906d8`, reached from `0xffe64a14` which the board initialiser calls after the presence code, through `0xffe64784`). A record with a flag of 0 is not read. For kind 1 (`0xffe90400`): read 8 bytes at offset 0 over I2C, check that they sum to 0 (else record status 3, "header checksum error"), then read each area the header offsets name (header bytes 2, 3, 4, 1 for selectors 1, 2, 3 and the unused product slot); an area is its first-byte version, its second-byte length in 8-byte units, its bytes read in full and checked to sum to 0 (status 2 on a read error, 3 on a bad sum, 1 when the offset is 0, i.e. absent). A failed 8-byte read sets status 2 in the record and every area. The area buffer is the **raw EEPROM bytes**; the L1 also parses the board area's strings into the record for its own use (`0xffe8f3a0`), without changing the buffer.

### Device 1 and device 98 for a module with a node EEPROM and no riser EEPROM (established for the behaviour; the strap polarity follows the branch, not a datasheet)

### What a model of the 350's L1 needs

- A per-module device table with the id map above, a presence byte per entry and, for each present entry, the bytes of its IPMI FRU: an 8-byte common header whose bytes sum to 0 and whose byte 3 is the board area's offset in 8-byte units, and a board area (version byte, length in 8-byte units, bytes summing to 0, the language, time, manufacturer, product name, serial number, part number and file id fields of the IPMI format). - Replies exactly as in "Reply" above: status 0, bytes left, raw window; `-104` for a cleared flag or an unmapped id, `-107` for a present entry whose EEPROM could not be read, `-105` for a selector above 4 or an offset at or past the area size, `-100` below five words.
- An emulated I2C EEPROM is not needed to answer this request: the L1 serves a RAM copy read once at boot. A fixed `-104` or `-107` for device 1 is the reply of a node with no readable EEPROM, which a real 350 does not have, so a fixed status is not faithful for device 1; the PROM carries on after a negative status (see the earlier section). A synthesised, correctly checksummed FRU image per board is the minimum faithful answer. An I2C-level model matters only if the model also runs the L1's own boot code.
- The riser-absent strap (expander 0, bit 1) is the L1's input, not the PROM's; a model that serves records directly does not need the expander.

## Request `0x1007` (event subchannel set) in the ColdFire L1 (type `O`) and the ARM L1 (type `F`), 1.62.1

Read in Ghidra (`68000:BE:32:Coldfire`, flat load at `0xffe00000`, 44-byte header skipped) from package 3 (`2MB image`, string `O5#=?`) of `l1-1.62.1.bin`, SHA-256 `14b7122d...a66e`, with the byte patterns checked in the carved image. The ARM side was cross-checked in Ghidra (`ARM:LE:32:v4`, flat load at `0x8000`) on the `l1` carved from package 4 (1,999,676 bytes, hash matches the table in [sn2-l1-1.62.1-packages.md](sn2-l1-1.62.1-packages.md)). The node side of the same request is in the chips repository, `software/firmware/snprom/l1-requests.md`, section "Request 0x1007 and the kernel console". Grades follow [AGENTS.md](../../../AGENTS.md).

**What the node sends (established, from the node's runtime).** Frame header byte `5 + slice`, destination word `0x0ffff006`, code `0x1007`, count byte 1, one integer argument: tag `00`, value `00 00 00 13`. The value is the subchannel slot the node has just reserved for events (slot 19), not a mask. The node waits for a reply and reads only the status.

**ColdFire handler (established, the whole block read).**

- **Place.** A block of the general-task dispatcher `0xffe3f9d4` (the dispatcher is one function; the compare chain tests `0x1007` at `0xffe3fc4e`), from `0xffe40ef6` to `0xffe40fc2`. It is reached after the common prologue: sender slab from the packet source tag, port tag from byte `0x17 >> 3` of the packet when the board has two or more ports (else 0), the trace line `L1REQ:` when the debug flag word `0x300013a4` is set, the status writer `0xffe48034` primed with status 0.
- **Inputs.** The word count at packet `+0x20` (code included). Below 2: status `-100` (`0xffffff9c`) and nothing else. Otherwise word 1 is the value, taken from the frame when its tag bits are 0 and fetched with the argument routine `0xffea855c` otherwise.
- **Effect.** The event word `0x30006d78` (offset 8 of the `0x30006d70` state block) is set to `port tag << 16 | tag`, where `tag` is the tag routine `0xffe3d530` of (sender slab, value): for brick types other than `6` and `@` it is `slab * 32 + (value & 0x1f)`. For the lone slab of an Altix 350 and value 19 the word is `0x00000013`. With the debug flag word set the handler prints `subc %d (%x << 16) | %x`. It then calls the setting writer `0xffe74330` with setting `0x13` and the word, so the subchannel can be restored after a soft reset of the L1 (below). **The reply is status 0 and no further field**: the status writer is the one the other zero-result handlers use (set field count 1), and the exit path at `0xffe42460` sends it. On the wire: `20 | n`, `00 00 00 00` and a zero argument count, where `n` is the request's slot.
- **Event gate.** The forwarder `0xffe3db60` sends environment events to the node only while the word is not -1 (test `0xffe3df3c`); it builds the event header as `(word & 0x1f) | 0x40`, so `0x53` for 19, and checks the slab and the slot count from the port table. `0x100a` runs the clear routine `0xffe3df54` (word -1, setting `0x13` = 0); `0x100b` clears it when the sender matches.
- **Initial value, settled for 1.62.1 package 3 (established).** `0xffe3d374` (the SysCom task start) stores -1 in the word on every start, then restores it from setting `0x13` only when the word at `0x301019ac` is non-zero (the soft-reset marker, read through `0xffe79974`) and the restored subchannel is 4 or more. So after a cold start the event word is -1 on the ColdFire L1 as on the ARM one: a ColdFire Altix 350 cannot send an event before the node's own `0x1007`. This replaces the "unread" initial value recorded for package 5 of 1.44.0 in the paragraph "ColdFire event word" above; the clear routine and the test have the same shape there (`0xffe3d4ec`, `0xffe3d4d4`).
- **Not read.** What `0x301019ac` is and who sets it (it is the same kind of flag as the ARM `exceptionIsSoftReset`); whether package 1 (`Legacy 2MB`) differs (not compared; the earlier notes found its `0x0006` handler matching).

**ARM handler (cross-check).** The ARM `l1` handler is `0xcb094` of `L1ReqIRouter` (see the code table above: `SysComSetTasknum`, setting `0x13` written, status 0 reply; established for the calls, the layout of the stored word inferred). Re-read this round: the SysCom init `0xc0584` sets the event word (state `+8`) to -1 and restores it from setting `0x13` only when the soft-reset test `0x217cc` is non-zero and the stored subchannel (`0xc119c`) is 4 or more; the clear routine `0xc4a84` stores -1 and writes setting `0x13` = 0. Both match the ColdFire `0xffe3d374` and `0xffe3df54` statement for statement. `L1ReqIRouter` itself did not decompile as one function in the flat image, so `0xcb094` was not re-read this round.

**What a model of either L1 needs.** Answer with status 0 and no arguments; keep the value as the event subchannel (events, if any, go out with header `0x40 | value`); on fewer than two words answer `-100`. Nothing else changes. The console traffic that follows (class-2 frames in, class-0 frames out, `0x44`/`0x04` for index 4) needs no state beyond the console mode and the subchannel learnt from output frames ([console-behaviour.md](console-behaviour.md), "Console input frame (L1 to node)" above).
