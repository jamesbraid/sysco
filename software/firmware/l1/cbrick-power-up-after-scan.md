# L1 1.44.0 C-brick: `power up` end to end, what it reads, waits for and prints

An ordered pre-read of the stock C-brick `power up` (package 0, `Base 1MB`, L1 1.44.0 of the IRIX 6.5.30 `l1.bin`) for a board model that has just got past the scan check ([scan-interface.md](scan-interface.md)). It joins the earlier readings ([power-reset-cbrick.md](power-reset-cbrick.md), [power-up-reads-restart-and-polling.md](power-up-reads-restart-and-polling.md), [serial-number-requests.md](serial-number-requests.md)) with the release tail read for this note. Grades: E established (routine read), I inferred, U unknown. A "tick" is 10 ms at the inferred 100 Hz ([board-boot-contract.md](board-boot-contract.md)).

**Short answer.** Apart from the scan's TDO compares, the C-brick `power up` has no compare against any value read from a board device, no power-good wait and no wait on the node or the PROM. Expander and monitor reads are made and used, but none is checked against an expected value in the power-up path. The scan is the only data-dependent gate, and it is at the end of the sequence (the release), after the supplies have been enabled. E for the routines read (below); the background tasks that start with power (environment poll, node-link and router tasks) were not searched exhaustively for a node-silence timer (U).

## What an error looks like

A failing step returns a negative code. The caller prints it as `ERROR: <class>:<text>` (the class and string tables are at `0xffe5c84c`; examples: `SerNum`, `SCAN`, `I2C`, `Port`, `Power`) and shows `Power Up Error` on the front panel; on success it shows `Powered Up`. A supply-enable write that fails, or a fan-start write that fails, runs the power-down with reason 5 and ends the sequence; an error from the port bring-up is latched and printed at the end without stopping the sequence; an error from the release is returned and the power state is not set to 1. E ([power-reset-cbrick.md](power-reset-cbrick.md)).

## In order

| # | Step | What it reads, and the value it needs | Wait | If it fails |
|---:|---|---|---|---|
| 0 | Boot, before any command | Board identity EEPROM at `0xa4` (name `IP35`), the PIMM PSC expander, the display expander, DIMM EEPROMs, every expander once for the cold-start application, the USB window probe. A silent bus gives type `?` ([cbrick-mbus-registration.md](cbrick-mbus-registration.md)). The PIMM PSC nibbles decide which PIMMs exist: `0xf` is absent, and a model that leaves the expander at its power-on `0xff` has no PIMM, so their supplies, processors and module steps below are skipped | | an unknown type (`?`) is the result of a silent bus; the later steps were not read for that case (U) |
| 1 | Command and serial check | Settings 13, 15 and 80, the board EEPROM serial. No bus read. Needs an assigned serial ([serial-number-requests.md](serial-number-requests.md)) | | `ERROR: SerNum:...` |
| 2 | Hold (`0xffe4f2f0`): the parallel-port pulse, then the hold hook | `PPDAT` read once by the pulse. The hold hook compares the PIMM type bytes with settings `0x56` and `0x57` and only logs a difference ("PIMM type changed, setting the default voltage margins"). The flag byte at `0x30000098` is set at board init, so the -900 exit is not taken. Writes the four reset-group bits low and `0xc0` into each present PIMM's expander | 10 ticks per present PIMM of a listed type | an expander write error is returned |
| 3 | Fan start and the supply walk | None. One expander write per enabled supply in table order (`FAN CONTROL` bit 7, `POWER CONTROL` bits 5 and 0, and per present PIMM its `PIMMn POWER` bits 0 and 3), the fan start first | 50 ticks, then 25 ticks after each supply | a write error: power-down with reason 5, `Power Up Error` |
| 4 | Settle | None | 100 ticks; then the environment is told the power phase ended (the restart is inert in this image, below) | none |
| 5 | Port bring-up (`0xffe50b74`, mode 3) | One `PORT CONTROL` read per port after setting its enable bit. Any value is accepted: remote power OK moves the port state to 4, absence leaves it at 3 ([power-up-reads-restart-and-polling.md](power-up-reads-restart-and-polling.md) section 5) | none | an expander error is latched and printed at the end |
| 6 | Release start | 50 ticks, then `reset(5)`: the hold again, 10 ticks, the release. A second hold-and-release pass runs after 400 ticks only when the second-reset predicate is nonzero (it needs a PIMM of a type in the hook's table, codes 2 to 4) | 10 ticks between hold and release | |
| 7 | Release wrapper (`0xffe4f144`): the pulse, the scan, the pulse | The scan's TDO samples: first 12 must be `1` then zeros, 32-bit pattern delayed one bit ([scan-interface.md](scan-interface.md)) | 10 ticks after the scan | `ERROR: SCAN:scan error - unable to reset scan hardware` (-2301) |
| 8 | Release wrapper tail: the L1's own port service calls, the release hook, port bring-up mode 5 | None. The L1-internal port calls (`0xffe36a04`, `0xffe52a30`) touch only the L1's own UART ports. The release hook writes `BEDROCK CNTL 2` bits 7:3 (straps), clears bit 3, sets `BEDROCK CNTL 1` bit 0, runs the module step for each present PIMM, then sets `BEDROCK CNTL 2` bit 0 and `BEDROCK CNTL 1` bit 1 ([power-reset-cbrick.md](power-reset-cbrick.md) section 6). Mode 5 of the port bring-up skips both C-brick ports (port 0 has the skip flag, port 1 has no link field) | 10 + 10 + 10 ticks in the hook, 3 + 10 per present PIMM of a listed type | an expander write error is returned and the power state stays 0 |
| 9 | Finish | Sets record-0 power state to 1, which publishes the power-state notice to a peer; shows `Powered Up` | | |

With no PIMM fitted (a model that leaves `PIMM PSC` at `0xff`) steps 3 and 8 skip the PIMM writes and module steps. Total time with the three C-brick supply enables and no PIMM is about 275 ticks (2.75 s) before the release, plus the release tail. The module steps for a present PIMM (the margin routines `0xffe4e4f8`, `0xffe4e450`) compute and write voltage margins; the device they write was not read (U), so a model with PIMMs present should be run once with the bus logging on.

## What it does not read

- **Bedrock.** The L1 has no register access to the Bedrock. Its only inputs from the node side are the `PORT CONTROL` bits (remote power OK, link LED), the PIMM `VCC OK` and `POWER` inputs, which the poll reads and whose hooks only log and post events, and the node-link UART. No power-up step compares any of them. E.
- **Monitors and the environment.** The restart routine that would configure the monitors and their limits returns at once (the word `0x300009c4` is zero), so the monitors are not configured and the poll does not shut the brick down; the poll still reads the monitor status registers `0x41` and `0x42`, where `0x00` is quiet ([cbrick-env-pimm-display-usb.md](cbrick-env-pimm-display-usb.md) section 5). A model whose expanders read `0xff` makes the VRM status inputs read as faults, which the hook logs only on a *change* of those bits, so a constant `0xff` produces no events. E for the mechanism, I for the model consequence.
- **The node and PROM.** `power up` returns after step 9 without waiting for the node. The first seconds after the release are the node's: the L1 holds the node link open on port 6 (channel 3 of the quad UART, 57,600 baud, class 3), ignores CTS in software ([node-link-cts-flow-control.md](node-link-cts-flow-control.md)), and answers whatever request frames arrive (the catalogue in [request-codes.tsv](request-codes.tsv)). No timer on node silence, no heartbeat and no expected first request were found in the routines read for this note (not exhaustively searched: U). What the stock PROM sends first is not an L1 property; it is in the request catalogue and the PROM-side readings.
- **Auto power-up.** The auto power-up task is created for type `C` only when setting `0x32` is nonzero, counts down 18 steps of 5 s, and then issues `* power up` to itself ([power-reset-cbrick.md](power-reset-cbrick.md) section 5). A window with setting `0x32` clear never starts it.
