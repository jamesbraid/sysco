# The Altix L1 image 1.62.1: packages, what changed from 1.44.0, and the tools that ship with it

Read from the `snxsc_firmware` 1.62.1-1 RPM of the Internal Support Tools 3.24 disc ("SGI SNx L1 and L2 System Controller Firmware", built 2008-11-10; files and hashes in [references/irix-files.md](../../../references/irix-files.md)). This is the controller firmware SGI shipped for the Altix and Prism line on Linux hosts. It carries two L1 containers: `l1-1.62.1.bin`, read here, and `l1_mips-1.48.1.bin`, which is the IRIX patch image again. The earlier note [sn2-brick-packages.md](sn2-brick-packages.md) ties the 1.44.0 packages to the Altix bricks; this one reads the 1.62.1 container the same way and compares the ARM Linux L1 program of the two versions. [sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md) records what the node's firmware asks the L1. Grades follow [AGENTS.md](../../../AGENTS.md).

## What changed in the container from 1.44.0

**Established** by comparing the 1.44.0 container (IRIX 6.5.30, seven packages) with this one.

- **Three ColdFire packages are gone and one is new.** `Base 1MB` (`CIPXYN&?RG`), `Fuel/PE/O300 1MB` (`%4A?`) and `MIPS 2MB` (`CIPXYN&%6780VQE9A?RG`) are not in the Altix container. Every character of those strings that no remaining package carries (`C`, `I`, `P`, `X`, `Y`, `N`, `&`, `%`, `4`, `A`, `G`, `6` to `9`, `0`, `V`, `Q`, `E`) is a type letter of the Origin 3000, Origin 300 and Onyx families. The new package is `NL3R 1MB image` with the string `?R`: it serves only the `R` letter, the router brick. It is a rebuilt 1 MB image; [COVERAGE.md version diffs](../../../COVERAGE.md) pairs it with `Base 1MB` by module list only (a guess), and its routine counts are there.
- **`2MB` and the two ARM packages keep their strings** character for character. `Legacy 2MB` keeps the same five letters in another order (`O5#=?` here, `5O#=?` in 1.44.0 and 1.48.1; the updater tests only whether a letter occurs). So the set of type letters the container can serve shrank by exactly the Origin-only ColdFire letters and gained none.
- **The ARM kernels are rebuilt, not replaced.** Legacy: Linux `2.4.25-vrs2-swl8c-sgil1`, built 2008-11-07 (1,353,548 bytes, SHA-256 `2fcef4b70720047d66883a704d4bcd393d5e0e05605f8cb88a828e7bd0cd3ba9`); the 1.44.0 kernel is the same release built 2006-06-09. Linux L1: `2.6.15.6-sgil1`, built 2008-10-26 (1,821,120 bytes, `bd9dbaaf046ced386d0ba0fd57b51356ea30559a2d15b2ff9ad6896444b98d6a`) against 1,821,072 bytes of 2006-06-09. The CramFS images are 3,047,424 bytes (`1742f50487566ee0942774849a63691b892570ff09408115899a6efc77c61db5`) and 3,891,200 bytes (`e470e7b536756f3d51b18b31ac2a41c2bd1c811771e72cc243eea6283d4f58f2`). The file-level and kernel-level differences against 1.48.1 are in [generated/version-diffs/cd-ist-3.24-linux-files.tsv](../../../generated/version-diffs/cd-ist-3.24-linux-files.tsv).
- **The root file system gains eight small programs** over the 1.44.0 Linux L1 image: `l1cmd`, `netwatch`, `rdmem`, `rdmem8`, `rdmem16`, `wrmem`, `wrmem8`, `wrmem16` in `/stand/sysco/bin` (49 files against 41). The L1 daemon `/stand/sysco/bin/l1` grew from 1,925,560 to 1,999,676 bytes (Linux L1) and from 1,363,912 to 1,368,336 bytes (legacy). Established as file names and sizes; what the new programs do was not read.

## The Altix 3000 C-brick and the other open items of the earlier note

- **C-brick type letter. Established: `5`, the board `IP41`; the 3000 C-brick is not `IP37` or `IP45`.** Read in `2MB image` (package 3 of this container, flat load `0xffe00000`; decompiled, with the key bytes checked in the raw body). The `Legacy 2MB image` (package 1) carries the same name strings and the same `IP41` module; its identity routine was not decompiled, so the same choice there is inferred.
  - **How the personality is chosen** (identity routine `0xffe7b404`; the type byte lives at `0x30000be0`, a source word at `0x30000be8`). Record `0xff` is read first; if the product name of its board information area starts `IPF_2UINT` (9 characters) the type is `O`. Otherwise record `0xfe` is read and its product name tested by prefix: `PXBRICK` (6) gives `#`, **`IP41` (4) gives `5`**, `NL4_TEST` (8) gives `!`, `IPF_2UINT` gives `O`. Only if the byte is still `?` does the persistent setting with key 9 supply it, from a fixed list of 36 characters that includes `5`, `3`, `4` and `C`. The source word is 1 when a record decided and 2 for the setting; the brick console command (`0xffe11490`) prints `EEPROM`, `NVRAM` or `OTHER` from it, and its type-change case answers with an error instead of storing when a record decided. No strap, jumper or pin read is in the choice. Established.
  - **Which EEPROM.** Records `0xfc` to `0xff` are fixed 12-byte descriptors at `0xffe90770`, `0xffe90764`, `0xffe90758` and `0xffe9074c`; their second bytes are `0xac`, `0xa0`, `0xa8` and `0xa4`, so `0xfe` is the descriptor with `0xa8`. Inferred, from the same descriptor shape in [mbus.md](mbus.md) where `0xa4` is a record at an I2C wire address on bus 0, that these are the write addresses of four serial EEPROMs. The compared string is the second field of the board information area, the product name (`0xffe8f3a0` copies manufacturer-skip, then name, serial, part number). Established for the field order, inferred for the standard FRU meaning. What a real C-brick's `0xa8` EEPROM holds was not captured: the node PROM carries a board string `Part:030-1604-001;Name:IP41` that agrees, but it is a built-in default, not a read.
  - **The three names.** The console name parser (`0xffe7ff50`, used by the `brick type` setter) maps `ip35` to `C`, `ip37` to `3`, `ip45` to `4`, `ip41` to `5`; the print routine (`0xffe80220`) names `0x33` `C (IP37)`, `0x34` `C (IP45)`, `0x35` `C (IP41)`. Of `3`, `4` and `5` only `5` is in a supported-brick string of this container (`O5#=?` in both 2 MB packages; `?R` in `NL3R 1MB image`, `?@BDSJKF^+LM...` in the ARM packages, all read at the label offsets in the table above). `IP45` is the Origin 300 board: record `0xfe` gives `4` in the Fuel/PE/O300 package of the IRIX container ([personalities.md](personalities.md)), and no package of this container identifies it. `IP37` has no identity route in any package: no record is compared with it; only the two console name tables carry it (the chips repository ties the name to the SN1 IA-64 headers; inferred for the board).
  - **The module is the Altix compute brick's.** Both 2 MB bodies carry the module `IP41.c` (36 `IP41` strings against 2 of `IP45`): `ip41_init` (`0xffe59678`, probes four processors, "called twice" guard), `IP41_Int`, `IP41_ScanInitIMPCTL`, and `IP41_DiscoverNL` with the text "SH%d NI0 always NL4 on IP41 brick", beside the SHUB node chip module. Established as strings and the init routine; the discovery code was not read further.
  - **What the L1 reports.** Requests `0x0002` and `0x0003` (dispatcher `0xffe3f9d4`, cases 2 and 3): status 0, the integer `bay | rack << 6`, then for `0x0003` the type byte unchanged, except `=` becomes `#` when a per-port flag is clear. So an `IP41` brick replies `0x35`. Request `0x0013` (case `0x13`): status 0, integer 0, the type byte. The `config` line shows `c`: the display fold (`0xffe8059c`) maps `5` to `c` before the final character call. Established for all three, with the type byte as the only input; the fold's last call is inferred to lower-case. The SHub 1 PROM (SAL 5.04, `0xffa7d510`) turns the `5` of this reply into `c` before it builds the module word, so the kernel sees an ordinary `c` brick; `o`, `m` and `@` fold to `c` the same way (established, Ghidra and `ia64-linux-gnu-objdump`; see the chips repository's PROM request page).
  - **ARM.** Neither ARM package lists `5` or `C`, so this brick is served only by the ColdFire packages. Unknown: whether an Altix 3000 shipped with an L1 flashed from the IRIX container (`C` and `R` there); the guide chapter naming the brick (007-4579-001) was not read for it.
- **R-brick.** Established that the router letter `R` is served in 1.62.1 by the dedicated `NL3R 1MB` package. That the same string serves the Altix 3700 R-brick is inferred (same letter and enclosure as the Origin 3000 R-brick, [sn2-brick-packages.md](sn2-brick-packages.md)).
- **IX-brick and PX-brick** remain in `Legacy 2MB` and `2MB` (`#`, `=`), as before.
- **Altix 350 compute module.** Inferred as before: ColdFire `O` (Opus, board record `IPF_2UINT`) in the two 2 MB packages, or ARM `F` (Opus TIO). Both are in 1.62.1. Which L1 CPU the 350's module carries is still unknown.
- **Prism.** Unknown whether `L` Dorado is the Prism; the evidence is that Dorado is the only ARM brick family besides Opus TIO, Gemini and the IP67 and IP69 blades that carries the IP57 node-board configuration (below), that the JTAG tool names `dorado_io9`, `dorado_io10` and `dorado_pcibridge` chain entries, and that the SHub 1 firmware names a `Doradobrick`. No page read says Dorado is the Prism.

## IP57 in the ARM L1: unchanged between 1.44.0 and 1.62.1

Method: the Linux L1 program `/stand/sysco/bin/l1` of both images (its dynamic symbol table defines 1,381 routines in 1.44.0 and 1,400 in 1.62.1, 2,257 and 2,302 symbols with the data objects) was decoded with an ARM decoder and every exported routine compared with the branch targets replaced by the callee's symbol name (or "local" for an unnamed one), every literal-pool load replaced by the symbol or string it points at, and the trailing literal pool dropped. Two routines are called the same when the resulting instruction sequences are equal. Limits: stack-slot offsets are part of the sequence, so a recompiled routine whose locals moved counts as changed even when its logic is the same; unnamed local routines are compared only through their callers.

**Established**:

- All twenty `IP57_*` routines are present in both versions and none changed: `IP57_Cfg_Init`, `_CpuDisable`, `_CpuEnable`, `_CpuPresent`, `_GetCpuMask`, `_Get_Cfg`, `_Init`, `_Int`, `_Nmi`, `_NodeDisable`, `_NodeEnable`, `_NodePresent`, `_NodeRemove`, `_PowerDown`, `_PowerUp`, `_Probe`, `_ResetHold`, `_ResetRelease`, `_Set_MemCfg` and `_SoftReset`. Four are byte-identical (`_CpuDisable`, `_CpuEnable`, `_NodeDisable`, `_NodeEnable`); sixteen differ only in addresses.
- The five brick families that carry an IP57 node-board configuration object (`OpusTio_IP57Cfg`, `Dorado_IP57Cfg`, `Gemini_IP57Cfg`, `IP67_IP57Cfg`, `IP69_IP57Cfg`, 20 bytes each) have the same contents in both versions once pointer-valued words are masked; so do 104 other per-brick tables of the Opus TIO, Dorado, Gemini, IP67, IP69, IP63, IP73 and IP75 families that were compared (EEPROM, port, power, monitor, fan, I/O-expander and I2C-mux tables). Exceptions: four power and fan tables listed below, one table whose size changed (`IP69_bladeOps`), and five objects in zero-initialised memory that carry no contents to compare.
- Therefore the Altix 350 node-board control sequence (CPU presence read from two I/O expanders, node reset hold and release, power up and down, memory configuration, NMI) is the same code in 1.62.1 as in 1.44.0. The behaviour is described by [arm-ip57-configuration-control-1.40.5.md](arm-ip57-configuration-control-1.40.5.md) and the notes it links.

What did change near IP57 (established as differing code; what each change does was not read):

- The `*_BrickOpsInit` routines of Opus TIO, Dorado, Gemini, IP67 and IP69, and `IP69_bladeOps` (136 to 144 bytes), differ in code. They register a family's tables, so a registration change is possible.
- `SHUB2_Init` (496 to 508 bytes), `SHUB2_Cfg_Init` (3,436 to 3,520), `SHUB2_ResetRelease`, `SHUB2_HandleJunkbusStatusInterrupt`, `TIOInit`, `TIOCfgInit`, `TIOPciResetInt`, `TIOSysComInt` and `NL4R_Cfg_Init` (916 to 1,240) differ. `TIO_Issue_CX_Probe` grew from 2,768 to 5,348 bytes.
- New in 1.62.1: the four `SHUB2_War*` routines (`WarCheck`, `WarEnable`, `WarReset`, `WarStatus`) beside the SHUB 1 `SHUB_War*` ones already present; `pcieInit`, `pcieGetSlotCfg`, `pcieRemove`, `pcieStatus` and the tables `PCIXE_pcieCfg` and `IE2S_pcieCfg` (PCI Express slots); the SHUB 2 configuration tables `IP73_SHUB2Cfg_MEM`, `IP75_667_400_SHUB2Cfg` and `IP81_667_400_SHUB2Cfg` with `IP81_eepromCfg` and `ip81_montvale_fsb667`; `RTRC_2177_002_powerCfg`, `RTRC_2177_003_monitorCfg` and `RTRC_2177_003_powerCfg`; `LinkErrEnable`, `LinkErrDisable` and `linkerr_calc_ber`; `L1CfgPortOpened` and `L1CfgPortClosed`; `BkDrInit` and `BkDrTask`; `FRU_SHUB2Init`, `FRU_SHUBInit`, `FRU_TIOInit` and `FRU_NL4RInit`. Removed: the `FRU` dump and name routines (`FRUDump`, `FRUDumpAll`, `FRUName`, `FRUUnpackData`, `FRUDetach` and the `L1FRU_2m_*` pair) and `L1CfgPortEnable` and `L1CfgPortDisable`. Established as symbol names; the "Montvale" reading of `ip81_montvale_fsb667` as the Itanium 2 9100 processor is inferred from the name.
- The power and fan tables that differ (after pointer masking): `IP63_powerCfg`, `IP69_powerCfg`, `IP73_powerCfg` and `IP73_autofanSubZoneCfg`. Their contents were not read, so which voltages or fan zones moved is unknown.
- The general request dispatcher of the Linux L1 gained three request codes, `0x0016`, `0x0017` and `0x5000` ([sn2-prom-link-1.62.1.md](sn2-prom-link-1.62.1.md)).

So for the Altix 350 (IP57) the 1.62.1 image adds nothing in the node-board code; the growth is in the SHub 2, TIO, PCI Express and Altix 4700 (IP73, IP75, IP81 blade) support. For the Altix 3000 C-brick the ARM L1 has no code at all: it is a ColdFire-package brick.

## `l1_mips` and `l2_mips`

**Established.** `l1_mips-1.48.1.bin` (16,027,376 bytes) and `l2_mips-1.48.0.bin` (2,993,732 bytes) have the SHA-256 of patch SG0007149's `l1.bin` (`536bfa4c...`) and `l2.bin` (`10258789...`): the seven-package IRIX container (`Base 1MB`, `Fuel/PE/O300 1MB`, `MIPS 2MB`, `Legacy 2MB`, `Legacy Linux L1`, `2MB`, `Linux L1`) at 1.48.1 and the L2 1.48.0. They are the controller firmware of the **MIPS** machines (Origin 300, Origin 350, Origin 3000, Onyx 300, Onyx 350, Onyx 3000), shipped on the Linux disc so that a Linux L3 or SGIconsole host can update the L1 and L2 of a system built from those machines. The Altix pair `l1.bin` and `l2.bin` is 1.62.1 and 1.62.0. Which of the two pairs `flashsc` offers a given system was not read (unknown; the updater rule that a brick type must occur in the package's string already keeps an Origin brick away from the Altix packages and the reverse). The Altix L2, 1.62.0, is 2,994,152 bytes with a PowerPC Linux 2.4.7 kernel built 2008-10-27 ([references/firmware-versions.md](../../../references/firmware-versions.md)).

## What the flash tools say

**Established** from the strings of the host tools in the RPM (not stripped; the usage text and diagnostics are short literals):

- `flashsc` carries no brick-type list. Its output messages ("A/B supported brick types mismatch", "SUPPORTED BRICK TYPES: %s", "%d controller%s skipped - no image available for this brick type") show that the list is the supported-brick string inside each image package. Its usage is `flashsc [-p [<maxgrp>]] [-f] [sysco options] <bin image> <target>` and `flashsc -version|-v|-vv <bin image>`, with connection options `--l2`, `--sc`, `--scdev`, `--interface`, `--ssn`, `--sysname`, `--pw`, `--serial`, `--dev` and the debug options `--irtr` and `--mtrace`. A recovery path ("RECOVERY FAILED--could not open serial connection!") writes a framing sequence and a flash header directly over a serial line.
- `flashfile` is the same host program for a plain file: it counts bricks by letter (R, C, I, X, P, PE, G, N bricks, "C/R/G brick (USB connection)", "C or I/O brick (422 connection)"), checks a relocation table in the image and refuses an image "that does not contain the correct image type for this brick".
- `flashpbay` flashes the power-bay image (`pbay-00.18.bin`, 5,888 bytes, identical to every `pbay.bin`).
- `flashioc4` is a shell script (version 0.5), "a wrapper around the x_svf utility for use in flashing the IOC4 configuration EEPROM on the IO9 card". It takes an SVF file and `<rack>.<slot>`, forms the brick id as `64 * rack + slot`, requires an L2 (it rejects a serial connection), reads the vector's version from an `IOC4 Bitstream Rev` or `IOC4 PROM, Rev.` header, and drives `x_svf` and `l2cmd`.
- `flashsvf` builds the JTAG scan chain from the controllers' own description of the system. Its brick filter prints "Invalid or unsupported brick type detected: '%c' (0x%02X)". Chain device names it carries (established as strings; which brick each belongs to is only partly stated by the tool): `ip57_001S2` (an IP57 node board, with a SHUB 2 chain entry `S2`), `tio_io10`, `dorado_pcibridge`, `dorado_io9`, `dorado_io10`, `ip41_001N0S%c` and `ip41_001N1S%c`, `ip53_001_br`, `twrtr_001`, `is_001`, `is_002`, `int2u_001`, `int_ws_001` to `int_ws_004`, `sgc_000` to `sgc_007`, `dm7_001` and `dm7_002`, `io9_01`, `io9_03`, `io9_04`, `io10_001`, `pcixtest_001`, `sio_001`, `tg3_001`, `altera_001`, `ssp_001`, `ssp_002`, `sa_001`, `sa_002`, `cpld_001` ("Adding GEMINI to chain"), and board descriptions `Opus w/PCI` (part `030_1808`) and `Opus w/PCIX` (`030_2031`). Brick names in its messages include `DAYTONA` and `ABACUS`. It states that automatic scan configuration needs an image "1.19.10 or greater".
