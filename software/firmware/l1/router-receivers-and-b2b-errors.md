# L1 1.44.0 C-brick: the router, its "receivers", and `B2B: no receiver for response`

Reads the packet router and its B2B (brick-to-brick) error lines in package 0 (`Base 1MB`, C-brick) of the IRIX 6.5.30 `l1.bin`, for a launch whose board log reads `nvram log reset`, `L1 booting 1.44.0`, `** fixing BSN mismatch`, `B2B: no receiver for response, port 00000001, dest 0000000e`, `USB0: waiting on open`, `power up (COMMAND)` and where no reply reaches the PROM. Grades: E established (routine read), I inferred, U unknown. Addresses are package 0, first copy. Peer-slot numbering is in [peer-link-slots-and-cables.md](peer-link-slots-and-cables.md); the frame layer in [node-link-receive-path.md](node-link-receive-path.md).

## 1. Where the line is printed and what a "receiver" is (E)

- **Print site.** `0xffe2eb38`, in the response router `0xffe2eadc(port, packet)`. The format is at `0xffe2f887`; the arguments are the router port (`%08x`) and the packet's destination word (packet `+0x18`). A second text, `B2B: queueing error for response`, is the same routine's other failure (the slot is open but its queue refused the packet). The request twin is `0xffe2ea3c`, and the default-route function `0xffe2e8e4` prints `B2B: no receiver (REQ)` and `(RSP)` when it can pick no port.
- **A receiver is an open slot, not a registered destination.** The test is the slot-open predicate `0xffe2e88c(port)`: it reads the pointer at `0x30004cd0 + 4 * port`, and is true only when that slot's structure has both its read handle (`+0xc`) and its write handle (`+0x10`) non-zero. Those handles are the slot's UART read and write opens ([rs422-router.md](rs422-router.md): each slot's read task and write task retry the open of their configured UART forever, waiting 100 and 200 ticks after more than five failures). The configured UART device per slot is the table at `0x30004c9c` (`-1` means none; predicate `0xffe2e8c4`). So there is no per-destination receiver table, and nothing is registered at link-up, on a hello or at node release: a slot becomes a receiver when its UART opens.
- **One router callback for everything else.** The router `0xffe2eb60(packet)` is registered once, at B2B initialisation (`0xffe2e2e4`, error text `B2B: could not register for requests/responses`), as the delivery routine for requests and responses that the packet library does not deliver locally. Events are registered separately (`could not register for events`). Per-slot queues `B2BQ_xxx`, read tasks `B2BR_xxx` and write tasks `B2BW_xxx` carry the three-letter slot name.
- **How a port is chosen** (`0xffe2eb60`). The destination word `+0x18`: if bit 31 is set the port is 14 or 15 (special); otherwise bits 31:28 index a 16-way table. Nibbles 1 and 2 are for this brick's own address (rack in bits 27:18 and bay in 17:12 are compared with the L1's own at `0x30000a24 + 8/+0xc`), nibbles 3, 4 and 6 resolve a port from the **source** word (`+0x1c`): the tag in its bits 11:5 goes through `0xffe34970` to a link index and the port is that index plus 1 when the task is 5, else plus 9 (`0xffe2ecaa` to `0xffe2ece4`); nibble 5 forces port 1; **nibble 0 and 7 to 13 do not resolve and fall to the default route** `0xffe2e8e4`. The packet type byte at `+0x16` selects request (0) or response (non-zero) routing.
- **The default route `0xffe2e8e4`.** It reads module record 0's word at `+0x58` (the learned route to the upstream L2 or peer; `-1` means "not yet known"): `-1` queues the packet on `0x30004a18` to wait; a non-zero value is returned as the port; zero falls to a scan of module records 5 and 10 for a valid peer of type `0x44`, then to the open-slot predicate for slots 1 and 2. A response that reaches the end with no open slot logs `B2B: no receiver (RSP)` and returns -1608. The port in the line seen is therefore either record 0's `+0x58` or the result of the record 5 scan; which one is U (below).

## 2. Ports, headers and the meaning of "port 1" and "dest 0xe"

- **UART channels on the C-brick (E).** The external quad UART (chip select 4) gives channel 0 = software port 3 (peer link, router slot 1, label `CTC port`), channel 1 = software port 4 (slot 9, `CTI port`), channel 2 = software port 5 (console, 38,400 baud) and channel 3 = software port 6 (the node link, 57,600 baud, client class 3) ([quad-uart-and-serial-links.md](quad-uart-and-serial-links.md), [peer-link-slots-and-cables.md](peer-link-slots-and-cables.md)). The L2 is reached over the USB device side (`USB0: waiting on open` is that link waiting for a host, [usb-overview.md](usb-overview.md)); the on-chip UART 1 is the power-bay link. **Router port 1 is slot 1, the `CTC` peer link on UART channel 0, not the node link.** Port numbers 1 and 9 are the same numbers the `+1`/`+9` rule above produces, which is why a source tag that maps to link index 0 for a task-5 reply also gives port 1.
- **The L1 link header byte** is class in bits 7:5 and index in bits 4:0; the address word follows ([node-link-sn1-vs-sn2.md](node-link-sn1-vs-sn2.md) section 3). When a request frame is parsed (`0xffe35634`), the **source word** the L1 attaches is built from a base word at `0x30004f48` with the 7-bit tag from `0xffe349a8(link, index)` placed in bits 11:5 (`0xffe35700` to `0xffe35724`), and the low five bits of the base word kept. A response is created with its destination equal to the request's source word (`0xffe32c08` to `0xffe32c1a` builds it from `$1c(request)`), and is then handed to `0xffe2eadc` with a port argument. E for the construction. That the port argument is "the port the request arrived on" is I (it is the caller's argument; the caller was not traced).
- **`dest 0000000e`.** Bits 31:28 zero, rack and bay fields zero, task (low five bits) 14. Nibble 0 is not resolved by the table, so such a response always goes to the default route, whatever link it came from. E for the decoding. What task 14 means is the event and management task (the task-14 event handler of [router-role-setting.md](../../../platforms/bricks/router-role-setting.md)); a destination of "task 14, rack 0, bay 0" with no tag is a packet addressed to the L1's own event task by an unconfigured address, or a source word whose tag and base word are both unset (I).

## 3. Ordering: what produces it

The line is printed after `fixing BSN mismatch` and before `power up`, so it is raised by a packet handled while the L1 boots, before any node traffic was needed. The sources of packets in that window that the firmware originates are the peer-link read and write tasks (their module-record handshake over slots 1 and 9, [rs422-router.md](rs422-router.md)) and the USB/L2 attach. Nothing in the boot task sends a request to the node. Which request is U: the log line carries only the port and destination. Two readings fit the retained evidence and are not separated by it: (a) a response to a peer-link request that arrived on slot 1 (for example the other board's L1 over the cross-connected `CTC` channel, if the board model connects the two L1s' channel 0), refused because slot 1's write handle is not open; (b) a response to a PROM request whose source word came out with an unset base (rack 0, bay 0, tag 0), which the library does not treat as local and hands to the router. Under (b) the router would send the node's replies to port 1 instead of the node link, which is exactly "no reply reaches the PROM". The retained sources cannot tell the two apart (U); the capture list below does.

What must happen before the L1 can answer the node: the L1 reads the PROM's frames as soon as the node-link UART is open and the PPP engine is set up (boot, `0xffe346ce`); it does not need `power up`, the scan, the release, the USB open or a hello. E (no such dependency exists in the receive path read; the node cannot run before the release, so this only matters for a model that sends earlier).

## 4. Is the B2B line benign?

Not as a probe of absent ports: it is a specific response that the router could not deliver, which happens when a response is routed to a port whose UART is not open. If the L1 had answered the PROM's `0x0003` or `0x0001` the reply would have been delivered through the library to the node-link writer without a B2B message, so the line is *consistent with* the node's replies being the packets that fail (reading (b)) but not proof of it (I). A successful answer prints nothing by default. **Verbose logging exists:** `l1dbg promreq on` (key 9, stores `0x30000b08`) makes the general request handler (`0xffe11eda`) print `L1REQ: <source word> - <request code>` for every request it handles (E), which shows at once whether the PROM's `0x0001` and `0x0003` are reaching the handler and with what source word. `l1dbg syscom <n>` (key 1, words `0x30000aac` and `0x30000ab0`) and `l1dbg irtr <n>` (key 2, word `0x30000afc`) raise the syscom (link and request) and irouter (router) debug levels; `l1dbg port on` (key 4, `0x30000b00`) prints the port state changes ([power-up-reads-restart-and-polling.md](power-up-reads-restart-and-polling.md) section 5); `l1dbg pppdump on` (key 8, `0x30000b10`) dumps the bytes of a bad PPP frame. The `log` command prints the ring; the hidden `b2b` command prints the brick-to-brick tag. E for the keys and words (jump table `0xffe17e62`).

## 5. `** fixing BSN mismatch`

Benign. It is the start-up sanitiser copying the board EEPROM's brick serial into setting 15 because the stored one (blank in a fresh window) differs from it ([serial-number-requests.md](serial-number-requests.md)). It runs once per boot, changes only setting 15 and does not touch the router. E.

## 6. After `power up`: unsolicited traffic on the node link

None found. The node-link writer sends replies and console characters. The L1's own unsolicited traffic goes to peers and the L2: the power-state notice at record-0 power-state changes ([power-reset-cbrick.md](power-reset-cbrick.md) section 7) and events. Nothing is sent to the node that the PROM must answer. I (absence in the routines read).

## What to capture to settle it

On the running board 0 through the gdb stub (addresses package 0, first copy):

1. **Break at `0xffe2eb38`.** On a hit, `d7` is the port and `a5` points at the packet: read the type byte at `a5+0x16`, the destination word at `a5+0x18` and the source word at `a5+0x1c`, plus the three words before them. A source word with a non-zero tag in bits 11:5 and a node-link index shows reading (b); a base word of 0 shows the unset address.
2. **Break at `0xffe2e8e4`** and read the return value (`d0` at `0xffe2ea32`) with module record 0's `+0x58`: the pointer is the word at `0x30000a78` and the record is its first `0x70` bytes; also records 5 and 10 (`+0` valid, `+0x10` type) at `+0x230` and `+0x460`.
3. **Dump** `0x30004c9c` (13 words: configured UART per slot, `-1` none) and `0x30004cd0` (13 pointers to the slot structures, each with the read handle at `+0xc` and the write handle at `+0x10`), and the word at `0x30004f48` (the source base) and `0x30004f50`.
4. **Turn on `l1dbg promreq on`** from the board console before the PROM starts (or set `0x30000b08` non-zero with the stub) to see each handled request as `L1REQ:`.
5. **Trace writes** to the quad UART's channel 0 and channel 3 transmit registers (chip select 4 window, `0x50000000`; register layout in [quad-uart-and-serial-links.md](quad-uart-and-serial-links.md)): a node reply appears as bytes on channel 3 starting `7e`; a response routed to port 1 would appear on channel 0 or nowhere.

## What the retained sources cannot settle

Which request the B2B response answers, whether the port came from module record 0 or from the peer scan, and whether the board model connects the two L1s' peer channel. Those need captures 1 to 3.
