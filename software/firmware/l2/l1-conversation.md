# The L2's side of the conversation with an L1

What the L2 daemon says to an L1 and what it does with the answers, in the order it happens: attach, the first and recurring configuration request, how the reply becomes a route, how a text command that arrives from a host (`p <id> pwr d`) turns into power commands for the bricks of one partition, and how a partition-record request addressed to controller type 1, task `0xa`, is answered. It joins the single-topic notes ([config-request-reply.md](config-request-reply.md), [power-queue.md](power-queue.md), [partition-task.md](partition-task.md), [partition-record.md](partition-record.md), [router-packet.md](router-packet.md)) into one sequence, re-checks them against the listings, and corrects three readings in them (section 9). A later independent review (section 11) corrected further points in this note.

Words used throughout. A **router word** is a 32-bit address: with bit 31 clear its top nibble is the form (0 for an L1, 1 for an L2, 2 for an L3) and the low five bits are the task; with bit 31 set the top two bits `10` give form 14 (task in bits 29 to 24) and anything else form 15. For form 0 the **brick address** is `rack << 18 | slot << 12` (rack ten bits, slot six bits), the **module field** is bits 12 to 27, and the value `0xffff` there means "the directly attached controller". A **brick record** is one 0x30-byte entry of a port's table in the L2's configuration object (layout in section 3).

## 1. The sequence in one table

| Step | What the L2 does | Grade | Section |
|---|---|---|---|
| 1 | A USB L1 device is opened; the L2 records a port in state 1 ("attached, not configured") with no brick records and arms a one-shot timer for 750,000 microseconds | established | 2 |
| 2 | The timer sends the L1 a configuration request: class 0, code 0, destination `0x0ffff00e`, three descriptors (integer 6, the system serial string or integer 0, integer 0) | established | 2 |
| 3 | The reply (destination task 4 of the L2, source form 0, status 0, selector 7) is parsed into brick records; the port goes to state 2 | established | 3 |
| 4 | The request repeats every 2 s until a reply has been parsed, then every NVRAM key 15 seconds (5 by default); a reply that changes the table forces one extra request after 1 s and a configuration check | established | 5 |
| 5 | Every packet for a destination `rack.slot` is sent to the port whose table holds a valid record with that rack and slot | established | 4 |
| 6 | A text command `p <id> pwr d` arriving for task 3 is parsed by the L2's own command interpreter; the partition `<id>` selects the non-router bricks whose table record carries that partition number; each gets the text `power down` as a task-3 request | established | 6 |
| 7 | A request for task `0xa` is handed to the local `l2part` client, which answers code 1 with the partition number of a brick | established | 7 |

## 2. Attach and the first request

**Port record.** The L2's configuration object is at `0x10044640` in `bin/l2`. It holds 40 port records of 0x1c bytes from offset `0x15c`; a record's first word is its state (0 free, 1 attached, 2 configured), the second the connection type (2 for USB), and offsets `+0x14` and `+0x18` the brick count and a pointer to the 0x30-byte brick records. Established from `L2CfgMAddPort` (libmain `0x13a8c`), `L2CfgMCfgPort` (`0x15a54`) and the readers in `bin/l2`; layout also in [l2/config-request-reply.md](config-request-reply.md) section 1.

**Attach.** `l1_open_usb_device` calls `L2CfgMAddPort` at `0x10004b04`. A return of -1 prints `ERROR: device is already in use.`; otherwise the same routine arms `EventAddTimeOut(0, 750000, 0x1000d9a8, slot)` at `0x10004b34` to `0x10004b54` (the 750,000 is `lis 0xb; ori 0x71b0`, name string `l1_open_usb_device`) and registers the input handler `0x100069b0` for the descriptor. Nothing is written to the device at open. Established. The port stays at state 1 and has no brick record until a reply is parsed (section 3).

**The request (callback `0x1000d9a8`, read in full).** The callback builds one packet with `IRouterMakePacket(0x10043ce8, &dest, 0, 0, 0, 2, 3, descriptors)`:

| Field | Value | Grade |
|---|---|---|
| destination word | `0x0ffff00e` (`lis 0xfff; ori 0xf00e`, `0x1000d9c8`): form 0, module field `0xffff`, task 14 | established |
| class, code | class 0 (request), code 0 (fifth and fourth arguments) | established |
| source word | the first word of the local record at `0x10043ce8` (the local L2 router address; `0x84000001` in the stock run of the earlier note) | E for where it comes from; the stock value is that note's observation |
| descriptor 0 | integer 6 (type 0) | established |
| descriptor 1 | `nvramGet(3)` as a string (type 9: string, free after copy), length `strlen + 1`, when non-empty; else integer 0 | established |
| descriptor 2 | integer 0 | established |

The sixth argument is the literal 2 in this request and in every other class-0 call read; the four answer builders (class 1: `0x1000e4e8`, `0x1001b16c`, `0x1001b878`, `0x100230b8`) instead pass the byte at the request's packet `+0x12` (wire byte 2, which is 2 in the requests read). Inside `IRouterMakePacket` (libIRouter `0x67e8`) its only use is the "local packet" test at `0x683c`, which needs it above 1 and the class to be 1, so it is not a wire field (the one other mention of a sixth-argument slot, at `0x6a48`, is another routine's own local). Established (corrected in section 9, item 4). The packet is written through `sub_10007478(fd, packet)`, which dispatches on the connection mode. Before building, the callback returns without sending and without re-arming when the slot's descriptor is -1 (`0x1000da94` to `0x1000daa4`, jump to the epilogue at `0x1000dcf8`), and it builds nothing while the word at `0x10043c00` is zero (section 5). Established.

## 3. The reply becomes a route

**Where the reply goes.** The input handler reads one packet, stores its slot number at packet `+0x0c`, and calls the router entry (section 4). A reply addressed to task 4 with class 1 reaches `sub_1000e664` (`0x1000e664` to `0x1000e9e4`), which acts only when the status byte at packet `+0x13` is 0. For a source word with form 0 it calls `L2CfgMCfgPort(cfg, slot, packet)`. When the brick table changed it cancels the slot's timer, re-arms one callback 1 s later (debug name `extra cfg_ping_l1`, same callback `0x1000d9a8`), and calls `sub_1000f93c(1)`. The first time a port reaches state 2 it also logs `INFO: USB device %s configured: %s` (string `0x100292ac`, call at `0x1000e84c`), but only when the word at `0x10043bc4` is above 1 (`0x1000e79c` to `0x1000e7a4`; that word is the USB debug level, loaded from NVRAM key 10 at start, `0x10003f38` to `0x10003f44`, and set by a command that also writes the key, `0x10011e20` to `0x10011e30`) and the port was not already in state 2 (`0x1000e7a8` to `0x1000e7c0`). The two text arguments are the port's name as it read before the configuration call (`L2CfgMDeviceName`, copied at `0x1000e754` to `0x1000e764`; for a state-1 port the text `L1 USB device <name> [<name>]`, libmain `0x11518`) and its name afterwards (state 2: `connection to <address>`, libmain `0x114a8` to `0x11504`, where the address comes from the first brick record's rack and slot through `L2CfgMAddrStr`). The rack-and-slot value computed at `0x1000e7c4` to `0x1000e7f8` is stored to a local at `0x68(r31)` that is never passed on. The first argument of the local `fprintf` wrapper is 0 on this path. Established for the call, its two conditions and the arguments; what the wrapper does with a null first argument was not read.

**What `L2CfgMCfgPort` accepts (libmain `0x15a54`).** It reads descriptor 0 and compares it with 7 and 6 only. With 7: descriptor 2 is the record count `N`, descriptor 3 the record size `S`, descriptor 4 a byte array of `N` table indices, descriptor 5 a block of `N` records of `S` bytes; each record goes through the builder `sub_156f4`. With 6: four records at fixed indices 0, 1, 5 and 6. Any other first descriptor leaves the port at state 2 with **no brick records**: before it looks at the selector the routine saves the old array pointer and count, sets the array pointer and count to 0 and the state to 2 (`0x15b00` to `0x15b30`), and for a selector that is neither 6 nor 7 it goes straight to the comparison (`0x15c24` to `0x15c2c`, `0x15db4`), which reports "changed" when the old count was nonzero and then frees the old array (`0x15e1c`). So a reply with a wrong selector empties a configured port and takes the extra-ping path below; sent to a port with no records it only moves the port to state 2. A call with no packet (`r5 == 0`) is the close path and frees the port. The builder copies at most 0x70 source bytes into a zeroed local, builds one 0x30-byte brick record, grows the port's array with `realloc`, and at the end compares the old and new arrays (record counts first, then `memcmp` over `0x30 * count` bytes, `0x15db4` to `0x15dfc`); a difference is the "table changed" result used above. Because the power, margin and partition bytes are inside the compared records, a reply in which any of them differs from the last one also counts as a change. Established.

**Brick record (0x30 bytes) and the source word each byte comes from.** Read from the stores at libmain `0x157b0` to `0x15828` (each source word is a big-endian 32-bit value of which only the low byte is kept; the stores are the same when the value exceeds 0xff and goes through `ntohl` first):

| Brick `+` | Source word `+` | Used by the daemon for | Grade |
|---|---|---|---|
| `0x00` | table index byte (descriptor 4) | index of the record in the L1's table; the route search keeps the smallest | established |
| `0x01` | `0x00` | valid flag; every search skips a record with 0 here | established |
| `0x03` | `0x08` | rack (route key; also the destination builder) | established |
| `0x04` | `0x0c` | slot, called "bay" in the L1 notes (route key; the address builders keep its low six bits, but the route compare uses the whole byte, section 4) | established |
| `0x05` | `0x10` | brick type character; selects the brick class for the sender and whether a brick counts as a router or a compute brick | established |
| `0x06` | `0x3c` | **partition number** of the brick; matched against the `p <id>` target and compared across bricks by the span check | E for the use; the L1 writer is U (U1) |
| `0x10` | `0x34` | **power state** of the brick: 0 off, nonzero on; read by `power down`, the status summary, and the skip flags of the sender | established |
| `0x11` | `0x38` | margin state (0 to 5) | established |
| `0x12` | `0x60` | a value of 0 is replaced by 2 when `+0x01` is nonzero | E (the store); role U |

The remaining bytes (`+0x02`, `+0x08`, `+0x0c` to `+0x0f`, `+0x14`, and the two 12-byte strings at `+0x18` and `+0x24`) are not read by anything in sections 4 to 7; they feed the `config` display. Established that the other routines here do not read them; the display routine itself was not read.

**What the L1 sends.** The L1 half is the earlier note's reading of Origin 300 L1 1.44.0 package 1: `config_exchange_request` (`0xffe325ec`) answers selector 6 with selector 7, count `N`, size 0x70, a byte array of indices and a data block of `N` records of 0x70 bytes, status 0, destination equal to the request's source, source `(identity << 12) | 0x0e`. Not re-read here; grade as in [l2/config-request-reply.md](config-request-reply.md) section 3 (established for package 1). Which L1 table fields hold the partition (`+0x3c`) and the power state (`+0x34`) was not found (U1).

## 4. Routing a packet by its destination

The router entry `sub_10022e50` hands class 0 and class 1 packets to `sub_10021158` (`0x10021158` to `0x10021ea4`). The destination word is packet `+0x18`; the source word packet `+0x1c`. Every branch that hands the packet on first adds one to the 15-bit count in packet `+0x04` (mask `0x7fff0000`, the reference count of [l2/router-packet.md](router-packet.md)), because each receiver frees it. Established for all rows.

| Destination | What the L2 does | Result when nothing matches |
|---|---|---|
| form 15 | looks the word up in the node list as a node id, then looks the low 24 bits up as an address key (byte-swapped unless the word at `0x10043cd8` is 1); the local node accepts class 1 only; a remote node gets the packet through its connection | `-0x260` (`NO RECEIVER`) |

| any form but 14 and 15, module field not `0xffff` | **brick route**: rack = bits 18 to 27, slot = bits 12 to 17; `L2CfgMFindBrickIP(cfg, rack, slot)` over every node, every port in state 2, every brick record with the valid byte set and whose stored rack byte and whole stored slot byte equal the 10-bit rack and 6-bit slot of the word (smallest index wins; libmain `0x160e8`, compares at `0x16218` and `0x16240`, so a rack of 256 to 1023 can never match because the stored rack is one byte); a local match is written to that port's descriptor by `sub_10007478(fd, packet)` (fd at `0x100512f0 + 0x48 * slot`); a remote match is forwarded to its node (`NR remote!` and `-0x260` if that node is gone); a local match for a packet whose destination form is 1 prints `NR R.S+IR_L2!` and fails | `-0x260`, unless the local node's word `+0x10` is 1 and `+0x14` names a default node, which then takes the packet |

| form 1, module field `0xffff` | **task dispatch** on the low five bits, table at `0x1002e4e0` | see next table |

## 5. After registration: the recurring request and what the L2 does with the answers

**The request repeats unchanged.** The callback `0x1000d9a8` rebuilds the same three-descriptor request on every firing; nothing in it depends on the previous reply. It re-arms itself at `0x1000dc5c` to `0x1000dcf8` (name `cfg_ping_l1 (%s)`) whenever the slot's descriptor is positive. The delay is the word at `0x10043d54` (`L2<->L1 freq`, NVRAM key 15, default 5; the `ping` command's sub-command "sets L2 to L1 ping frequency in seconds" is the record at `0x10040984`), **unless the port record's state word is not 2, in which case it is 2 s**. So the L2 asks every 2 s until the first reply has been parsed, then every `key 15` seconds. A table-changing reply additionally cancels the pending timer (`0x1000e880`) and fires once after 1 s (`0x1000e8a0`); the re-arm is decided when the callback fires, from the state at that moment. Established. **The stock-run timings (0.0, 2.0, 7.0, 12.0 s) do not confirm this for a reply that carries bricks.** The first parsed selector-7 reply takes the table from 0 to N records, which is a change, so a real L1 is expected to give requests at about 0, 1, 6, 11 s (the first firing re-arms at 2 s because the state is still 1; the reply cancels that timer and re-arms at 1 s; the 1 s firing sees state 2 and re-arms at 5 s). The 0, 2, 7, 12 sequence fits only a reply that moved the port to state 2 without changing the table, which is what a wrong selector does on an empty port (section 3). So the stock run was a reply of that kind, consistent with the earlier note's "guessed reply", and shows the state-dependent period but not the 1 s path. Inferred from the code; no run of a real L1 reply was made (U10).

**Gating.** The word at `0x10043c00` (initial 1) is the auto-scan flag. The two timer set-ups `sub_1000f710` (periodic `cfg_setup_config_check`, callback `0x1000f93c`) and `sub_1000f7bc` (`cfg_setup_l2ping`, callback `0x10010454`) each set it to 1 when given a nonzero period and to 0 when given zero (stores at `0x1000f784`, `0x1000f7a0`, `0x1000f830`, `0x1000f84c`); they are called at start-up and from the `config` and `ping` commands. A manual `config` scan with the flag set prints `WARNING: config auto-scan is enabled; skipping manua...` (`0x10011124` to `0x1001114c`). While the flag is zero the request callback builds and sends nothing, and still re-arms. Established.

**Nothing times a port out.** The callback never counts unanswered requests, and no routine found clears a USB port's state because replies stopped; the port leaves service only when the device is closed (`sub_10004bf8` calls `L2CfgMCfgPort(cfg, slot, 0)`, which frees the port, `0x10004d4c` to `0x10004d60`), which the repeated read and write error counters trigger ([l2/daemon.md](daemon.md)). The record of a brick therefore keeps its last reported power, margin and partition bytes until the next reply. Established for the callback and the close path; inferred for the absence of any other clearing path (the callers of `L2CfgMDeletePort` and `L2CfgMDeleteNode` in `bin/l2` are the network close and the L2-to-L2 ping, `0x10007e54`, `0x100105a4`, `0x10010628`).

**What the exchange feeds.** Every later decision in sections 6 and 7 reads brick records filled by the reply, never anything the L2 asks a second time: route keys (rack, slot), type, partition, power and margin bytes. The `power` command's own state reads are the cached `+0x10` and `+0x11` bytes ([l2/power-queue.md](power-queue.md): sub-command 3 counts them), so the L2's idea of "which bricks are on" is at most one request period old. Established for the readers; inferred for "at most one period" (it assumes each reply carries a fresh `+0x34`, U1).

**Configuration event to peers.** `sub_1000f93c` is the timer callback armed by `sub_1000f710` under the name `cfg_setup_config_check` (`0x1000f76c`); the reply handler also calls it directly with 1 when a reply changed the table. It takes two `L2CfgMQuery` strings (query 0 and query 2), compares them with the copies it kept (`strcmp` at `0x1000fa9c` and `0x1000fae4`), and builds a packet with `IRouterMakePacket(0x10043ce8, ...)` that it sends with `sub_10022e50` (failure text `ERROR: can't create packet for configuration event.`). Established for the call chain; that the packet goes to peer L2s, and the exact condition for sending, are not followed (U6).

## 6. The routed shutdown: `p <id> pwr d`

The sender of this line is not in these images. The repository's L1 notes ([l1/power-reset-cbrick.md](../l1/power-reset-cbrick.md) section 1) record that IRIX sends it as a text request to `0x1ffff003` after asking for the partition id; this is a hint, not read here. The L2's handling is read below.

**Receive (established).** `0x1ffff003` has form 1, module field `0xffff`, task 3: the task dispatch of section 4 sends a class-0 packet to `sub_1001af4c` (`0x1001af4c` to `0x1001b484`).

**Command text (established).** The routine takes the text from the **second** descriptor: it tests the type bits of the descriptor at packet `+0x2c`; type 0 means the word at `+0x30` is used, otherwise `IRArg(packet, 1)` supplies the pointer. The first descriptor is not read. The L2's own sender puts an integer 0 first and the text second, so does the user-space text client in `l1cmd`/`l2cmd` ([host-tool-options.md](../../userland/host-tool-options.md)). A request with one descriptor gives a null text, and the first instruction of the parser, `lbz` of the first text byte at `0x10010ad4`, would fault on it (inferred: from `IRArg` returning 0 for an index beyond the count). What descriptors IRIX actually sends is U2.

**Bookkeeping (established).** The routine stores the requester's source word at `0x10043d5c`, its sequence number (packet bytes `+0x14` and `+0x21`) at `0x10043d60`, packet byte `+0x12` at `0x10043d64`, and the five-bit field of byte `+0x17` at `0x10043d68`; clears the output buffers; clears the destination context with `sub_1001e458` (all racks and slots selected, no partition selected); and runs the text through `sub_10010aac`, the L2's command-line executor (`CmdProcess` over the table at `0x1003ec08`, 188 records of 0x44 bytes, with the context at `0x10043c58`). When the context is already busy (`context + 0x1c` nonzero, `0x1001afb4` to `0x1001afc4`) the routine instead runs the line with a null context and answers at once, with `ERROR: command library is busy` if that fails (inferred: read from the structure).

**Target and command parse (established).**

- `p <rng>` or `partition <rng>`: `CmdProcess` (libsys `0xb200`, the compares at `0xbf10` to `0xbfe4`) parses the range into the 64-byte **partition mask** at `target + 0x1b4` with the shared range parser `sub_ccd0` (libsys `0xccd0`: `*` or `all` fills every byte with 5, `**` with 6, a lone number sets its byte to 1, a run `a-b` with `a < b` marks 2 at `a`, 3 between and 4 at `b` (`a == b` marks 1, `a > b` is a parse error), comma-separated items accumulate; a number not below the buffer size, here 64, is a parse error, as is an empty item or a dangling `-`; libsys `0xcd98` to `0xd104`), and **clears the rack mask (0x100 bytes) and the slot mask (0x40 bytes)**. `rack`/`r` and `slot`/`s` fill the other two masks the same way and clear the partition mask. So a partition of 1 to 63 is addressable by this prefix; the console command `select partition` is a separate parser whose error text names partitions 1 through 255.
- `pwr d`: the command record `power|pwr` with sub-word `down|d` (record `0x10040cf8`, sub-command 2) calls the `power` handler `0x10013ba8`; the handler first builds the brick table (`sub_1001e554`) from the target, fails with `ERROR: no L1s found to match that destination` when it is empty, and jumps through `0x1002c350` to the power-down code at `0x10014390`.

**Brick selection, `sub_1001e554(destination, target)` (established, read in full).** Walks the node list from the local node, the 40 ports of each node (only state 2), and each port's brick records **from the last to the first**. A record is skipped when its valid byte is 0, its rack is 0 or above 0xff or its slot is 0 or above 0x3f. If the target's partition mask has any nonzero byte the **partition mode** (destination word `+0x180` = 2) applies; otherwise rack/slot mode (`+0x180` = 1). In partition mode a record is taken when mask byte 0 is 5 (`p *`: any brick, routers included), or else when its type character is not `R`, `D` or `-` (**routers are never taken by a partition number**) and the mask byte at index `record[6]` is nonzero. In rack/slot mode both mask bytes (rack index, slot index) must be nonzero. A brick address already in the list is not added twice. A record whose type is one of `C 3 5 4 A 6 9 7 8 0 Q @ O B F L M $ , } . {` is appended; every other type is inserted at the front. The list therefore holds the non-compute bricks (reverse discovery order) followed by the compute bricks (discovery order). The resulting word for each entry is `rack << 18 | slot << 12`, stored in `destination + 0x184 + 4 * i`, count at `+0x1184`.

**Power down (established; `0x10014390` to `0x100149e4`).**

1. **Span check, `sub_1001f15c`.** Only when the target has rack mask byte 0 in {5, 6} and slot mask byte 0 in {5, 6} (the default destination, or `* *`), or has no mask at all, does it build the table and compare the partition byte of every brick: a difference fails the command with `current destination spans partitions, explicit target required.` (or `default destination ...`). A `p <id>` target has empty rack and slot masks, so the check returns 0 at once.
2. **Router step, only in partition mode.** Over every present non-router brick of every node (not just the destination), count those **outside** the destination list (match on rack and slot) and, of those, the ones whose power byte `+0x10` is 0. When the two counts are equal, that is, when every non-router brick outside the partition is already off (also when there are none), the L2 queues one `power down` text request, with the wait flag set and no delay, to **each present router that is on**. Otherwise routers are left alone. The partition's own shutdown therefore takes the routers down only when it leaves nothing else running.
3. **Broadcast.** In every case a `power down` text is queued for the destination's bricks through the sender `sub_1001c90c` (mode 1 parallel, wait flag set, no delay, class mask `0xff`, broadcast flag set), which starts the queue. Classes are served in the order routers (1), I/O (2), compute (4), other (`0x80`); in partition mode the router class of the list is empty, so only step 2 reaches routers.

**What goes on the wire to each L1 (established).** One router packet per brick: destination `rack << 18 | slot << 12 | 3` (the sender clears the low five bits of the list entry and sets task 3; the router step in 2 builds the same word with `ori 3`), class 0, code 0, two descriptors: integer 0, then the string `power down` (type `0x0a`: string, free after copy; length `strlen + 1`). Source word the L2's local router address. The L2 writes the text `power down`, not `pwr d`. The L1 side is [l1/power-reset-cbrick.md](../l1/power-reset-cbrick.md): the handler acts on the L1's own brick, and a brick of type `9`, `A` or `Q` with an event subchannel registered defers its first `power down` and wants it repeated; the L2 sends each text once and has no repeat. `C`, `I` and the Origin 300 `4` do not defer.

**The wait flag and the reply timer (established for the queue, I for the requester's reply).** Every queued packet has the wait flag, so the runner records an outstanding reply for each and arms the 15 s reply timer (word `0x10043c70`, [l2/power-queue.md](power-queue.md)). The L1's text reply is class 1 on task 3, so it is routed to `sub_1001bbc4`, which hands it to the collector `sub_1001b920`; the collector appends each L1's output to a growing buffer, frees the packet, and lets the runner continue. After parsing the original line, `sub_1001af4c` tests the outstanding-reply count at `context + 0x1c`; when it is zero the answer is built at once, otherwise the answer is sent when the last reply (or the timer) completes the run. That deferral is inferred from the structure of the three routines (the final send at `0x1001b878` to `0x1001b8e8` reads the saved source word, sequence and task bits that `0x1001b200` to `0x1001b280` stored); no run was made.

**The answer to the requester (established for its shape).** `IRouterMakePacket(local router record, &saved source, saved task bits, code 0, class 1, saved byte +0x12, count, descriptors)` (the sixth argument is the byte saved at `0x10043d64`, not a literal; the call is at `0x1001b878`): destination the requester's saved source word, class 1, sequence restored into packet bytes `+0x14` and `+0x21`. Descriptor 0 is an integer. On the busy-library path (`0x1001b004`) it is -1. On the normal path `sub_1001af4c` stores -1 there when `sub_10010aac` fails (`0x1001b350`), but the completion routine `0x1001b50c` then overwrites that value with its fourth argument (`0x1001b660`), which comes from the word at offset `+0xc` of an output record, `0x1005097c` on the immediate path (`0x1001b458`) and the same offset of the record handed to the collector on the deferred path (`0x1001ba94`; records at `0x10050970` and `0x10050980`). The stores that clear the word are at `0x1001b2d4` (every new line) and the start-up `memset` (`0x1001adc8` to `0x1001addc`); the stores that set it to -1 are in the reply collector and are listed in section 12 (an earlier reading of this paragraph found only the zeros and missed them). So a command line that fails before anything is queued (`no L1s found`) answers with integer 0 and the failure in the text descriptor (established from the stores and the call at `0x1001b458`), while a line that was queued and then met a failing, missing or unsendable L1 reply answers -1 (section 12). The busy-library case is separate and still -1. The text follows as one string descriptor (type `0x0a`, length `strlen + 1`) per chunk, cut at line ends into pieces under 64 KiB (`0x1001b680` to `0x1001b83c`), so an empty output leaves a one-descriptor answer. The text of a refused command is the error line of the failing step above.

## 7. Task `0xa` and the partition-record reply

**What asks (partly E).** The boot firmware of the stock IP35 PROM sends a request to `0x1ffff00a`. Read from the payload: at file offsets `0x57450` to `0x574d0` (and the identical copy at `0x5e91c` to `0x5e9a0`) it initialises a request context with task `0xa` (`addiu a1, zero, 0xa`, `0x57450`), builds the destination `lui 0x1fff; ori 0xf00a` (`0x5748c`, `0x57494`), and calls the request builder `0x53ae0` with **request code 1** (`addiu a2, zero, 1`, `0x5747c`) and **one descriptor** (`addiu t0, zero, 1` at `0x57470`) of type 0 (`sb zero, 0xa0(sp)` at `0x57478`; the value `ld 0xf0(sp)` stored at `0xa8(sp)`). The builder writes the code halfword at block offset `0x32` (`sh s2` at `0x53be8`) and the descriptors from block offset `0x34` (loop `0x53c44` to `0x53d34`), which is wire offsets `0x12` and `0x14` of the segment layout in [l2/router-packet.md](router-packet.md) once the block's 0x20-byte lead is removed. **Dispatch (established).** The destination `0x1ffff00a` has form 1, module field `0xffff`, task 10, so the dispatch of section 4 takes the local-client row: `L2CfgMFindNode(cfg, 0, 0x1ffff00a, 0)`, and the packet is delivered to the process that registered with `sn1SCInitL2App(host, 0, 10)`, which is `l2part` (`li r5, 0xa` at `0x10000e8c`). `l2part` runs only at inittab run level 5 and starts after a 5 s sleep ([l2/partition-task.md](partition-task.md)); when no client holds task 10 the router fails with `-0x260`, and the send routine answers the requester with an error response of status byte 8 and no descriptors (section 12, a correction: this line used to say no reply reaches the sender). Established.

**Handler for code 1 (established; `l2part` `0x10001384`, read in full).** The brick is the halfword at packet `+0x2a` when the first descriptor has type 0 (the low half of the big-endian value word at `+0x28`), else `IRArg(packet, 0)`; it is sign-extended from 16 bits (`extsh` at `0x100013bc`) and passed to the wrapper at `0x10002054`, which calls `get_partid_for_brick` and **replaces a negative result with 0** (`cmpwi/bge/li` at `0x10002090` to `0x1000209c`). The reply record: result descriptor type 0 value 0 (status zero), integer descriptor type 0 with the partition number in the value word, count 2 (`stw 2, 0x58(r31)` at `0x1000142c`).

**The reply on the wire (established for fields from the builder; the source word I).** One 36-byte segment: length `0x0024`, byte 2 = 2, status 0, the request's sequence copied, first-segment flag `0x81` (one segment), class 1, destination the request's source word, source the L2's local address, descriptor count 2, code `0x0001`, result descriptor (value 0), integer descriptor (value = partition number, 0 to 63, big-endian 32-bit at wire offset `0x20`). Byte-by-byte table and the five test vectors are in [l2/partition-record.md](partition-record.md); re-checked here for the fields above.

## 9. Corrections to earlier notes

1. **Destination mode 2 is a partition destination, not a rack destination.** [l2/power-queue.md](power-queue.md) reads the word at `destination + 0x180` as 2 when "the destination names whole racks". The word is set by `sub_1001e554` (`0x1001e648` to `0x1001e664`) from the test of the 64-byte mask copied from `target + 0x1b4`, which the `p`/`partition` prefix and `select partition` fill; the rack mask is at `+0x40`/`+0x74`. The slow and fast power-up branches and the power-down router rule that test the word are therefore partition-mode branches. The router counts in power down are of **non-router bricks outside the destination**, not of routers: the loop skips types `R`, `D`, `-` (`cmpwi 0x52/0x44/0x2d` at `0x100144c4` to `0x10014528`), so the rule powers routers down only when everything else is already off.
2. **`ver check` is the L2's own command line, not a request.** The call at `0x10013d04` and the one at `0x10014f5c` pass the text `ver check` to `sub_10010aac`, the command-line executor, with the destination saved before and restored after (`memcpy` of 0x1188 bytes at `0x10013ce4` and `0x10013d14`). The command (`version|ver` records, handler `0x1001a120`) sends the text `ver` to the L1s and L2s of the destination and prints mismatches. Power up and reset run it; **power down does not** (the code at `0x10014390` starts with the span check, and the two string uses above are the only ones). [l2/power-queue.md](power-queue.md) says power down shares the precursor.
3. **Order of the brick table inside a class** (the open question in [open-questions.md](../../../questions/README.md)): answered by the walk and insertion rule in section 6: records are visited last to first, compute types are appended, every other type is inserted at the front.

## 12. What changes for 128 processors

### Answer in short

- **Router levels.** Nothing in the L2 changes. The L1 changes at the router brick: the 2 MB image can be set to one of three metarouter levels, the older images only to meta or ordinary. What a level does on the board is unknown (U16). Test, in two halves: for the L2, the search of U16 in section 10 (any use of brick record byte `+0x05` beyond the compute-class compare); for the board, in package 5 list every reader of persistent setting `0x3c` and every store that reaches `ROUTER CONTROL` bits 7 to 4 besides the reset-release write. If the release write is the only consumer, no shipped image says what a level does and only a published description of the router board's control pins can settle it; a second consumer would be read next.
- **Rack numbers.** Routing and power work for racks 1 to 255; partition tables name racks 1 to 63; the L1 stores 10 bits. A large system is limited by the partition identifier before it is limited by anything else (row 6; U15 asks whether the identifier is ever packed for a larger rack).
- **The tables.** The reply carries at most 10 records, not 15 (rows 1 and 3). With 40 ports an L2 sees at most 400 records (row 5). Whether a USB-attached L1 shows only itself and its neighbours or the whole system depends on how records above 0 are filled (U14, already open for the single-brick case). The 0x30-byte record stride is not a limit.

### 12.1 The answer to `p <id> pwr d`

One class-1 router packet to the requester's saved source word, task bits and sequence as saved at receive time (section 6), **code 0**, built at `0x1001b878` from the stack descriptors at `0x10050170` (eight bytes each: type byte, flag byte, length halfword, value or pointer word). Descriptor 0 is always an integer; descriptors 1 to n are string chunks (type `0x0a`, length `strlen + 1`), none when the output is empty, so the count is 1 plus the number of chunks. Established.

The answer is built by the completion routine only when two counters in the command queue are both zero (`sub_1001f7d0` tests the word at `+8`, `sub_1001ffa8` the word at `+0x14`; `0x1001b55c` to `0x1001b578`); otherwise the routine only appends its text argument to the output buffer and returns. The word at `+8` belongs to the list of nodes still waiting to be sent (the list `sub_1001f80c` empties), and `+0x14` is the count of sent packets whose entries the collector `sub_1001feb8` has not yet taken off; the matcher decrements a third counter (`+0x1c`) on each match and returns it, and the reply handler runs the collector when that reaches 0 (`0x1001bbf8` to `0x1001bc28`). So the answer goes out once, after the last L1 reply or the timeout. Established for the guard and the call order; the names of the counters are inferred from those uses.

### 12.2 When a request cannot be delivered: the error response

`sub_10022e50` is the single send entry (callers include the reader `0x10006d8c`, the answer builders and the queue runner). It classifies the packet's class byte; a class outside 0 to 2 fails with `-0x259`; class 2 goes to one router, 0 and 1 to the other (`0x10021158`). On a nonzero result it prints `NO RECEIVER` when the result is `-0x260`, and **then, if the packet was a class-0 request, builds an answer**: `IRouterMakePacket` with destination the request's source word (`+0x1c`), the request's task bits, the request's code halfword (`+0x22`), class 1, the request's byte `+0x12`, zero descriptors, and sends it back through the router (`0x100230b8` to `0x10023164`). The status byte of that answer (wire byte 3, packet `+0x13`) is `(-result) mod 100`: `-0x260` gives **8**, `-0x259` gives 1, `-0x25c` gives 4; the sequence bytes (`+0x14`, `+0x21`) are copied. A packet of class 1 or 2 that fails is freed with no answer (`0x10023040`). Established, whole routine read.

**Consequence for task 10.** A request to `0x1ffff00a` before `l2part` has registered (the first 5 s, and always at run levels other than 5) is answered by the L2 itself with a 20-byte answer: length `0x14`, status byte 8, class 1, code copied, no descriptors. The earlier text said no reply reaches the sender; that was wrong. What the boot firmware does with status 8 is its own sheet's question. The same holds for a text request to task 3 that cannot be routed: the requester gets a status-8 answer, not silence.

### 13.2 Who writes setting 14, and what a change does

- **The apply routine `0xffe332c8` (established).** If the new value differs from record 0's `+0x3c`, it stores it there, calls `0xffe30acc`, publishes a partition notice (kind 6: rack, bay, and the record's `+0x3c`, sender `0xffe33060`) and, only when this brick's type is one of `C 3 5 4 A 6 9 7 8 0 Q @ O B F H L`, queues four further configuration sends of kinds 1, 3, 14 and 15 through `0xffe31b10` (what they carry was not read; I: they refresh the peers' and the L2's view). ### 13.3 The database-enable flag (setting 18)

Setting 18 (`0x12`, byte `+0x14` bits 3:2) is the "partition database" flag the console command `partdb` toggles: enable writes 1, disable writes 0 (handler `0xffe19588`, sub-commands 1 and 2, stores at `0xffe195da`). Its two status texts say a brick with it set "gets its partition from the OS via the L2" and with it clear "from L1 NVRAM". The request pair `0x000b` (read) and `0x1008` (write) are the same setting; this settles the "meaning of the field unknown" entry for `0x000b` in [l1/request-codes.tsv](../l1/request-codes.tsv). Established for the field and its three readers (`0xffe128de`, `0xffe149e4`, `0xffe195ec`, found by scanning for every getter call with key 18). Nothing in the L1 reads it to decide whether to keep, ignore or overwrite setting 14: `brick partition` only prints a warning when it is set and still writes, and `0x1006` ignores it. So the flag is advice to the boot firmware, not a lock (established for the L1's side; I that the boot firmware reads `0x000b` first and takes the L2 path when it is set, which fits the task-10 fetch in section 7 followed by a `0x1006` set).

Consequence for two partitions (inferred): with the flag clear every brick must have its own setting 14 pre-loaded and nothing on the L2 is consulted; with it set the L2 database must list each compute brick (or its rack) in the layout, because an unlisted brick gets partition 0 (section 7), which the `p` parser then cannot address (it counts partitions from 1) and which any other unlisted or fresh brick shares.

### 13.4 Console expectations

**What the L1 holds.** A console destination word in RAM (block `0x30005140`, word `+0x9f4`, i.e. `0x30005b34`), laid out like a router word for form 0: rack in bits 27 to 18, bay in 17 to 12, a 7-bit subchannel in 11 to 5, task 5 in the low bits (built at `0xffe368a0` to `0xffe368cc`; E). It names where the processor console of this L1 is relayed. Subchannels 0 to 3 are CPUs a to d and 4 is "console" (`select subchannel` sub-commands at `0xffe19a0c` push 4 for the word `console` and the letter minus `a` for a to d; E).

Rules the L1 applies to that destination, all read in the listing:

1. **Rack or bay 0 never volunteers (established).** The volunteer routine `0xffe36948` returns 0 without touching the destination when the rack or the bay passed in is 0 (`0xffe36960` to `0xffe36968`). A fresh L1 reports rack 0 and bay 0 ([l2/config-request-reply.md](config-request-reply.md)), so a brick not yet given a rack and bay cannot become a console owner. The request `0x1003` (volunteer) and the `select` sub-command for a named rack and slot both end here, and only the second is limited to type `C` (`0xffe199d2`).
2. **Retargeting by a peer or by the `0x1002` request is limited to one partition (established).** Three routines change the destination. `0xffe3681c` (request `0x1002`, console subchannel) rebuilds the word from this brick's own rack and bay and the new subchannel, and only when the module record of the current console owner exists and has the same `+0x3c` as this brick's record 0 (`0xffe36880` to `0xffe36898`). The receivers of event codes 1 and 2 (`0xffe3360c`, `0xffe334a0`) move the destination to the announcing brick only when the announcer's record and the current owner's record have equal `+0x3c` (`0xffe336a8` to `0xffe336ac`, `0xffe33586`). The volunteer routine of rule 1 has no such test. So a notice from a partition-1 brick does not take the console away from a partition-2 owner; a local `0x1003` or a local rack-and-slot select does.
3. **Two partitions with equal numbers share a console route (inferred).** The test compares only the numbers. Bricks left at partition 0 (the unpartitioned default) all match each other.

The text console of the L1 itself (the ctrl-D and ctrl-T states in [l1-console-behaviour.md](../l1/console-behaviour.md)) is per brick. The scan for direct reads of setting 14 (constant-key getter calls only) finds six sites, none in the console state routines; those routines were not checked for a read of record `+0x3c` (U14).

**What the L2 expects.** The L2 chooses one console per partition from the brick records its L1s sent (`L2CfgMGetConsole`, libmain `0x180e4`, read in full; result cached per partition in a 256-entry table behind the configuration object at `+0x5c4`, and only a nonzero cached value is reused):

- It walks every node, every port in state 2 and every brick record with the valid byte set, skipping records whose rack or slot byte is 0 (`0x18384` to `0x18398`). Only compute types count: `C 3 5 4 A 6 9 7 8 0 Q @ O B F L M $ , } . {` (compare chain `0x1839c` to `0x1844c`; note `H`, which the L1 lists, is not in it). E.
- The partition of the brick is the record byte `+0x06`, which is the L1's `+0x3c` (section 3). With the argument -1 every partition is filled; with a number only that partition's bricks are considered. E.
- Per partition it keeps two candidates, a preferred one and a fallback, each as a pair of minima (rack, slot) started at all-ones, and replaces a candidate only when the new brick's rack is at most the stored rack and its slot is at most the stored slot (`cmplw ... bgt` pairs at `0x18484` to `0x184a4`, `0x1864c` to `0x18670`). A brick with a lower rack but a higher slot than the stored pair is therefore rejected, which is not a lexicographic minimum. E for the comparisons; I for which arrays are which, because the arrays are reached through relocations that are not in the loaded file.
- The preferred candidate also needs a helper (`0x18b00`) to return 4. The helper reduces the brick record's word at `+0x08` (the L1's module `+0x14`, its subchannel word) modulo 24 for type `6`, 20 for type `@` and 32 for every other type. The value 4 is the console subchannel above, so I read the preferred candidate as a brick whose subchannel word already selects "console". I (the arithmetic is E; the reading is the L1's subchannel numbering, section 13.4 first paragraph).
- The stored console for a partition is the router word rack, slot, subchannel (low 7 bits of the same `+0x08` word) with task 5, in the same layout as the L1's own destination (`0x184e8` to `0x18500`, `0x18544`); racks of 512 and above take the other address form (the test of the top bit at `0x18574`). I for the last clause.
- Operator commands read it: `p <n>` / `partition` sets the partition and system console for console access, `select` forms set rack, slot and subchannel, and the texts report "no system console for partition %d defined" when the table entry is 0 and that partition numbers run from 1 up to a limit (strings in `bin/l2`; limit I from U7). `l2term -syscon <partition>` redirects to the L2 that holds the console and warns when "current configuration shows no partition %d console" (`bin/l2term`). A line in `libmain` warns that accessing a partition of a system from an L2 other than the suggested access point is not advised. The condition for that warning, and the string "default system console override" in `bin/l2` (no reference to it was found by a search for the address pair), are U13.
- If the L1 of the chosen brick is found in console mode when the L2 wants its own L1 prompt, the L2 sends it back to L1 mode first (string "L1 appears to be in console mode, switching it to L1 mode"); the code was not read (U13).

**Per-partition console expectations in one line (inferred).** For each partition number there must be at least one compute brick with nonzero rack and slot whose L1 has reported it; its lowest-rack, lowest-slot candidate is the console, and the L1s of that partition agree on it only through the partition-equal test above.
