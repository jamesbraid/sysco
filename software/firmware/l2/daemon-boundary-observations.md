# The L2 daemon at the L1 boundary: what a scripted peer saw, and what the image says about each point

Written 2026-11-13. A user-mode run of the daemon with a scripted L1 peer produced logs of the packets the daemon exchanged with that peer and of the daemon's own output. Per the rule in [../../AGENTS.md](../../AGENTS.md) those logs are a **hint**, not a finding: nothing here is called established because a log showed it. Every point below is settled from the shipped image, and each row says whether the logs agree. The run used L2 1.44.0 (`l2.bin` of IRIX 6.5.30, sha256 `6bcfda07a24cb4d56850922dab17a98223abcd14221d307e3a8c3778434e8761`; `bin/l2` sha256 `9923b1ee573c2815...`; `bin/l2part` `7fb4ccec5bf686f6...`), whose banner prints the daemon's own version as 1.43.4; the carve and the listings are those of [image-layout.md](image-layout.md) and `retools/tools/sysco/l2_list.py`, and the recipe for running the daemon is [user-mode.md](user-mode.md). Addresses are virtual addresses in the named file: `bin/l2` and `bin/l2part` load at `0x10000000`, libraries at 0 (`lib/libsys`, `lib/libmain`, `lib/libpart`, `lib/libIRouter`). Only 1.44.0 was read; the other three held sets were not compared.

Grades follow [../../AGENTS.md](../../AGENTS.md): **established** (the whole routine or table was read and the claim follows), **inferred** (reasoning stated), **unknown**. Each carried claim is marked *re-read: confirmed*, *re-read: corrected* or *not re-read*.

**Probe labels.** The observation set numbers its own scripted variants P0 to P12. They are not the probes P1 to P14 of [l1-conversation.md](l1-conversation.md) section 12.4, which this note answers by content. The set's P0, P3, P5, P6, P7 and P8 are one-descriptor text packets (all crash the daemon, section 5); P1, P2, P4 and P9 were queued behind the first crash and never reached it; P10 is a task-10 fetch; P11 and P12 are the two-descriptor text packets `p 1 pwr d` and `p 0 pwr d`. The two-partition Origin 3400 layout could not be run, so every run had one partition.

## 1. U10 and U11

### U10: the timing with a real first reply

The scripted peer answered the first configuration packet with a captured 181-byte reply (selector 7, one brick record, so the brick table goes from 0 to 1 record). The daemon's packets then arrived at 0.751, 1.752, 6.752 and 11.752 s, and then every 5.00 s (hub clock; three other runs show the same pattern with up to 70 ms of jitter on a loaded host).

Image (re-read: confirmed, `bin/l2`): the first packet comes from the 750,000 microsecond timer armed at attach (`0x10004b34` to `0x10004b54`, carried, not re-read this time). The callback re-arms itself at `0x1000dc5c` to `0x1000dcf8` with the delay read from the word at `0x10043d54` (NVRAM key 15, default 5), **replaced by 2 s when the port's state word is not 2** (`cmpwi r0,2 / li r0,2` at `0x1000dc80` to `0x1000dc8c`). The reply handler, on a table-changing reply, calls `EventRemoveTimeOut` on the pending timer (`0x1000e880`) and `EventAddTimeOut(1, 0, 0x1000d9a8, slot, "extra cfg_ping_l1")` (`0x1000e884` to `0x1000e8a0`), then runs the configuration check `sub_1000f93c(1)`. So the first firing (state 1, would re-arm at 2 s) is superseded by the 1 s extra firing, which sees state 2 and re-arms at 5 s: 0.75, 1.75, 6.75, 11.75. The run reproduces this to the millisecond. Established. This confirms the prediction in [l1-conversation.md](l1-conversation.md) section 5 and the reading that the stock-run timings (0, 2, 7, 12 s) came from a reply that reached state 2 without changing the table.

What the run does not settle: which selector a real L1 puts first. The replayed reply was captured from a model of the L1, not from L1 firmware, so the selector 7 in it is the L1 notes' reading, not an independent observation (inferred).

### U11: descriptor 0 of the answer after a failure

Both values occur, by where the failure happens (`sub_1001af4c`, `0x1001af4c`, re-read; collector callback `0x1001bce8`, re-read). The runs saw two cases:

- `p 1 pwr d` with no brick of partition 1: status byte 0, descriptor 0 integer **0**, one string descriptor `ERROR: no L1s found to match that destination`, nothing sent to any L1, answer 8 ms after the packet. Image: `0x1001b2d4` stores 0 into the output record's word at `+0xc` before every line (re-read), the handler `0x1001a670` writes the text at `0x1001a8b0` to `0x1001a8c4` and returns -1, and the completion routine takes the zero from the record, not the return value (carried from [l1-conversation.md](l1-conversation.md) section 6, the completion routine not re-read).
- `p 0 pwr d` with L1s that never answer: after 15.01 s one answer, descriptor 0 **-1** (`0xffffffff`), one string descriptor holding `ERROR: no response from ...` per brick. Image: the callback's null-packet arm stores -1 at `0x1001bd40` (re-read), the transport-error arm at `0x1001be6c` (re-read), the failing-reply arm at `0x1001c074` (carried). The 15 s is the word at `0x10043c70` (carried).

So the earlier statement in [l1-conversation.md](l1-conversation.md) section 12.1 holds: 0 for a line that fails before it is sent, -1 after. Established; the logs agree for the two cases they covered and say nothing about the nonzero-first-descriptor case.

One text detail the logs disagree with the earlier note on: the answer for a silent L1 prints `ERROR: no response from 001` once per brick, and the four bricks of that run (bays 4, 7, 10 and 14 of rack 1) all print the same `001`. The earlier note read the printed word as the destination of the unanswered packet (inferred). The formatter `L2CfgMAddrStr` (libmain `0x17b68`), given a form-0 brick destination, prints rack, type letter and slot (`%03d%c%02d`, `0x17ce4` to `0x17d10`), which would give `001c04` and so on. So the word the callback formats is not the brick's own destination; what it is was not traced (callback `0x1001bce8` formats `*(r5)`, the value `sub_1001feb8` leaves in the collector's local at `0x1001b960` to `0x1001b97c`). Unknown, listed below.

## 3. The partition fetch (task 10, code 1)

Each flagged L1 sent one 28-byte class-0 packet to `0x1ffff00a` with source `0x44215` or `0x47215` (rack 1, bay 4 or 7, tag `0x10`, task `0x15`: consistent with the source-word rule of [the L1 chunked-frame note](../l1/chunked-request-frames.md)), code 1, one integer descriptor equal to the bay. It got a 36-byte answer: wire byte 2 equal 2, status 0, class 1, destination the sender's source word, source `0x8a000001`, count 2, code 1, result descriptor 0, partition descriptor 0, both descriptors' segment byte 0 (the question left open in [partition-record.md](partition-record.md): the segment-number byte of an integer descriptor is 0 in this run). Hint level; the image reading follows.

**What the handler does (re-read in full, `bin/l2part` `0x10001384` to `0x10001430` and the wrapper `0x10002054` to `0x100020c0`: confirmed).** With the type bits of the first descriptor's byte at packet `+0x24` equal to 0 it takes the halfword at `+0x2a` (the low half of the big-endian value word), else `IRArg(packet, 0)`; `extsh` sign-extends it; the wrapper calls `get_partid_for_brick(libpart 0x546c)` and replaces a negative result by 0; the answer is count 2, result 0, the partition in descriptor 1. `l2part` sets the daemon flag `isDaemon` to 1 at its start (`0x10000db8`), so libpart's loader writes the selected mode into the static `workingmode` that `get_partid_for_brick` reads (re-read: `unpack_mode_db` stores to `workingmode` only on the daemon branch, `0x4914` and `0x4db0`).

**What 0 means.** `partid_for_brick` (libpart `0x5374` to `0x5468`, re-read in full: confirmed) returns, in order: 0 when the mode's byte at `+0x20` is zero (`0x5394` to `0x53a0`); otherwise the brick masked with `0x0fc0` when the flag at `+0x18` is set (`0x53ac` to `0x53c4`), else unmasked; then the signed partition byte of the first table entry (4 bytes each from `+0x30`, halfword id at `+0`, byte at `+2`) whose id equals the brick (compare after `extsh` on both sides); -1 if none matches (`0x5454`). The wrapper turns -1 into 0. Four situations therefore give 0:

| Situation | Path | Grade |
|---|---|---|
| no database loaded, or a database with no mode: `workingmode` is in `.bss` (libpart section 26, `NOBITS`, so zero), its byte at `+0x20` is zero | first branch | established |
| the selected mode's layout is unpartitioned (byte at `+0x20` zero) | first branch | established ([libpart.md](libpart.md) reads the byte as "has partitions", inferred there) |
| partitioned layout, the brick is not listed | -1 clamped | established |
| the brick is listed with partition number 0 | the partition byte | established |

An empty database is the case of the run: in a fresh flash `l2part` builds the default database (`create_default_db`: no modes), so `validmodes` is 0 and the loop that fills `workingmode` never runs (libpart `0x48ec` to `0x4900`, `0x4d88` to `0x4d9c`). The reply is 0 for every brick, and the L2 offers no way to tell "unassigned" from "assigned to 0". The boot firmware's test for -1 can never fire (as in [partition-record.md](partition-record.md)).

**Populated database, the four lookups** (re-read against the bytes of `partid_for_brick`; the older table in [partition-record.md](partition-record.md) is confirmed):

| Entry in the layout | Lookup of identifier `b` | Result |
|---|---|---|
| a listed brick, layout flag clear | exact halfword compare of `b` with the entry's id | the entry's partition byte, signed (128 and up reads negative and clamps to 0) |
| a rack-wide layout (flag set) | `b & 0x0fc0` against the entry id **verbatim**: the entries must hold rack-only ids | the partition byte of the entry for that rack |
| an unlisted brick | no match | -1, answered as 0 |
| a layout whose byte at `+0x20` is zero | returns before any compare | 0 |

**Bay or identifier.** The brick identifier is 16 bits: type index in bits 15 to 12, rack field in 11 to 6, slot in 5 to 0 ([libpart.md](libpart.md)). Re-read: `format_brick_id` (libpart `0x2cd0`) prints the type from `crikxdpn%9012345` (`0x15c90`, index 0 is `c`), the rack field through `format_rack_id` (`0x3390`, re-read in full) and the slot as two digits. **A rack field of 0 prints as rack `001`**: the rack label's digits are (bit 5 of the field, then 2 or 3 bits, then 1 plus the low bits), so field 0 is `001`, field 7 is `008`, field 8 is `011`. The identifier `0x0004` is therefore a legal value, not "rack 0, slot 4": it is the brick `001c04` (type index 0, rack label 001, slot 4), and `0x0007` is `001c07`. A bare 4 can match a populated entry: exactly when the database lists the C-type brick in slot 4 of rack 001; in a rack-wide layout the masked value 0 matches the entry for rack field 0, which is rack 001. The run's arguments (4 on bay 4, 7 on bay 7, both rack 1, both most likely C-bricks) are exactly those identifiers, and they are also the bare bays, so the run cannot show which the sender means. What would separate them: a flagged L1 of another type or rack (an I-brick in rack 1 would send `0x2004` if the sender builds the identifier). Whether the sender's converter maps rack 1 to field 0 is the open question U4/U15 of [l1-conversation.md](l1-conversation.md) (the boot firmware image is the one named there; its converter was not read here). Grade: the handler's use of the low 16 bits as the identifier is established; that the sender passes the identifier and not the bay is inferred from the shape of the data (the earlier note's assumption, now consistent with the run, not proven by it).

## 4. `p <n> pwr d`: the parse, `p 0`, `p 1` and `p 99`

The runs: `p 1 pwr d` (no brick in partition 1) gave the no-L1 error and nothing on the wire; `p 0 pwr d` sent `power down` as a task-3 text command to every brick; `p 99 pwr d` was **not rejected**: the text `p 99 pwr d`, not `power down`, went to every brick as a task-3 text command, and 15 s later the usual no-response text came back.

**Mechanism (established; `bin/l2` and `lib/libsys`, read as follows).**

1. The command line is run by `sub_10010aac` (`0x10010aac`) → `CmdProcess` (libsys `0xb200`) over the 188-record table at `0x1003ec08` (records of 0x44 bytes: up to ten pattern words, a handler at `+0x28`, six trailing words from `+0x2c`; the table was dumped from the `.data` bytes). A pattern word of 0 to 11 is a token kind, anything larger points to a `|`-separated list of literal words matched by exact string compare (`sub_cba8`, libsys `0xcba8`; `0xcc28`), so `p` cannot match a longer command name. The kinds are dispatched through the table at libsys `0x14630`: kind 5 is one token, kind 6 is the whole rest of the line (`strtok` with an empty delimiter set, libsys `0xb730`), kind 7 a dotted address, kind 9 `ip:port`, kind 11 a `%d%c%d` rack-slot name, **kind 10 the target prefix** (`0xbc48` to `0xbff4`).
2. Kind 10 reads one token: `*` or `all` selects everything (`0xbcb4`); `r`/`rack` then a range, optionally `s`/`slot`; or **`p`/`partition` (`0xbf10` to `0xbf4c`) then one more token, which is passed to the range parser `sub_ccd0` (libsys `0xccd0`) with the 64-byte partition mask at `target + 0x1b4` and the size `0x40` (call at `0xbf90`)**. A nonzero result takes the record's no-match exit (`0xbf98` to `0xbfa8`, which stores 0 in the record-matches flag at `0x238(r31)` and moves on to the next record). Only on success are the rack mask (`target+0x74`, 0x100 bytes) and the slot mask (`target+0x174`, 0x40 bytes) cleared (`0xbfac` to `0xbfd8`).
3. `sub_ccd0` first clears the mask, then (`0xcd98` to `0xd104`): a lone number is read with `sscanf`, and **a value that is not below the size is an error** (`cmpw`, `blt` at `0xce28` to `0xce2c`, error flag stored at `0xce30`); otherwise byte `n` of the mask is set to 1 (`0xd0c0` to `0xd0d0`, no lower bound, so `p 0` is accepted). Ranges `a-b` and lists are as in [l1-conversation.md](l1-conversation.md) section 6 (re-read: confirmed). `99` is not below 64, so the parse fails with the mask left empty.
4. A failed target prefix only fails *that record*. The scan continues, and **record 187 (kind 6 alone, handler `0x1001aa5c`, trailing word 0, "sends L2/L1 command to default destinations") matches any line**, as does record 186 (kinds 10 and 6, same handler) for a line whose prefix parses. For `p 99 pwr d`, every record that begins with kind 10 (the power records 130 to 133 among them) fails at the prefix, and the kind-6 record takes the whole line as its one string argument.
5. Handler `0x1001aa5c` (re-read in full): if the target selects explicit slots (slot mask not `**` and some byte nonzero) it sends the line as L1 text at once; when the slot mask is `**` or empty, as here, it calls `CmdProcess` again in check mode (`0x1001ab2c`, mode 0, no output) on the same line, to see what command it is; a result of -0x320 (not found) or the record indices 0xba and 0xbb (186 and 187, i.e. the catch-all itself) means "not an L2 command", and it calls `sub_1001a670` (`0x1001ab74`) to send the line as L1 text; any other record index calls `sub_1001a480` to send it as an L2 command. `p 99 pwr d` returns 0xbb, so it goes to `sub_1001a670`.
6. `sub_1001a670` (re-read in full): the record's trailing word is 0 or 1, so it takes the ordinary path (`0x1001a88c` to `0x1001a8f4`): `sub_1001e554` builds the brick list; **with all three target masks empty it uses the destination context's defaults** (`0x1001e578` to `0x1001e60c`: target absent or every mask zero, so the context cleared by `sub_1001e458`, which sets every rack byte and every slot byte to 1 and the partition mask to 0). That selects every valid brick with nonzero rack and slot, routers included (rack/slot mode skips no type). The queue sender `sub_1001c90c` then sends **`*(target+0x4c)`, the whole line**, as the text, one task-3 packet per brick (integer 0, string), wait flag set, so the 15 s timer and the answer layout of section 1 apply.

**The difference from `p 0`.** `p 0`: `sub_ccd0("0")` succeeds, setting byte 0 of the partition mask, so record 132 (kinds 10, `power|pwr`, `down|d`, handler `0x10013ba8`) matches and the power handler runs. Because the mask has a nonzero byte, `sub_1001e554` is in **partition mode** (`0x1001e64c` to `0x1001e664`): it takes every record whose type is not `R`, `D` or `-` and whose partition byte indexes a nonzero mask byte, i.e. every non-router brick whose partition number is 0, which is every brick no one has assigned (the default of the L1 setting, [two-partition-nvram-and-console.md](two-partition-nvram-and-console.md)). The text sent is the handler's own `power down`. For `p 1` the same path finds no brick (bricks have partition 0), hence the no-L1 text. So `p 99` is not "unknown means all": it is "unparseable means forward the line unchanged to everything", which also means a partition number of 64 or more, and any other line the range parser rejects (`p 3-1`, `p 1,,2`, `p x`), reaches every L1 as that literal text. The earlier reading that such a number is a parse error stays right; what is new is the consequence. Established.

Corrections to earlier notes: [l1-conversation.md](l1-conversation.md) section 13.3 says the `p` parser cannot address partition 0 (a note already placed against it in [routed-shutdown-and-partition-fetch.md](routed-shutdown-and-partition-fetch.md)); section 10, U7, wonders whether 64 or more can reach the L2 and says the parser rejects it. It reaches the L2; the *target parse* rejects it, and the line is then forwarded as text. A host that sends `p <n> pwr d` with `n` of 64 or more therefore does not get the partition shutdown and does not get an error: every L1 receives the line `p <n> pwr d` as a console command.

## 5. The task-3 crash

**Fault site (established).** The daemon's fatal-signal handler (the function at `bin/l2` `0x10002d34` that prints the text below; its registration was not read) prints the banner line `L2 %d.%d.%d received fatal signal %d` (arguments 1, 43, 4: the 1.43.4 of the banner) and a `TR:` list of 32-bit program addresses from glibc `backtrace` (it starts at index 1 and prints eight a line), then calls `syslog(9, "l2.c", 153, 0, text)` (`0x10002ec8` to `0x10002ee4`); that is why the log says `PANIC: l2.c line 153`. The addresses in the run's logs map as:

| Address | Where | What |
|---|---|---|
| `0x10010ad4` | `sub_10010aac`, the command-line executor | **the faulting instruction**: `lbz r11, 0(r9)` with `r9` the text argument (`lwz r9, 0xc(r31)`, the stored `r4`) |
| `0x1000e9c4` | `sub_1000e664`, return address of an `IRouterFreePacket` call | a stale value: the executor's frame has not yet stored anything at `+4` of its own frame (the saved return address of its first callee), and glibc's walk prints that slot first; the configuration-reply handler used the same stack depth earlier. Inferred (reasoning from the prologue, `0x10010aac` to `0x10010ad0`, and the callee) |
| `0x1001b314` | `sub_1001af4c` (the task-3 handler), after its call at `0x1001b310` | caller of the executor |
| `0x100219c8` | `sub_10021158` (router), after its call at `0x100219c4` | task dispatch |
| `0x10022fcc` | `sub_10022e50` (the send entry), after its call at `0x10022fc8` | |
| `0x10006d90` | the reader callback, after its call at `0x10006d8c` | |
| `0xff54560`, `0xff5461c`, `0x10003c70`, `0xfc674f8` | libraries and `main` | not followed |

The text pointer comes from `sub_1001af4c` (`0x1001af7c` to `0x1001afb0`): if the type bits of the byte at packet `+0x2c` (the second descriptor) are 0 it uses the word at `+0x30`, otherwise `IRArg(packet, 1)`. `IRArg` (libIRouter `0x72cc`, re-read in full) returns 0 when the index is not below the descriptor count held in the byte at `+0x20` (`0x72ec` to `0x7304`). A one-descriptor packet has count 1, so a string-only packet gives a null pointer by `IRArg`: the fault address is exactly 0 (displacement 0 in the `lbz`). For an integer-only packet the second descriptor's slot is past the count and the word at `+0x30` is whatever the packet buffer holds there; the run crashed too, so it was zero or unmapped (inferred; the buffer is not zeroed by the code read). The executor's first instruction on the text is the dereference, before its length test. The task-10 handler has no such step (it never dereferences a descriptor: it reads the halfword at `+0x2a` and `IRArg` result as integers), which is why the fetch with the same framing did not crash.

**The NVRAM erase (established).** Not before the fault: it is the panic path itself. `syslog` is libsys `0x86dc`; level 9 selects the arm at libsys `0x87c8` (jump table at `0x134e0`, entry 9), which formats `PANIC: %s line %d ; ` plus the text (`0x8810`), calls the **log hook** if one is set (`blrl` at `0x8874`), writes the line to standard error and calls `exit(-1)` (`0x88a4` to `0x88a8`; `li r3,-1`, hence the exit status 255 seen). The daemon installs the hook at start (`syslogLibInit(0x10002f08)`, `0x10002f9c` to `0x10002fa0`): the hook passes the text to `nvramLogInsert` when the level is 0 to 2 or 9 (`0x10002f24` to `0x10002f48`). `nvramLogInsert` (libmain `0xd398`) writes the record (time, text, newline) into the in-RAM log ring, recomputes the checksum and, when the NVRAM backing store is flash (the word at `0x31f24` equal 3), calls `sub_de14` (libmain `0xde14`), which is `nvramSave`: `flash_erase` of 0x4000 bytes at `0xfe3f0000` (`lis r3,-0x1c1`) and `flash_program` (`0xde54`, `0xdec8`; messages `nvramSave: error erasing NVRAM`, `error programming`). So the one extra sector erase is the log write of the panic text itself, executed after the fault, inside the handler. The `exit(1)` after `syslog` in the handler (`0x10002eec`) is never reached; no counter or setting is persisted by the handler beyond that log record. The daemon is `respawn` under `init` at run levels 3 to 5 (`etc/inittab`: `l2:345:respawn:/stand/sysco/bin/l2`), so on a board it would be started again; the run had no `init`, hence no respawn. Established for the handler, hook and erase; the respawn is the `inittab` line, and what `init` does with a process that dies at once again (its own throttle) was not read.

## 6. Can IRIX or the boot firmware ever send a one-descriptor task-3 packet?

Short answer: **none of the shipped senders read does.** Every path builds integer 0 then the text string, or hands the L1 a frame whose conversion adds the integer.

A one-descriptor task-3 packet therefore needs a sender that writes router packets itself with count 1 (a hand-built client of the router library or of the L2's network port), or an L2 peer. None is in the held images. The shipped L1 cannot produce one: its frame conversion always puts an integer first, and a frame with no argument yields a one-descriptor packet whose only descriptor is an integer, which no kernel path sends to task 3. The crash is a robustness defect of the daemon's task-3 handler, not a path a stock IRIX or boot firmware takes.
