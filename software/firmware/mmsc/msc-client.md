# MSC client in the MMSC firmware

The multi-module system controller (MMSC) firmware talks to up to two module system controllers (MSC, also called ELSC) over two serial lines. This note reads that client from the controller side: how it frames a request, what it sends on its own, what it accepts from the MSC, and what it does with each unsolicited line. Everything is read by linear disassembly of the image; no loader was used.

Image: `usr/cpu/firmware/mmscfw.bin` of IRIX 6.5.30, MMSC firmware 2.3 (`6c3db7ffd7fb4cc4...`; byte-identical in the 6.5.7, 6.5.9 and 6.5.10 sets). Header and symbols as in [../controllers.md](../../../evidence/controllers.md): little-endian a.out, text 0xa7bd8 bytes at 0x108000, data 0x28c00 bytes, bss 0x1e198, 7,907 nlist entries. Reading a routine's addresses needs no more than the text base. Data addresses (strings, tables) assume the data segment follows the text directly, at 0x1afbd8. That placement is inferred, and every data read below supports it: the bay-name table reads `UL`, the serial default table reads 9600 baud six times, and the tuning table's name strings sit on their records.

Grades follow [../../AGENTS.md](../../../AGENTS.md). A routine is established when its whole body was read here and the entry states what it does. Addresses are 6.5.30 virtual addresses; a size is the distance to the next symbol and so includes the routine's trailing string pool. Names are the image's own symbols; a symbol the table gives to a static routine is marked static. The routine the static routed-request handler (0x12ca94) at 0x12ca94 is static and is attributed by the symbol table's nearest global (`_routeProcessELSCCommand+1440`) in a naive listing; this note uses the static name.

## What was read

The object `elsc.o` of the image (0x12303c to 0x1245e8) holds 14 global routines, not the 10 the survey counted: `_elscCheckResponse`, `_elscDoAdminCommand`, `_elscInit`, `_elscPrintMsg`, `_elscProcessCommand`, `_elscProcessInput`, `_elscQueryModuleNum`, `_elscSendCommand`, `_elscSendPassword`, `_elscSetPassword`, `_elscSetup`, `_elscUpdateDisplay`, `_elscUpdateModuleNums`, `_elscUpdateSaveInfo`. The line framing is in `msg.o` (`_msgNew`, `_msgClear`, `_msgWrite`, `_msgRead`, 0x128a40 to 0x129430). The mode routines and the command that reaches them are in the command modules. The two routes into the client from the router are `_routeProcessELSCCommand` (0x12c4f4) and `_routeDoAdminCommand` (0x12c4d4). All of these are entries below.

## The two MSC slots

`_ELSC` (0x1e27f8) is an array of two slots of 0x3c bytes each, one per MSC bay. The bay letters are `U` and `L`, from the two-byte table `_ffscBayName` (0x1b0f78). Fields, as the routines use them (word means 4 bytes):

| Offset | Meaning | Evidence |
|---|---|---|
| +0 | flags; bit 0 means the MSC did not complete setup or could not be contacted | `_elscSetup` sets it on failure and clears it on success; `_elscQueryModuleNum` sets it when the MSC does not answer |
| +4 | owner state: 0 not usable, 1 idle and owned by the router, 2 or 3 owned by a console in MSC mode (3, or 2 when the console record's word at +0xc is 4) | the router listens only for state 1; `_elscSendCommand` refuses any other |
| +8 | file descriptor of the serial line; -1 when the port is not open | slot 0 takes `_ffscPortFDs[1]`, slot 1 takes `_ffscPortFDs[2]` |
| +0xc | slot index, 0 or 1 | `_elscInit` |
| +0x10 | module number the MSC reported; -1 unknown | `_elscQueryModuleNum` |
| +0x14 | rack that receives this MSC's text lines; -1 none | `_elscPrintMsg`, saved in NVRAM |
| +0x18 | rack that receives the alternate text lines; -1 none | same |
| +0x1c | ten bytes of display text sent by the MSC; the byte at +0x24 is the ninth | `_elscUpdateDisplay` |
| +0x26 | four-character MSC password, default `none`, NUL at +0x2a | `_elscInit`, `_elscSetPassword` |
| +0x2b | bay letter | `_elscInit` |
| +0x2c | per-MSC log handle, or 0 | `_elscInit`; each routine writes a log line when it is set |
| +0x30 | input message (160-byte text area), named `MSC<slot>` | `_elscInit` |
| +0x34 | request message (80-byte text area), named `R2E<bay>r` | `_elscInit` |
| +0x38 | answer message (128-byte text area), named `R2E<bay>a` | `_elscInit` |

A message (`msg_t`, 0x20 bytes, `_msgNew`) holds the name at +0 (8 bytes), the text area pointer at +8, the write cursor at +0xc, the text capacity at +0x10, the descriptor at +0x14 and a state at +0x1c. Its state values are: 0 empty, 1 and 0x14 request being written, 4 reading an unsolicited line, 5 waiting for an answer, 0xa invalid, 0xb complete, and 0x16 to 0x1a the line parser's own states (see the framing section).

## Routine entries

Grades: established unless the entry says otherwise. "Setup" below means `_elscSetup`.

- `_elscInit` at 0x12346c, 0x2f0 bytes, 6.5.30 MMSC 2.3. Called once from `_ffscInit` (0x126eb5). Established. It reads NVRAM record 5 (64 bytes, two 32-byte entries). If the read fails it zero-fills the record, writes the defaults into it (both rack words -1, password `none`, flag word 3) and writes it back. For each slot it then clears the flags and state, copies the port descriptor and slot index, sets the module number to -1, takes the text rack from entry word 0, the alternate rack from entry word 1 only when the entry's flag word has bit 0 (else -1), the password from the entry only when the flag word has bit 1 (else `none`), the bay letter and the log handle, and clears ten bytes of display text. A descriptor of 0 or more makes the slot state 1. It allocates the three messages with `_msgNew` (sizes 0xa0, 0x50, 0x80) and returns -1 if any allocation fails. It runs Setup on each slot, and when Setup succeeds it asks the MSC for its module number with `_elscQueryModuleNum`; a changed number is stored and, after both slots, `_elscUpdateModuleNums` publishes them. Returns 0.
- `_elscSetup` at 0x12435c, 0xf0 bytes. Called from `_elscInit`, from the line handler when an MSC announces itself, and from the scan command (0x114ecd). Established. It sends the admin request `fsc 1` and expects a reply that starts with `ok`. On a send failure it sets flag bit 0 and returns -1 without a message. On any other reply it logs that the MSC rejected `fsc 1`, sets flag bit 0 and returns -1. On success, if the slot state is 1, it sends the admin request `ech 0`, ignoring its reply; it clears flag bit 0 and returns 0. What the MSC does on `fsc 1` and `ech` is not shown by this image; the names suggest a full-feature-controller announcement and echo off (hint, not graded).
- `_elscQueryModuleNum` at 0x123dcc, 0x190 bytes. Established. Takes a slot index and an output word. Sets the output to -1, sends the admin request `mod`, and on a send failure logs that the MSC cannot be contacted, sets flag bit 0 and returns -1. If the reply does not start with `ok` it logs the rejection and returns 0 with the output left at -1. Otherwise it converts the text from reply offset 3 as a hexadecimal number. A trailing character or a value above 0xff logs an invalid module number and returns 0 with the output left at -1. A value of 0 is stored as -1. Any other value is stored. The accepted reply grammar is therefore `ok <hex>`.
- `_elscUpdateModuleNums` at 0x1244bc, 0x80 bytes. Established. Copies the 28-byte local identity record at `_ffscLocal` (0x1f62b8), replaces its last two words (offsets 20 and 24) with the module numbers of slot 0 and slot 1, and passes the copy to `_addrdUpdateLocalIdentity`. So the rack's identity record carries the module numbers reported by the two MSCs.
- `_elscUpdateSaveInfo` at 0x12453c, 0xac bytes. Called from `_elscSetPassword` and from the static handler `_cmdEMSG_rack` (0x115a98, call at 0x115c58), which sets a slot's text rack and was read only in outline. Established. Builds the 64-byte NVRAM record 5 from both slots: per 32-byte entry, word 0 is the text rack, word 1 the alternate rack, bytes 8 to 11 the password, and the flag word at +0x1c is always 3. Writes the record. On failure logs that the MSC information could not be saved and returns -1; otherwise 0.
- `_elscSendCommand` at 0x123f5c, 0x1a0 bytes. Called from `_routeProcessELSCCommand`. Established. Takes a slot index and a command text. It first clears the slot's answer message. If the slot state is not 1 it writes `ERROR INUSE` into the answer, marks it complete (state 0xb) and returns. Otherwise it clears the request message, formats it as CR, byte 0x14, the text, CR, marks it state 1 and writes it to the MSC. A write error or a request that does not reach state 0xb puts `ERROR SEND` in the answer, marks it complete and returns. After a successful write the answer message is set to state 5 (waiting for a reply) and, when the slot has a log, the line `<<COMMAND:  text>>` is logged. The routine returns 0 on every path and carries failures in the answer text. It does not read the reply: the router's response loop does (see `_routeProcessELSCCommand`). The request text area is 80 bytes and the formatting step has no length check, so any limit on command length sits with the callers (not read).
- `_elscDoAdminCommand` at 0x12320c, 0x260 bytes. Established. Takes a slot index, a command text and an optional reply buffer; it is the synchronous form used for the controller's own requests. If the descriptor is negative it logs a send to an offline MSC and returns -1. It formats the request exactly as `_elscSendCommand` does, writes it, and on a send failure writes `ERROR SEND` into the reply buffer when one was given and returns -1. It then clears the answer message, marks it state 5 and reads it with the answer timeout (default 5 s); a read failure returns -1, and an answer that is not complete (state 0xb) logs the state and returns -1. A complete answer is cut at its first CR or LF, logged as `<<ADMIN RESPONSE: ...>>` when the slot has a log and the debug flag 0x10 is set, copied to the caller's buffer without a length check, and the routine returns 0. It does not require state 1, which is how the console routines use it while a console owns the slot.
- `_elscProcessInput` at 0x123bcc, 0x200 bytes. Called by the router (0x12c285) when select reports the slot's descriptor readable. Established. If the slot state is not 1 it logs the owner and returns -1. It clears the input message, sets state 4 and reads one line with the unsolicited-line timeout (default 1 s); a read failure returns -1. An invalid line (state 0xa) is logged and the routine returns 0. A complete line has its CR LF stripped (an empty complete line goes on as empty console text); a line stopped after a CR has that CR stripped. A read that ends with no bytes in any other state is logged as an empty message and the routine returns 0. A line that does not start with byte 0x14 is MSC console text: the routine forms the source tag `R<rack><bay>` and hands the text to `_elscPrintMsg`. A line that starts with 0x14 and is complete goes to `_elscProcessCommand` with the 0x14 removed; an incomplete one is logged as incomplete. Returns 0 on those paths.
- `_elscProcessCommand` at 0x12394c, 0x280 bytes. Called from `_elscProcessInput`, `_elscCheckResponse` and the system console's MSC-mode input routine. Established. Splits the first token at blanks and tabs, upper-cases it, and tests it in this order. An empty line logs and returns -1. `DSP` calls `_elscUpdateDisplay` with the rest of the line. `DP` logs a warning that it was received and then does the same as `DSP`. A token that begins with `ELSC` (first four characters) or `MSC` (first three) means the MSC is announcing itself: the routine logs `<<MSC x COMING ONLINE>>` when the slot has a log, runs Setup, and when that succeeds asks for the module number and republishes it if it changed. `MSG` forms the tag `E<rack><bay>` and hands the rest of the line to `_elscPrintMsg`. Anything else is logged as an unrecognised command and the routine returns -1. All other paths return 0.
- `_elscCheckResponse` at 0x12306c, 0x1a0 bytes. Called from the router's response loop (0x12d326). Established. Takes a slot pointer and an answer text. It splits the text at every byte 0x14: each piece that ends at a 0x14, cut also at its first CR, is run as an MSC command through `_elscProcessCommand`. The text after the last 0x14 is moved to the front of the buffer with `memmove` of its string length, which does not copy the terminating NUL, so the bytes after the moved text are whatever the buffer held before; the router cuts the reply at its first CR straight afterwards. With no 0x14 the text is untouched. This is how commands the MSC sent while the controller waited for a reply are separated from the reply itself.
- `_elscPrintMsg` at 0x12375c, 0x1f0 bytes. Called from `_elscProcessInput` and `_elscProcessCommand`. Established. Takes a slot, a source tag and a text. It writes the text to the slot's log when there is one. Then it routes the text to two destinations in turn, each a rack number held in the slot. For the text rack (slot +0x14): when it equals the local rack, it formats `MSG tag:text` and sends it with `_userSendCommand` to the second entry of the user table (`_users`+4), logging `Text:  ...` and returning -1 if that fails; when it is another rack and not -1, it formats `R <rack> MMSG TEXT tag:text` and hands it to `_routeDoAdminCommand`. The alternate rack (slot +0x18) is handled the same way with the third user-table entry (`_users`+8) and `R <rack> MMSG ALTTEXT tag:text`; a local send failure there also returns -1. Otherwise 0. Who the two user-table entries are is not read here.
- `_elscUpdateDisplay` at 0x12444c, 0x70 bytes. Called from `_elscProcessCommand`. Established. Clears the slot's ten display bytes at +0x1c and, when the argument is not NULL, copies up to ten bytes of it in. When the slot has a log it writes `<<DISPLAY CHANGE: message="%.8s" code=%d>>`, with the first eight bytes as the message and the ninth byte (at +0x24) as a code printed as a signed value. So the MSC's display line is eight characters followed by a code byte and one more byte. Whether another routine reads the stored bytes was not searched.
- `_elscSendPassword` at 0x1240fc, 0xc0 bytes. Called from `_elscSetPassword`, from `_ceEnterELSCMode` and from `_routeProcessELSCCommand`. Established. Takes a slot and the caller's authority level. If the slot's stored password is empty it does nothing and returns 0. Otherwise it sends the admin request `pas` alone when the level is 499 or less, and `pas` followed by a blank and the stored password when the level is 500 or more. A reply starting `ok` returns 0. Any other reply logs `Attempt to set ELSC password failed: ...` and returns -1; an admin send failure returns -1 without a message. The authority levels the command table names are BASIC 100, SUPERVISOR 500 and SERVICE 1000 (table `_AuthorityLevels`, 0x1b0aac, read), so a supervisor or service user presents the stored password and a basic user sends the bare request. What the bare `pas` does on the MSC is not shown (inferred as dropping privilege; not graded).
- `_elscSetPassword` at 0x1241bc, 0x1a0 bytes. Called from the password command (0x11278d). Established. Takes a slot, a new password and a push flag. It clears the answer message. When the flag is set and the new password is not empty it requires slot state 1 (otherwise `ERROR INUSE`), presents the stored password at level 1000 with `_elscSendPassword`, sends `pas s` followed by the first four characters of the new password and requires the reply to be exactly `ok`; a failure at any of these returns -1. In every case that gets past this it copies up to four characters of the new password to slot +0x26, saves NVRAM record 5 through `_elscUpdateSaveInfo`, writes `OK` into the answer, marks it complete and returns 0. The command's `SET` subcommand passes the push flag as 1; `SETMMSC` and `UNSET` pass 0, and `UNSET` passes an empty password. So `SETMMSC` and `UNSET` change only the controller's stored copy. The password command takes a subcommand (`SET` 1, `SETMMSC` 2, `UNSET` 3, table `_PasswordSubCmds` at 0x1b0adc), a type from `_AuthorityLevels` (`MSC` and `ELSC` map to -1, which selects this routine), and for `SET` and `SETMMSC` the new text. Changing the MSC password requires the caller's level to be above 499.
- `_routeDoAdminCommand` at 0x12c4d4, 0x20 bytes. Established. Passes its command text and the sixth user-table entry (`_users`+20) to the static routed-request handler at 0x12ca94, the routed-request handler that all routed requests use. `_elscPrintMsg` uses it to deliver text to another rack. Nothing about the MSC is done here.
- `_routeProcessELSCCommand` at 0x12c4f4, 0xf0 bytes. Called from `_cmdELSC`. Established. Takes a command text, the issuing user and a parsed destination. The destination holds one byte per rack at offset 4; the routine reads the byte of the local rack. For each slot 0 and 1: if the slot's bit is set it calls `_elscSendPassword` with the user's level (user +0x20) and then `_elscSendCommand` with the text. If the bit is clear but the byte's top bit is set, it writes `OFFLINE` into that slot's answer and marks it complete. The replies are collected afterwards by the static routed-request handler (0x12ca94): it waits in a select loop on the response slots (the slots' answer messages are entries 23 and 24 of its response table), reads each with `_msgRead`, and for an answer slot passes the answer text through `_elscCheckResponse`, cuts it at its first CR, logs it as `<<RESPONSE: text>>`, and appends `R<rack><bay>:` and the reply to the user's response, with a comma between one MSC's text and the next. A reply that did not complete is reported as `ERROR TIMEOUT (routed-request handler)` or `ERROR BADRESP (routed-request handler)` (the second for an invalid answer state). The loop's wait times are tuning values (see below). I read the answer-slot path of the static routed-request handler (0x12ca94) and not the whole of it.

- The handler of the `PWR` command, at 0x11a0d8, 0x220 bytes, 6.5.30 MMSC 2.3. Established. Its command-table row (0x1b0950) has no help text, so the help listing does not show it. It splits the first argument at blanks and tabs and accepts only the exact words `u` and `c`; any other argument, or none, returns 2. It then counts the racks the destination selects (`_destNumRacks`, one per non-zero byte among 23 rack bytes) and returns 2 unless more than one rack is selected. It formats `pwr <word>`. Unless the user's class word (+0x10) is 3, it first tells the user `WAIT <w> Please wait <s> secs to sequence power for <n> racks`, where w is the power delay (tuning entry 36, default 5,000,000 microseconds) times (n - 1) as a plain integer, s is the same product divided by 1,000,000 and n is the rack count, and writes that line out through `_msgWrite`; if that fails it logs a message that the wait line could not be sent, answers `ERROR WAIT` and returns 0. It then walks racks 0 to 22 in order: for each selected rack after the first it sleeps for the power delay (`nanosleep`), and it hands the text to `_routeProcessELSCCommand` when the rack is the local one (so both local MSCs are sent it, after the password step) or to `_remStartRemoteCommand` otherwise. Returns 3. The effect is a staggered power sequence across racks, one delay apart. `u` and `c` are the only words; the image does not say what they mean (`c` may be a power cycle, as the host driver's `pwr c`; `u` is read nowhere in the host driver; hint, not graded).

## Line framing: `_msgNew`, `_msgWrite`, `_msgRead`

- `_msgNew` at 0x128af0, 0x210 bytes. Established. `_msgNew(size, descriptor, third, name)` allocates a 0x20-byte `msg_t` and a text area of size+1 bytes, stores the size, descriptor and third argument at +0x10, +0x14 and +0x18, copies up to eight characters of the name (NUL at +7) and clears the message. Returns NULL with a log line if either allocation fails. `_msgClear` (0x128a40) sets the cursor to the start of the text area, the state to 0 and zero-fills size+1 bytes.
- `_msgWrite` at 0x129310, 0x120 bytes. Established. Takes the message and a timeout; the routine reads only the message. A negative descriptor marks the message complete and returns 0 without writing. Otherwise it loops on `write` with `strlen` of the unwritten text, sets state 0x14 after each write, and sets 0xb when all text is out. A write that returns 0 or less logs the error and returns -1 with the state unchanged. The whole text is sent as one line, byte for byte; the CR, 0x14 and CR around a command come from the caller's format string, not from here.
- `_msgRead` at 0x128d00, 0x610 bytes. Established as to its state machine; the debug-only character-substitution branches were read and are described only where they change the framing. Takes the message and a timeout in microseconds. The function sets a timer (`_timeoutSet`, which divides the value by 1,000,000 into seconds and the remainder into nanoseconds, so the unit is microseconds), then polls the descriptor with `ioctl` request 1 (bytes available; a hint from the usual numbering, not shown by the image) with one-tick delays until a byte is ready or the timer expires. It reads one byte at a time into the message's cursor and runs it through the state in the message's state word. Read error: returns -1; end of file: returns -1; timer expiry: returns 0 with the message state unchanged. On completion it returns 0 with state 0xb. If the text area fills first it appends CR LF and marks the line complete.

### Frames, read from the parser

All line numbers refer to states of `_msgRead` (jump table at 0x128f10 for states 2 to 26; states 7 to 20 are not valid and log an unknown state).

Controller to MSC: `CR`, byte `0x14`, the command text, `CR`. Format string at 0x123113. Both `_elscSendCommand` and `_elscDoAdminCommand` send exactly this. The MSC is never sent a line feed.

MSC to controller, an unsolicited line (state 4, set by `_elscProcessInput`): any bytes, ended by CR LF or by LF CR. A NUL byte is logged and ignored. A lone CR or LF inside a line is removed from the text (in the debug configuration with flag bit 3 set it is kept as a dot). The line is complete on the second terminator byte. The router then strips the two bytes. A line that starts with `0x14` is a command from the MSC (`DSP`, `DP`, `ELSC`/`MSC`, `MSG`; see `_elscProcessCommand`); any other line is console text for `_elscPrintMsg`.

MSC to controller, a reply (state 5, set before waiting for an answer): bytes before the first `0x14` are logged as extraneous input (up to 80 are kept for the log) and dropped. The `0x14` starts the reply and is not stored. The text is then collected up to CR (state 25) and must be followed by LF (state 26); a CR not followed by LF is dropped from the text and a CR directly after a CR keeps only one. After the LF the buffer is complete if it begins with `ok` or `err`. If it begins with neither and contains no `0x14`, the parser logs that a piggybacked MSC command was found and keeps collecting (state 25 again); this is how an MSC command that arrives while the controller waits ends up in front of the reply. If it contains a `0x14` the buffer is complete. `_elscCheckResponse` then splits the buffer at each `0x14`: everything before each one is an MSC command, and what follows the last one is the reply. So a reply is `0x14`, text starting `ok` or `err`, CR LF, and any number of MSC command lines may precede it, each ending in CR LF and each followed in the buffer by the next line's `0x14`.

Replies the image checks for: `ok` as the first two characters (setup, module number, password presented), the exact word `ok` (password set), and `ok <hex>` (module number). `err` is accepted as a complete reply and is passed to the user without parsing. The reply text of an unsolicited command's exchange is never inspected beyond these.

Other states in the jump table (2 and 6, 3 and 21) read raw bytes or read to a CR. No routine of this client sets them; they belong to the other response slots the same parser serves, which this note does not cover.

### Timing

The client's waits come from the tuning table `_ffscDefaultTuneInfo` (0x12601c), loaded into `_ffscTune` at start and saved in NVRAM record 8; the image's own defaults are in microseconds:

| Table index | Default | Used for |
|---|---|---|
| 10 | 1,000,000 | reading an unsolicited line in `_elscProcessInput` |
| 11 | 5,000,000 | reading an admin reply in `_elscDoAdminCommand` |
| 16 | 1,000,000 | passed to `_msgWrite`, which ignores it |
| 14 | 1,000,000 | per-slot read in the routed-request handler's response loop |
| 19 | 4,500,000 | the loop's select timeout when its local counter is not positive |
| 20 | 16,000,000 | the same when it is positive |
| 36 | 5,000,000 | the gap between racks in the `PWR` command |

The names are the image's own strings in the default table; their wording separates a local wait from a remote one, but the use was not traced far enough to confirm which the router's counter selects, so the counter's meaning is unknown.

### Serial lines

Each MSC slot's descriptor is one of the controller's six serial devices (`/tyCo/0` to `/tyCo/5`, opened by `_ttyInit` at 0x12e638, read in full for this question). The default table at 0x12dfc8 gives all six lines 9600 baud and the logical numbers 0 to 5, and `_ttyInit` sets the speed with `ioctl` request 4 and the options with request 3 and a zero argument (both request numbers are the usual VxWorks values and are hints from the numbering, not shown by the image). The logical numbers 1 and 2 are the two MSC lines. The record that overrides the defaults is NVRAM record 4; this note does not read its fields. Framing is 9600 baud with options zero; the character format (data bits, parity, stop bits) is set by the VxWorks serial driver defaults and was not read here.

## MSC mode: a console talks to an MSC directly

A console (a user connection on the MMSC) can take over one MSC's serial line. These routines are the controller's side of that. The console record fields used are named by offset; their purpose is read from the use.

- `_cmdELSC` at 0x117710, 0x460 bytes. Established as to its branches; the meaning of the state strings it returns is inferred. The `ELSC` command. With any non-blank argument text it hands the text to `_routeProcessELSCCommand` as a one-shot request and returns 1. With no argument it asks to enter MSC mode on one bay. A user of class 1 or 3 is refused with `ERROR SOURCE`. A destination that is not exactly one bay gives `ERROR DEST`. For a user of class 6 (a remote MMSC) the destination must be a local bay (else `ERROR DEST`); if the slot is not idle it answers `R<rack><bay>:ERROR INUSE` and returns 1; if `_userAcquireRemote` fails it answers `ERROR BUSY`; otherwise it sends the text `STATE FE<slot> FU<descriptor> M3` to that user with `_userSendCommand`. For any other user and a destination on another rack, a class-4 user gets `ERROR TOOREMOTE`; the others start a remote connection to that rack for `ELSC` (`_remStartConnectCommand`) and the reply is `OK;STATE BS<0x8000> FS<handle> M4` or `ERROR CONNECT,<text>`. For a local destination, a slot that is not idle gives `ERROR INUSE`, and an idle one gives `OK;STATE BS<0x8000> FE<slot> M3`, then the routine sets `_routeCheckBaseIO` and returns 0. The numbers 3 and 4 after `M` match the mode value 3 that `_ceEnterELSCMode` stores for the console. The meaning of `BS`, `FS`, `FE` and `FU` is not read.
- `_ceEnterELSCMode` at 0x11a9b0, 0x2d0 bytes. Established. If the console's slot is not idle it clears the console's slot pointer, sets bit 0x10 of its flag word and enters FFSC mode instead. Otherwise it sets the console's mode word to 3, two state words to 1, clears its two data buffers, attaches the MSC descriptor to buffers +0x68 and +0x6c and the console's own descriptor to +0x70 and +0x74 (so +0x68 carries MSC output toward the controller and +0x6c the other way, and +0x70 and +0x74 likewise for the console), attaches the slot's log to +0x74, sets the slot state to 3 (2 for a class-4 console), and asks the router to re-select its descriptors. If flag 0x4000 is set it writes `R<rack>:READY` and a CR to the console and clears it; if flag 0x8000 is set it writes `*** Entering MSC mode, type <exit character> to exit ***` between line breaks and clears it. It presents the MSC password with `_elscSendPassword` using the user's level and writes a warning to the console if that fails; when the console's user record has bit 2 set it sends `ech 1`. It then releases the first buffer and returns 0.
- `_clLeaveELSCMode` at 0x11ba00, 0x100 bytes. Established. Holds the first buffer, detaches the four buffers' descriptors and the log, zeroes five console fields, and if the console still has a slot sets the slot idle (state 1), sends `ech 0`, clears the slot's flag bit 0 whatever the reply was, asks the router to re-select, sends the console's own FFSC command `R . NOP` with the dummy response and clears the slot pointer. Returns 0.
- `_csSysInELSC` at 0x11f9f8, 0x370 bytes (static). Established. Reads the MSC's bytes for a console in MSC mode. State 1 passes bytes straight to the console, except at a byte `0x14`: it passes the bytes before it, drops them from the input buffer and goes to state 2. State 2 scans for CR; State 3 needs LF. A line `0x14 text CR LF` is a command from the MSC: unless the text starts with `ok` or `err` (a reply that arrived late, which is passed to the console whole, including the `0x14`), the CR is overwritten and the text after the `0x14` goes to `_elscProcessCommand`; the line is then removed. So while a console owns the line, the MSC's `0x14` commands are consumed the same way as on the router path, and every other byte, including lines that are not commands, reaches the console unchanged. When the MSC's stream is logged the whole data goes to the slot's log first.
- `_cuUserInELSC` at 0x120948, 0x140 bytes (static). Established. Takes the console's input. If the console's state word is not 1 it logs and returns -1. It copies the bytes before the console's exit character to the MSC with no framing and no translation. If the exit character is absent the input is cleared. If it is present it logs the exit, sends the console's FFSC command `R . EXIT` and prints the response; the exit character itself and the bytes after it are not sent. Returns 0.

## Request and reply grammar from the controller's side

Established from the routines above, for the MSC link of 6.5.30 MMSC 2.3:

| Direction | Form | Where |
|---|---|---|
| controller to MSC, its own and routed requests | CR, `0x14`, text, CR | `_elscSendCommand`, `_elscDoAdminCommand` (format at 0x123113) |
| controller to MSC, console keystrokes in MSC mode | the user's bytes unchanged, up to the exit character | `_cuUserInELSC` |
| MSC to controller, reply | `0x14`, text starting `ok` or `err`, CR LF | `_msgRead` state 5 |
| MSC to controller, command | `0x14`, command text, CR LF (or LF CR) | `_elscProcessInput`, `_csSysInELSC`, `_elscCheckResponse` |
| MSC to controller, console text | any other line, CR LF or LF CR | `_elscProcessInput` |

Requests the controller itself sends, with the reply it requires: `fsc 1` (`ok`), `ech 0` and `ech 1` (reply ignored), `mod` (`ok <hex>`), `pas` and `pas <password>` (`ok`), `pas s <four characters>` (exactly `ok`), and `pwr u` or `pwr c`, built by the `PWR` command (entry below) and sent through the same path as a user request, with the reply collected by the router like any other. User requests from the `ELSC` command pass through as typed, after the password step; the text is not parsed on the way, so an operator can send the MSC any request it understands, including the ones the host driver uses.

Commands the controller accepts from the MSC, first token compared after upper-casing: `DSP <text>` and `DP <text>` (the same, with a warning for `DP`) set the display bytes; a token starting `ELSC` or `MSC` announces the MSC and triggers `fsc 1`, `ech 0` and `mod`; `MSG <text>` is console text with the tag `E<rack><bay>`. Nothing else is accepted.

### Comparison with the host driver

The host-side reading is [../elsc-host-requests.md](../../../formats/elsc_host/README.md) (the kernel driver object, 6.5.30). The two sides share the request text style and little else.

| Aspect | Host driver | MMSC client | Grade |
|---|---|---|---|
| Link | I2C master, slave argument 8, one combined write-and-read per request | serial line, 9600 baud, one of two lines per MMSC | each side established; that they reach the same MSC firmware by different ports is inferred |
| Request frame | length byte, text, negative-sum checksum byte | CR, 0x14, text, CR; no length, no checksum | established both sides |
| Reply frame | length byte, text, checksum byte, in the same transfer | 0x14, text, CR LF, read on the line later | established both sides |
| Reply words | `ok` with up to three space-separated words, or `err` with `csum`, `cmd`, `arg`, `perm` or `pwr_state` | `ok`, `ok <hex>` or `err`; nothing after `err` is read | established both sides; the same reply words, inferred to be one controller grammar |
| Asynchronous traffic | none sent by the controller; the host polls with `get` and receives console bytes (`acp`) or message lines | the MSC sends a line whenever it likes: console text, `0x14 DSP`, `0x14 MSC` or `0x14 ELSC`, `0x14 MSG`; commands can also arrive in front of a reply | established both sides |
| Requests | `ver`, `tas`, `dsc`, `dsp`, `pwr q`, `pwr r`, `pwr d`, `pwr c`, `rst`, `rsw`, `nic`, `hbt`, `acp`, `get` | `fsc 1`, `ech 0`, `ech 1`, `mod`, `pas`, `pas <pw>`, `pas s <pw>`, `pwr u`, `pwr c`, plus any text an operator types | established both sides |

What the two request sets share is one text: `pwr c`. The MMSC's literal list was found by scanning the whole text and data of the 6.5.30 image for each of the host driver's request words (`ver`, `tas`, `dsc`, `dsp`, `pwr`, `rst`, `rsw`, `nic`, `hbt`, `acp`, `get`) and the controller's own (`fsc`, `ech`, `mod`, `pas`) at the start of a string; the only hits are `pwr %s`, `fsc 1`, `ech 0`, `ech 1`, `mod`, `pas`, `pas %s` and `pas s %.4s`. The 6.4-origin to 6.5.30 host objects were searched earlier for `fsc 1`, `ech ` and `pas ` with no hit. So the controller-only requests (`fsc`, `ech`, `mod`, `pas`, `pwr u`) are not issued by the kernel, and the kernel-only ones (`ver`, `tas`, `dsc`, `dsp`, `rst`, `rsw`, `nic`, `hbt`, `acp`, `get`, `pwr q`, `pwr r`, `pwr d`) are not issued by the MMSC on its own. Nothing blocks an operator from sending a kernel-only request through the MMSC's `ELSC` command, because the text is passed unparsed.

- The word `dsp` runs both ways: the host sends `dsp <eight characters>` to set the display, and the MSC sends `DSP <text>` to the MMSC to report what it shows (inferred from the names and the 8-character field both sides use; the MSC side is not in either image).
- The host driver sets a lock with `tas` and polls with `get`; the MMSC takes the line for itself instead: an `ELSC` console takes the slot (state 2 or 3) and the router stops reading it. The MSC has no visible lock arbitration with the MMSC in this image (unknown).
- `hbt` has no counterpart on the controller side: the MMSC sends no heartbeat. `pwr d` (power down with a value) and `rst` are likewise absent.
- The host reply grammar's `err pwr_state` appears only from IRIX 6.5.5; the MMSC code takes no action on any `err` text, so it cannot tell the codes apart.
